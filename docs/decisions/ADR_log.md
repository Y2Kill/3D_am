Ссылки «ТЗ x.y» в ADR-0001…0023 указывают на пункты v1.1 (в v1.2–v1.6 нумерация §1–§10 не менялась). ADR-0024…0029 ссылаются на [ТЗ v1.6](../tz/drafts/TZ_catalog_3D_2D_draft_v1.6.md) — §11–§13, принятые в v1.3–v1.5. ADR-0030…0034 — на ТЗ v1.7 (§14), ADR-0035 — на [ТЗ v1.8](../tz/drafts/TZ_catalog_3D_2D_draft_v1.8.md) §19, ADR-0036 — на свод решений R-01…R-09 к нему, ADR-0037 — на журнал решений v0.11/v0.12 (RC-1), ADR-0038 — на результаты спайка S7 (задача T-004).

## ADR-0001. Тулчейн и стандарт
- **Контекст:** ТЗ 3.4 — C++20, CMake, MSVC/GCC/Clang, Windows первым.
- **Решение:** C++20 (без C++23 в публичных заголовках; разрешены `std::expected`-подобные типы только из своего `am::Result`). CMake ≥ 3.28, генератор Ninja, `CMakePresets.json`. Минимальные компиляторы: MSVC 19.40 (VS 17.10), GCC 13, Clang 17. Флаги: `/W4 /permissive- /utf-8 /Zc:__cplusplus`, `-Wall -Wextra -Wpedantic`. Исходники в UTF-8 без BOM.
- **Последствия:** `std::format`, `std::span`, concepts и `std::jthread` доступны. Модули C++20 **не используются** (нестабильная поддержка в CMake, Ninja и IDE).

## ADR-0002. Управление зависимостями: vcpkg manifest mode
- **Контекст:** ТЗ 3.5 — воспроизводимость, офлайн-сборка, контроль версий; открытый вопрос 12.
- **Решение:** vcpkg в manifest mode (`vcpkg.json` + `builtin-baseline` с конкретным commit-ом реестра). Каждая зависимость — vcpkg-фича, ядро собирается с минимальным набором. **Qt — из официального установщика** (собирать Qt через vcpkg слишком долго), путь задаётся пресетом `AM_QT_ROOT`. Офлайн-режим: `VCPKG_BINARY_SOURCES=clear;files,<repo>/.cache/vcpkg-bin,readwrite` и `X_VCPKG_ASSET_SOURCES=clear;x-azurl,file:///<repo>/.cache/vcpkg-assets`. Каталоги кэша не попадают под git.
- **Отклонено:** Conan (второй язык конфигурации, Python), FetchContent для всех зависимостей (нет бинарного кэша, хуже офлайн-сборка).
- **Последствия:** первый запуск на новой машине либо скачивает зависимости, либо берёт подготовленный кэш (ТЗ 3.5.6).

## ADR-0003. Топология процессов
- **Контекст:** ТЗ 3.1.4–5 — ядро без GUI, CLI; 3.3.5 — изоляция аварий плагинов (открыто).
- **Решение:** три исполняемых файла поверх одной библиотеки `am_core`: `am-gui` (Qt Widgets), `am` (CLI) и `am-worker` (служебный процесс без UI). Длительные и рискованные операции (распаковка чужих архивов, парсинг 3D, рендер превью, вызовы плагинов сторонних авторов) можно выполнять в пуле `am-worker`, IPC — через именованный канал или Unix socket с length-prefixed сообщениями в JSON (CBOR позже). **MVP выполняет всё in-process** за интерфейсом `IExecutor`. Вынос в worker — этап M9, без изменения API.
- **Последствия:** авария обработчика в worker не роняет GUI и не портит ассет: запись ZIP выполняет только основной процесс по протоколу ADR-0006. Это решение по ТЗ 3.3.5.

## ADR-0004. Слои и зависимости модулей
> **Статус: заменено ADR-0024** (линейный стек → граф уровней ТЗ §12). Текст сохранён для истории.
- **Решение:** строгая слоистость (нижний слой не знает о верхнем):
  1. `am_base` — Result/Error, пути (long path), UTF-8/кодировки, UUID, хеши, логирование, FS-утилиты.
  2. `am_container` — формат ассета: манифест, чтение и запись ZIP, проверка целостности, безопасная фиксация.
  3. `am_archive` — чтение входных архивов (libarchive, 7z-плагин), определение томов.
  4. `am_catalog` — библиотека, SQLite-индекс, пользовательские данные, синхронизация, корзина.
  5. `am_jobs` — фоновые задания, персистентная очередь.
  6. `am_import`, `am_dedup`, `am_preview`, `am_convert`, `am_session` — прикладные сервисы.
  7. `am_core` — фасад API (`am::Core`), реестр команд, плагин-хост.
  8. Приложения: `am-gui`, `am` (cli), `am-worker`.
  Модули форматов (stl, 3mf, assimp, images, svg, dxf, gcode…) — **плагины или встроенные плагины**, зарегистрированные через тот же реестр (ТЗ 3.2.4). Пример ограничения из ТЗ 3.5.4: `am_catalog` не зависит от рендеринга, и это проверяется в CMake.
- **Последствия:** каждый слой — отдельная статическая библиотека с собственными тестами (ТЗ 3.4.4).

## ADR-0005. Формат контейнера ассета
> **Статус: пересмотрено ADR-0035.** Маркер `am-asset`, каталоги `derived/`, `previews/`, `scenes/`, `ext/` и короткие ID отменены; правила сжатия, ZIP64, без шифрования и без data descriptor действуют. Текст сохранён для истории.
- **Контекст:** ТЗ 4.1–4.3, открытые вопросы 2 и 4.
- **Решение (формат v1):**
  ```
  <uuid>.zip
  ├── am-asset                 ← 1-я запись, STORED, ASCII: "application/vnd.am.asset+zip;v=1\n"
  ├── manifest.json            ← 2-я запись, DEFLATE, UTF-8, источник истины
  ├── content/                 ← исходные файлы побайтово
  │   ├── i001/…               ← входной набор №1 с исходной иерархией
  │   └── i002/…
  ├── derived/<op-id>/…        ← результаты явной конвертации (ТЗ 9.4.3)
  ├── previews/                ← превью, созданные программой (оригинальные картинки остаются в content/)
  │   ├── p-<id>.png
  │   └── p-<id>.render.json   ← параметры генерации (ТЗ 8.2.5)
  ├── scenes/<id>.json         ← сохранённые сцены (ТЗ 8.3.4)
  └── ext/<plugin-ns>/…        ← крупные данные плагинов (необязательно)
  ```
  - Маркер `am-asset` по аналогии с EPUB `mimetype`: быстро и надёжно распознаёт «свой» контейнер (ТЗ 6.1.3) по первым ~80 байтам файла.
  - Все имена — UTF-8 с битом 11. ZIP64 включается автоматически.
  - Сжатие: DEFLATE (zlib-ng, уровень 6) для сжимаемых данных; **STORED** для заведомо сжатых (jpg, png, webp, gif, mp4, zip, 7z, rar, 3mf, gcode.3mf, lys?). Решение принимается по расширению и по пробному сжатию первых 64 КБ (если коэффициент больше 0,95 — STORED).
  - Без шифрования ZIP. Без data descriptor (бит 3) — размеры и CRC в локальном заголовке, это упрощает восстановление.
  - Ограничение пути внутри ZIP — 200 байт UTF-8 (ADR-0012).
  - В библиотеке файл называется `<uuid>.zip`. При полном экспорте — `<Название ассета>.zip` (с санитизацией имени), внутренний ID не меняется (ТЗ 4.4.3).
- **Последствия:** контейнер открывается любым ZIP-архиватором, пользователь видит понятную структуру.

## ADR-0006. Протокол безопасной записи ZIP (commit protocol)
- **Контекст:** ТЗ 4.6, 4.8.2, открытый вопрос 13.
- **Решение:**
  1. Перед операцией в `state.sqlite` пишется запись журнала `pending_ops(op_id, asset_id, kind, target, temp, state='prepared', started_at)`.
  2. Создаётся новый ZIP `<dir>/.am-tmp/<asset>.<op_id>.zip` **на том же томе**. Неизменённые записи копируются **raw** (без декомпрессии и рекомпрессии, CRC сохраняется), новые записи сжимаются со стримовым SHA-256.
  3. `FlushFileBuffers` / `fsync`, закрытие файла.
  4. Проверка: повторное открытие, маркер, парсинг манифеста и валидация схемы, совпадение каталога записей с манифестом, CRC всех записей, SHA-256 **новых и изменённых** записей (полная проверка — по флагу).
  5. `state='verified'`.
  6. Замена: Windows — `ReplaceFileW(target, temp, backup=<target>.am-bak)` с fallback на `MoveFileExW(MOVEFILE_REPLACE_EXISTING|MOVEFILE_WRITE_THROUGH)`; POSIX — `rename()` + `fsync(dir)`. `state='committed'`.
  7. Обновление индекса в `index.sqlite`, `state='indexed'`, удаление `.am-bak`, удаление записи журнала.
  - **Восстановление при старте:** `prepared` → удалить temp. `verified` → повторить проверку и закоммитить (если target не изменился с момента начала, сверяется по mtime+size+SHA-256 манифеста) или откатить. `committed` → переиндексировать и очистить. Файлы `.am-tmp/*`, не упомянутые в журнале, удаляются только если они старше 24 ч и **не открыты** (ТЗ 4.6.5).
  - Для сетевых и съёмных томов используется тот же алгоритм. Если `ReplaceFileW` не поддерживается, применяется двухфазный rename через `.am-bak`, отмеченный в журнале.
- **Последствия:** в любой момент на диске существует хотя бы один корректный ZIP (ТЗ 4.6.2).

## ADR-0007. Хранилище библиотеки: три базы SQLite
- **Контекст:** ТЗ 4.8, 5.10, 7.6.3–4, 10.3.5 — индекс восстановим, а пользовательские данные нет.
- **Решение:** структура каталога библиотеки:
  ```
  <Library>/
  ├── am-library.toml          ← id библиотеки (UUIDv7), имя, версия схемы, настройки
  ├── assets/<xx>/<uuid>.zip   ← xx = последние 2 hex-цифры uuid (равномерно, ≤ 256 подпапок)
  ├── trash/<uuid>.zip         ← корзина (ТЗ 10.8)
  └── .am/
      ├── index.sqlite         ← ПЕРЕСТРАИВАЕМЫЙ: копии метаданных, FTS, хеши, признаки, кэш состояний
      ├── userdata.sqlite      ← НЕВОССТАНАВЛИВАЕМЫЙ: реестр связей, заключения, коллекции, избранное, сохранённые поиски, словарь тегов/синонимов, определения пользовательских полей
      ├── state.sqlite         ← ОПЕРАЦИОННЫЙ: журнал pending_ops, очередь заданий, сессии редактирования, журнал операций
      ├── cache/thumbs/…       ← миниатюры (удаляемы)
      ├── cache/geom/…         ← подготовленная геометрия (удаляема)
      ├── sessions/<8hex>/     ← рабочие каталоги сессий (не мусор! ТЗ 8.8.1)
      └── .am-tmp/             ← временные файлы операций (на том же томе)
  ```
  Режим WAL, `synchronous=NORMAL` для index и `FULL` для userdata и state. Резервное копирование userdata — через `VACUUM INTO` по расписанию и перед миграциями.
- **Последствия:** удаление `index.sqlite` безопасно (выполняется rebuild). Удаление `userdata.sqlite` теряет только связи, коллекции и словари — ассеты не страдают.

## ADR-0008. Идентификаторы
> **Статус: пересмотрено ADR-0035.** ID, видимые в ZIP, — UUIDv4; локальные `i001/f00001/g001` отменены; независимая копия — ревизия 1 `asset_created` с `creation_kind = independent_copy` (**ADR-0036 п. 4**; прежняя формулировка про событие `asset_copied` заменена). UUIDv7 — для ID вне ZIP.
- **Решение:** ID ассета — **UUIDv7** (RFC 9562): упорядочен по времени, хорошо ложится в индексы, не раскрывает MAC-адрес. Текстовая форма — 36 символов в нижнем регистре. ID библиотеки, входного набора, операции и превью — тоже UUIDv7. Внутри манифеста короткие локальные ID: входные наборы `i001`, записи файлов `f00001`, группы `g001`.
- **Конфликт ID при импорте готового ассета (ТЗ 4.4.5, 6.3.4):** одинаковый ID и SHA-256 манифеста → «идентичен». Одинаковый ID и иная ревизия → показать сравнение и предложить: пропустить, заменить (только явно), импортировать как **новую независимую копию с новым ID** (записывается `derived_from: <старый id>`).

## ADR-0009. Плагины: C ABI + C++ SDK
> **Статус: Кандидат, пересмотрено ADR-0026.** Тип `gui-qt` из v1 исключён; C ABI утверждается после спайка S6.
- **Контекст:** ТЗ 3.2–3.3, открытый вопрос 9.
- **Решение:**
  - Плагин — динамическая библиотека с одной экспортируемой функцией `extern "C" const am_plugin_v1* am_plugin_entry(const am_host_v1* host)`. Структуры — POD с полем `struct_size` (расширение без ломки ABI) и `abi_version`. Строки — UTF-8 `const char*` + длина, буферы — через callbacks хоста, исключения через границу не проходят.
  - Рядом лежит `plugin.toml`: id (reverse-DNS), версия (semver), `requires_api = ">=1.0,<2"`, список capabilities (`format.read`, `preview.generate`, `convert`, `metadata.extract`, `dedup.method`, `command`, `gui.panel`) и описание. Хост читает toml **без загрузки DLL** — это даёт список плагинов и включение/выключение (ТЗ 3.3.3) без риска падения.
  - Header-only C++ SDK (`sdk/include/am/plugin.hpp`) скрывает C ABI за классами.
  - Встроенные модули используют **тот же** интерфейс реестра (статическая регистрация), поэтому модуль можно перенести между встроенным и внешним без переделки (ТЗ 3.2.4).
  - GUI-расширения: плагин регистрирует команды (без Qt в ABI). Панели с Qt — отдельный тип плагина `gui-qt`, совместимый только с той же мажорной версией Qt и тем же компилятором; этот тип помечен в манифесте как ABI-хрупкий.
  - Каталог настроек плагина: `config/plugins/<id>.toml`, пространство имён метаданных `x.<plugin-id>.*`.
- **Последствия:** обновление программы не требует пересборки плагинов в пределах `abi_version` 1.x (ТЗ 3.3.1).

## ADR-0010. Манифест: структура
> **Статус: заменено ADR-0035** (топология ТЗ §19.4.19). Текст сохранён для истории.
- **Решение:** см. `docs/specifications/container_manifest_v1.md` и `schemas/manifest.v1.schema.json`. Главные секции: `format`, `asset`, `provenance.sources[]`, `inputs[]`, `files[]` (реестр включённых и исключённых записей), `groups[]`, `classification`, `characteristics`, `fields.user`, `previews[]`, `scenes[]`, `derived[]`, `history[]`, `ext{}` (поля плагинов; неизвестные ключи сохраняются как есть). В `history[0]` пишется версия программы, профиль импорта и версии обработчиков (закрывает потерю П-4).

## ADR-0011. Импорт: распознавание контейнеров и томов
- **Решение:** тип контейнера определяется **по сигнатуре**, расширение — подсказка. Наборы томов собираются по заголовкам (RAR5: флаг volume и номер тома, RAR4: флаги MHD_VOLUME/FIRSTVOLUME, 7z split: проверка последовательности `.NNN`, zip split: `.z01…`). Имена (`.partN`, ` (N)` от Telegram, `.rNN`) — только для формирования кандидатов. Статусы записей: `included`, `included_renamed{reason}`, `excluded{reason}`. Правила исключения **применяются до раскрытия вложенных архивов** (кейс `._anime+23.3mf`). Детектор AppleDouble — по сигнатуре `00 05 16 07`.

## ADR-0012. Пути и кодировки
- **Решение:** на Windows все обращения к ФС идут через `\\?\`-префиксированные пути (`am::fs::native()`), `longPathAware=true` в манифесте приложения. Внутренний путь в ZIP ограничен 200 байтами UTF-8, запрещены `<>:"|?*`, управляющие символы, компоненты `.`/`..`, хвостовые точки и пробелы, имена устройств (CON, NUL…). При нарушении путь укорачивается: `<сокращённый-префикс>~<8hex>.<ext>`, исходный путь и причина пишутся в манифест. Декодирование имён из ZIP: бит 11 → extra 0x7075 → строгий UTF-8 → эвристика (CP866/CP1251/GBK/Shift-JIS/CP437) → ручное переопределение. Если имя не было валидным UTF-8, в манифест пишется `name_raw_b64`.

## ADR-0013. Метаданные: базовые и пользовательские поля
> **Статус: пересмотрено ADR-0035** (`field_definitions[]` с FieldID, значения в `custom_values`, `metadata` у asset/group/file, `claims`).
- **Решение:** базовые необязательные поля `title`, `description`, `authors[]`, `publisher`, `license{text, code, file_ref, url}`, `links[]`, `dates{published, acquired}`, `tags.confirmed[]`, `categories[]` (полные пути), `characteristics{}` (типизированные значения с единицами). **Пользовательские поля** определяются в библиотеке (`userdata.sqlite: field_defs`), а в ассете хранятся значение и **копия определения** (`fields.user.<key> = {type, unit, value}`). Происхождение значения: `value_origin ∈ {user, file, measured, inferred, plugin:<id>}` и `confirmed: bool` (ТЗ 5.8.2–3). Закрывает потерю П-1.

## ADR-0014. Хеширование
- **Решение:** SHA-256 обязателен (ТЗ 5.5). Считается в потоке при упаковке, а для исходных архивов и томов — отдельным чтением, параллельно с распаковкой при возможности (реализация через `std::jthread` и кольцевой буфер). CRC32 исходных записей сохраняется. Для быстрого «уже видели этот файл?» в index хранится колонка `size + sha256` с индексом. XXH3-128 используется только для кэшей.

## ADR-0015. Система заданий
- **Решение:** см. `docs/architecture/jobs_and_sessions.md`. Задание — персистентная запись в `state.sqlite` (тип, параметры JSON, состояние, прогресс, ошибки, `needs_decision`). Состояния: `queued → running → (paused) → succeeded | failed | cancelled | needs_decision`. Пул потоков с отдельными ограничителями для I/O и CPU, параллелизм — по типу носителя (HDD: 1 I/O-поток на устройство, SSD: N). Идемпотентность через `op_id`: повторный запуск не создаёт второй ассет, так как проверяется журнал `pending_ops` и наличие ассета с `history[0].op_id`.

## ADR-0016. Поиск совпадений и проверка наличия
- **Решение:** **быстрый режим** — SQL по `sha256`, `(name, size)`, мультимножеству хешей файлов (Jaccard по множеству sha256 через MinHash-сигнатуру, 128 значений в index). **Углублённый режим** — pHash/dHash изображений (BK-tree), 3D-дескрипторы, эмбеддинги (плагин). Добавлена операция **`lookup`** — проверка наличия без импорта для изображения, файла, архива или папки (закрывает потерю П-3). Результаты унифицированы: `MatchResult{a, b, level(file|group|asset), method, kind, score?, evidence[]}`. Пользовательские заключения хранятся в `userdata.sqlite` и привязаны к `(asset_id, revision)`.

## ADR-0017. GUI
- **Решение:** Qt 6 Widgets. Главное окно — `QMainWindow` с docking: «Навигация» (библиотеки, категории, теги, источники, коллекции, сохранённые поиски), центральная область (`QListView` IconMode с собственным делегатом / `QTableView` над одной `AssetListModel` с ленивой подгрузкой страниц из SQLite), «Свойства», «Превью», «Задания». Строка состояния с **постоянным индикатором «Требуется решение: N»** (ТЗ 10.10.6). Главное меню, контекстные меню, панели инструментов и горячие клавиши строятся **из реестра команд** (С-1). 3D-просмотрщик — `QOpenGLWidget` с собственным рендерером. **Qt Quick 3D не используется** (GPL-3 в open-source).

## ADR-0018. Просмотр и превью
> **Поправка ADR-0025:** ключ миниатюры — хеш источника превью и параметров рендера, а не `<asset>-<rev>`.
- **Решение:** миниатюры каталога — WebP/JPEG 256 px и 512 px в `cache/thumbs/<xx>/<asset>-<rev>-<size>.webp`, создаются лениво. Постоянные превью — PNG до 2048 px в `previews/` внутри ZIP. Автоматический выбор: (1) картинка рядом с архивом в папке ассета, (2) изображение верхнего уровня внутри архива с наибольшей площадью, (3) встроенное превью (3MF, G-code, CTB, Blend), (4) рендер «самого крупного» STL в изометрии с matcap. Геометрия загружается по требованию, LOD генерируется meshoptimizer при числе треугольников больше 2 млн.

## ADR-0019. Конвертация
- **Решение:** интерфейс `IConverter{describe() → {inputs, outputs, params, known_losses}, run(job)}`. Адаптеры: Assimp (меш-форматы), lib3mf (3MF), OCCT (STEP → меш, плагин), внешние утилиты через `ExternalToolConverter` (шаблон командной строки, timeout, проверка результата независимо от exit code — ТЗ 9.5.4). Результат «в ассет» пишется в `derived/<op-id>/` с записью в `derived[]` манифеста (входы с sha256, конвертер, версия, параметры).

## ADR-0020. Сеть
- **Решение:** базовая программа **не обращается в сеть**. Сетевые функции (проверка URL, скачивание моделей эмбеддингов и LLM, проверка обновлений) — только в плагинах, выключенных по умолчанию; в строке состояния отображается индикатор сетевой активности. Закрывает потерю П-2.

## ADR-0021. Лицензионная политика
- **Решение:** ядро и базовая поставка — только MIT/BSD/Apache/Zlib/BSL/MPL-2.0/PD. LGPL — динамически (Qt, OCCT, FFmpeg). GPL/AGPL — только во внешних необязательных плагинах. 7z.dll не распространяется вместе с программой. Лицензия самого проекта не определена владельцем, поэтому выбор оставлен открытым, но политика зависимостей не мешает ни открытой, ни закрытой лицензии.

## ADR-0022. Настройки и режимы установки
- **Решение:** TOML. Обычный режим: `%APPDATA%\AM\config\` (Windows), `$XDG_CONFIG_HOME/am/` (Linux). **Портативный режим** включается, если рядом с exe есть файл `portable.flag`: тогда используется `<exe-dir>/data/`. Список библиотек хранится в `config/libraries.toml` (путь + id библиотеки, при недоступности носителя библиотека помечается offline, а не удаляется). Реестр Windows не используется.

## ADR-0023. Локальная LLM
> **Статус: сценарии (Lua) и флаг `llm_allowed` заменены ADR-0027.** Остаётся в силе: LLM — плагины, отложена на последнюю веху.
- **Решение:** отложено на этап M10. Архитектурная заготовка: LLM-плагин получает доступ только к **реестру команд с флагом `llm_allowed`** и к read-only запросам каталога. Изменяющие команды требуют подтверждения пользователя через механизм «Требуется решение». Сценарии — Lua-скрипты (sol2) в `scenarios/`.

## ADR-0025. AssetRepository: снимки, блокировки, запросы изменений, события, перемещение (дополняет ADR-0006, ADR-0008, ADR-0018)
- **Контекст:** ТЗ §12.7 (v1.4). В подготовке не было снимков для читателей, оптимистического контроля ревизий и межбиблиотечного перемещения (отчёт 03, К-1…К-8).
- **Решение:**
  1. **Единственный писатель.** `storage::AssetRepository` — **единственный** код, который меняет действующие ZIP. Остальные модули готовят данные во временной области `.am/.am-tmp/` и передают запрос.
  2. **Идентификация:** `AssetRef{library_id, asset_id}`. Любая операция чтения или записи привязана к `revision`.
  3. **Снимок чтения.** `AssetSnapshot` = открытый дескриптор ZIP + ревизия + разобранный манифест.
     - **Основной режим (NTFS, Windows 10 1709+).** ZIP открывается с `FILE_SHARE_READ | FILE_SHARE_DELETE`. Замена — переименование с POSIX-семантикой: `SetFileInformationByHandle(FileRenameInfoEx, FILE_RENAME_FLAG_POSIX_SEMANTICS | REPLACE_IF_EXISTS)`. Открытые дескрипторы видят старое содержимое до закрытия.
     - **Режим поколений** — где POSIX-семантика не поддерживается (exFAT, часть SMB). Новая ревизия пишется как `<uuid>.zip`, старая переименовывается в `.am/gen/<uuid>.<rev>.zip`. Она удаляется, когда счётчик снимков (в памяти и в `state.sqlite: snapshots`) падает до нуля, либо при следующем старте.

     Режим выбирается по итогам спайка **S5+**. `ReplaceFileW` из ADR-0006 остаётся запасным путём для томов без открытых читателей.
  4. **Конкурентность:** много читателей, один писатель на ассет.
     - В процессе — `std::mutex` на `AssetRef`.
     - Между процессами — блокировка `.am/locks/<uuid>.lock` (`LockFileEx`/`flock`) на время фиксации.

     Разные ассеты фиксируются параллельно.
  5. **Запрос изменения:** `ChangeRequest{ref, expected_rev, ops[], op_id, reason}`, где `ops` — типизированные намерения из перечня `history.op` ([спецификация манифеста](../specifications/container_manifest_v1.md)).
     - Если `expected_rev` устарела, коммутирующие операции переприменяются к свежей ревизии. Коммутирующие — это изменение *разных* полей метаданных и добавление файлов с несовпадающими путями.
     - Остальные операции дают `Errc::conflict` и требуют решения пользователя.

     Callback-мутатор `commit_update(ref, fn)` остаётся внутренним низкоуровневым API хранилища (ТЗ §12.7.6).
  6. **Жизненный цикл** — шаги ADR-0006. Состояние «ZIP зафиксирован, индекс не обновлён» (`committed`) распознаётся при старте и долечивается переиндексацией.
  7. **События** `AssetCreated/Updated/Restored/Removed` публикуются после состояния `indexed` через `contracts::IEventBus`. Источником истины они не являются: потери компенсируются журналом `pending_ops` и сверкой (`sync`).
  8. **Кэши** инвалидируются по зависимостям результата. Ключ миниатюры — `sha256(источник превью) + hash(параметры рендера) + размер` (заменяет `<asset>-<rev>` из ADR-0018). Изменение тегов кэши не затрагивает.
  9. **Межбиблиотечное перемещение.** Запись `pending_ops(kind='move')` в журнале **исходной** библиотеки, состояния `copying → copied → verified → registered → source_removed`.
     - Исходник удаляется только после регистрации копии в целевой библиотеке.
     - Сбой до `registered` — неполная копия удаляется.
     - Сбой после `registered` — удаление исходника завершается с проверкой ID и SHA-256 манифеста.

     Две корректные копии в промежутке допустимы.
  10. *(Пересмотрено ADR-0035: FileID/GroupID — UUIDv4, удалённые — в `historical_files`.)* **FileID и GroupID (вопрос 33):** локальные ID манифеста (`f00001`, `g001`, `i001`) устойчивы в пределах ассета и никогда не используются повторно. Удалённый ID помечается в `history`.
- **Последствия:** в `state.sql` добавлены таблица `snapshots` и поля `pending_ops.kind='move'`, `target_library_id`, `expected_rev`.
  - в M1 — `AssetRepository`, снимки и kill-тесты фиксации при открытом читателе;
  - в M2 — перемещение между библиотеками.

## ADR-0026. Плагины: жизненный цикл, владение ресурсами, GUI-точки (пересматривает ADR-0009)
- **Контекст:** ТЗ §12.5.2, §12.8 (v1.4):
  - C ABI — пока кандидат;
  - манифест читается до загрузки кода;
  - жизненный цикл управляемый;
  - владение ресурсами явное;
  - GUI расширяется только через контролируемые точки.

  См. отчёт 03, П-1…П-7.
- **Решение:**
  1. **ABI — кандидат.** `sdk/include/am/am_plugin.h` остаётся черновиком v1: POD-структуры с `struct_size` и `abi_version`, без исключений и STL на границе.

     Утверждение — после спайка **S6**, который проверяет:
     - плагин, собранный другим тулсетом MSVC и clang-cl;
     - передачу буферов и callback;
     - отказ загрузки;
     - выгрузку при остановке.
  2. **Манифест** `plugin.toml` читается до загрузки кода — без изменений.
  3. **Жизненный цикл:** `discovered → checked(compatible|incompatible|missing_deps) → loaded → registered → active → draining (новые вызовы запрещены) → stopped → unloaded`.
     - Отключение вступает в силу после завершения или отмены активных заданий.
     - Горячая выгрузка DLL не обещается; при необходимости — после перезапуска, с сообщением пользователю.
     - Если при восстановлении задания нужного плагина нет — состояние `needs_decision` с диагностикой, без подмены обработчика.
  4. **Владение.** Для каждой структуры ABI документируются владелец и способ освобождения:
     - память, выделенная хостом, освобождается через `host->free`;
     - память, выделенная плагином, — через `plugin->release`;
     - callback и подписки действуют до явного `unsubscribe` или до `draining`;
     - сырые указатели хоста после возврата из вызова не удерживаются.

     Правило вносится в комментарии `am_plugin.h` и в документ SDK.
  5. **GUI-точки v1:**
     - команды (меню, панели, горячие клавиши) через реестр;
     - страницы настроек по декларативной схеме;
     - обработчики предпросмотра (вывод — изображение);
     - панели, описанные данными.

     Тип `gui-qt` (Qt-виджеты в ABI) **исключён**. Произвольные виджеты — после отдельного проектирования.
  6. **Тестовые плагины** (`tests/plugins/`):
     - корректный;
     - с устаревшим `requires_api`;
     - с отсутствующей зависимостью;
     - с отказом `init`;
     - с ошибкой обработки;
     - с долгой отменяемой задачей;
     - проверяющий сохранение неизвестных полей `ext`;
     - с аварией во внешнем процессе.

     Тестовые плагины появляются **вместе с плагин-хостом**, а не в M9. Пример плагина — `plugins/examples/`; SDK собирается без приложения.
- **Последствия:** ADR-0009 действует в части манифеста, пространств имён и capabilities.

## ADR-0027. Сценарии, полномочия команд и AI-слой (заменяет часть ADR-0023)
- **Контекст:** ТЗ §11 (v1.3):
  - движок сценариев не зависит от LLM и появляется раньше неё (этапы A–C до D–F);
  - сценарии — переносимые версионированные данные;
  - есть Dry Run;
  - три уровня полномочий;
  - идемпотентность объявляется для каждой операции;
  - нужен тестовый AI-адаптер.

  См. отчёт 03, Л-1…Л-3, Л-7…Л-9.
- **Решение:**
  1. **Полномочия команды.** У `contracts::Command` есть поля:
     - `permission ∈ {read, prepare, modify}`;
     - `dangerous`;
     - `scriptable`;
     - `idempotency ∈ {none, by_op_id, natural}`.

     Реестр проверяет выданный уровень в `invoke_as(id, inv, granted)` до вызова обработчика. Флаг `llm_allowed` упразднён. *Реализовано в коде и покрыто тестами.*

     Соответствие классификации воздействия ТЗ §14.6.10 (v1.7): «чтение» = `read`; «изменение» = `prepare`/`modify`; «разрушительное изменение» = `modify` + `dangerous` (массовое окончательное удаление, перезапись, восстановление поверх текущих данных). Полномочие изменять теги не даёт права на `dangerous`-команды.
  2. **Формат сценария** — JSON-документ, проверяемый JSON Schema (`schemas/scenario.v1.schema.json`, веха M-S):
     ```json
     { "format": "am-scenario", "version": 1, "id": "...", "title": "...",
       "requires": [{"command": "am.asset.set_tags", "min_api": 1}],
       "permission": "modify",
       "params": {"tag": {"type": "string"}, "q": {"type": "string"}},
       "trigger": {"kind": "manual", "event": null},
       "steps": [
         {"id": "s1", "command": "am.search", "args": {"query": "${params.q}"}},
         {"id": "s2", "foreach": "${s1.result.assets}", "when": "not (${item.tags} contains 'nsfw')",
          "command": "am.asset.set_tags", "args": {"asset": "${item.id}", "add": ["${params.tag}"]},
          "on_error": "continue"} ] }
     ```
     - `trigger.kind ∈ {manual, event, schedule, batch}`; `on_error ∈ {continue, stop, ask}`.
     - Выражения — ограниченный язык: сравнения, `contains`, `and/or/not`, доступ к результатам предыдущих шагов. Без вложенных циклов произвольной глубины и без вызовов вне реестра.
     - Уровни хранения: `app/`, `<library>/.am/scenarios/`, пользовательские.
     - Импортированный сценарий требует явного разрешения на исполнение.

     Это ответ на вопрос 29.
  3. **Dry Run.** Обход шагов с вызовом у команды необязательного метода `plan(args) → {affected, actions, warnings, confirmations}`. Если результат шага неизвестен до исполнения, следующие шаги помечаются как «прогноз».
  4. **Исполнение** — через `am_jobs`:
     - каждый изменяющий шаг — отдельное задание с `op_id`;
     - ошибки отдельных ассетов не откатывают всю партию;
     - неоднозначность → `needs_decision`.
  5. **AI-слой** `am_ai` (опция):
     - интерфейс `IAiAdapter{capabilities(), complete(ctx, schema)}`;
     - сборка ограниченного контекста;
     - валидация ответа по JSON Schema и правам;
     - **тестовый адаптер** с заданными ответами.

     Конкретные движки — плагины (llama.cpp; локальный HTTP-сервис). Адрес, отличный от `localhost`, — это сетевая активность и требует явной настройки (ADR-0020).
  6. **Lua** — не базовый механизм. Возможен позже как необязательный плагин-исполнитель.
- **Последствия:** веха **M-S «Сценарии»** — после M5, когда реестр команд и задания уже готовы. LLM (этапы D–F) — последняя веха.

## ADR-0028. Статусы значений и хранение предложений (дополняет ADR-0010, ADR-0013)
> **Статус:** пп. 1–2 (представление статусов в ZIP) **пересмотрены ADR-0035** — `metadata.claims[]`; пп. 3–5 действуют. П. 3 **уточнён ADR-0036 п. 3**: решение Dismiss хранится в `userdata.sqlite`, `suggestions.state` в индексе — производный.
- **Контекст:** ТЗ §11.2 (v1.3):
  - статусы «предложено / вычислено / подтверждено»;
  - у значения есть источник, обработчик, версия, основание, время и уверенность;
  - неподтверждённые предложения хранятся в служебных данных библиотеки, ревизии ZIP из-за них не растут.

  См. отчёт 03, Л-4…Л-6.
- **Решение:**
  1. **Статус и происхождение.** Каждое значение метаданных с происхождением имеет `status ∈ {suggested, computed, confirmed}` и `origin{kind: user|file|measured|inferred|plugin, handler?, handler_version?, basis?, analyzed_at?, confidence?}`.

     Соответствие старой модели:

     | Было | Стало |
     |---|---|
     | `measured` | `computed` |
     | `inferred` или `plugin` без подтверждения | `suggested` |
     | `confirmed: true` | `confirmed` |

     `confidence` пишется, только если метод даёт осмысленную оценку. Ответ LLM не считается калиброванной вероятностью.
  2. **В ZIP хранятся:**
     - подтверждённые значения;
     - вычисленные характеристики;
     - **предположения, сделанные при создании ассета** (источник и автор по имени папки, группы масштабов) — это provenance (ТЗ §5.2.4, критерий 27).
  3. **В библиотеке хранятся** предложения **последующего** анализа (классификаторы, LLM) — таблица `index.sqlite: suggestions(asset_id, target, value, handler, handler_version, basis, confidence, created_at, content_key)`. Она воспроизводима и ревизию не увеличивает. Подтверждение переносит значение в ZIP одной фиксацией (пакетно — через задания).
  4. **Приоритет пользователя.** Подтверждённое пользователем значение повторным анализом не перезаписывается; альтернатива показывается рядом.
  5. **Словарь тегов** в `userdata.sqlite`: отношения `synonym`, `related`, `parent` (иерархия) и статус `proposed|accepted`.
- **Последствия:** схемы уже обновлены:
  - `manifest.v1.schema.json` — `$defs.valueStatus` и `$defs.originDetail`;
  - [спецификация манифеста](../specifications/container_manifest_v1.md) — раздел о статусах;
  - `index.sql` — таблица `suggestions`;
  - `userdata.sql` — таблица `tag_relations`.

  Реализация — в M1–M2.

## ADR-0029. Исследование ресурсов и тестовые наборы
- **Контекст:** ТЗ §13 (v1.5):
  - коллекция не является эталоном;
  - 16 универсальных сценариев и матрица покрытия;
  - три уровня анализа без создания ассетов;
  - отчёты MD+JSON со статусами полноты;
  - лимиты разбора;
  - обработчики общие с импортом;
  - наборы: синтетические, реальные минимальные, комплексные;
  - эталоны `expected.json`;
  - трассировка к требованиям.

  См. отчёт 03, И-1…И-9.
- **Решение:**
  1. **Режим исследования** — это первые стадии конвейера импорта (`Scanner → ContainerProbe → ArchiveWalk → BoundaryProposer`) без `AssetBuilder`.
     - **Команда:** `am analyze <path> --level inventory|structure|deep --profile <p> --out <dir>`. Пишет `report.md` и `report.json` по схеме `schemas/analysis.v1.schema.json` (M3).
     - **Статусы объектов:** `analyzed{level}`, `partial{reason}`, `unsupported`, `unavailable`, `skipped{reason}`, `incomplete{limit}`. Для каждого объекта указываются обработчик и версия, основание распознавания, исходные байты имени.
     - **Обезличивание:** флаг `--redact` убирает абсолютные пути и URL.
     - **Кэш:** по `(size, mtime)` — для предварительной оценки; утверждения о совпадении — только по SHA-256.
     - **Повторный анализ** выборочный — по версии обработчика или правил.

     Это ответ на вопрос 38.
  2. **Лимиты** (секция `[limits]` профиля): глубина, число записей, распакованный объём, коэффициент распаковки, время на контейнер, временное место.
     - Достижение лимита — статус `incomplete{limit}`, а не успех.
     - Пути, выходящие за рабочую область (`..`, абсолютные, имена устройств), не распаковываются.
  3. **Правила, специфичные для источника** (Telegram и др.), — только в профилях. Схема имён томов `copy_suffix` настраивается секцией `[volumes]`. *Реализовано: `VolumeNamingRules`.*
  4. **Тестовые данные:**
     - **Синтетические** — `tests/fixtures/<case>/` с файлом `expected.json`.
       - Генерируются скриптами из `tools/fixtures/`; малые файлы допустимы в репозитории.
       - Схема эталона — `schemas/expected.v1.schema.json`.
       - ID и время сравниваются по свойствам.
     - **Реальные минимальные и комплексные** — **реестр** `tests/real/registry.json`: путь в коллекции, размер, SHA-256, назначение, сценарий.
       - Тесты читают коллекцию на месте, **только для чтения**.
       - Если коллекции нет, тест пропускается (`GTEST_SKIP`).
       - Файлы коллекции в репозиторий не копируются (CLAUDE.md, ТЗ §13.4.9).
  5. **Трассировка:**
     - тесты помечают требования через `RecordProperty("req", "K-72")`;
     - скрипт `tools/coverage/req_report.py` (M1) собирает отчёт из JUnit XML ctest;
     - матрица 16+ сценариев — [`docs/plan/coverage_matrix.md`](../plan/coverage_matrix.md).
  6. **Регрессии.** Каждый исправленный воспроизводимый дефект получает регрессионный тест в `tests/regression/`.
- **Последствия:**
  - `am analyze` входит в M3;
  - реестр реальных данных и генератор fixtures — с M1.

## ADR-0030. Резервное копирование и восстановление библиотеки
- **Контекст:** ТЗ §14.3 (v1.7), критерии 118–120, вопрос 43; отчёт 04, Р-2. Раньше было только `VACUUM INTO` для `userdata` (ADR-0007) и временный `.am-bak` при фиксации (ADR-0006). Протокола копии библиотеки не было.
- **Решение:**
  1. **Состав.**
     - **Входят:** ZIP ассетов, **корзина** (по умолчанию; исключение — только явным выбором), `userdata.sqlite`, `am-library.toml`.
     - **Не входят:** `index.sqlite`, кэши, `.am-tmp`.
     - `state.sqlite` и рабочие каталоги сессий — отдельный режим «расширенная копия» (§14.3.8). Подтверждённые данные копируются отдельно от аварийного сохранения сессий.
     - Секреты интеграций не копируются без явного решения (§14.6.9).
  2. **Структура копии** — самодостаточный каталог: `backup-manifest.json`, `library/am-library.toml`, `library/assets/…`, `library/trash/…`, `library/.am/userdata.sqlite`.
     - Манифест копии (`format: "am-backup"`, `version: 1`, схема `schemas/backup.v1.schema.json`) содержит:
       - LibraryID;
       - дату;
       - версию приложения;
       - режим (`full | extended`);
       - полноту (`complete | partial{reason}`);
       - по каждому ZIP: путь, AssetID, ревизию, размер, SHA-256 файла;
       - перечень пользовательских данных с версиями схем.
  3. **Согласованная точка восстановления (§14.3.3):**
     1. `AssetRepository::begin_backup_epoch()` дожидается завершения текущих фиксаций и **кратко** приостанавливает приём новых `ChangeRequest`.
     2. Фиксируется перечень `(asset, revision)`.
     3. Для каждого ZIP открывается `AssetSnapshot` (ADR-0025).
     4. `userdata.sqlite` копируется через `VACUUM INTO` (или SQLite Online Backup API) **внутри той же паузы** — штатный механизм для WAL (§14.3.4).
     5. Пауза снимается. Затем ZIP копируются из снимков в фоне, чтение и запись библиотеки продолжаются.

     Ассеты, изменённые после точки, попадают в копию в зафиксированной ревизии благодаря снимку.
  4. **Запись копии** транзакционна:
     - сначала каталог `<dest>/.partial-<id>/`, в конце — переименование;
     - прерывание не трогает предыдущие копии;
     - **последняя известная пригодная копия никогда не удаляется** очисткой по сроку хранения (§14.3.10).
  5. **Проверка копии** — 4 уровня (§14.3.6):
     - `copied` (комплектность и размеры);
     - `structure` (ZIP открываются, манифесты читаются);
     - `content` (SHA-256 файлов по манифесту копии);
     - `trial_restore` (восстановление во временный каталог и `library verify`).
  6. **Восстановление (§14.3.7):**
     - всей библиотеки — по умолчанию в **новый каталог**, LibraryID сохраняется, индекс перестраивается;
     - отдельных ассетов;
     - отдельно `userdata`.

     Перезапись или слияние с существующими данными — только через разрешение конфликтов (ADR-0008) и подтверждение. Восстановление не исполняет бинарники и плагины из копии (§14.6.11).
  7. **Позже, без изменения формата ZIP:** инкрементальные копии (по ревизиям из манифеста копии), шифрование, сетевое назначение. В первый выпуск не входят (вопрос 43 остаётся открытым в части окончательного решения).
- **Последствия:**
  - веха M2: `am library backup|restore|verify-backup`, команды с полномочием `modify`; восстановление поверх существующих данных помечено `dangerous`;
  - запуск по расписанию — через систему заданий;
  - схема `backup.v1` вносится в реестр версий ([`versioning.md`](../specifications/versioning.md)).

## ADR-0031. Владелец записи библиотеки, режим «только чтение», возможности носителя (дополняет ADR-0025)
- **Контекст:** ТЗ §14.4.5, §14.5.2–3, 14.5.8–12, §14.7.11, критерии 123, 125–127; отчёт 04, Р-3. ADR-0025 блокирует только отдельный ассет на время фиксации.
- **Решение:**
  1. **Один владелец записи библиотеки.**
     - Процесс, открывший библиотеку на запись, держит `.am/library.lock` (`LockFileEx` с эксклюзивной блокировкой / `flock(LOCK_EX)`) **всё время открытия**.
     - В файле — PID, имя хоста, версия приложения, время (только для диагностики; доверие — блокировке ОС, а не содержимому).
     - Второй процесс (GUI, CLI, другая версия программы) получает `Errc::locked` с действием `open_read_only` и может открыть библиотеку только для чтения.
     - IPC для передачи команды владельцу — позже.
     - Блокировка ассета из ADR-0025 п. 4 остаётся внутренним уровнем.
  2. **Режим «только чтение»** (`LibraryMode::read_only`):
     - поиск, просмотр, анализ, экспорт и lookup по существующему индексу;
     - если индекс отсутствует или устарел, используется временный индекс в кэше пользователя, а не в библиотеке;
     - любая изменяющая команда получает `Errc::read_only`;
     - отсутствие права записи диагностируется явно; «заменяющая» библиотека неявно не создаётся (§14.5.10).
  3. **`StorageCapabilities`** — диагностика при подключении библиотеки:
     - `readable`, `writable`;
     - `max_file_size` (FAT32 → 4 ГиБ − 1);
     - `posix_rename`, `replace_file`;
     - `locks_reliable`;
     - `durability ∈ {verified, assumed, unknown}`;
     - `fs_kind`, `is_removable`, `is_network`.

     Значения берутся из таблицы режимов ФС по итогам S5/S5+, а **не** из пробного create/rename: пробная операция проверяет только право записи (§14.5.12).
  4. **Матрица режимов ФС** (`docs/specifications/fs_support.md`, заполняется по S5/S5+):
     - NTFS и ext4 — базовые, с полными тестами;
     - exFAT, FAT32, XFS, Btrfs, SMB, NFS — с документированным режимом:
       - `full`;
       - `write_with_limits`;
       - `read_only_default`.
     - **Сетевые ФС** по умолчанию открываются только для чтения, пока конфигурация не отмечена проверенной. SQLite WAL на сетевой ФС не размещается (§14.5.9).
  5. **Недоступный носитель:**
     - библиотека получает статус `unavailable`, её задания приостанавливаются, ассеты **не** считаются удалёнными;
     - при возврате проверяются LibraryID, журнал `pending_ops` и конфликтные копии (§14.5.8).
- **Последствия:**
  - M1: `AssetRepository` принимает `LibraryMode` и `StorageCapabilities`; `max_file_size` проверяется до фиксации;
  - M2: `library.lock`, режим «только чтение», статус `unavailable`, тест одновременного запуска GUI/CLI (критерий 123);
  - S5: добавлены ext4 и раздельная проверка атомарности, долговечности и восстанавливаемости.

## ADR-0032. Структурированная модель ошибок (дополняет ADR-0001)
- **Контекст:** ТЗ §14.4.2: стабильный код, серьёзность, компонент, операция/JobID/AssetID/LibraryID, техническая причина, понятный текст, допустимые действия; коды не привязаны к локализованным сообщениям. §14.8.1: английский UI с переводами. Отчёт 04, Р-4.
- **Решение:**
  1. `am::Error` (`include/am/foundation/result.hpp`) содержит:
     - `code` (`Errc`);
     - `severity` (`info|warning|error|critical`);
     - `component`;
     - `ctx{operation, job_id, asset_id, library_id, detail}`;
     - `message` — технический текст на английском, **не текст UI**;
     - `message_id` — стабильный ключ локализуемого сообщения;
     - `actions` (`retry|skip|decide|abort|open_read_only|free_space`);
     - `cause` — цепочка, `shared_ptr<const Error>`.

     ID — строки, потому что `foundation` не зависит от `domain`.
  2. **Коды стабильны:**
     - у `Errc` явные числовые значения, которые никогда не меняются и не переиспользуются;
     - машинное имя `errc_name()` вида `am.insufficient_space`;
     - новые коды добавляются в конец.

     Добавлены `resource_exhausted`, `insufficient_space`, `read_only`, `locked`.
  3. Текст для пользователя строит GUI/CLI по `message_id` из каталога сообщений (ADR-0034 п. 2). При отсутствии перевода используется английский текст каталога, при отсутствии ключа — `message`.
  4. **Журналы и CLI:**
     - журналы используют `to_log_string()` — код, компонент, операция, причина по цепочке;
     - структурированная запись журнала (spdlog, JSON-строки) содержит те же поля (§14.4.9);
     - обезличенный экспорт убирает `detail` с абсолютными путями.
  5. **На границе C ABI плагинов** передаются только числовой код и UTF-8 сообщение; `message_id` — необязательное поле следующей версии ABI после S6.
- **Последствия:**
  - `Error::make(code, msg, ctx)` сохранён — существующий код не менялся;
  - новые поля задаются цепочкой `.in() .op() .id() .allow() .caused_by()`;
  - *реализовано, тесты `Error.*`*.

## ADR-0033. Ресурсы, свободное место и профили производительности
- **Контекст:** ТЗ §14.2 (особенно 14.2.1, 14.2.5, 14.2.7–8, 14.2.10), критерии 115–117, вопрос 42; отчёт 04, Р-5.
- **Решение:**
  1. **Свободное место — часть протокола фиксации** (дополняет ADR-0006 п. 1–3).
     - Перед `prepared` вычисляется `need = оценка размера нового ZIP + временные данные + запас` (запас — параметр, по умолчанию `max(5 %, 256 МиБ)`; значение подлежит уточнению измерениями).
     - Если места не хватает — `Errc::insufficient_space` с действиями `free_space|abort`, до создания временного файла.
     - Во время записи место контролируется по мере роста файла. Нехватка прерывает операцию **до** замены; последний корректный ZIP сохраняется (критерий 117).
     - Также проверяется `StorageCapabilities::max_file_size` (ADR-0031).
  2. **`jobs::ResourceManager`** (уровень `jobs`):
     - отдельные пулы и лимиты: CPU, чтение, запись, GPU, внешние процессы;
     - приоритет интерактивных задач над фоновыми;
     - профиль и приоритет задаются для каждого задания;
     - начальные значения адаптируются к типу накопителя.

     Учёт RAM/VRAM — **бюджеты** (декларация задания плюс фактическое измерение, где возможно), а не жёсткий контроль чужого кода. Жёсткий контроль — только через отдельный процесс `am-worker` (M9).
  3. **Состояния задания** дополнены:
     - `waiting_resources`;
     - `resource_error`;
     - `cannot_continue_safely`.

     Автоматические повторы ограничены числом и интервалом, бесконечных повторов нет (§14.2.8, §14.4.3).
  4. **Профили ресурсов:** `economy`, `balanced` (по умолчанию), `performance`, `custom`. Профиль задаёт управляемые параметры (параллелизм, кэши, качество просмотра) и не подменяет фактические лимиты оборудования.
  5. **Кэши** ограничены по объёму и могут размещаться на другом диске. Незавершённые сессии внешнего редактора кэшем не являются и механизмом очистки не удаляются (§14.2.6).
- **Последствия:**
  - M1: проверка места и `max_file_size` в `AssetRepository`, тест на заполненный том;
  - M3: `ResourceManager` с пулами, состояниями и профилями;
  - M6: бюджеты VRAM и режимы качество/баланс/экономия;
  - числа по умолчанию — гипотезы, уточняются по [плану измерений](../architecture/nfr_measurement_plan.md).

## ADR-0034. Язык интерфейса, локализация и документация
- **Контекст:** ТЗ §14.8 (v1.7, уточнение владельца): английский — базовый обязательный язык UI и fallback; украинский — необязательный кандидат; русской локализации на начальных этапах нет; i18n закладывается с начала. Отчёт 04, Р-6 (принят владельцем, включая предложение по языку документации).
- **Решение:**
  1. Строки GUI и CLI — **английские**.
  2. **Механизмы перевода:**
     - GUI — `QObject::tr()` / Qt Linguist (`.ts` → `.qm`);
     - ядро не содержит готовых пользовательских текстов, а возвращает `message_id` (ADR-0032), который переводится каталогом сообщений;
     - каталог сообщений — TOML/JSON-ресурс по ключу, английский обязателен;
     - плагины поставляют собственные каталоги (§14.8.1).
  3. Пользовательские данные (названия, теги, поля, пути) при смене языка UI не меняются. Хранение и поиск данных на любом языке, включая русский, не ограничены (§14.8.2).
  4. **Язык документации:**
     - **документация разработки** (ТЗ, ADR, отчёты, планы, руководство разработчика) — русский, это язык обсуждения с владельцем;
     - **пользовательская документация** (руководство начала работы, полное руководство) и **публичная техническая документация** (формат ZIP, API, плагины, сценарии) — английский;
     - исходный формат — Markdown (§14.8.11);
     - спецификации формата пока ведутся на русском и переводятся при стабилизации формата.
  5. **Пользовательский `CHANGELOG.md`** (английский) — с первого выпускаемого CLI (M1). Это не история редакций ТЗ (§14.8.12).
- **Последствия:**
  - `CLAUDE.md` уточнён;
  - `libraries.md` дополнен разделом i18n;
  - в M5 — проверка полного английского интерфейса, HiDPI и клавиатуры (критерии 134–135).

## ADR-0035. Формат ZIP-ассета 1.0 по ТЗ §19 (пересматривает ADR-0005, 0008, 0010, 0013, 0028; дополняет ADR-0006, 0012, 0025)
> **Статус:** действует. П. 10 (адресат claims) и п. 14 (оболочка `extensions`) **уточнены ADR-0036**; п. 11 (`asset_copied`) **заменён ADR-0036 п. 4**. П. 7 (opaque-записи, V4), п. 10 (`review` без `state`) и п. 12 (`generation` нормативен) **уточнены ADR-0037**.
- **Контекст:**
  - ТЗ v1.8 §19.4 (MF-01…MF-12): согласованная модель ZIP-ассета, FormatID, UUIDv4, топология `manifest.json`;
  - отчёт [05](../reports/05_TZ_v1.8_format_vs_prepared.md) принят владельцем целиком (2026-11-06).

  Код манифеста к этому моменту не написан, поэтому замена затрагивает только документы и схемы.
- **Решение:**
  1. **Источник формата — ТЗ §19.4.**
     - [`container_manifest_v1.md`](../specifications/container_manifest_v1.md) — рабочая формализация.
     - [`manifest-1.0.draft.schema.json`](../../schemas/manifest-1.0.draft.schema.json) — **не нормативный** черновик.
     - Формат 1.0 объявляется опубликованным только при наличии трёх вещей (§19.6.4):
       - схема;
       - валидатор V1–V4;
       - положительные и отрицательные golden ZIP.
  2. **Носитель:**
     - `manifest.json`;
     - `content/<InputID>/…`;
     - `generated/…`;
     - `extensions/<ExtensionID>/…`.

     Отменены:
     - запись-маркер `am-asset`;
     - каталоги `derived/`, `previews/`, `scenes/`, `ext/`.

     **Правило писателя (не требование к читателю):** `manifest.json` — первая запись ZIP. Тогда «свой» контейнер распознаётся по локальному заголовку со смещением 0. Если JSON повреждён, но в первой записи найден FormatID, контейнер считается «своим, повреждённым», а не чужим ZIP (ТЗ 6.1.3).

     Для этого SHA-256 и размеры новых данных должны быть известны до записи. При импорте они считаются заранее для lookup (ADR-0014, ADR-0016); при записи хеш сверяется потоково. Если заранее их узнать нельзя, писатель кладёт `manifest.json` последним — контейнер остаётся корректным.
  3. **Формат и версии.**
     - `format.id = "urn:uuid:0d40b3a5-39ae-48e6-a8e8-da18b1b8c128"`.
     - `format.version = {major, minor}`.
     - `min_reader` отменён. Вместо него — матрица `recognize/read/validate/write/migrate` в [`versioning.md`](../specifications/versioning.md).
  4. **Идентификаторы (пересматривает ADR-0008 и ADR-0025 п. 10).**
     - **UUIDv4 в нижнем регистре** для всех ID, видимых в ZIP: AssetID, InputID, InputObjectID, SourceEntryID, SourceID, FileID, GroupID, PreviewID, OperationID, AttachmentID, ClaimID.
     - Короткие локальные ID (`i001`, `f00001`, `g001`) отменены.
     - `pending_ops.op_id` совпадает с `history.entries[].operation_id`, поэтому идемпотентность ADR-0015 сохраняется и тоже использует v4.
     - ID, которых нет в ZIP, остаются **UUIDv7**: LibraryID, задания, снимки, `rel_id` и т. п. Их упорядоченность по времени полезна в журналах; §19.4.2.5 этого не запрещает.
     - Удалённые FileID не используются повторно и записываются в `historical_files`.
  5. **Ревизия:**
     - +1 за успешную фиксацию, изменившую постоянные данные, включая миграцию схемы и компактизацию истории;
     - no-op, чистая перепаковка, кэш и переиндексация ревизию не меняют.

     Вопрос 47 ТЗ закрыт.
  6. **Из ADR-0005 сохраняется:**
     - Stored/Deflate и правило выбора метода;
     - ZIP64 по необходимости;
     - бит 11 (UTF-8 имена);
     - без шифрования;
     - без data descriptor;
     - имя в библиотеке `<AssetID>.zip`;
     - выгрузка под санитизированным названием.
  7. **Полная проверка перед фиксацией (дополняет ADR-0006, шаг 4; §19.4.7.4).**
     - Для всех зарегистрированных потоков (`files`, `extensions.*.attachments`) за один проход сверяются: размер, CRC и SHA-256.
     - Неизвестные (opaque) записи, перенесённые raw-копией, проверяются по CRC и размеру и **не объявляются** проверенными по SHA-256 (§19.5).
     - Время правки метаданных крупного ассета — показатель [плана измерений](../architecture/nfr_measurement_plan.md). Ослабить проверку можно только новой ADR после замера.
  8. **Пути (дополняет ADR-0012).**
     - Лимит 200 байт UTF-8 действует на **весь** `storage_path`, включая `content/<InputID>/`. По инвентаризации коллекции это даёт ~1,9 % переименований вместо ~0,5 %; исходные имена сохраняются в `inputs[].entries[]`.
     - Новое правило: два пути одного ZIP, совпадающие после NFC и Unicode simple case folding, считаются коллизией и разрешаются суффиксом `~<8hex>`. Это нужно для переносимости на NTFS и macOS. Исходная форма имени не нормализуется.
  9. **Метаданные (пересматривает ADR-0013).**
     - `metadata` есть у asset, group и file.
     - Корневой `field_definitions[]`:
       - FieldID в виде `user:<UUIDv4>` или `plugin:<plugin-id>:<field-key>`; пространство `core:` зарезервировано;
       - `schema_revision`.
     - Значения — в `custom_values[]` по FieldID; копия определения при значении отменена.
     - `userdata.sqlite: field_defs` остаётся библиотечным каталогом определений для GUI с ключом по FieldID.
  10. **Утверждения (пересматривает ADR-0028, пп. 1–2).**
      - Пара `status`/`origin` при каждом значении заменена на `metadata.claims[]`: UUID, `target`, `relation ∈ {supports_selected, alternative, rejected}`, `method`, `evidence`, `review`, `confidence` (decimal-строка).
      - Соответствие старой модели:

        | Было | Стало |
        |---|---|
        | `confirmed` | claim с подтверждённым `review` |
        | `suggested` | claim без `review` |
        | `computed` | `method ∈ {geometric_measurement, content_analysis}` |

      - **ADR-0028, пп. 3–5 действуют:** предложения последующего анализа хранятся в `index.sqlite: suggestions` и ревизию не меняют; приоритет пользователя; словарь тегов.
  11. **Независимая копия ассета:**
      - новый AssetID;
      - событие `asset_copied{source_asset_id, source_revision}` в `history`.

      Заменяет `derived_from` уровня ассета из ADR-0008.
  12. **Производные файлы:**
      - запись `files[]` с `origin_kind = "generated"`;
      - `derived_from[{file_id, sha256}]`;
      - `generation{tool, tool_version, params}`.

      `generation` — [ПРЕДЛОЖЕНИЕ] для формализации §19.5. Он заменяет `derived[].converter` и `*.render.json`.
  13. **Сцены** в формат 1.0 не входят. Это объект ядра для будущей `minor` версии (этап P2), а не расширение.
  14. **Строгость схемы:**
      - для известной версии ядро проверяется с `additionalProperties: false`;
      - `extensions.<id>` — свободное содержимое;
      - неизвестные ключи ядра от более новой `minor` читаются с сохранением; запись по умолчанию запрещена матрицей возможностей.
  15. **Ошибки (дополняет ADR-0032):**
      - `invalid` → `Errc::corrupt_data`;
      - `unsupported` → `Errc::unsupported`;
      - `incomplete` → новый `Errc::incomplete = 15` (код — после снятия паузы).

      Детальные диагностики валидатора выражаются через `message_id` вида `am.manifest.<code>`.
- **Последствия:**
  - переписаны спецификация манифеста и схема (черновик 1.0), обновлены `index.sql`, `userdata.sql`, `versioning.md`, `roadmap.md`;
  - старая `manifest.v1.schema.json` удалена;
  - **код (после снятия паузы, M1):** `Uuid::v4()`, `Errc::incomplete`, тестовые пути `content/<uuid>/`;
  - **открыто и блокирует публикацию 1.0** — перечень §19.5: ExtensionID и FieldID regex, полная схема `origin`/`inputs` и raw filenames, `claims` и привязка к стандартным полям, единицы и `constraints`, `attachments.dependencies`, компактные диапазоны и обязательные события истории, точные пути.

## ADR-0036. Уточнения формата 1.0 по решениям R-01…R-09 (частично пересматривает ADR-0008, 0028, 0035)
> **Статус:** действует. П. 2 (модель `review` — была открыта) и п. 6 (кандидатные шаблоны TypeID, форма `dependencies`, объём гарантии точных чисел) **уточнены ADR-0037**.
- **Контекст:**
  - [свод R-01…R-09](../tz/R01-R09_approved_handoff.md): 44 пункта, утверждённые владельцем 2026-11-06 после ADR-0035;
  - сверка с репозиторием — [отчёт 06](../reports/06_R01-R09_vs_prepared.md);
  - [решения владельца по шести вопросам отчёта](../tz/R01-R09_owner_decisions_2026-11-07.md) (2026-11-07).

  Как и в ADR-0035, код манифеста ещё не написан, поэтому меняются только документы, черновая схема, SQL-контракты и тесты схемы. Положения прежних ADR, не названные ниже, действуют.
- **Решение:**
  1. **Адресат утверждения (R-01…R-03; уточняет ADR-0035 п. 10).**
     - `claims[].target` — объект, а не JSON Pointer:
       - `{kind: "standard", field}` — стандартное поле `metadata`;
       - `{kind: "standard_item", field: "authors", item_id}` — конкретный автор;
       - `{kind: "custom", field_id}` — значение `custom_values[]` по FieldID;
       - `{kind: "self"}` — владелец `metadata` целиком.
     - Владелец задаётся расположением `claims` (asset, group, file или источник `origin.sources[]`).
     - `authors[].id` — необязательный UUIDv4; обязателен, если на автора ссылается claim (V3).
     - Устойчивые ID у элементов других массивов (`tags`, `categories`) не вводятся.
     - Полный реестр стандартных полей по scope и реестр `standard_item` — O-02; в черновой схеме — поля §9.1 спецификации.
  2. **Отношения (R-04, R-05).**
     - `supports_selected` не содержит `value`; выбранное значение существует в нормативном поле.
     - `alternative` и `rejected` содержат типизированное значение.
     - V3 проверяет разрешимость target, тип и единицу значения, наличие выбранного значения и ссылки на автора.
     - Таблица допустимых состояний `review` и сочетаний с `relation` и `self` не утверждена (O-01).
  3. **Отклонение предложений (R-06; уточняет ADR-0028 п. 3).**
     - Обычный Dismiss — постоянное локальное решение в `userdata.sqlite: suggestion_decisions` (**черновой контракт**). Оно попадает в резервную копию (ADR-0030) и переживает перестроение индекса.
     - `index.sqlite: suggestions.state = dismissed` — производный статус, не источник истины. Новая таблица не ссылается на rowid индекса.
     - По умолчанию отклоняется значение для конкретного адресата и конкретного основания (`scope = current_basis`); режим `asset_field_value` предусмотрен моделью, но необязателен для первого GUI.
     - Идентичность — CandidateKey (AssetID, адресат, значение) и BasisKey (основание), а не rowid и не версия анализатора. Алгоритмы ключей, канонизация значений и ограничения уникальности по ключам открыты (O-03, O-04) и в SQL не вводятся.
     - Переносимое отклонение — только явная операция Record rejection: claim `rejected`, новая ревизия, запись в истории.
     - Решения не удаляются при временном отсутствии ZIP и не наследуются независимой копией.
  4. **Независимая копия (R-07; заменяет ADR-0035 п. 11 и формулировку об `asset_copied` в статусе ADR-0008).**
     - Копирование файла ZIP сохраняет AssetID и ревизию; Create independent copy — новый AssetID.
     - Ревизия 1 копии — `operation = asset_created` с `details.creation_kind = "independent_copy"` и `details.source_asset = {asset_id, revision}`. Эта запись не компактизируется. Событие `asset_copied` из словаря операций исключено.
     - Новые UUIDv4 для FileID, GroupID, PreviewID, InputID, InputObjectID, SourceEntryID, SourceID, AttachmentID, ClaimID и OperationID. FieldID и ExtensionID сохраняются.
     - Все нормативные ссылки переназначаются по отображению `old→new`; результат проходит полный V1–V4.
     - Переносится текущее состояние; старая история не переносится. Если `historical_files`/`derived_from` нельзя корректно представить, операция отказывает (O-05, O-06).
     - Если безопасное переназначение неизвестных расширений не доказано — отказ; остаётся обычное копирование ZIP (O-07).
     - Байты полезных файлов не меняются; локальные данные `userdata.sqlite` не копируются.
  5. **Теги (R-08; отменяет решение по вопросу 24 о канонизации при записи).**
     - `metadata.tags[]` хранит ровно выбранное пользователем написание; синонимы при записи не подставляются. При вводе алиаса GUI может предложить исходное или каноническое написание; в ZIP пишется выбранное.
     - Нормализация (предварительно NFKC → case folding, не зависящий от локали → trim → схлопывание пробелов) — только для поискового ключа индекса и словаря. Точный алгоритм и версия Unicode — O-08.
     - Точный дубликат строки — ошибка (схема: `uniqueItems`); варианты регистра допустимы, совпадение поискового ключа — предупреждение V3. Нормативная валидность ZIP от словаря не зависит.
     - Словарь (`tag_dict`, `tag_aliases`, `tag_relations`) — в `userdata.sqlite`; его изменение не меняет ZIP и ревизию. Массовая замена тегов в ZIP — отдельная подтверждённая операция: охват заранее, транзакция по каждому ассету, новая ревизия только при изменении, проверка точных дублей.
  6. **Специализированные типы и расширения (R-09; уточняет ADR-0035 п. 14).**
     - 11 базовых типов неизменны. Дополнительно — TypeID `plugin:<PluginID>:<TypeKey>`, отдельный от FieldID. Неназванный тип (`vector3`) в 1.0 — ошибка. Точный regex — O-11; в черновой схеме — тот же шаблон, что у plugin-части FieldID.
     - Значение plugin-типа — JSON по контракту расширения. Без обработчика: просмотр, экспорт и сохранение **неизменённого** значения. Такой манифест ядро-валиден, но «семантика плагина не проверена» — это не `invalid`.
     - Отчёт проверки указывает отдельно V1/V2, V3, V4 и plugin-validation.
     - Оболочка `extensions.<id>` строгая (`schema_version`, `data`, `attachments`, `dependencies`); свободный JSON — только в `data`. Формулировку ADR-0035 п. 14 «`extensions.<id>` — свободное содержимое» следует читать так.
     - `format.version.minor` в схеме 1.0 — ровно 0; более новые minor обрабатываются матрицей возможностей, без очистки неизвестных данных.
     - Числа неизвестного JSON сохраняются точно (исходная лексема) или запись запрещена. Спайк **S7** обязателен до утверждения формата 1.0; до его положительного итога запись контейнеров с неизвестными числами, точность которых сериализатор не гарантирует, запрещена (O-13).
     - Зависимости значения различают `none`/`declared`/`unknown`; отсутствие сведений — `unknown`. Единый контракт с `attachments.dependencies` — O-12.
     - Без обработчика индексируются FieldID, TypeID, scope и факт наличия значения; внутреннюю семантику ядро не интерпретирует.
  7. **Уточнения контракта по решениям владельца 2026-11-07.**
     - `metadata.publisher` — необязательный объект `{name, url?}`: `name` — непустая строка, `url` — URL. Это новое уточнение контракта: ТЗ v1.8 структуру не задаёт.
     - `groups[].file_refs`: читатель допускает отсутствие, оно равно `[]`; писатель всегда пишет массив.
     - `license` не может быть пустым объектом; `links[].rel` обязателен (ТЗ §19.4.19.3).
  8. **Проверка черновой схемы** — тест CTest `schema_check` (S-01…S-17 и прежние отрицательные случаи). Режимы: по умолчанию отсутствие `jsonschema` — **провал** теста; в CI (`-DAM_REQUIRE_PYTHON_TESTS=ON`) отсутствие Python или `jsonschema` — ошибка конфигурации; SKIP — только при явном локальном `-DAM_ALLOW_PYTHON_SKIP=ON` (с CI-режимом несовместим).
- **Последствия:**
  - обновлены спецификация, черновая схема и пример, `userdata.sql`, `index.sql`, `versioning.md`, `roadmap.md` (спайк S7), `libraries.md` (nlohmann/json — условно выбрана до S7), матрицы, вопрос 24;

## ADR-0037. Уточнения формата 1.0 после e2472e9: журнал v0.11/v0.12 (108 принципов, 11 блоков; частично уточняет ADR-0035, 0036)
- **Контекст:**
  - [журнал решений v0.11](../tz/RC1_decisions_after_e2472e9_v0.11.md): 108 принципов в блоках O-01, O-02, O-11, O-12, O-13/S7 (только требования), O-14, O-15, O-16, O-18, X-01, X-02. Согласованы владельцем 2026-11-10;
  - независимая проверка — [отчёт 07](../reports/07_RC1_v0.11_vs_prepared.md), вопросы K-1…K-10;
  - [ответы на K-1…K-10](../tz/RC1_report07_response_K01-K10_DRAFT_2026-11-10.md): утверждены владельцем 2026-11-10 («Approve, apply»). Возражение владельца по K-6 принято, рекомендация исполнителя отозвана.

  Код ядра на паузе: меняются документы, черновая схема, `index.sql` и тесты. Полная формулировка каждого принципа — в журнале. Здесь — решение и то, что из него следует для проекта. Положения ADR-0035 и ADR-0036, не названные ниже, действуют.
- **Решение:**
  1. **Утверждения (O-01, O-02; уточняет ADR-0036 пп. 1–2 и таблицу ADR-0035 п. 10).**
     - `review` — необязательный объект `{at}`; поля `state` нет. `relation` и `review` описывают разное: отношение к выбранному значению и факт пользовательской проверки.
     - `supports_selected` — без `value`; `alternative` — `value` обязателен; `rejected` — `value` и `review` обязательны (это не локальный Dismiss).
     - `target.kind = self` и `standard_item` — только `supports_selected`.
     - Один набор стандартных полей (`title`, `description`, `authors`, `publisher`, `license`, `tags`, `categories`, `links`, `dates`) для asset, group и file; значения между уровнями **не наследуются**. `standard` адресует поле целиком (`license.spdx` и т. п. недопустимы). `standard_item` — только `authors[]`.
     - `dates = {published?, acquired?}` (`YYYY-MM-DD`); `acquired` — первоначальное получение объекта, а не добавление в библиотеку.
     - Отдельный реестр для `origin.sources[].claims`: `kind`, `name`, `url`, `published_at`, `retrieved_at`; допустимы `standard` и `self`.
     - Тип `value` у `alternative`/`rejected` = тип целевого поля. Утверждение о массиве целиком не доказывает каждый элемент.
     - Таблица ADR-0035 п. 10 читается так: «`confirmed` → claim с `review`».
  2. **Идентификаторы (O-11, K-7, K-8; заменяет кандидатные шаблоны ADR-0036 п. 6).**
     - `LABEL = [a-z0-9](?:[a-z0-9-]{0,61}[a-z0-9])?`; `PluginID = ExtensionID = LABEL ("." LABEL)+`, 3..96 байт.
     - `FieldKey = TypeKey = RelKey = [a-z][a-z0-9_]*(?:[.-][a-z0-9_]+)*`, 1..64 байта. Грамматика нормативна: `-` и `.` — только внутренние, `_` — в любой позиции, кроме первой.
     - `TypeID = plugin:<PluginID>:<TypeKey>`, plugin FieldID `= plugin:<PluginID>:<FieldKey>` — разные роли. `user:<UUIDv4>` и зарезервированный `core:` без изменений.
     - Сравнение точное, побайтовое. Версия в TypeID не кодируется; несовместимое изменение смысла — новый TypeKey. Отсутствие плагина не делает TypeID ошибкой. PluginID не подтверждает доверие; ID возможностей SDK — отдельная сущность.
  3. **Зависимости (O-12, K-9; уточняет ADR-0036 п. 6).**
     - Один `$defs.dependencies` `{state, refs}` для `extensions.<id>` (весь блок `data` + вложения) и для `custom_values[]` с plugin TypeID.
     - `state`: `none` — `refs` отсутствует или пуст; `declared` — непустой полный список; `unknown` — список может быть неполным; отсутствие поля = `unknown`.
     - Ссылка — объект по `kind`: `file{file_id, sha256?}`, `group{group_id}`, `field_value{owner_scope, owner_id, field_id}`; только внутри ассета; без структурных дублей.
     - Писатель сортирует `refs`: `file < group < field_value`, затем побайтово по ID (`file_id` / `group_id` / `(owner_scope, owner_id, field_id)`), затем по `sha256`. Читатель принимает любой порядок.
     - Удаление или замена зависимого объекта при `unknown` или непроверенном переназначении блокируется. `none`/`declared` не доказывают клонируемость (O-07 открыт). `derived_from` и `claims.evidence` остаются отдельными механизмами.
  4. **Точные числа неизвестного JSON — требования к S7 (O-13, K-4; уточняет ADR-0036 п. 6).**
     - Гарантия **общая**: исходная лексема каждого неизвестного числа и её место сохраняются везде, где формат допускает непрозрачный JSON. Минимум шесть мест: `extensions.*.data`; `custom_values[].value` с plugin TypeID; `files[].generation.params`; `claims[].value` при адресате с plugin TypeID; `field_definitions[].default`/`constraints` для plugin-типов; `history.entries[].details` и дополнительные ключи `changes[]`.
     - Побайтовая идентичность всего `manifest.json` не требуется.
     - Приёмка S7: полный цикл ZIP — чтение → правка постороннего поля → транзакционная запись → повторное открытие. Фикстуры из журнала; недопустимые числа (`01`, `+1`, `NaN`) отвергаются. Windows и Linux, замеры памяти и времени. Валидация не должна терять число раньше сериализации.
     - Fail-closed по R-09.8 действует без исключений. **O-13: требования утверждены, технический итог OPEN**; результат S7 оформляется отдельной ADR.
  5. **Описательные поля, производные файлы, время (O-14).**
     - `publisher` без изменений.
     - `license` — непустой объект; текстовые поля непусты, `url` — URI, `file_ref` разрешается V3. `spdx` — SPDX license expression (грамматику проверяет V3).
     - `links[].rel` — `^[a-z][a-z0-9_-]{0,63}$` или `plugin:<PluginID>:<RelKey>`. Открытый словарь известных значений: `source`, `homepage`, `documentation`, `download`, `license`, `author`, `publisher`, `mirror`, `related`, `preview`.
     - `files[].generation{tool, tool_version?, params?}` — нормативен: обязателен для `origin_kind = generated`, для остальных отсутствует. Грамматика `tool` — OPEN.
     - `extensions.<id>.schema_version` — обязательная непустая строка, не число и не SemVer.
     - `asset.modified_at` = timestamp последней записи истории; `created_at` = timestamp ревизии 1. При no-op, переиндексации, экспорте, backup время не меняется.
     - Хеш и размер файла меняются атомарно с байтами.
  6. **Происхождение и входные данные (X-01, K-2, K-5, K-6).**
     - `inputs[].completeness ∈ {complete, incomplete, unknown}` — **обязательно** у каждого Input.
     - `entries[].entry_kind ∈ {file, directory}` — **обязательно**. У каталога нет FileID; `included_renamed`/`excluded` для каталогов — OPEN.
     - Тома нумеруются с 0: индекс — позиция тома в наборе.
     - `name_raw`/`path_raw` — строгий RFC 4648 Base64; байты не синтезируются.
     - `container` (тип архива по сигнатуре, только для `archive`/`multivolume_archive`) и `name_encoding` (способ декодирования имён записей внутри объекта) **сохраняются** как необязательные поля с явной семантикой.
     - `asset.flags.incomplete` не существует. Индексный `assets.incomplete` вычисляется: есть Input с `completeness ∈ {incomplete, unknown}`. Исходы различаются: `unavailable` (недоступно), `failed` (доступно, ошибка чтения), `not_processed`.
  7. **Единицы и ограничения (X-02).**
     - Три слоя: `dimension` определения, рекомендуемый `unit` определения, `unit` значения. UCUM-коды для известных единиц; неизвестная единица сохраняется как есть и не конвертируется. Dimension не выводится из имени поля.
     - Для `integer`/`decimal` с физической dimension `unit` значения обязателен (V3). Преобразования — только совместимые и точные.
     - `constraints` — закрытая структура по типу: числа — `minimum`/`maximum {value, unit?}`; строки — `min_length`/`max_length` в code points; даты — `minimum`/`maximum`; `multi_enum` — `min_items`/`max_items`; для `boolean`/`url`/`file_ref`/`enum` — отсутствует; для plugin-типов — непрозрачный JSON плагина.
     - `default` — рекомендация, проверяется как значение.
     - **OPEN:** грамматика `dimension`, физический `default`, движок UCUM.
  8. **История (O-18).**
     - Ревизии `1..asset.revision` покрыты ровно один раз записями `entries[]` или диапазонами `compacted_ranges[]`. Ревизия 1 и последняя — всегда отдельные записи.
     - Не компактизируются: `asset_created`, `format_migrated`, `provenance_changed`, `history_compacted`, операции с неизвестной семантикой и записи с недоказанно сохранёнными историческими фактами.
     - Сводка диапазона — `{revision_count, operation_counts?}`, без выдуманных деталей. Компактизация — отдельная ревизия `history_compacted`; в P0 не выполняется.
     - `historical_files` не компактизируются. Неизвестные расширения и незавершённые операции — fail-closed.
     - **OPEN:** словарь `changes[].kind`, plugin-`operation`.
  9. **Непрозрачные записи ZIP и V4 (O-15, K-1, K-10; уточняет ADR-0035 п. 7).**
     - Классы записей: `registered` (`files[]`, `attachments[]`), `known_structural` — **только `manifest.json`** (маркер `am-asset` отменён ADR-0035 п. 2 и остаётся `opaque`), `opaque`. В новом 1.0 opaque-записи запрещены.
     - Неизвестные данные существующих контейнеров не удаляются; если сохранность не доказана — read-only.
     - Raw-copy — оптимизация, а не сертификат: CRC проверяется по распакованному потоку. Неизвестные extra fields слепо не переносятся. Правила безопасности ZIP действуют без исключений для opaque.
     - Отчёт V4 по потокам: `verified_sha256`, `verified_crc_size_only`, `unverifiable`, `unsupported`, `failed`.
     - Свод: `failed` → `Errc::corrupt_data`; `unsupported` → `Errc::unsupported`; `verified_crc_size_only`/`unverifiable` → `container_verification = partial`, не ошибка; `full` — все зарегистрированные потоки `verified_sha256`, структурные проверки пройдены, opaque нет. `manifest.json` проходит структурную проверку и проверку ZIP, самохеш не требуется.
     - **OPEN:** реестр extra fields, граница legacy/1.0.
  10. **Точный `uint64` в индексе (O-16, K-3).**
      - В `index.sqlite` размеры (`assets.zip_size`, `files.size`, `input_entries.size`, `input_objects.size`) и сумма `assets.content_bytes` — канонический десятичный `TEXT COLLATE BINARY` с `CHECK`.
      - `NULL` ≠ `'0'`. Порядок — `(length(size), size)`; индексы — по этому выражению. `CAST`/`SUM`/`TOTAL`/`double` запрещены.
      - `content_bytes` считается в C++ с контролем переполнения; при переполнении — `NULL` + диагностика `content_bytes_overflow`, без статуса `corrupt`.
      - Перестроение индекса не меняет ZIP.

  - обновлены спецификация, черновая схема и пример, `index.sql`, `import_pipeline.md`, `jobs_and_sessions.md`, `versioning.md`, `roadmap.md` (S7), `libraries.md`, матрицы;
  - тесты: расширен `schema_check`, добавлен `sql_check` (DDL `index.sql` в SQLite);
  - **не закрыты:** итог O-13/S7, O-17, O-03…O-10, поддетали X-02, O-18, O-15 и O-14 (`generation.tool`); матрица старых версий, валидатор V1–V4, golden ZIP. Формат 1.0 не опубликован; ТЗ не менялось;

    | A | nlohmann DOM | 2/11 (3 отказа разбора) | дроби и большие целые → `double`; переполнение стека на глубине 100 000 (Windows) |
    | B | nlohmann SAX + лексемы | 10/11 (3 отказа) | теряет знак целого `-0`; `1e400` отвергается до SAX |
    | C | RapidJSON `NumbersAsStrings` | 11/11 (3 отказа) | экспонента вне диапазона отвергается при разборе |
    | D1 | правка исходного текста по позициям токенов | **14/14** | — |
    | D2 | гибрид: известная часть в DOM, непрозрачные фрагменты + собственный писатель | **14/14** | — |
    | E | jsoncons `lossless_number` | 12/14 | теряет знак целого `-0` |

  - Валидаторы V2: **pboettch json-schema-validator ложно принимает** документ, запрещённый `unevaluatedProperties` (не поддерживает draft 2020-12, на котором написана черновая схема); jsoncons и Python `jsonschema` его отвергают.
  - Ресурсы на манифесте 64 МиБ: полный цикл D2 — 6,3 с (Windows) / 7,0 с (Linux, drvfs); пик стенда ~837 / ~775 МиБ определяют две копии документа, карты сверки и ZIP; разбор и сериализация одного D2 — ~325 МиБ при входе ~91 МиБ.
- **Решение:**
  1. **Механизм — гибрид D2.** Кодек манифеста (`processing`/`storage`, уровень — при проектировании M1):
     - читает `manifest.json` **собственным строгим токенизатором** (V1): грамматика RFC 8259, UTF-8 без BOM, дубли ключей отвергаются (SPEC §1), предел глубины проверяется **до** построения любого рекурсивного DOM;
     - находит корни непрозрачных поддеревьев во всех шести местах ADR-0037 п. 4 и хранит каждое как **исходный фрагмент текста**;
     - известную часть строит в `nlohmann::ordered_json`, где на месте каждого фрагмента стоит **заглушка типа `binary`** с номером фрагмента. В JSON нет типа binary, поэтому содержимое манифеста не может подделать заглушку; при сдвиге элементов массива заглушка переезжает вместе с владельцем;
     - правки — только в DOM известной части (доменная модель → DOM);
     - пишет **собственным писателем** обхода DOM: ключи и известные значения экранирует nlohmann, на месте заглушки выводит фрагмент только после повторного строгого разбора фрагмента как ровно одного полного JSON-значения. Текстовая подстановка по шаблону запрещена (принцип 8).
  2. **D1 не принимается** как механизм продукта. Он сохраняет числа так же надёжно, но каждая правка становится текстовым патчем по позициям: структурные правки, порядок `refs` (ADR-0037 п. 3) и миграции пришлось бы выражать заплатками к исходному тексту. D1 остаётся в стенде как контроль.
  3. **Числа известной части** не проходят через `double`: известные числовые поля по схеме — целые (ревизии, индексы томов) в пределах своего типа, размеры — строки uint64 (ADR-0037 п. 10), decimal — строки. Число известного поля, не представимое в своём типе без потерь, — ошибка V1/V2, а не округление.
  4. **V2 — jsoncons JSON Schema (draft 2020-12)** на теневом документе: известная часть как есть, каждое непрозрачное поддерево заменено пустым значением того же JSON-типа (`{}`, `[]`, `0`, `""`, литерал). Ограничения схемы на JSON-тип непрозрачного значения проверяются; содержимое непрозрачного значения — не предмет V2 ядра. jsoncons в продукте используется **только как валидатор**: данные он не хранит и не сериализует (кандидат E отвергнут).
  5. **pboettch json-schema-validator исключается** из зависимостей программы: на схеме 2020-12 он даёт ложное принятие. Python `jsonschema` остаётся инструментом тестов (`schema_check`).
  6. **Защита записи обязательна** независимо от механизма (принцип 7, R-09.8): перед атомарной заменой ZIP `AssetRepository` (ADR-0025) повторно разбирает результат и сверяет все непрозрачные значения, их типы и числовые лексемы с исходными **по ключам владельцев** — ExtensionID, FieldID, FileID/GroupID как область, ClaimID (`id`), OperationID (`operation_id`); внутри фрагмента — типизированный JSON-путь. Неоднозначный владелец (одинаковые ID) — отказ записи. Сверка по индексам массивов недопустима: она ложно срабатывает на законных структурных правках. Расхождение → запись не выполняется, ZIP не меняется, ограничение не выдаётся за повреждение.
  7. **Пределы стенда — не нормативы.** Глубина 1024, размер 128 МиБ, тайм-аут 60 с — гипотезы испытания; значения для продукта назначаются по O-17 и плану измерений (ТЗ §14.9.13).
- **Последствия:**
  - **O-13: технический итог принят** (механизм D2, V2 jsoncons, защита по ключам владельцев). По принципу 9 вопрос закрывается, когда кодек продукта с тестами пересериализации и транзакции ZIP войдёт в CI (T-005 и задача кодека M1). До этого запись контейнеров с непрозрачными числами остаётся заблокированной фактически: кодека ещё нет.
  - Формат 1.0 по-прежнему **не опубликован**: остаются валидатор V1–V4, golden ZIP, интеграционные тесты в CI.
  - **Зависимости (задача M1):** в `vcpkg.json` добавить `jsoncons` (BSL-1.0, допустима по ADR-0021), удалить `json-schema-validator`; `nlohmann-json` — ✅ для известной части. `libraries.md` обновлён.
  - **Для кодека M1** (из замечаний приёмки T-004): индекс владельцев и группы непрозрачных мест строить один раз на документ (в стенде — повторно для каждого листа); для `changes[]` без собственного ID ключ — OperationID + индекс изменения, правило сопоставления при правке существующих `changes[]` — OPEN для спецификации (вместе со словарём `changes[].kind`, ADR-0037 п. 8).
  - Не решается этим: O-17 (лимиты и политика ресурсов), O-07, O-14 (`schema_version`), V3/V4.

## ADR-0039. Кандидат нормативной схемы 1.0: поддетали X-01, X-02, O-14, O-15, O-18 и единица claim (уточняет ADR-0035, 0036, 0037)
- **Контекст:** формат 1.0 публикуется при нормативной схеме, валидаторе V1–V4 и golden ZIP (ADR-0035 п. 1). Валидатор готов (T-006, T-010, T-011, T-012), golden ZIP — T-013, точные числа — ADR-0038. Схему держали черновиком открытые поддетали ADR-0037 («Последствия») и пробел, найденный при T-011: у `claims[]` нет единицы значения. Отчёт [08](../reports/08_format_1.0_publication_decisions.md) разделил открытое на блокирующее (Ф-1…Ф-10) и не относящееся к формату (разд. 3). Владелец 2026-11-12 принял все рекомендации.
- **Решение:**
  1. **`dimension` (Ф-1).** Базовый ключ `^[a-z][a-z0-9_]{0,63}$` или `plugin:<PluginID>:<FieldKey>` (грамматики O-11). Реестр 16 ключей SPEC §8 нормативен для семантики преобразований; неизвестный корректный ключ сохраняется, преобразований для него нет (V3 — `unverifiable`). Добавление ключа в реестр — минорная версия.
  2. **Физический `default` (Ф-2).** У `integer`/`decimal` — строка типа или `{value, unit}` (закрытая структура, как у границ `constraints`). Для физической `dimension` (кроме `dimensionless`) — только `{value, unit}`; это проверяет V3.
  3. **Пересчёт единиц (Ф-3)** — не часть формата. Нормативна запись: непустая строка, известные единицы — точный регистрозависимый UCUM-код, исходная строка не исправляется. Движок и таблицы — решение реализации (`libraries.md`); пока его нет, разные единицы — `unverifiable`.
  4. **Единица claim (Ф-4).** В `claims[]` необязательное поле `unit`. Если адресат — `custom`-значение поля `integer`/`decimal` с физической `dimension` и в claim есть `value`, `unit` обязателен (то же правило, что у `custom_values`, X-02 п. 4). В остальных случаях `unit` в claim — ошибка V3.
  5. **`changes[].kind` (Ф-5).** Базовый словарь: `file_add`, `file_remove`, `file_replace{old_sha256, new_sha256}`, `file_move{old_path}`, `metadata_set`, `group_add`, `group_remove`, `group_change`, `preview_add`, `preview_remove`, `claim_add`, `claim_remove`, `claim_change`, `field_definition_change`, `extension_change`. Иные имена по грамматике `^[a-z][a-z0-9_]{0,63}$` и `plugin:<PluginID>:<Key>` сохраняются с неизвестной семантикой и делают запись некомпактируемой (O-18 п. 3). Расширение словаря — минорная версия.
  6. **`operation` и компактизация (Ф-6).** Плагинные операции — `plugin:<PluginID>:<Key>`, семантика для ядра неизвестна, запись защищена. Критерий «нет скрытых ссылок на OperationID» в 1.0: компактизация допустима только в ассете **без `extensions`** и без непрозрачных `details`/дополнительных ключей `changes[]` в компактизируемых записях. Точный критерий для ассетов с расширениями — минорная версия после контракта плагинов (S6, O-07).
  7. **Записи ZIP (Ф-7, O-15).** Единственная служебная запись корня — `manifest.json`. Писатель 1.0 пишет только extra field `0x0001` (ZIP64). Читатель принимает любые корректно оформленные extra fields, смысл берёт только из `0x0001`; прочие игнорируются при чтении и не переносятся в изменённые заголовки (raw-копия неизменённой записи сохраняет их как есть). `0x7075` (Unicode Path) для имени не используется: имя — из основного поля при обязательном бите 11. Legacy-форматов нет: 1.0 — первая версия; без нашего `format.id` — чужой ZIP; `major ≠ 1` — неподдерживаемая версия.
  8. **`generation.tool` (Ф-8).** `core:<FieldKey>` или `plugin:<PluginID>:<FieldKey>`; `tool_version` — свободная непустая строка. Префикс `core:` в остальных местах остаётся зарезервированным.
  9. **Каталоги в описи входа (Ф-9, X-01).** `excluded` у каталога распространяется на всё содержимое; потомки всё равно перечисляются своими записями `entries[]` (тоже `excluded`). `included_renamed` у каталога — переименован сам каталог (словарь `rename_reason` тот же); `storage_path` потомков использует новое имя, их `path` — исходное. Каталог `excluded` с потомком не `excluded` — ошибка V3.
  10. **[ПРЕДЛОЖЕНИЯ] SPEC утверждены (Ф-10):** каноническое время писателя с миллисекундами; `files[].type = {id, by}`, `id` — `^[a-z0-9]+(\.[a-z0-9_-]+)*$`, реестр значений не часть формата; `groups[].type` и `authors[].role` — открытые словари.
  11. **Вне формата 1.0 (разд. 3 отчёта 08):** O-03, O-04 (ключи и показ отклонённых предложений — индекс/GUI), O-05…O-07 (независимая копия: в P0 отказ), O-08, O-09 (поисковый ключ и показ тегов — индекс/GUI; правило V3 `tags_search_key` остаётся отложенным предупреждением), O-10 (адресация одного тега — будущая минорная версия), O-17 (формат не задаёт числовых лимитов, кроме 200 байт `storage_path`; превышение лимитов реализации — отчёт «не проверено / лимит», а не «контейнер неверен»). Матрица старых версий — одна строка 1.0.
- **Последствия:**
  - Схема `manifest-1.0.draft.schema.json` переведена в статус **кандидата** (п. 1, 2 — форма, 4, 5, 6, 8, 10); файл переименуется в `manifest-1.0.schema.json` и `$id` теряет суффикс `:draft` при публикации. `schema_check` — 149 случаев (24 новых `F*`). Тестовые значения `generation.tool` переведены на `core:` (пример, `schema_check`, фикстуры S7, юнит-тесты).
  - Правила V3 под пп. 2, 4, 5, 9 (и снятие `x02_physical_default_open`, `claim_value_unit_unexpressible`) — задача исполнителю; golden ZIP (T-013) строятся по кандидату.
  - **Публикация 1.0** — после правил V3, golden ZIP и зелёного CI Windows/Linux: переименование схемы, строка в `versioning.md`, запись в `CHANGELOG.md`.
  - Не решается этим: выбор движка UCUM (реализация), числовые лимиты (O-17, замеры P0.8), контракт плагинов (S6, O-07).
