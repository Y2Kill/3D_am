# Матрица режимов файловых систем (ADR-0031 п. 4)

**Версия:** 0.2 (2026-11-12). **Источник:** спайки S5/S5+ в части NTFS, выполненные в задаче [T-009](../tasks/T-009-commit-protocol.md), на встроенном диске. Остальные ФС и типы носителей не испытывались.

**v0.2:** NTFS разделена по типу тома: `full` — только встроенный диск (`DRIVE_FIXED`); съёмные носители и RAM-диски — предварительно `read_only_default` (замечание 3 приёмки T-010, исправление — T-011).

Документ задаёт значения `StorageCapabilities` (ADR-0031 п. 3) по типу ФС. Значения берутся **из этой таблицы**, а не из пробной операции create/rename при подключении библиотеки: пробная операция проверяет только право записи (ТЗ §14.5.12).

## 1. Что проверяется

Свойства проверяются раздельно (ADR-0031, «Последствия»; ТЗ §14.5.3):

| Свойство | Что означает | Чем подтверждается |
|---|---|---|
| Атомарность видимости | Любой читатель, открывший файл по имени, видит целиком либо старую, либо новую версию ZIP, без промежуточного состояния | Параллельный наблюдатель во время замен: каждое чтение проверяет CRC и SHA-256 всех записей и побайтно совпадает с одной из ожидаемых версий |
| Восстанавливаемость | После завершения процесса в любой точке протокола ADR-0006 `recover()` приводит ассет к старой или новой проверенной версии, журнал и `.am-tmp` пусты | kill-тесты: `TerminateProcess` без деструкторов в 10 точках, по 3 повтора |
| Долговечность | Подтверждённая фиксация переживает отключение питания или сбой контроллера и кэша | Только испытание отключением питания. Без него — не выше `assumed` |
| Снимки читателей (ADR-0025) | Уже открытый читатель дочитывает старую версию после замены | Открытый с `FILE_SHARE_DELETE` дескриптор во время замены |
| Блокировка ассета | Межпроцессная блокировка `.am/locks/<AssetID>.lock` исключает два писателя и снимается ОС при завершении процесса | Блокировка из другого процесса, затем его kill |

Значения `durability`: `verified` — проверено отключением питания; `assumed` — протокол использует сброс на диск (`FlushFileBuffers`, SQLite `synchronous=FULL`, `MOVEFILE_WRITE_THROUGH` или `fsync` каталога), но сбой питания не испытывался; `unknown` — не испытывалось ничего.

## 2. Режимы

| Режим | Смысл |
|---|---|
| `full` | Запись разрешена, протокол фиксации ADR-0006 применяется без ограничений |
| `write_with_limits` | Запись разрешена с документированными ограничениями: предел размера файла, режим поколений вместо замены при открытом читателе и т. п. |
| `read_only_default` | Библиотека по умолчанию открывается только для чтения (`LibraryMode::read_only`). Запись — только после того, как конфигурация отмечена проверенной |

## 3. Таблица

| ФС | Режим | `posix_rename` | `replace_file` | `locks_reliable` | `durability` | `max_file_size` | Статус испытаний |
|---|---|---|---|---|---|---|---|
| **NTFS, встроенный локальный диск** (`DRIVE_FIXED`) | `full` | да | да (не используется) | да | `assumed` | без ограничения | S5/S5+ (часть NTFS) — T-009, см. §4 |
| NTFS, съёмный носитель (`DRIVE_REMOVABLE`) или RAM-диск | `read_only_default` (предварительно) | — | — | — | `unknown` | без ограничения | не испытывались: извлечение носителя во время фиксации и кэш записи USB-накопителей — отдельные условия |
| ext4 | `read_only_default` (предварительно) | — | — | — | `unknown` | — | не испытывалась; ветка POSIX в `commit_zip` написана, но на Linux не собиралась |
| exFAT | `read_only_default` (предварительно) | — | — | — | `unknown` | — | не испытывалась |

| XFS, Btrfs | `read_only_default` (предварительно) | — | — | — | `unknown` | — | не испытывались |
| SMB, NFS | `read_only_default` | — | — | — | `unknown` | — | не испытывались; сетевые ФС по ADR-0031 п. 4 по умолчанию только для чтения, SQLite WAL на них не размещается |

**Предварительный режим** означает: до испытания ФС запись на неё не разрешается по умолчанию. Это консервативное значение, а не вывод о свойствах ФС. Каждая строка пересматривается по итогам своего испытания (S5/S5+). Первая на очереди — ext4, вместе с CI Linux (T-005).

«—» — значение не установлено; `StorageCapabilities` возвращает для него «неизвестно».

## 4. NTFS: результаты T-009

**Среда:** Windows 10 Pro, сборка 19045; NTFS, локальный том `D:\`; MSVC 14.44, Windows SDK 10.0.26100.0. Тестовые библиотеки — в `.cache/commit-tests/` на этом томе. Замер выполнен исполнителем и повторён управляющим при приёмке (логи `.cache/mgr_t009_*.log`).

**Замена.** Используется `SetFileInformationByHandle(FileRenameInfoEx)` с флагами `FILE_RENAME_FLAG_POSIX_SEMANTICS | FILE_RENAME_FLAG_REPLACE_IF_EXISTS` через тот же дескриптор, которым временный файл хешировался и проверялся. Совместный доступ у дескриптора — только чтение и удаление, поэтому от проверки до переименования в файл никто не может писать. Запасной `MoveFileExW(MOVEFILE_REPLACE_EXISTING | MOVEFILE_WRITE_THROUGH)` допускается только при ответе «не поддерживается» (`ERROR_INVALID_PARAMETER`, `ERROR_NOT_SUPPORTED`, `ERROR_INVALID_FUNCTION`); после него цель сверяется по SHA-256 всего файла. `ReplaceFileW` и резервные копии `.am-bak` не используются.

| Свойство | Итог | Данные |
|---|---|---|
| Атомарность видимости | **подтверждена экспериментально** | Наблюдатель во время трёх замен на разные версии: 577 наблюдений в прогоне CLI, 441 в офлайн-прогоне. Промежуточных, отсутствующих и повреждённых ZIP — 0 |
| Восстанавливаемость | **подтверждена** для завершения процесса | 10 точек × 3 повтора в каждом полном прогоне. До записи `verified` — откат, цель старая; после — завершение, цель новая (таблица исходов — в отчёте T-009). Подмена временного файла или цели после сбоя распознаётся по SHA-256 всего файла |
| Долговечность | **`assumed`** | `FlushFileBuffers` временного файла, SQLite WAL с `synchronous=FULL`. Отключение питания и сбои кэша контроллера не испытывались |
| Снимки читателей | **подтверждены** при условии `FILE_SHARE_DELETE` | Открытый с `FILE_SHARE_DELETE` дескриптор дочитывает все старые записи с верными CRC и SHA-256; новые открытия видят новую версию; то же после kill сразу после замены. Читатель **без** `FILE_SHARE_DELETE` блокирует замену: `am.commit.replace_failed`, старый файл и откат — без потерь |
| Блокировка ассета | **подтверждена** | `LockFileEx` из другого процесса даёт `am.commit.locked`; после kill того процесса блокировка снята ОС |

**Требование к читателям.** Любой код, открывающий действующие ZIP библиотеки, обязан открывать их с `FILE_SHARE_DELETE` (`asset_zip::file_source(path, true)`), иначе он блокирует фиксацию. Это входит в контракт `AssetRepository`/`AssetSnapshot`.

**Стоимость (замер без норматива, O-17).** Фиксация 1 ГиБ нулей с проверкой — около 31 с, пик рабочего набора около 15 МБ. Дополнительный проход SHA-256 всего файла измерен только на сжатом ZIP размером около 1 МБ и для больших несжимаемых файлов не показателен; замер на несжимаемых данных — в плане NFR (`docs/architecture/nfr_measurement_plan.md`).

**Резерв свободного места** `max(⌈5 %⌉, 256 МиБ)` от оценки размера остаётся гипотезой (O-17).

## 5. Открытые вопросы по ФС

- **NTFS:** испытание отключением питания для перевода `durability` в `verified`; поведение при открытом читателе без `FILE_SHARE_DELETE` из сторонних программ (антивирус, проводник, индексатор) — сейчас это отказ замены с последующим откатом, частота на практике не измерена.
- **ext4:** `rename` + `fsync` каталога, kill-тесты и отключение питания (Linux CLI, T-005).
- **exFAT, FAT32:** есть ли атомарная замена при открытом читателе; если нет — нужен ли режим поколений (ADR-0025, S5+); предел размера FAT32 проверяется до фиксации.
- **SMB, NFS:** семантика замены и блокировок, поведение при обрыве связи; до проверки конфигурации — только чтение.
