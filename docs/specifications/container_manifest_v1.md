# Контейнер ассета и манифест — формат 1.0 (рабочая формализация, не нормативная)

**Источник:** ТЗ v1.8 §19.4 (MF-01…MF-12) и утверждённые уточнения [R-01…R-09](../tz/R01-R09_approved_handoff.md). Также журнал решений [v0.11](../tz/RC1_decisions_after_e2472e9_v0.11.md) (108 принципов) с [ответами K-1…K-10](../tz/RC1_report07_response_K01-K10_DRAFT_2026-11-10.md). Решения — [ADR-0035, ADR-0036, ADR-0037](../decisions/ADR_log.md), отчёты [05](../reports/05_TZ_v1.8_format_vs_prepared.md), [06](../reports/06_R01-R09_vs_prepared.md), [07](../reports/07_RC1_v0.11_vs_prepared.md).

**Статус.**
- Документ формализует согласованные принципы §19.4 для реализации.
- Формат 1.0 **не опубликован**, пока нет трёх вещей (§19.6.4):
  - нормативной JSON Schema;
  - валидатора V1–V4;
  - положительных и отрицательных golden ZIP.
- Черновик схемы: [`schemas/manifest-1.0.draft.schema.json`](../../schemas/manifest-1.0.draft.schema.json). Пример: [`schemas/examples/manifest-1.0.example.json`](../../schemas/examples/manifest-1.0.example.json).

**Как читать документ.**
- Пункты со ссылкой «§19.x» согласованы владельцем.
- Пункты со ссылкой «R-n», «ADR-0036», «ADR-0037» или ID блока журнала (O-01, X-01, …) — утверждённые уточнения после ADR-0035. Пометка **O-n** — открытый вопрос свода R-01…R-09: применена только согласованная часть.
- Пункты с пометкой **[ПРЕДЛОЖЕНИЕ]** — наша детализация того, что §19.5 оставил для формализации. Они меняются без новой ADR, пока формат не опубликован.

Прежний черновик (маркер `am-asset`, короткие ID `i001`/`f00001`, `history[]` массивом) отменён ADR-0035. Его история — в git.

## 1. Носитель

```text
<AssetID>.zip
├── manifest.json                       # ровно один, в корне, UTF-8 JSON (§19.4.1.1)
├── content/<InputID>/<safe-path>       # исходные полезные файлы, байты неизменны
├── generated/<…>                       # постоянные производные файлы, зарегистрированы в files[]
└── extensions/<ExtensionID>/<…>        # служебные бинарные данные расширений, зарегистрированы в attachments[]
```

1. **`manifest.json`** — UTF-8 без BOM, без дублирующихся ключей, с ограничениями глубины и размера при разборе (§19.4.7.2, §19.4.17.8).
   - **Правило писателя:** `manifest.json` записывается **первой** записью ZIP (ADR-0035 п. 2). Хеши новых данных при этом известны заранее; если нет — манифест пишется последним, контейнер остаётся корректным.
   - Читатель на этот порядок не полагается.
2. **Распознавание «своего» ZIP (§19.4.14.2):**
   - корректный ZIP;
   - один корневой `manifest.json`;
   - `format.id` совпадает;
   - версия совместима или определённо не поддерживается.

   Если JSON повреждён, но в первой записи найден FormatID, результат — «свой, повреждённый» (`Errc::corrupt_data`), а не «чужой ZIP».
3. **Произвольных файлов в корне нет** (§19.4.14.7). **Классы записей** (O-15, ADR-0037 п. 9):
   - `registered` — поток описан в `files[]` или `extensions.*.attachments[]`;
   - `known_structural` — **только `manifest.json`** (маркер `am-asset` отменён ADR-0035 п. 2; встреченная запись `am-asset` — `opaque`);
   - `opaque` — запись, которую текущая версия не интерпретирует.

   В **новом** контейнере 1.0 opaque-записи запрещены: ни в `content/`, `generated/`, `extensions/`, ни в корне. Неизвестные безопасные записи **существующих** (старых или будущих) контейнеров не удаляются молча:
   - они переносятся raw-копией (ADR-0006); raw-copy — оптимизация, а не сертификат: CRC сверяется по **распакованному** потоку, согласованность локального заголовка и центрального каталога проверяется;
   - неизвестные extra fields и комментарии сохраняются, только если это доказуемо безопасно; вслепую в изменённые заголовки не переносятся;
   - если сохранить нельзя — контейнер только для чтения (§19.4.16.5); понижение версии и выбрасывание данных запрещены.

   Дубликаты и коллизии путей, traversal, шифрование, zip bomb и прочие нарушения безопасности не получают исключений из-за `opaque`. Реестр допустимых extra fields и граница legacy/1.0 — OPEN.
4. **Внешние упаковочные архивы** (ZIP/RAR/7z, из которых шёл импорт) целиком не вкладываются (§19.4.1.5).
   - Вложенный архив может быть полезным файлом — только по явному решению `preserve` в `inputs[].entries[]`.
5. **Записи ZIP:**
   - метод Stored или Deflate; Stored — для заведомо сжатых данных по правилу ADR-0005;
   - ZIP64 — по необходимости;
   - бит 11 (UTF-8 имена);
   - без шифрования (§19.4.17.7);
   - без data descriptor (ADR-0005).
6. **Пути** во всех пространствах (`content`, `generated`, `extensions`):
   - разделитель `/`;
   - нет absolute, `.`, `..`, пустых компонентов;
   - правила ADR-0012;
   - **не более 200 байт UTF-8 на весь путь**, включая `content/<InputID>/`;
   - коллизия = совпадение после NFC + Unicode simple case folding (ADR-0035 п. 8);
   - переименование — `~<8hex>`; исходное имя остаётся в `inputs[].entries[]`.

## 2. Корень манифеста (§19.4.19)

| Ключ | Тип | Обязателен | Раздел |
|---|---|---|---|
| `format` | object | **да** | §3 |
| `asset` | object | **да** | §4 |
| `origin` | object `{sources[]}` | нет | §5 |
| `inputs` | array | нет | §5 |
| `files` | array, может быть `[]` | **да** | §6 |
| `historical_files` | array | нет | §6 |
| `groups` | array | нет | §7 |
| `previews` | object `{primary_id?, items[]}` | нет | §7 |
| `field_definitions` | array | нет | §8 |
| `extensions` | object, ключ — ExtensionID | нет | §10 |
| `history` | object `{entries[], compacted_ranges?[]}` | **да** | §11 |

**Общие правила.**
- **Отсутствие необязательного поля вместо `null`** (§19.4.19.1). Фиктивные значения не создаются.
- **Порядок ключей** несущественен. Порядок массивов значим только там, где это сказано явно (§19.4.19.13).
- **Идентификаторы** (§19.4.8):
  - все ID объектов — UUIDv4 в каноническом нижнем регистре: `^[0-9a-f]{8}-[0-9a-f]{4}-4[0-9a-f]{3}-[89ab][0-9a-f]{3}-[0-9a-f]{12}$`;
  - ID не зависят от имени, пути, позиции и содержимого;
  - ID не используются повторно.
- **Числа** (§19.4.9):
  - размеры в байтах — строки `uint64` `^(0|[1-9][0-9]*)$`, не больше 18446744073709551615;
  - `revision` и `format.version.*` — JSON-целые до 2^53−1.
- **Время** — RFC 3339 в UTC с `Z`.
  - **[ПРЕДЛОЖЕНИЕ]** Каноническая форма писателя: `YYYY-MM-DDTHH:MM:SS.sssZ` (миллисекунды). Читатель принимает любую дробную часть.
- **Хеши** — SHA-256, 64 hex в нижнем регистре.
- **Строгость:**
  - для известной версии ключи ядра строгие (`additionalProperties: false`);
  - свободное (непрозрачное) содержимое допустимо только там, где это сказано явно: `extensions.<id>.data`, значения и `default`/`constraints` plugin-типов, `generation.params`, `history.entries[].details` и дополнительные ключи `changes[]`. В них действует гарантия точных чисел (§10, ADR-0037 п. 4);
  - неизвестные ключи ядра из более новой `minor` читаются с сохранением; запись запрещает матрица возможностей ([`versioning.md`](versioning.md)).

## 3. `format`

```json
"format": { "id": "urn:uuid:0d40b3a5-39ae-48e6-a8e8-da18b1b8c128", "version": { "major": 1, "minor": 0 } }
```

- `id` — постоянный FormatID (§19.4.14.1).
- `version` не зависит от версии приложения, AssetID и ревизии.
- `major` — несовместимые изменения; `minor` — совместимые. Право записи старым приложением `minor` **не гарантирует** (§19.4.18.1).

## 4. `asset`

| Поле | Тип | Обяз. | Правило |
|---|---|---|---|
| `id` | UUIDv4 | да | Не меняется при переносе, переименовании, экспорте, правке, миграции. Независимая копия получает новый ID (§19.4.2.2) |
| `revision` | integer ≥ 1 | да | +1 за успешную фиксацию с изменением постоянных данных, включая миграцию и компактизацию. No-op, перепаковка, кэш, переиндексация — без изменения (§19.4.2.3, 6) |
| `created_at` | RFC 3339 | да | Создание логического ассета, а не текущего ZIP. Равно `timestamp` записи ревизии 1 (O-14). Перепаковка не меняет |
| `modified_at` | RFC 3339 | да | Равно `timestamp` последней записи `history` (O-14): обновляется при каждой фиксации новой ревизии. No-op, переиндексация, экспорт, перепаковка, backup, сбой и откат — без изменения. Авторитетный порядок изменений — ревизия, а не время |
| `metadata` | object | нет | §9 |

- `LibraryID` в ZIP не входит (§19.4.2.5).
- Совпадение ID и ревизии не доказывает идентичность содержимого (§19.4.2.4).

## 5. `origin` и `inputs` (§19.4.3)

**`origin.sources[]`** — источники распространения. Авторство из них не выводится.

| Поле | Обяз. | Описание |
|---|---|---|
| `id` | да | SourceID, UUIDv4 |
| `kind` | да | Расширяемая строка (X-01): `website`, `telegram_channel`, `marketplace`, `person`, `local_collection`, `unknown` |
| `name`, `url`, `published_at`, `retrieved_at` | нет | Описание источника; `url` — абсолютный URI, без сетевых проверок |
| `claims` | нет | Как установлен источник (§9.3), например `directory_inference`. Отдельный реестр адресатов (O-02 п. 7): `standard` по полям `kind`, `name`, `url`, `published_at`, `retrieved_at` и `self`; `custom` и `standard_item` запрещены |

Источник распространения не означает автора (X-01 п. 1).

**`inputs[]`** — входные комплекты. Каждый комплект — один акт импорта или добавления.

| Поле | Обяз. | Описание |
|---|---|---|
| `id` | да | InputID, UUIDv4; имя каталога `content/<InputID>/` |
| `source_refs` | нет | SourceID, с которыми связан комплект |
| `imported_at` | да | Время акта |
| `mode` | да | `strict` (по умолчанию) или `partial` — только с явного разрешения (§19.4.3.6) |
| `completeness` | да | Фактическая полнота акта (X-01 п. 2, ADR-0037 п. 6): `complete`, `incomplete`, `unknown`. Не путать с `mode`. Нормативного `asset.flags.incomplete` нет |
| `objects[]` | да | Исходные технические объекты |
| `entries[]` | да | Все обнаруженные записи и их судьба |

**`inputs[].objects[]`** (X-01):

| Поле | Описание |
|---|---|
| `id` | InputObjectID |
| `kind` | `file`, `directory`, `archive`, `multivolume_archive` |
| `name` | Исходное имя (§5.1 ниже) |
| `relative_path` | Путь относительно корня, выбранного при импорте. Абсолютные локальные пути **не пишутся** (§19.4.3.7) |
| `size_bytes`, `sha256` | Для файлов и архивов |
| `container` | Необязательно, только для `archive`/`multivolume_archive`: тип контейнера, **установленный по сигнатуре** (`zip`, `rar4`, `rar5`, `7z`…; ADR-0011). Отсутствие — тип не установлен. Это не связь вложенности (ADR-0037 п. 6, K-6) |
| `volumes[]` | Для многотомных: `{index, name, size_bytes?, sha256?, missing?}` — все известные тома, включая отсутствующие (`missing: true`). `index` — уникальный, **с 0**, позиция тома в наборе (а не номер из имени). Размер и SHA — только при достоверном знании |
| `parent_object_id`, `parent_entry_id` | Для вложенных архивов |
| `nested_action` | `extract`, `preserve` или `exclude` |
| `name_encoding` | Необязательно: общий способ декодирования **имён записей внутри объекта**, например `utf-8(bit11)`, `cp866(heuristic)` (ADR-0012). Не заменяет `path_raw` отдельной записи и `name_raw.encoding_guess` имени самого объекта; если способ неизвестен, поле не пишется (K-6) |

V3 для вложенности: родитель существует в том же Input, пара `parent_object_id`/`parent_entry_id` согласована, циклов нет. `preserve` сохраняет вложенный архив полезным файлом только по явной политике; `exclude` не создаёт FileID.

**`inputs[].entries[]`** (X-01) — все **обнаруженные** записи; ненаблюдавшиеся из-за прерывания не создаются. SourceEntryID не зависит от пути, одинаковые пути у разных записей допустимы:

| Поле | Описание |
|---|---|
| `id` | SourceEntryID |
| `object_id` | InputObjectID, из которого запись |
| `entry_kind` | **Обязательно** (ADR-0037 п. 6): `file` или `directory`. У каталога нет FileID; `included` для каталога означает сохранение структуры. Смысл `included_renamed`/`excluded` для каталогов — OPEN |
| `path` | Исходный логический путь внутри объекта, `/` как разделитель (§5.1). Не равен `files[].storage_path`; опасные пути хранятся для аудита, но не используются для извлечения |
| `size_bytes`, `crc32`, `modified_at_raw` | Как в источнике. Время без пояса хранится как есть, без выдуманного UTC (§19.4.11.1) |
| `result` | `included`, `included_renamed`, `excluded`, `unavailable` (запись или том недоступны), `failed` (доступна, но чтение или декодирование завершилось ошибкой), `not_processed` (операция не выполнялась) |
| `file_id` | Для `included*` у `entry_kind = file` — FileID, получивший содержимое. **Исторический:** не переписывается при замене или удалении файла (§19.4.13.2); V3 разрешает его через `files ∪ historical_files` |
| `rename_reason` | Для `included_renamed`: `path_too_long`, `invalid_chars`, `encoding`, `collision`, `reserved_name`. Компоненты `..` и префикс диска (`C:`) в исходном пути дают `invalid_chars`: путь обезвреживается, исходный сохраняется в `path` (решение управляющего 2026-11-10, T-001) |
| `exclusion` | Для `excluded`: `{rule, rules_version, by: auto\|user\|profile}` |
| `problem` | Для `unavailable`/`failed`: `{code, message_id}` (ADR-0032) |

### 5.1. Представление исходных имён (X-01 п. 9–10)

- Имя или путь, корректно декодированный в Unicode, — строка без нормализации.
- Если исходные байты не декодировались однозначно, рядом пишется `name_raw`/`path_raw: {encoding_guess?, base64}` — строгий RFC 4648 Base64 без переводов строк. Это прежний `name_raw_b64` из ADR-0012. Если исходных байтов нет, они **не синтезируются** из предполагаемого текста. Лимит размера — O-17.
- `modified_at_raw` — исходное время как есть, в том числе без часового пояса; UTC не выдумывается. `imported_at`/`retrieved_at` — отдельные известные UTC-времена.
- V3: `source_refs` → `origin.sources`; `entries.object_id` → объект того же Input; `claims.evidence` → SourceID/InputObjectID/SourceEntryID; FileID — через `files ∪ historical_files`. История происхождения не переписывается задним числом.

## 6. `files` и `historical_files` (§19.4.4, §19.4.13)

**`files[]`** — **единственный** реестр текущих полезных файлов.

| Поле | Обяз. | Правило |
|---|---|---|
| `id` | да | FileID, UUIDv4. Сохраняется при перемещении и явной замене содержимого. Одинаковые байты → два разных FileID |
| `storage_path` | да | Уникальный безопасный путь в `content/` или `generated/` |
| `size_bytes` | да | Точный размер несжатого потока, строка `uint64`, включая `"0"` |
| `sha256` | да | SHA-256 несжатых байтов |
| `origin_kind` | да | `imported`, `user_added`, `generated` — способ появления, не тип файла |
| `type` | нет | [ПРЕДЛОЖЕНИЕ] `{id: "mesh.stl.binary", by: "signature"\|"extension"\|"user"}` |
| `derived_from` | нет | `[{file_id, sha256}]` — версии источников. Ссылка может указывать на удалённый FileID |
| `generation` | для `generated` — **да**; для `imported`/`user_added` — **нет поля** | `{tool, tool_version?, params?}` (O-14 п. 5–6): `tool` — непустой стабильный ID обработчика (грамматика — OPEN), `params` — объект JSON, не код. Фиксирует известные параметры, но не доказывает побитовую воспроизводимость. Числа в `params` — под гарантией §10. `derived_from` остаётся отдельным механизмом; пустой `derived_from` допустим (§19.4.5.5) |
| `metadata` | нет | §9 |

- Состояние зависимости производного файла (`current`, `stale`, `unverifiable`, `source_missing`) **вычисляется** и в ZIP не хранится (§19.4.13.5).
- **Удаление файла** снимает запись из `files[]` и добавляет её в `historical_files[]` (§19.4.19.6). Поля записи:
  - обязательные: `id`, `removed_at_revision`;
  - если известны: `last_known_sha256`, `last_known_size_bytes`, `last_known_storage_path`.
- ID из `historical_files` никогда не совпадает с ID текущего файла.
- Повторное добавление тех же байтов после удаления даёт **новый** FileID (§19.4.13.6).
- Хеш и размер меняются в `files[]` атомарно с байтами (O-14 п. 9); при неизменных байтах не пересчитываются. Старые SHA в `derived_from` не переписываются — так вычисляется `stale`.
- `historical_files` не компактизируются вместе с историей (O-18 п. 8).

## 7. `groups` и `previews` (§19.4.5)

**`groups[]`:**
- поля: `id` (GroupID), `name`, `type`, `parent_id?`, `file_refs[]`, `metadata?`;
- `file_refs` (ADR-0036 п. 7): читатель допускает отсутствие поля, оно равно `[]`; **писатель всегда пишет массив**, в том числе пустой;
- `type` — расширяемая строка; [ПРЕДЛОЖЕНИЕ] начальные значения: `variant`, `scale`, `part_set`, `version`, `supports`, `custom`;
- у группы не больше одного родителя, циклов нет, корневая группа — без `parent_id`;
- `file_refs` — только непосредственное членство, порядок не значим;
- один файл может состоять в нескольких группах.

**`previews`:**
- `{primary_id?, items[{id, file_id, group_refs?[]}]}`;
- `file_id` — текущий FileID;
- `primary_id` обязан существовать в `items`;
- предпросмотра может не быть;
- оригинальные изображения остаются в `content/`, сгенерированные — `files[]` с `origin_kind=generated` в `generated/`;
- миниатюры каталога хранятся вне ZIP.

Сцены в формат 1.0 не входят (ADR-0035 п. 13).

## 8. `field_definitions` (§19.4.10, §19.4.11)

| Поле | Обяз. | Правило |
|---|---|---|
| `id` | да | FieldID: `user:<UUIDv4>` или `plugin:<PluginID>:<FieldKey>` (O-11); `core:` зарезервировано |
| `schema_revision` | да | integer ≥ 1. Растёт при изменении определения |
| `name` | да | Отображаемое имя; не определяет идентичность |
| `type` | да | Один из 11 базовых типов: `string`, `text`, `integer`, `decimal`, `boolean`, `date`, `datetime`, `enum`, `multi_enum`, `url`, `file_ref`; **или** TypeID плагина `plugin:<PluginID>:<TypeKey>` (R-09.2). TypeID ≠ FieldID. Тип без пространства имён (`vector3`) в 1.0 — ошибка структуры. Стабильный TypeID сохраняет смысл; несовместимое изменение — новый TypeKey и явная миграция; версия в TypeID не кодируется (O-11) |
| `scopes` | да | Подмножество `asset`, `group`, `file` |
| `description`, `dimension`, `unit`, `constraints`, `options[{id, label, deprecated?}]`, `default` | нет | X-02 — см. ниже; `options[].id` — стабильный уникальный OptionID |

**Грамматики идентификаторов (O-11, K-7, K-8; ASCII, сравнение побайтовое):**

```text
LABEL       = [a-z0-9](?:[a-z0-9-]{0,61}[a-z0-9])?
PluginID    = LABEL ("." LABEL)+          ; 3..96 байт; ExtensionID = PluginID
FieldKey    = [a-z][a-z0-9_]*(?:[.-][a-z0-9_]+)*   ; 1..64 байта
TypeKey     = RelKey = FieldKey             ; синтаксис общий, роли разные
TypeID      = "plugin:" PluginID ":" TypeKey
FieldID     = "user:" UUIDv4 | "plugin:" PluginID ":" FieldKey
```

- `-` и `.` — только внутренние разделители; `_` — в любой позиции, кроме первой (`a_`, `a__b` допустимы).
- Нормализации Unicode и регистра нет. Новые резервные префиксы PluginID не вводятся. PluginID не подтверждает доверие; ID возможностей SDK (`metadata.extract`) — отдельная сущность.
- Длина `storage_path` (200 байт) проверяется отдельно: длинный ExtensionID оставляет под путь вложения меньше места.

**Единицы и ограничения (X-02):**
- три слоя: `dimension` — физический смысл поля; `unit` определения — рекомендуемая единица для UI; `unit` значения (§9.2) — единица хранимого значения. Настройки UI не переписывают ZIP;
- `dimension` не выводится из имени поля. Базовые ключи: `dimensionless`, `length`, `area`, `volume`, `mass`, `time`, `temperature`, `temperature_interval`, `speed`, `acceleration`, `force`, `pressure`, `energy`, `power`, `frequency`, `angle`; неизвестный корректный ключ сохраняется. Грамматика и полнота реестра — **OPEN**;
- `constraints` — закрытая структура по типу:
  - `integer`/`decimal`: `minimum?`, `maximum?` = `{value, unit?}` (включительно; `value` — строка типа поля). Для физической величины `unit` границы обязателен (V3); рекомендуемая `unit` определения неявной не считается;
  - `string`/`text`: `min_length?`, `max_length?` — неотрицательные целые, считаются Unicode code points без нормализации;
  - `date`/`datetime`: `minimum?`, `maximum?` в формате типа;
  - `multi_enum`: `min_items?`, `max_items?` — по уникальным OptionID;
  - `boolean`, `url`, `file_ref`, `enum`: `constraints` нет;
  - plugin TypeID: непрозрачный JSON плагина (R-09, §10), ядром не проверяется;
- regex, скрипты и бизнес-правила в ядро 1.0 не входят;
- `default` — рекомендация, не значение; проходит те же проверки типа, вариантов и ограничений. Форма `default` для физической величины — **OPEN**;
- изменение типа, dimension, границ или options повышает `schema_revision`, существующие значения проверяются;
- `deprecated` не делает уже использованный OptionID невалидным; `multi_enum` сравнивается как множество.

**Представление значений по типам (§19.4.11):**

| Тип | Значение |
|---|---|
| `integer` | Строка int64 |
| `decimal` | Строка без экспоненты |
| `date` | `YYYY-MM-DD` |
| `datetime` | RFC 3339 с `Z` |
| `enum` | OptionID |
| `multi_enum` | Массив уникальных OptionID |
| `file_ref` | Текущий FileID |
| plugin TypeID | Любое JSON-значение по контракту расширения (R-09.3). Ядро его не интерпретирует и не приводит к базовому типу |

- Отсутствие значения, `""`, `"0"`, `false` и `[]` — **разные** состояния.
- `default` не превращается в подтверждённое значение.

**Значения plugin-типов без обработчика (R-09.4, R-09.5):**
- манифест остаётся валидным для ядра; результат проверки — «семантика плагина не проверена», а не `invalid`;
- разрешены просмотр, экспорт сырого JSON и сохранение **неизменённого** значения; универсальный редактор не меняет его структуру;
- изменения соседних данных допускаются с учётом зависимостей значения (§10);
- числа сохраняются точно (§10, R-09.8).

## 9. `metadata` (asset / group / file; §19.4.6, §19.4.19.3)

### 9.1. Стандартные поля

Все поля необязательны:
- `title`, `description` — строки;
- Набор стандартных полей **один** для `asset`, `groups[]` и `files[]` (O-02 п. 1). Значения между уровнями **не наследуются**: отсутствие лицензии или автора у файла не превращается в значение ассета.
- `authors[]` — `{id?, name, role?}`; [ПРЕДЛОЖЕНИЕ] `role`: `author`, `sculptor`, `designer`, `photographer`, `other`. `id` — UUIDv4 (R-03): необязателен, но **обязателен**, если на автора ссылается claim; перестановка и правка имени ссылку не меняют;
- `publisher` — `{name, url?}` (ADR-0036 п. 7): `name` — непустая строка, `url` — URL. Новое уточнение контракта: ТЗ v1.8 структуру не задаёт;
- `license` — `{name?, spdx?, url?, notice?, file_ref?}`, хотя бы одно поле, текстовые поля непусты (O-14 п. 2–3). `url` — абсолютный URI; `file_ref` — текущий FileID (V3). `spdx` — SPDX license expression, включая `LicenseRef-…` (грамматику проверяет V3); `name`/`notice` в SPDX автоматически не превращаются. Отсутствие лицензии **не** означает свободного использования, наличие поля не удостоверяет правовую силу;
- `tags[]` — строки ровно в выбранном пользователем написании (R-08.1). Сериализатор не подставляет синонимы и не меняет регистр, Unicode, пробелы, пунктуацию. Точный дубликат строки — ошибка; варианты вроде `PETG`/`petg` допустимы (совпадение поискового ключа — предупреждение V3). Нормализация — только в индексе и словаре библиотеки (ADR-0036 п. 5);
- `categories[]` — `{path: ["Figures", "Anime"]}`;
- `links[]` — `{url, rel}`, оба обязательны (§19.4.19.3). `rel` — точный регистрозависимый идентификатор: `^[a-z][a-z0-9_-]{0,63}$` или `plugin:<PluginID>:<RelKey>` (O-14 п. 4). Открытый словарь известных значений: `source`, `homepage`, `documentation`, `download`, `license`, `author`, `publisher`, `mirror`, `related`, `preview`; неизвестные корректные значения сохраняются;
- `dates` — `{published?, acquired?}`, строго `YYYY-MM-DD` (O-02 п. 3); `acquired` — первоначальное получение описываемого объекта, а не добавление ZIP в библиотеку. Календарную допустимость проверяет V3.

### 9.2. `custom_values[]`

- Запись: `{field_id, value, unit?, dependencies?}`; `field_id` должен быть разрешим в `field_definitions`.
- У `integer`/`decimal` с физической `dimension` (кроме безразмерной) `unit` значения обязателен, даже если единица указана в определении (§19.4.11.2, X-02 п. 4).
- Единицы — точные регистрозависимые UCUM-коды (`mm`, `cm`, `g`, `kg`, `Cel`). Неизвестная единица — непустая исходная строка: сохраняется, не конвертируется, помечается `unverifiable`. Исправлений написания нет (X-02 п. 2). Движок UCUM и таблицы преобразований — **OPEN**.
- Сравнение и перевод — только при известной совместимой размерности, точной decimal/rational арифметикой; абсолютная температура и температурная разность различаются. Исходная `unit` без действия пользователя не меняется (X-02 п. 5).
- `dependencies` — только у значений plugin-типов (§10, O-12).

### 9.3. `claims[]` (§19.4.12, §19.4.19.10)

| Поле | Обяз. | Правило |
|---|---|---|
| `id` | да | ClaimID, UUIDv4 |
| `target` | да | Типизированный адресат (R-01, R-02), владелец — `metadata`, где лежит claim:<br>`{kind: "standard", field}` — стандартное поле §9.1;<br>`{kind: "standard_item", field: "authors", item_id}` — конкретный автор (R-03);<br>`{kind: "custom", field_id}` — значение `custom_values[]`;<br>`{kind: "self"}` — владелец целиком (для источника `origin.sources[]` — сам источник).<br>Строки JSON Pointer (`/title`, `/authors/0`) **не используются**. `standard` адресует поле **целиком** (`license.spdx`, `dates.published` недопустимы); `standard_item` — только `authors[]` (O-02). Для `origin.sources[].claims` — отдельный реестр (§5) |
| `relation` | да | `supports_selected` — подтверждает текущее значение и **не** дублирует его; `alternative` — значение `value` предложено, но не выбрано; `rejected` — отклонено пользователем |
| `value` | для `alternative`/`rejected` | Значение в представлении типа **конкретного** поля: `publisher` — объект, `authors` — массив авторов, `custom` — тип по определению (§8, O-02 п. 8); при `supports_selected` отсутствует (R-04). Для plugin-типов — непрозрачный JSON под гарантией §10 |
| `method` | да | `user_input`, `file_metadata`, `document_extraction`, `filename_inference`, `directory_inference`, `content_analysis`, `geometric_measurement`, `external_metadata`, `ai_inference`, `imported_metadata`, `unknown` (расширяемо) |
| `evidence[]` | нет | Ссылки `{file_id?, sha256?, source_entry_id?, input_object_id?, source_id?, note?}` — без копирования объектов |
| `handler` | нет | `{id, version}` анализатора |
| `confidence` | нет | Decimal-строка `0..1`; не универсальная вероятность |
| `review` | для `rejected` — **да**, иначе нет | `{at}` — факт и время явной пользовательской проверки (O-01). Поля `state` нет; без имени, email, ОС пользователя (§19.4.12.6) |
| `created_at` | да | Время утверждения |

**Допустимые сочетания (O-01, O-02):**

| `relation` | `value` | `review` | `target.kind` |
|---|---|---|---|
| `supports_selected` | запрещено; выбранное значение или адресуемый объект существует (V3) | необязателен | `standard`, `standard_item`, `custom`, `self` |
| `alternative` | обязательно, тип поля | необязателен | `standard`, `custom` |
| `rejected` | обязательно, тип поля | **обязателен** | `standard`, `custom` |

- `self` и `standard_item` в 1.0 — только `supports_selected`. Альтернативу всему массиву авторов выражает `standard`/`authors` со значением-массивом.
- Утверждение о массиве (`authors`, `tags`, `links`) целиком не доказывает происхождение каждого элемента.
- `claims` — не второе хранилище выбранного значения: единственный его источник — стандартное поле или `custom_values[]` (R-04).
- Предложения **последующего** анализа в ZIP не пишутся. Они хранятся в `index.sqlite: suggestions` и ревизию не меняют (ADR-0028 п. 3).
- **Dismiss** (R-06) — локальное решение в `userdata.sqlite: suggestion_decisions`; ZIP и ревизия не меняются.
- **Record rejection** — явная операция: claim `relation = rejected` с отклонённым значением, новая ревизия, `changes[].kind = claim_add`.
- **Accept** записывает выбранное значение и применимые подтверждения одной фиксацией.
- В ZIP попадают:
  - подтверждения;
  - предположения, сделанные при создании ассета (provenance);
  - явно сохранённые альтернативы.

## 10. `extensions` (§19.4.14, §19.4.16)

```json
"extensions": {
  "org.example.slicer": {
    "schema_version": "2",
    "data": { "…": "любой JSON, сохраняется без потерь, включая числа > 2^53" },
    "attachments": [ { "id": "<UUIDv4>", "path": "extensions/org.example.slicer/cache.bin",
                       "size_bytes": "1048576", "sha256": "…" } ],
    "dependencies": { "state": "declared", "refs": [ { "kind": "file", "file_id": "<UUIDv4>", "sha256": "…" } ] }
  }
}
```

- **ExtensionID** = PluginID (O-11, §8): обратная доменная нотация, 3..96 байт. Не доказывает авторство и не даёт доверия. TypeID без секции `extensions[PluginID]` допустим.
- **`schema_version`** — **обязательная** непустая строка (O-14 п. 7): версия контракта данных расширения, а не плагина и не ZIP. `"1"`, `"2"`, `"2.1"`; в число не превращается, SemVer не предполагается. Сравнение и миграцию определяет обработчик; неизвестная версия сохраняется с запретом небезопасной записи.
- **`attachments[]`:**
  - у каждого вложения один владелец;
  - путь только внутри `extensions/<свой ExtensionID>/`;
  - вложения участвуют в полной проверке.
- **Оболочка строгая** (R-09.9): допустимы только `schema_version`, `data`, `attachments`, `dependencies`. Свободный JSON плагина — только в `data`. Неизвестный ключ оболочки в контейнере 1.0 — ошибка структуры; данные более новой minor не удаляются ради схемы 1.0, а обрабатываются матрицей возможностей (R-09.10).
- **`dependencies`** (O-12, ADR-0037 п. 3) — одна форма `{state, refs?}` для `extensions.<id>` (весь блок `data` + `attachments`) и для `custom_values[]` с plugin TypeID:
  - `none` — подтверждённое отсутствие, `refs` нет или пуст; `declared` — полный проверяемый непустой список; `unknown` — полнота не установлена, `refs` может содержать неполный список; отсутствие объекта = `unknown` (§19.4.16.3);
  - ссылка — объект по `kind`: `file{file_id, sha256?}`, `group{group_id}`, `field_value{owner_scope, owner_id, field_id}`; только объекты внутри ассета, без внешних путей; без структурных дублей;
  - писатель сортирует `refs`: `file < group < field_value`, затем побайтово по ID (`file_id` / `group_id` / `(owner_scope, owner_id, field_id)`), затем по `sha256`; читатель принимает любой порядок (K-9);
  - V2 — форма и сочетания; V3 — разрешимость ID и хешей (исторический FileID → `stale`/`source_missing`, а не текущий файл); V4 — физические файлы;
  - удаление, замена или переназначение зависимого объекта при `unknown` или непроверенном переназначении блокируется; неизвестные данные не выбрасываются. `none`/`declared` — декларация источника, а не проверка ядром и не доказательство клонируемости (O-07);
  - `derived_from` и `claims.evidence` — отдельные механизмы, зависимостями не заменяются.
- **Без обработчика** данные расширения сохраняются при записи. Если безопасно сохранить их нельзя — запись запрещена.
- **Точность чисел** (R-09.8, O-13, ADR-0037 п. 4): гарантия **общая** для всех мест непрозрачного JSON (§2), минимум: `extensions.*.data`; `custom_values[].value` с plugin TypeID; `files[].generation.params`; `claims[].value` при адресате с plugin TypeID; `field_definitions[].default`/`constraints` plugin-типов; `history.entries[].details` и дополнительные ключи `changes[]`.
  - Сохраняется исходная лексема каждого числа (знак, экспонента, завершающие нули) и её место; преобразование числа в строку или `double` запрещено. Побайтовая идентичность всего `manifest.json` не требуется.
  - Механизм — итог спайка **S7**, [ADR-0038](../decisions/ADR_log.md): строгий собственный разбор; известная часть в DOM, непрозрачные поддеревья — исходные фрагменты, повторно проверяемые при выводе; перед фиксацией — сверка всех непрозрачных значений и лексем по ключам владельцев. Если сверка не прошла, запись не выполняется (чтение и экспорт разрешены). Ограничение не выдаётся за повреждение ZIP.

## 11. `history` (§19.4.15)

```json
"history": {
  "entries": [
    { "revision": 1, "operation_id": "<UUIDv4>", "timestamp": "…", "operation": "asset_created",
      "tool": { "application_version": "0.1.0", "profile": { "id": "telegram", "version": 1, "sha256": "…" },
                "handlers": { "archive": "libarchive 3.8.1" }, "exclusion_rules_version": 1 },
      "changes": [ { "kind": "file_add", "target": "<FileID>" } ] }
  ]
}
```

- **Одна фиксация — одна запись `entries[]`** с `revision` и `operation_id`.
  - `operation_id` совпадает с `pending_ops.op_id` (ADR-0006, ADR-0015).
  - Изменения внутри транзакции перечисляются в `changes[]`.
- **Ревизия 1** содержит `asset_created` и `tool`. В `tool` пишутся только реально применимые версии, без фиктивных значений.
- **Параметры операции** записываются в `details` (непрозрачный JSON, §2).
- **Независимая копия** (R-07, ADR-0036 п. 4): ревизия 1 — `asset_created` с `details = {"creation_kind": "independent_copy", "source_asset": {"asset_id": …, "revision": 12}}`. Эта запись не компактизируется; доступность исходного ZIP не требуется. Копирование файла ZIP AssetID и ревизию не меняет.
- **Базовый словарь `operation`** (O-18 п. 4): `asset_created{creation_kind?: import|user|independent_copy, source_asset?}`, `files_changed`, `metadata_changed`, `groups_changed`, `previews_changed`, `provenance_changed`, `field_definitions_changed`, `extension_data_changed`, `format_migrated{from, to, steps[]}`, `history_compacted`, `session_committed`. Иные корректные имена сохраняются как непрозрачные; неизвестная семантика не делает запись пригодной для компактизации. Закрытость словаря и plugin-`operation` — **OPEN**.
- **[ПРЕДЛОЖЕНИЕ, OPEN] Словарь `changes[].kind`:** `file_add`, `file_remove`, `file_replace{old_sha256, new_sha256}`, `file_move{old_path}`, `metadata_set`, `group_*`, `preview_*`, `claim_*`.
- Импорт готового ассета ревизию не меняет: запись идёт в журнал библиотеки, а не в ZIP.
- **Покрытие (O-18):** ревизии `1..asset.revision` представлены **ровно один раз** — записью `entries[]` или одним диапазоном `compacted_ranges[]`; без пропусков, пересечений и повторов; оба массива упорядочены по начальной ревизии. Ревизия 1 (`asset_created`) и последняя (`revision = asset.revision`, `timestamp = asset.modified_at`) — всегда отдельные записи.
- **`compacted_ranges[]`** — `{from_revision, to_revision, summary: {revision_count, operation_counts?}}`: `revision_count = to − from + 1`; `operation_counts` — точные счётчики известных операций, сумма = `revision_count`. Сводка не заменяет первичную историю; detail, operation ID и timestamps удалённых записей не выдумываются.
- **Не компактизируются:** `asset_created`, `format_migrated`, `provenance_changed`, `history_compacted`; записи с неизвестной `operation`; записи с `file_remove` и иными историческими фактами, сохранность которых в `historical_files`, `origin`, `inputs` не доказана. Для `session_committed` проверяется каждый элемент `changes[]`.
- Компактизировать можно только смежные разрешённые записи; ранее свёрнутые диапазоны с новыми не сливаются. Компактизация — **отдельная ревизия** `history_compacted` (новый `operation_id`, `modified_at`); байты файлов не меняются.
- Fail-closed: при неизвестных расширениях, которые могут ссылаться на OperationID, при незавершённой операции или если восстановление опирается на отдельные `operation_id`, — не компактизировать.
- В P0 компактизация **не выполняется**; чтение и проверка корректной структуры поддерживаются.
- Ошибки и неудачные задания в историю не попадают.

### 11.1. Независимая копия (R-07)

- Новые UUIDv4 для FileID, GroupID, PreviewID, InputID, InputObjectID, SourceEntryID, SourceID, AttachmentID, ClaimID, OperationID. FieldID и ExtensionID сохраняются.
- Все нормативные ссылки (`file_refs`, `previews`, `derived_from`, значения `file_ref`, `license.file_ref`, `claims.evidence`, `authors[].id`/`item_id`, ссылки `inputs`, зависимости вложений) переназначаются по отображению `old→new`. Результат проходит полный V1–V4 до регистрации.
- Переносится текущее состояние: файлы, метаданные, группы, превью, применимое происхождение, безопасно переносимые расширения. Старые `history.entries` не переносятся.
- **Отказ** вместо фальшивой истории, если `historical_files`/`derived_from` нельзя корректно представить (O-05, O-06), или если безопасное переназначение неизвестных расширений не доказано (O-07). Альтернатива — обычное копирование ZIP.
- Байты полезных файлов не преобразуются, SHA-256 сохраняется. Источник не изменяется. Данные `userdata.sqlite` (аннотации, коллекции, решения Dismiss) не наследуются.

## 12. Проверка (§19.4.7)

| Уровень | Что проверяется |
|---|---|
| V1 | ZIP-структура, один `manifest.json`, синтаксис JSON, лимиты разбора |
| V2 | JSON Schema версии `format.version` |
| V3 | Семантика (дополнения ADR-0037 — по разделам §4–§11: claims, `origin`/`inputs`, зависимости, единицы и ограничения, покрытие истории, время): уникальность ID и путей; разрешимость активных ссылок (`file_refs`, `previews`, `file_ref`, `primary_id`, `custom_values.field_id`); нет циклов групп; связи `inputs`↔`origin`; `historical_files` ∩ `files` = ∅; история: ревизия 1, последняя запись = `asset.revision`, диапазоны не пересекаются. **Claims (R-05):** target разрешим (стандартное поле допустимо для scope, FieldID определён и допускает scope, `item_id` существует в `authors[]`); `value` соответствует типу и единице поля; для `supports_selected` выбранное значение существует. **Теги:** предупреждение о совпадающем поисковом ключе. **Типы:** `custom_values` соответствует определению для базовых типов |
| V4 | Физика: каждая запись `files`/`attachments` существует; размер, CRC и SHA-256 совпадают; у новых контейнеров нет opaque-записей (§1). Статус **по каждому потоку**: `verified_sha256`, `verified_crc_size_only`, `unverifiable`, `unsupported`, `failed` (O-15) |

- Режимы `quick`, `selective` и `full` выбирают объём V4 и не зависят от разбиения V1–V4.
- **Перед фиксацией** созданного или изменённого ZIP — полный V1–V4 по всем зарегистрированным потокам (ADR-0035 п. 7).
- Результат проверки указывает фактически пройденные уровни **раздельно**: V1/V2 (структура), V3 (семантика), V4 (физика) и **plugin-validation** (R-09.7). Без установленного обработчика семантика plugin-типов и расширений не объявляется проверенной.
- **Свод V4 (O-15, K-10):**
  - `failed` (несовпадение реально проверенных размера, CRC или SHA, ошибка чтения, конфликт каталогов) → `Errc::corrupt_data`;
  - `unsupported` (метод сжатия, шифрование, небезопасные флаги) → `Errc::unsupported`;
  - `verified_crc_size_only` и `unverifiable` — не ошибка, а `container_verification = partial`; потенциально опасная запись при этом запрещена;
  - `full` — только если все зарегистрированные потоки `verified_sha256`, структурные проверки пройдены и opaque-потоков нет. `manifest.json` проходит структурную проверку и проверку ZIP; самохеш манифеста не требуется.
- Коды ошибок:
  - `invalid` → `Errc::corrupt_data`;
  - `unsupported` → `Errc::unsupported`;
  - `incomplete` → `Errc::incomplete`;
  - детали — `message_id` вида `am.manifest.<code>`.
