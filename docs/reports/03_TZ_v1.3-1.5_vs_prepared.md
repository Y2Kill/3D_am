## 2. Общий вывод сравнения

Новые разделы ТЗ и подготовленные материалы **в основном совпадают по принципам**:
- модульный монолит;
- статические внутренние библиотеки и динамические плагины;
- единственный писатель ZIP;
- восстановимый индекс и отдельные невосстановимые пользовательские данные;
- общая система заданий;
- манифест плагина читается до загрузки кода;
- необязательный внешний процесс-обработчик;
- офлайн-режим и тестовые наборы без изменения коллекции.

Существенные расхождения сосредоточены в трёх местах:

1. **Раскладка слоёв.** Где находятся задания, предметная модель и реестр команд (§12.1, §12.5, §12.6).
2. **Конкурентный доступ.** Согласованные снимки, оптимистический контроль ревизий, межбиблиотечное перемещение (§12.7). Эти требования в подготовленном **не проработаны** — это пробел подготовки, а не спор вариантов.
3. **Сценарии и LLM.** Независимый декларативный движок с Dry Run против Lua-скриптов, отложенных вместе с LLM (§11.3).

Есть и формальный момент. ТЗ сознательно оставляет **открытыми** выбор библиотек, ABI, GUI-фреймворка и менеджера зависимостей (§12, вводный абзац; §17 пуст), а в ADR эти решения записаны как «Принято». Реального конфликта нет, но статусы стоит выровнять (см. Р-1).

## 4. Сводные рекомендации (что решить владельцу)

**Р-1. Выровнять статусы ADR.** Архитектурные решения, совпадающие с ТЗ (А-1, К-1, П-2, П-6 и т. п.), оставить «Принято». Технологические выборы — vcpkg, Qt 6 Widgets, minizip-ng, libarchive, SQLite, C ABI и остальное из `libraries.md` — перевести в статус **«Предложено для §17»**. ТЗ по-прежнему держит §17 пустым; подготовленный `libraries.md` и есть исследование, которого требует §17. Владелец переносит в §17 то, что принимает.

**Р-2. Реструктуризация.** Предлагаемая раскладка — вариант ТЗ §12.6 с тремя отступлениями из А-11:

```text
3D_am/
├── CMakeLists.txt, CMakePresets.json, vcpkg.json
├── cmake/modules/, cmake/toolchains/
├── sdk/include/am/            # отдельный SDK плагинов (§12.8.10)
├── include/am/<level>/<module>/
├── src/
│   ├── foundation/            # base: Result, пути, кодировки, UUID, хеши, лог, конфигурация
│   ├── contracts/             # узкие интерфейсы: ICommand, IJobStore, ICatalog, IArchiveReader…
│   ├── domain/                # модель ассета, манифест, метаданные, ревизии
│   ├── storage/               # asset_zip, archive (входные), repository, db, library_data, trash
│   ├── jobs/                  # очередь, исполнители, recovery (только foundation + contracts)
│   ├── processing/            # formats, analyzers, converters, renderers
│   ├── services/              # import/analyze, export, catalog, search, dedup, preview, sessions
│   ├── automation/            # command registry, scenarios, scheduler
│   ├── plugin_runtime/
│   ├── ai/                    # необязательно: интерфейс адаптера, контекст, тестовый адаптер
│   └── application/           # публичный API (фасад), gui/, cli/
├── plugins/, plugins/examples/
├── schemas/, profiles/
├── tests/{unit,integration,regression,fixtures,performance,plugins,real}
├── tools/, docs/, packaging/{windows,portable}
```

Цель CMake — по одной на каталог уровня, всего 11–12 целей (ТЗ: 9–11). `jobs` отделены от `automation`, как в ТЗ: `catalog_jobs` и `catalog_automation`. Переделка готового кода механическая:

| Было | Стало |
|---|---|
| `base` | `foundation` |
| `archive/volume_detect` | `storage/archive` |
| `formats/stl_probe` | `processing/formats` |
| `import/exclusion_rules` | `services/import` |
| `core/command_registry` | `automation` |

44 теста переносятся без изменения логики.
