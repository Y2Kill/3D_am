# 08. Решения владельца, необходимые для публикации формата 1.0

**Дата:** 2026-11-12 · **Автор:** управляющий · **Основа:** `main` после T-012, ТЗ v1.8 §19.5, ADR-0035…0038, журнал RC-1 v0.11, снимок открытых вопросов `e2472e9`, [`container_manifest_v1.md`](../specifications/container_manifest_v1.md) §14.

## 1. Зачем этот отчёт

Формат 1.0 объявляется опубликованным, когда есть три вещи (ADR-0035 п. 1, ТЗ §19.6.4): **нормативная схема**, **валидатор V1–V4** и **golden ZIP**.

| Условие | Состояние |
|---|---|
| Валидатор V1–V4 | Готов: кодек T-006, V4 T-010, V3 T-011 (38 правил), общая проверка отдельного ZIP T-012 |
| Точные числа (O-13/S7) | Механизм выбран и реализован (ADR-0038); O-13 закроется прогоном тестов кодека в CI — задача T-005 (GitHub Actions) |
| Golden ZIP | Задача T-013 готова к выполнению после T-005; строится по черновой схеме и перегенерируется при её изменении |
| **Нормативная схема** | **Ждёт решений этого отчёта.** Схема `manifest-1.0.draft.schema.json` остаётся черновиком, пока не закрыты пункты ниже |

Отчёт делит открытое на две группы:
- **раздел 2 — блокирует публикацию:** решение меняет то, что лежит в ZIP, или то, что V2/V3 считают ошибкой. Без него формат 1.0 нельзя заморозить;
- **раздел 3 — не блокирует:** вопрос касается индекса, GUI, будущих функций или численных лимитов реализации. Предлагается **явно вывести его за пределы формата 1.0** и решать в своей вехе.

По каждому пункту: что сейчас, варианты, **рекомендация** и последствия. Ничего не принято допущением: до ответа владельца всё остаётся открытым (CLAUDE.md).

## 2. Блокирующие пункты

### Ф-1. Грамматика и реестр `dimension` (X-02, поддеталь 1)

**Сейчас.** SPEC §8: 16 базовых ключей (`dimensionless`, `length`, `area`, …, `angle`); неизвестный корректный ключ сохраняется; грамматика и полнота реестра — OPEN. В схеме `dimension` — строка без шаблона.

**Варианты:**
- (а) закрытый список из 16 ключей; всё прочее — ошибка V2;
- (б) открытый: грамматика ключа + базовый реестр; неизвестный ключ сохраняется, преобразования для него нет, V3 даёт `unverifiable`;
- (в) (б) плюс пространство имён плагинов `plugin:<PluginID>:<Key>`.

**Рекомендация — (в).** Грамматика: базовый ключ `^[a-z][a-z0-9_]{0,63}$`; плагинный — `plugin:<PluginID>:<FieldKey>` по грамматикам O-11. Реестр 16 ключей — нормативный для семантики преобразований; добавление ключа в реестр — минорная версия формата. Так новые величины (например, `density`) не ломают старые читатели, а плагины не занимают базовые имена.

**Последствия:** шаблон в схеме, правило V3 «неизвестная dimension → `unverifiable`» (сейчас уже так для преобразований).

### Ф-2. Форма `default` для физической величины (X-02, поддеталь 2)

**Сейчас.** `default` — рекомендация, проходит проверки типа; форма для физической величины — OPEN. Сейчас V3 даёт `unverifiable` (правило `x02_physical_default_open`).

**Варианты:** (а) строка типа без единицы — единица берётся из `unit` определения; (б) `{value, unit}` — та же структура, что у границ `constraints`; (в) запретить `default` у физических полей в 1.0.

**Рекомендация — (б).** Структура уже утверждена для границ (X-02 п. 7: рекомендуемая единица определения не бывает неявной). Одинаковая форма у `default`, `minimum`, `maximum` — меньше особых случаев в схеме, V3 и редакторе полей. `unit` в `default` обязателен, если `dimension` физическая.

**Последствия:** правило `x02_physical_default_open` превращается в обычную проверку (ошибка при отсутствии `unit`, `unverifiable` при неизвестной единице).

### Ф-3. Движок UCUM и таблицы преобразований (X-02, поддеталь 3)

**Сейчас.** Единицы — точные регистрозависимые UCUM-коды; движок и таблицы — OPEN. V3 сравнивает только совпадающие коды, разные — `unverifiable` (правило `x02_unit_conversion_open`).

**Варианты:** (а) формат 1.0 нормативно привязывается к конкретной таблице преобразований; (б) формат фиксирует только **запись** (точный UCUM-код как строка), а преобразование — возможность реализации, не часть формата.

**Рекомендация — (б).** Формат описывает данные, а не арифметику: ZIP не меняется от того, умеет ли программа переводить `cm` в `mm`. Нормативно: код единицы — непустая строка, известные единицы пишутся точным UCUM-кодом, исходная строка не исправляется (X-02 п. 2 — уже утверждено). Выбор библиотеки или собственной таблицы — решение реализации (`libraries.md`, веха редактора полей), без влияния на формат. Пока преобразования нет, разные единицы дают `unverifiable`, а не ошибку — это уже так.

**Последствия:** пункт снимается с блокирующих; правило `x02_unit_conversion_open` остаётся `unverifiable` до появления движка; появление движка — не изменение формата.

### Ф-4. У `claims[]` нет единицы значения (пробел, найден при T-011)

**Сейчас.** `custom_values[]` = `{field_id, value, unit?, dependencies?}`, и `unit` обязателен у физической величины (X-02 п. 4). Но claim с `relation = alternative`/`rejected` и `target = {kind: custom}` несёт только `value` — **единицу выразить нельзя**. Альтернативное значение «12.5» для поля «высота» неоднозначно. Сейчас V3 даёт `unverifiable` (правило `claim_value_unit_unexpressible`). Этот пробел не покрыт ни ТЗ, ни R-01…R-09, ни RC-1.

**Варианты:**
- (а) добавить в claim необязательное поле `unit` с тем же правилом, что у `custom_values` (обязательно, если адресат — физическое числовое поле);
- (б) для физических полей `value` claim — объект `{value, unit}`;
- (в) в 1.0 запретить `alternative`/`rejected` для физических полей.

**Рекомендация — (а).** Симметрично `custom_values` (одно правило в V3 для обоих мест), не меняет тип `value` в зависимости от поля (у (б) тип `value` зависел бы от определения поля — сложнее для V2 и для чужих читателей), не урезает модель (в).

**Последствия:** поле `unit?` в `$defs.claim`, правило V3 `claim_value_unit_unexpressible` заменяется проверкой `value_unit_required` для claims; новые случаи в `schema_check` и golden ZIP.

### Ф-5. Словарь `changes[].kind` (O-18, поддеталь 1; [ПРЕДЛОЖЕНИЕ, OPEN])

**Сейчас.** Предложение SPEC §11: `file_add`, `file_remove`, `file_replace{old_sha256, new_sha256}`, `file_move{old_path}`, `metadata_set`, `group_*`, `preview_*`, `claim_*`. Реализованный `AssetRepository` уже пишет `file_add`, `file_remove`, `file_replace`, `metadata_set`.

**Варианты:** (а) закрытый словарь; (б) базовый словарь + сохранение неизвестных как непрозрачных; (в) (б) + плагинные `plugin:<PluginID>:<Key>`.

**Рекомендация — (в)** с конкретным базовым словарём:
`file_add`, `file_remove`, `file_replace{old_sha256, new_sha256}`, `file_move{old_path}`, `metadata_set`, `group_add`, `group_remove`, `group_change`, `preview_add`, `preview_remove`, `claim_add`, `claim_remove`, `claim_change`, `field_definition_change`, `extension_change`.
Неизвестный или плагинный `kind` сохраняется как есть и по O-18 п. 3 делает запись некомпактируемой. Расширение базового словаря — минорная версия.

**Последствия:** перечисление в схеме (с допуском неизвестных корректных имён), правило V3 для обязательных полей известных видов.

### Ф-6. Плагинные `operation` и критерий «нет скрытых ссылок на OperationID» (O-18, поддетали 2–3)

**Сейчас.** Базовый словарь `operation` утверждён (O-18 п. 4); закрытость словаря и plugin-`operation` — OPEN; критерий скрытых ссылок для компактизации — OPEN. Компактизация в P0 **не выполняется**.

**Рекомендация:**
- плагинные операции — имя `plugin:<PluginID>:<Key>`; семантика для ядра неизвестна → запись защищена от компактизации (уже следует из O-18 п. 3);
- критерий скрытых ссылок **в 1.0 максимально простой:** компактизация разрешена, только если в ассете **нет `extensions` вообще** и нет непрозрачных `details`/`changes[]`-ключей в компактизируемых записях. Точный критерий для ассетов с расширениями — минорная версия, когда появится контракт плагинов (S6, O-07).

**Последствия:** формулировка в SPEC §11; код не меняется (компактизации нет).

### Ф-7. Реестр корневых служебных записей, ZIP extra fields, граница legacy/1.0 (O-15)

**Сейчас.** `known_structural` — только `manifest.json`; реестр допустимых extra fields и граница legacy/1.0 — OPEN. Наш писатель пишет только ZIP64 extra (`0x0001`).

**Рекомендация:**
- **корень:** в 1.0 единственная служебная запись — `manifest.json` (так уже написано; утвердить как окончательное). Будущая служебная запись — только с новой минорной версией;
- **extra fields:** писатель 1.0 пишет только `0x0001` (ZIP64). Читатель принимает любые корректно оформленные extra fields, но смысл берёт только из `0x0001`; прочие (`0x000a` NTFS-времена, `0x5455` extended timestamp, `0x7875` Unix UID/GID, `0x7075` Unicode Path и др.) игнорируются при чтении и **не переносятся** при перезаписи изменённых заголовков (raw-копирование неизменённых записей по-прежнему сохраняет их как есть). `0x7075` не используется для имени: имя берётся из основного поля при флаге UTF-8 (бит 11), который обязателен;
- **граница legacy/1.0:** 1.0 — первая версия формата, «старых» версий нет. Контейнер без нашего `format.id` — чужой ZIP; с нашим `format.id` и `major ≠ 1` — неподдерживаемая версия. Матрица старых версий в `versioning.md` состоит из одной строки 1.0.

**Последствия:** уточнение SPEC §1/§12 и `versioning.md`; в коде — проверка, что писатель действительно не переносит чужие extra fields в изменённые заголовки (T-008 это уже делает только по разрешению).

### Ф-8. Грамматика `generation.tool` (O-14, поддеталь)

**Сейчас.** `tool` — непустой стабильный ID обработчика; грамматика OPEN.

**Рекомендация.** `tool = "core:" FieldKey | "plugin:" PluginID ":" FieldKey` (грамматики O-11): встроенные обработчики (`core:thumbnail.stl`), плагинные (`plugin:com.example.slicer:gcode`). `tool_version` — свободная непустая строка (семантика версий у разных инструментов разная). Префикс `core:` в других местах остаётся зарезервированным.

**Последствия:** шаблон в схеме, правило V3 при необходимости.

### Ф-9. `included_renamed` и `excluded` для каталогов (X-01, поддеталь)

**Сейчас.** `entries[].entry_kind` = `file`|`directory`; смысл `included_renamed`/`excluded` для каталогов — OPEN.

**Рекомендация:**
- `excluded` у каталога означает: каталог и **всё его содержимое** исключены; потомки при этом **всё равно перечисляются** своими записями `entries[]` (тоже `excluded`), чтобы опись входа оставалась полной и проверяемой. Каталожная запись — сводная, не замена записей файлов;
- `included_renamed` у каталога: изменено имя самого каталога, `rename_reason` — по тому же словарю; пути потомков в `storage_path` используют новое имя, а их `path` в описи — исходное;
- противоречие (каталог `excluded`, а потомок `included`) — ошибка V3.

**Последствия:** уточнение SPEC §5.1, правило V3 согласованности каталога и потомков, случаи в golden ZIP.

## 3. Не блокирует публикацию — предлагается вынести за пределы формата 1.0

| ID | Суть | Почему не формат | Где решать |
|---|---|---|---|
| O-03 | Канонизация CandidateKey/BasisKey | Ключи живут в `userdata.sqlite`/`index.sqlite`, не в ZIP | M2/M4 (предложения и Dismiss) |
| O-04 | Когда отклонённое предложение показывается снова | Поведение анализатора и GUI | M4/M5 |
| O-05, O-06 | Родословная и карта FileID при независимой копии | В P0 — безопасный отказ (ADR-0036 п. 4); при добавлении — новые необязательные поля, минорная версия | P1+ |
| O-07 | Контракт clone/remap для плагинов | Зависит от C ABI (спайк S6); без него — отказ | M5P |
| O-08 | Алгоритм поискового ключа тега | Теги в ZIP не нормализуются (R-08); ключ — в индексе. Правило V3 `tags_search_key` (предупреждение) отложено, ошибкой не бывает | M2 (индексатор) |
| O-09 | Показ тегов с одинаковым ключом | GUI | M5 |
| O-10 | Происхождение одного элемента `tags[]` | В 1.0 адресуется поле целиком (утверждено O-02); адресация элемента — новый вид адресата, минорная версия | P1+ |
| O-17 | Численные лимиты разбора и ресурсов | **Рекомендация:** формат 1.0 не задаёт числовых лимитов, кроме уже утверждённого (200 байт на `storage_path`). Читатель вправе отказать при превышении **своих** лимитов, и это отчёт «не проверено / превышен лимит» (`incomplete`), а не «контейнер неверен». Значения — параметры реализации по замерам (ТЗ §14.9.13) | M3a / P0.8 (замеры) |
| — | Матрица старых версий | 1.0 первая (см. Ф-7) | `versioning.md` при выпуске 1.1 |

Если владелец согласен с этой таблицей, формат 1.0 не ждёт вех M2–M5 и замеров O-17.

## 4. Что будет после ответа

1. Решения оформляются новой **ADR-0039** («Нормативная схема 1.0: закрытие поддеталей X-01, X-02, O-14, O-15, O-18 и пробела единицы claim»).
2. Управляющий переводит схему из черновика в `schemas/manifest-1.0.schema.json`, обновляет SPEC §14 и `versioning.md`, дополняет `schema_check`.
3. Задача исполнителю: правила V3 под Ф-2, Ф-4, Ф-5, Ф-9 (и снятие соответствующих `unverifiable`), перегенерация golden ZIP (T-013) по нормативной схеме.
4. После зелёного CI на Windows и Linux — **публикация формата 1.0**: строка в `versioning.md`, запись в `CHANGELOG.md`.
