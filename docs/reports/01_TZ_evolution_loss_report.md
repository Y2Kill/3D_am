# Отчёт: сверка эволюции ТЗ v0.1 → v1.1 и выявленные потери

**Дата:** 2026-11-06
**Объект проверки:** [`docs/tz/description.txt`](../tz/description.txt) и [`docs/tz/drafts/`](../tz/drafts/) `TZ_catalog_3D_2D_draft_v0.1.md` … `v1.1.md` (11 версий, 36 КБ → 223 КБ).
**Итог:** структура ТЗ росла монотонно и аккуратно: критерии приёмки 10 → 68, открытые вопросы 11 → 26, ни один раздел не удалён. Обнаружено **6 реальных потерь** (одна значимая, три средних, две малых) и **2 неявных сужения смысла** исходного описания. Остальные ~80 автоматически найденных расхождений оказались корректными переформулировками или переносами текста в другие разделы.

---

## 1. Методика

1. **Попарный дифф абзацев** (vN → vN+1): каждый абзац, пункт списка и строка таблицы старой версии сопоставлялись с наиболее похожим фрагментом следующей версии (Jaccard по словоформам + `difflib` + мера вхождения). Порог «потенциальной потери» — 0.55. Найдено 84 кандидата.
2. **Попарный дифф предложений**, только для пунктов с меткой `[СОГЛАСОВАНО]` (порог 0.6 по основам слов). Найдено 50 кандидатов, в большинстве совпадающих с п. 1.
3. **Словарь исчезнувших терминов**: слова, которые встречались в любой ранней версии, но отсутствуют в v1.1, с указанием версии первого появления.
4. **Сквозное отслеживание фраз**: для каждой подозрительной формулировки определено, в какой версии она исчезла.
5. **Сверка `description.txt` → v1.1**: каждое утверждение исходного описания отдельно сверено вручную.
6. **Ручная проверка** каждого кандидата по полному тексту v1.1 (прочитан целиком).

Скрипты анализа лежат в `tools/tz_audit/` и могут быть запущены повторно для будущих версий ТЗ: `python tools/tz_audit/tzdiff.py docs/tz/drafts out.txt`.

## 2. Реальные потери

### П-1. Определяемые пользователем поля метаданных и перечень кандидатных полей — **ЗНАЧИМАЯ**

| | |
|---|---|
| Было (v0.1–v0.5, §5.1) | «Предусмотреть расширяемый набор полей. Первоначально обсуждаются: название, происхождение, автор, источник…» и `[ПРЕДЛОЖЕНИЕ]` «Дополнительные возможные поля: описание, категории/теги, **лицензия**, издатель, ссылки, даты, технические характеристики, **пользовательские поля**». |
| Исчезло | v0.5 → v0.6, при согласовании раздела 5. |
| Стало (v1.1) | Расширяемость обеспечивается **плагинами** (5.1.3) и **типизированными техническими характеристиками** (5.6.3). Пользователь может *заполнять* поля (5.1.2), но **возможность определять собственные поля без плагина** не указана нигде. Поле **«лицензия / условия использования»** исчезло полностью. «Описание» уцелело только косвенно (в 10.4.1 как поле поиска). |
| Почему важно | В `description.txt` прямо сказано: «набор полей обсуждаемый и **должен быть легко модифицируемым**». Для коллекций из Telegram и Patreon лицензия (личное использование / коммерческое / запрет перепродажи) — практически важный атрибут. В коллекции 569 файлов `.rtf` и десятки `.txt`/`.pdf`; по опыту это в основном лицензии и readme. |
| Решение (принято, см. ADR-0013) | (а) Вводятся **пользовательские поля, определяемые на уровне библиотеки** (имя, тип, единица, допустимые значения). Значения хранятся в ZIP (пространство имён `user.*`), а определения дублируются в манифесте, поэтому ассет остаётся самодостаточным. (б) В базовую схему добавляются необязательные поля `description`, `license` (свободный текст + необязательный SPDX-подобный код + ссылка на файл лицензии внутри ассета), `links[]` и `dates` (дата публикации, дата получения). |

### П-2. Работа программы без сети — **СРЕДНЯЯ**

| | |
|---|---|
| Было (v0.1–v0.3, §14.2) | «…резервное копирование; переносимость библиотеки и **работа без сети**». |
| Исчезло | v0.3 → v0.4: формулировку заменили на «численные показатели совместимости, переносимости…». |
| Стало (v1.1) | Требуется только **офлайн-сборка** (3.5.6, критерий 19). Требования к **офлайн-работе самой программы** нет. |
| Почему важно | Локальная LLM, генерация превью, поиск похожих и извлечение метаданных из URL-файлов могут незаметно получить сетевую зависимость (загрузка моделей, онлайн-сервисы распознавания). |
| Решение (ADR-0020) | Все базовые функции работают **без сети**. Любой сетевой доступ (например, получение метаданных по URL из `.url`-файлов или скачивание моделей) — только в отдельных плагинах, выключен по умолчанию и с явным индикатором. Добавлен критерий приёмки К-69. |

### П-3. Поиск «по изображению» как самостоятельный запрос — **СРЕДНЯЯ** (потеря при переходе description → v0.1)

| | |
|---|---|
| Было (`description.txt`) | «стоит предусмотреть возможность "**поиска" по изображению** (поиск похожих, поиск совпадающих)», а также ответ на вопрос «**а есть ли у нас уже этот ресурс или нет**». |
| Стало (v0.1–v1.1) | Сравнение изображений и поиск дубликатов описаны только **между ассетами библиотеки** (7.1, 7.3) и **в ходе импорта** (6.3). Сценарий «пользователь берёт произвольную картинку (скриншот из Telegram, превью с сайта) или файл/архив и спрашивает, есть ли у нас такое, **ничего не импортируя**» явно не сформулирован ни в одной версии. |
| Почему важно | Это основной повседневный сценарий из исходного описания: прежде чем скачивать архив на 2 ГБ, проверить по превью, нет ли его уже в библиотеке. |
| Решение (ADR-0016) | Вводится операция **«Проверить наличие» (lookup)**: на вход — изображение, файл, архив или папка, режим только чтения, без создания ассета. Для изображений — визуальный поиск; для файлов и архивов — хеши, имена и состав (как в 6.3). Доступна через drag & drop в GUI, через CLI (`am lookup <path>`) и через буфер обмена. Добавлен критерий приёмки К-70. |

### П-4. Версия программы/импортёра, создавшего ассет — **СРЕДНЯЯ**

| | |
|---|---|
| Было (v0.1–v0.5, §5.2) | «Отдельно сохранять доступные временные метки, формат и метод упаковки, **сведения о процедуре импорта и её версии**». |
| Исчезло | v0.5 → v0.6. |
| Стало (v1.1) | Сохраняются версия **формата** контейнера (4.5) и «признаки упаковки» (5.3.2). Версия **программы, профиль импорта и версии использованных обработчиков** при создании ассета не упомянуты (для конвертации аналогичное требование есть в 9.3.4 и 9.5.6, для импорта — нет). |
| Почему важно | Без этого нельзя найти ассеты, созданные версией импортёра с ошибкой (например, с неверной эвристикой исключения файлов `._*`), и выборочно запустить повторный анализ (5.8.4). |
| Решение (ADR-0010) | В манифесте `history[0]` (операция `create`) записываются: `app.version`, `app.build`, имя и хеш профиля импорта, версии обработчиков архивов (libarchive/7z), правила исключения (версия набора правил). |

### П-5. Отдельный отчёт об исследовании коллекции — **МАЛАЯ**

| | |
|---|---|
| Было (v0.1–v0.2, §13) | «Результатом исследования сделать **отдельный отчёт** с репрезентативными примерами, статистикой форматов, **типовыми сценариями импорта** и проблемными случаями». |
| Исчезло | v0.2 → v0.3 (заменено статусом «проведена первичная инвентаризация»). |
| Стало (v1.1) | Только «дополнить первичную карту разбором проблемных архивов и репрезентативных примеров». Требование «типовые сценарии импорта» как результат исследования пропало. |
| Решение | Выполнено в рамках этой подготовки: `docs/reports/02_collection_findings.md`, раздел «Типовые сценарии импорта». |

### П-6. Детализация результата обработки исходного элемента — **МАЛАЯ**

| | |
|---|---|
| Было (v0.1–v0.5, §5.3) | Для каждого исходного элемента: «включён в ассет, **переименован, перемещён**, конвертирован, исключён **либо требует ручного решения**». |
| Стало (v1.1, 5.9.1) | Только «включён (с соответствием внутреннему пути) либо исключён (с причиной)». |
| Анализ | «Конвертирован» убран **намеренно и корректно**: конвертация при импорте запрещена (4.2.3). А вот **переименование** при упаковке технически неизбежно: слишком длинные пути (найдено 2 980 путей длиннее 260 символов), недопустимые символы, имена в нераспознанной кодировке. Явного статуса для этого случая в ТЗ нет. |
| Решение (ADR-0011) | Статус записи: `included` / `included_renamed` (с указанием причины: `path_too_long`, `invalid_chars`, `encoding`, `collision`) / `excluded` / `pending_decision` (только во время импорта, в готовом ассете запрещён). |

## 3. Неявные сужения смысла исходного описания (не потери, но стоит знать)

| # | `description.txt` | Как отражено в v1.1 | Комментарий / решение |
|---|---|---|---|
| С-1 | «функциональные меню программы — легко расширяемые» | Пункт «Функциональные меню должны легко расширяться» удалён в v1.1, его заменили реестр команд (10.9.4), контекстные меню (10.9.3) и «пункты меню» от плагинов (3.2.3). | Смысл **сохранён** через 3.2.3 и 10.9. Явного упоминания **главного меню** нет. Решение: главное меню строится из реестра команд, так же как контекстные (ADR-0017). |
| С-2 | macOS-артефакты: «директории с идентичными именами файлов, но… в другой — все одного размера» | 6.5: правила по именам (`__MACOSX`, `._*`) + «структура и сигнатуры». Эвристика **«одинаковый размер всех файлов-двойников»** явно не указана. | Решение: детектор AppleDouble проверяет сигнатуру `0x00051607` и типичный размер (4 096 байт или около того). Инвентаризация подтвердила 6 135 таких записей, сигнатурная проверка надёжнее проверки размера. |

## 4. Что проверено и потерей не является (выборочно)

- «Один источник → несколько ассетов» (v0.2 §2.3). Понятие «источник» **переопределено** в v0.3 (теперь это происхождение, а не входной файл), связи многие-ко-многим перенесены в 2.4.2 и 2.3 (вопрос оставлен открытым). Корректно.
- «Восстановление индекса по ZIP» (v0.1 §5.4, предложение) → согласовано в 4.8.3 и 5.10.3. Усилено.
- «Защита от повреждённых архивов, недопустимых путей, чрезмерной распаковки» (v0.1) → 6.9.3. Сохранено.
- «Для результатов неточного поиска хранить метод и оценку уверенности» (v0.1 §7.2) → 7.2.3, 10.6.5. Сохранено.
- «Допустимо ли хранить оригинальную и производную версии» (v0.5 §4.2, открыто) → решено в разделе 9 (производные файлы отдельно, оригинал неприкосновенен).
- «Физическое имя ZIP: название или ID» (v0.5 §4.1.8, открыто) → 4.4.3 (имя по ID внутри библиотеки, по названию при экспорте). Решено.
- «Распознавание боковых файлов со ссылками на публикацию» (v0.7 §6.1) → 5.2.4 (URL-файлы). Сохранено.
- «Возможность повторить импорт с другими правилами» (v0.7 §6.3) → 6.6.4 (открыто). Сохранено как открытый вопрос.
- Перечень «сайт, Telegram-сообщение, канал» для происхождения (v0.6) → 2.3, 5.2.1. Сохранено.
- История изменений (§18) последовательна, каждая версия описывает свои изменения, противоречий не найдено.

## 5. Предлагаемые правки для ТЗ v1.2

> **Статус:** внесены в [`TZ_catalog_3D_2D_draft_v1.2.md`](../tz/drafts/TZ_catalog_3D_2D_draft_v1.2.md) с меткой [ВОССТАНОВЛЕНО], плюс С-1, С-2 и критерий 73 (версия импортёра, П-4). Требуют подтверждения владельцем.

Ниже — текст для включения в следующую версию ТЗ (сами файлы ТЗ **не изменялись**).

1. **§5.1, новый п. 5:** «[СОГЛАСОВАНО] Пользователь может определять в библиотеке собственные поля метаданных (имя, тип, единицы, допустимые значения) без установки плагинов. Значения и достаточное описание полей сохраняются в ZIP-ассете».
2. **§5.6, новый п.:** «[СОГЛАСОВАНО] В базовый набор необязательных описательных полей входят: описание, лицензия/условия использования (текст, код, ссылка на файл лицензии в ассете), ссылки, даты публикации и получения».
3. **§7.1, новый п.:** «[СОГЛАСОВАНО] Проверка наличия без импорта: пользователь предъявляет изображение, файл, архив или каталог и получает список совпадений и похожих ассетов; входные данные не изменяются, ассет не создаётся».
4. **§5.9.1, дополнение:** статус «включён с переименованием» с причиной; сохраняется исходное имя (включая исходные байты имени при неизвестной кодировке).
5. **§4.5.2 или §5.9, дополнение:** «запись о создании ассета содержит версию программы, профиль импорта и версии использованных обработчиков».
6. **§14.1, новый пункт:** «Все основные функции работают без подключения к сети; сетевые функции только в необязательных модулях, выключенных по умолчанию».
7. **§15, новые критерии:** К-69 (офлайн-работа), К-70 (проверка наличия по изображению/файлу без импорта), К-71 (пользовательское поле переживает перенос ассета в другую библиотеку), К-72 (файл с путём > 260 символов и именем в CP437/CP866 импортируется без потери исходного имени).
