## A. Результат проверки и предмет решения

По отчёту исполнителя: 108/108 проверены; 26 соответствуют состоянию репозитория, 78 требуют согласованных правок, 2 противоречат текущему проекту, 2 зависят от открытых деталей X-02. Внутренних конфликтов между блоками O-01/O-02/O-11/O-12/O-13/O-14/O-15/O-16/O-18/X-01/X-02 не найдено. **Это оценка исполнителя, не результат нашего независимого повторного прогона тестов.** Опыты выполнены только для грамматик O-11 и SQLite O-16; 46 прежних тестов схемы не проверяют новую дельту; сборка здесь не запускалась.

Ниже каждый пункт имеет решение для последующего согласования. Пометка **ПРИНЯТЬ** означает техническую рекомендацию в этом документе, **не** статус APPROVED владельцем.

## B. Ответы K-1…K-10

### K-1 — O-15: нормативные структурные ZIP-записи — ПРИНЯТЬ возражение

Для **создаваемого** ZIP-ассета версии 1.0 единственная `known_structural` запись — `manifest.json`. Маркер `am-asset` отменён ADR-0035 п. 2 и не возрождается. Случайно обнаруженный `am-asset` — незарегистрированная (`opaque`) запись: для нового строгого ZIP 1.0 она запрещена, для совместимого существующего/будущего файла действуют O-15 fail-closed/read-only правила, а не признание его новой стандартной структурой. Не путать `manifest.json` с произвольной структурой будущего ZIP.

**Изменить:** O-15 п.1 в новой ADR-0037 и SPEC §1; негативный тест появления `am-asset` в новом контейнере 1.0.

### K-2 — X-01: неполный импорт — ПРИНЯТЬ с уточнением исходов

В `import_pipeline.md` заменить ненормативное `asset.flags.incomplete` на `inputs[].completeness`; локальное `assets.incomplete` в **производном** `index.sqlite` вычислять как `EXISTS(input.completeness IN ('incomplete','unknown'))`. Пустой `inputs[]` не создаёт автоматически значение `incomplete` (отдельные состояния наличия/отсутствия входных данных не подменять). `status=unreadable` удалить как несуществующий нормативный исход и **классифицировать по факту**:

- `unavailable`: исходная запись/том недоступны для получения;
- `failed`: запись была доступна, но чтение/декодирование завершилось ошибкой;
- `not_processed`: операция над обнаруженной записью не выполнялась.

Не заменять **все** технические ошибки `unreadable` на `unavailable` без различения причины. Если отдельный случай невозможно доказательно классифицировать, сохранить причину и применить явное безопасное диагностическое состояние в пределах согласованной модели X-01. Точное разграничение `complete`/`unknown` в крайних случаях — совместно с O-17.

**Изменить:** `import_pipeline.md`, SPEC §5, индексатор/контракт `assets.incomplete` (код позже), тесты partial/unavailable/failed.

### K-3 — O-16: `assets.content_bytes` — ПРИНЯТЬ пропуск

Включить `assets.content_bytes` в область O-16. Это **производная сумма**, а не размер отдельного файла. В SQLite — `TEXT COLLATE BINARY` с **nullable** значением, без старого `NOT NULL DEFAULT 0`; для суммы, укладывающейся в `uint64`, хранить ту же каноническую десятичную форму. Вычислять точно с детектированием переполнения, **не** через SQLite `SUM()`/REAL. Если сумма за пределами `uint64`, хранить `NULL` и явную диагностику вида `content_bytes_overflow` в `health_detail` (или эквивалентном структурированном диагностическом поле) без объявления ZIP повреждённым. `NULL` без диагностики нельзя выдавать как известный ноль; отдельно документировать различие «неизвестно» и «сумма выходит за диапазон». Более широкий формат суммы (bigint) — отдельное будущее решение, не менять O-16 молча.

**Изменить:** `index.sql` (`assets.content_bytes` + CHECK/NULL), индексатор позже, точные тесты при сумме > max(uint64), `health`/`health_detail` без ложного `corrupt`.

### K-4 — O-13/S7: область сохранения неизвестного JSON — ПРИНЯТЬ и расширить ОБЩИМ правилом

Сохранность исходных лексем неизвестных JSON-чисел является **общей гарантией**, а не привилегией двух путей. Обязательные тестовые области, как минимум:

1. `extensions.<ExtensionID>.data`;
2. значения `metadata.custom_values[].value` при plugin TypeID;
3. `files[].generation.params` с неизвестными числовыми поддеревьями;
4. `metadata.claims[].value` (и применимые `origin.sources[].claims[]`), когда `target` относится к plugin-typed полю;
5. `field_definitions[].default` и `field_definitions[].constraints` для plugin TypeID;
6. `history.entries[].details` и нестандартизованные разрешённые ключи `changes[]`.

Этот перечень **не исчерпывающий**: если спецификация разрешает иные непрозрачные плагинные JSON-поддеревья, гарантия действует и там. Любые неизвестные числовые лексемы не переводятся в строки/double, не нормализуются скрыто. Все шесть групп включить в фикстуры S7 с циклом ZIP read → edit unrelated standard field → transactional write → reopen и проверкой отказа от записи до успешного S7. Нормативные стандартные числовые поля со своим точным типом проверяются по собственным контрактам, а не через «opaque».

**Изменить:** O-13 п.1/§10 SPEC, S7 roadmap/fixtures, тесты O-13, ADR-0037; результат S7 по-прежнему OPEN.

### K-5 — X-01: обязательность новых полей — ПРИНЯТЬ

`inputs[].completeness` **обязательно у каждого существующего Input**, enum `complete|incomplete|unknown`. `inputs[].entries[].entry_kind` **обязательно у каждой записи**, enum `file|directory`. Если `inputs` отсутствует — `completeness` не требуется ни в каком фиктивном месте. Для `entry_kind=directory` никакого FileID полезного файла нет; `included` может обозначать сохранение структурного факта каталога. Семантика `included_renamed`/`excluded` для каталогов — **отдельная явно открытая поддеталь**, нельзя без решения изобретать FileID или silently принять недоказанные комбинации. До выпуска нормативной схемы формат 1.0 не публиковался, поэтому мы не сохраняем альтернативную семантику «поле отсутствует = unknown».

**Изменить:** SCHEMA input/inputEntry, SPEC §5, пример, schema- и V3-тесты.

### K-6 — X-01: `inputObject.container` и `name_encoding` — **ОТКЛОНИТЬ рекомендацию об автоматическом удалении обоих полей**

По SPEC §5 уже имеется самостоятельный смысл обоих кандидатных полей:

- `inputs[].objects[].container` = **тип контейнера, определённый по сигнатуре** (`zip`, `rar4`, `rar5`, `7z` и т.п.; ADR-0011); **не** ссылка на родительский архив. `parent_object_id` / `parent_entry_id` описывают вложенность, а не формат архива. X-01 ранее приводил пример `"container": "rar5"`.
- `inputs[].objects[].name_encoding` = **метод/кодировка декодирования имён записей внутри архивного объекта**, например `utf-8(bit11)` или `cp866(heuristic)` (ADR-0012). В отличие от него `inputObject.name_raw.encoding_guess` относится к **имени самого исходного объекта**, а `inputs[].entries[].path_raw.encoding_guess` — к **конкретной записи**. Объектный метод может быть неизвестен, поэтому его нельзя выдумывать.

Смысл полей действительно следует формализовать и устранить риск избыточности. **Предлагаемое действие:** оставить `container` как необязательное поле только для `archive|multivolume_archive`, значение из реально установленного типа по сигнатуре; отсутствие = тип не установлен. `name_encoding` оставить необязательным **временным кандидатом с явно определённой семантикой общего метода декодирования имён записей**, не заменяющим индивидуальный `path_raw`. Если при детализации импорта выяснится, что он нигде не нужен, удаление можно отдельно согласовать до публикации 1.0. В отсутствие этого анализа автоматическое удаление обоих полей могло бы потерять информацию об исходном архиве.

**Изменить:** SPEC §5 (словарь `container` и область `name_encoding`), SCHEMA условно по kind; добавить тест `rar5` ≠ связь вложенности и тест на разные кодировки имён. **До окончательного утверждения владельца этот пункт K-6 спорный; не применять его молча.**

### K-7 — O-14: `RelKey` — ПРИНЯТЬ

Для `links[].rel` в плагинной форме `plugin:<PluginID>:<RelKey>` установить ту же грамматику/длину, что для `FieldKey`/`TypeKey` по O-11 (1–64 ASCII байта). `RelKey` — другой по смыслу ключ, даже при одинаковом синтаксисе. Для стандартных `rel` оставить уже утверждённый открытый словарь и машинный формат, не вводить закрытый enum.

**Изменить:** SPEC §9.1/§8, `$defs.relKey`, тесты на границы/регистр.

### K-8 — O-11: подчёркивание в FieldKey/TypeKey — ПРИНЯТЬ техническую поправку

Нормативной считать ранее использовавшуюся грамматику вида `^[a-z][a-z0-9_]*(?:[.-][a-z0-9_]+)*$` **при отдельном строгом ограничении длины 1–64 байта**. `_` разрешён после первой позиции, включая конец и последовательности `__`; `-` и `.` являются только внутренними разделителями. Допускаются `a_`, `a__b`, но не `_a`, `a-`, `a.`, двойные `..` или `--`. Это **не** изменение FieldID/TypeID пространств, только уточнение словесного описания синтаксиса. Проверить применимость шаблонов для движка ECMA-262, а не только Python `re`.

**Изменить:** O-11 в ADR-0037/SPEC, `$defs.fieldId/typeId/relKey`, regex-тесты.

### K-9 — O-12: стабильный порядок `dependencies.refs` — ПРИНЯТЬ с уточнением сортировки

Сериализатор нормативной схемы **выдаёт стабильный порядок**: сначала `kind` в порядке `file < group < field_value`, затем байтовое сравнение канонического набора ID: `file_id`, `group_id` или кортеж `(owner_scope, owner_id, field_id)`. При совпадении основного идентификатора учитывать дополнительные нормативные поля (`sha256`, если есть) для полностью детерминированной записи. Не переименовывать сущности и не менять их семантику ради сортировки. **Читатель обязан принимать любой порядок refs; V2/V3 не отклоняют только за несортированный массив**. Структурные дубликаты остаются запрещены по O-12.

**Изменить:** SPEC §10/ADR-0037 и writer-тест на воспроизводимый порядок, reader-тест на произвольный порядок.

### K-10 — O-15: свод V4 и Errc — ПРИНЯТЬ с дополнительной оговоркой для `manifest.json`

Для каждого **потока полезного содержимого** V4 отчёт содержит `verified_sha256|verified_crc_size_only|unverifiable|unsupported|failed`. Несоответствие реально проверенной CRC/SHA/размера = `failed`, общая ошибка `Errc::corrupt_data`. Невозможность прочитать метод сжатия/функцию = `unsupported`, ошибка `Errc::unsupported`. `verified_crc_size_only` и `unverifiable` **не равно** доказанной полной целостности; для допустимых read-only сценариев итог `container_verification=partial`. 

Итог `full` **только** если все зарегистрированные полезные файлы проверены SHA-256, все обязательные структурные проверки манифеста/ZIP пройдены, и **нет** непроверенных/непрозрачных потоков. `manifest.json` как структурная запись проходит нормативную структурную проверку и проверку ZIP; **не требуется невозможный самохеш манифеста, встроенный в него же**. При наличии `failed`/`unsupported` операция возвращает соответствующий `Errc` и подробный V4-отчёт, а не маскирует ошибку как успешный `partial`. При частичной верификации потенциально опасная запись остаётся запрещённой по O-15, даже если чтение частично допустимо.

**Изменить:** SPEC §12, ADR-0037, модель отчёта V4 и Errc, тесты смешанных verified/opaque/unsupported/corrupt.

## C. Способ документирования и применение — ПРИНЯТЬ предложенную структуру с контрольными ограничениями

Одна **новая ADR-0037** с принятой дельтой всех 11 блоков и точными ответами K-1…K-10; **не** редактировать решения ADR-0035 и ADR-0036 задним числом. В старых ADR только отметки о частичном уточнении, если стиль журнала это допускает, и ссылки на ADR-0037. Результат и выбор конкретного механизма S7 — **отдельная ADR после успешных воспроизводимых опытов**. После явного разрешения на применение обновить SPEC, draft SCHEMA, пример, index.sql, import_pipeline, versioning, roadmap, библиотеки, acceptance matrix, schema fixtures согласно §5 отчёта 07.

Два разных уровня готовности:

- **Принять архитектурную дельту к применению** после утверждения этих ответов — можно, код ядра остаётся на паузе, существующее ТЗ v1.8 не редактируется автоматически.
- **Опубликовать нормативный формат ZIP 1.0** — нельзя до положительного S7, закрытия соответствующих поддеталей X-02/O-18/O-15/O-17, валидатора V1–V4, golden ZIP и матрицы старых версий.

## D. Проверки после применения

1. Отразить **все 108** принципов с трассировкой к изменённым файлам и тестам; не закрывать два blocked X-02 одним редакторским изменением.
2. Запустить новую расширенную матрицу Schema 1.0, включая негативные `am-asset`, обязательные `completeness`/`entry_kind`, `relKey`, `dependencies.refs` и `review` без `state`; отчёт должен указывать число реально исполненных тестов, не только исходные 46/46.
3. Проверить `index.sql` реальной SQLite: CHECK, NULL/0, граничный `uint64`, сортировка `(length(size),size)`, индекс и overflow для `content_bytes`.
4. Проверить, что в `roadmap.md` S7 охватывает **все** разрешённые непрозрачные JSON-поддеревья; результаты S7 не подменять документом/списком фикстур.
5. Подтвердить, что правки к `import_pipeline` не породили новый `asset.flags.incomplete`/`unreadable`, и что поля `container`/`name_encoding` не потеряны без отдельного согласованного решения.
6. Проверить отсутствие регрессий R-01–R-09/ADR-0036 и согласованность с O-01–O-16, X-01/X-02/O-18; не объявлять формат 1.0 опубликованным.
7. Зафиксировать статус каждого K-пункта как `APPLIED`, `TESTED`, `OPEN` либо `NEEDS_OWNER_DECISION`, а не «все решено» без проверки.
