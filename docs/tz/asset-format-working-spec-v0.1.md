# ZIP-ассет каталогизатора 3D/2D: рабочая спецификация v0.1

**Статус:** рабочая консолидация согласованных принципов §19.4.1–19.4.7; **НЕ утверждённая нормативная спецификация формата v1.0**.  
**Основание:** ТЗ `TZ_catalog_3D_2D_draft_v1.7.md`, разделы 4–6, 8, 12–14, и последующее согласование §19.4.1–19.4.7 в диалоге 2026-11-06.  
**Язык документа:** русский; первоначальный интерфейс программы — **английский** (украинская локализация необязательна, русская в ранних выпусках не предусмотрена).  
**Назначение:** явное разделение **[СОГЛАСОВАНО]**, **[РАБОЧЕЕ ПРЕДЛОЖЕНИЕ]** и **[ОТКРЫТО]** при подготовке машинной JSON Schema, сериализатора и эталонных фикстур для P0.2.

## 1. Принципы хранения [СОГЛАСОВАНО]

1. Каждый ассет — обычный **ZIP/ZIP64** с `manifest.json` в корне, содержимым `content/` и, при необходимости, постоянными производными файлами в `generated/`.
2. Архив **самодостаточен**: без исходной библиотеки или её SQLite-индекса восстанавливаются собственные метаданные, файлы, происхождение, группы, предпросмотры, ревизия и история.
3. Содержимое включённых оригинальных файлов сохраняется **побайтово**; архивы, являвшиеся внешней упаковкой входных ресурсов, целиком внутрь ассета не копируются. Для исходных архивов и томов сохраняются технические сведения и SHA-256.
4. `content/<InputID>/<relative-path>` разделяет различные входные комплекты, сохраняя их иерархию. Физические пути и исходные имена — разные поля. Источник происхождения публикации не равен техническому входному архиву.
5. Постоянные данные ассета хранятся в ZIP. Поисковый индекс SQLite перестраивается. Постоянные **данные библиотеки** (включая межассетные пользовательские отношения) сохраняются отдельно от индекса и должны иметь собственное резервирование.
6. Только сервис хранилища изменяет действующий ZIP через временный контейнер, проверку и безопасную фиксацию. Откат содержимого к предыдущим ревизиям по одному лишь `history` **не гарантируется**.
7. Логические группы и назначения предпросмотра описывают **ссылки** на текущие файлы без физического копирования. Внешние автоматически перестраиваемые кэши не изменяют ZIP.
8. Чтение, интерпретация и возможность записи контейнера — отдельные способности. Неизвестный формат не считается повреждённым автоматически, но несовместимый ZIP не изменяется.

## 2. Физическая структура [СОГЛАСОВАНО + РАБОЧЕЕ ПРЕДЛОЖЕНИЕ]

```text
<AssetID>.zip
├── manifest.json                           [СОГЛАСОВАНО: обязательная запись]
├── content/                                [СОГЛАСОВАНО: оригинальные файлы]
│   └── <InputID>/
│       ├── Models/model.stl
│       ├── preview.png
│       └── README.txt
├── generated/                              [СОГЛАСОВАНО: постоянные производные, если есть]
│   └── ...
└── extensions/                             [РАБОЧЕЕ ПРЕДЛОЖЕНИЕ: безопасные данные расширений]
    └── ...
```

- ZIP-записи используют относительные пути с `/` и без выхода через `..`, абсолютных путей и двусмысленных имён. Записи с одинаковым нормализованным путём недопустимы [СОГЛАСОВАНО].
- Основной манифест — JSON UTF-8; дублирующиеся JSON-ключи недопустимы [СОГЛАСОВАНО].
- `extensions/` как **имя отдельного физического каталога** не утверждено; это рабочий кандидат. Неизвестные безопасные физические записи нельзя молча удалять. Опасные или несовместимые записи могут блокировать запись.
- Оригинальные изображения предпросмотра остаются в `content/`. Постоянные сгенерированные изображения могут быть в `generated/`; обычные миниатюры отображения предпочтительно хранить во внешнем перестраиваемом кэше.
- Физическое ZIP-имя ассета внутри библиотеки может строиться по AssetID, но сам AssetID от имени ZIP не зависит. При полном экспорте файл может называться по человекочитаемому названию.

## 3. Модель разделов манифеста

| Раздел | Смысл | Статус принципа / деталей |
|---|---|---|
| `format` | ID формата, major/minor | **Согласовано** разделение; точная строка ID открыта |
| `asset` | UUIDv4, revision, системные даты, описательные метаданные | **Согласовано**; точные типы всех вложенных описательных значений открыты |
| `origin.sources` | источники происхождения/распространения | **Согласовано** несколько источников; точная схема доказательств открыта |
| `inputs` | входные комплекты, объекты, обнаруженные записи и результат импорта | **Согласовано** модель; точная JSON-структура — рабочая |
| `files` | **текущие** физически сохранённые файлы | **Согласовано** FileID, safe path, size, SHA-256; формат локальных ID открыт |
| `groups` | логические вложенные и пересекающиеся группы | **Согласовано** один непосредственный родитель в первой схеме, множественное участие файлов |
| `previews` | назначения изображений, одно основное, групповые | **Согласовано** семантика; имена ключей рабочие |
| `field_definitions` | переносимые пользовательские определения полей | **Согласовано** обязательность определений; расположение и JSON-типы рабочие |
| `extensions` | namespaced-данные плагинов, сохраняемые без потерь | **Согласовано** принцип; имя пространства и метасхема рабочие |
| `history` | компактный журнал успешных commit-ревизий | **Согласовано** семантика; схема событий и лимиты открыты |

### 3.1. `format` и `asset`

- `format.id` — постоянный ID типа ZIP-контейнера; **значение `asset-catalog/zip` в фикстурах ВРЕМЕННОЕ**.
- `format.version.major/minor` — целочисленные версии формата, независимые от версии программы.
- `asset.id` — **UUIDv4**; не изменяется при переименовании, обычном редактировании, переносе или экспорте. Независимая новая копия получает новый AssetID.
- `asset.revision` — положительное целое число, начиная с 1; одна успешно зафиксированная транзакция изменения постоянных данных создаёт одну ревизию. Неуспешная операция или отсутствие фактических изменений ревизию не меняет.
- Техническая **миграция схемы**, изменяющая постоянное представление, увеличивает ревизию и записывается в `history` **[СОГЛАСОВАНО в §19.4.7]**. Чистая перепаковка без изменения логического постоянного состояния — нет.
- Совпадение AssetID и ревизии **не доказывает** идентичность состояния двух копий: сравниваются данные и содержимое; конфликт не разрешается молчаливой заменой.
- Системные метки времени — UTC/RFC 3339; не равны датам исходного произведения и не служат единственным критерием актуальности.
- `LibraryID` — библиотечный контекст, не часть самостоятельной идентичности ZIP.

### 3.2. `origin` и `inputs`

- `origin.sources[]` допускает несколько неполных источников: сайт, публикация, репозиторий, Telegram-канал/сообщение и др. Авторство и лицензия **не выводятся автоматически** из сайта распространения.
- Достоверность отдельных утверждений может различаться: наблюдение, гипотеза, введено пользователем, подтверждено пользователем, конфликт. Точная структура evidence пока рабочая.
- Каждый входной комплект имеет устойчивый InputID. Он содержит `objects[]` (технические входы: файл, директория, архив и многотомный архив как один объект) и `entries[]` (обнаруженные записи).
- Для **каждого тома** исходного многотомного архива сохраняется собственное имя, размер и SHA-256. Раскрытые вложенные архивы сохраняют связи с родителем и выбранное действие (`extract`/`preserve`/`exclude`).
- Для обнаруженных записей различают `included`, `included_renamed`, `excluded`, `unavailable`, `failed`, `not_processed`. Только включённые текущие файлы находятся в `files`; исключённые не содержат собственных байтов в ZIP.
- Результаты исходного импорта и даже сведения о позднее удалённых файлах сохраняются исторически. Неполный импорт — только по явному разрешению с маркировкой.
- Абсолютные локальные пути по умолчанию не экспортируются в переносимый манифест; необходимые оригинальные относительные пути и байты имён при нераспознанной кодировке сохраняются.

### 3.3. `files`

- FileID — устойчивый **локальный** идентификатор логического файла, не хеш и не путь. Сохраняется при перемещении и явной замене содержимого; никогда не переиспользуется для нового файла.
- `storage_path` — относительный безопасный путь ZIP; `size_bytes` — размер **несжатого** файла; `sha256` — SHA-256 **несжатых** байтов. Само ZIP-сжатие не влияет на хеш.
- `origin_kind`: `imported`, `user_added`, `generated` — способ появления файла, **не** его функциональная роль.
- Для производного файла возможно `derived_from` с FileID, SHA-256 исходных данных, параметрами и обработчиком. Исторический FileID может ссылаться на уже удалённый файл; активные групповые/preview-ссылки — нет.
- Нормативная связь обнаруженной входной записи с FileID предпочтительно хранится в `inputs.entries[].result`, чтобы избежать двустороннего дублирования отношений.
- **[ОТКРЫТО]** Формат локальных FileID; 64-битные размеры: десятичная строка — **рабочее предложение**, ещё не окончательно утверждённое.

### 3.4. `groups` и `previews`

- GroupID устойчив и локален; первая версия модели имеет **не более одного непосредственного родителя** на группу и не допускает циклов. Один файл может входить в несколько групп, не дублируясь в ZIP.
- Типы групп открыты для расширений; прямое членство отличается от рекурсивного. Группа не является категорией библиотеки, а логическая группа не является пространственной сценой.
- `previews.items[]` ссылается на реальные файлы по FileID. `primary_id` независимо определяет основное изображение; можно иметь множество дополнительных/групповых preview или не иметь изображений вообще.
- Генератор может фиксировать камеру, освещение, использованные FileID **и их SHA-256** для обнаружения устаревшего preview. Устаревшее изображение не удаляется автоматически.
- Удаление группы или назначения preview не удаляет физические файлы; удаление самого файла требует проверки активных ссылок.

### 3.5. `metadata`, `field_definitions`, `extensions`

- Стандартные необязательные поля: название, описание, авторы, издатель, лицензия, категории (с переносимым иерархическим путём), теги, ссылки и даты. Отсутствующее название не принудительно заполняется из имени исходного файла.
- Уровни значений: asset / group / file; наследование — вычисляемое поведение, не автоматическая запись копий.
- Пользователь может создать FieldID, название, тип, единицы и варианты значений без плагинов. Определения **используемых** полей включаются в ZIP для переносимости.
- Типы-кандидаты: `string`, `text`, `integer`, `decimal`, `boolean`, `date`, `datetime`, `enum`, `multi_enum`, `url`, `file_ref`. Точные JSON-форматы чисел/дат/единиц ещё открыты.
- Плагины сохраняют данные в именованных версионированных областях; отсутствие плагина не позволяет терять или искажать его данные. При изменении других полей неизвестные JSON-значения сохраняются без семантических потерь, включая большие числа.
- Подтверждённые пользователем описательные значения не перезаписываются молча результатом повторного анализа. Системные контрольные суммы не являются свободно редактируемыми полями.

### 3.6. `history`

- Одна **успешно зафиксированная** транзакция постоянного изменения — одна новая ревизия, даже если операция включает несколько изменений. Ошибки заданий и неудачные попытки относятся к отдельному журналу заданий, а не `history` ZIP.
- Начальная запись `created` содержит версии приложения, использованного профиля, обработчиков и набора правил исключения, **когда применимо**.
- `history` хранит компактные события, ссылки на затронутые FileID/GroupID и при необходимости прежний/новый SHA-256. Не хранит старые версии байтов файлов и не гарантирует восстановление старого состояния.
- Исторические ссылки могут указывать на удалённые из актуального `files` объекты; **активные** ссылки из групп и предпросмотров обязаны быть разрешимыми.
- Лимит роста и правила компактизации истории **[ОТКРЫТО]**. Нельзя удалять сведения, обязательные для происхождения и прослеживаемости исходного импорта.

## 4. Формальная JSON Schema и образцы

В этом комплекте находятся:

| Файл | Содержание | Статус |
|---|---|---|
| `manifest-1.0.draft.schema.json` | JSON Schema Draft 2020-12; структурные ограничения и provisional-поля | **Рабочий черновик, не нормативная v1.0** |
| `manifest-v1.example.json` | Полный пример с `format`, `asset`, `origin`, `inputs`, `files`, `groups`, `previews`, `field_definitions`, `extensions`, `history` | Пример, прошедший черновую схему |
| `fixture_source_package.zip` | **Искусственный входной** архив с STL, PNG, Unicode-README и служебной записью | Только тестовый вход, не часть ZIP-ассета |
| `fixture_asset.zip` | Самодостаточный ZIP-ассет, созданный из полезного содержимого входного архива | Положительная фикстура |
| `invalid_missing_file_ref.json` | В намеренно некорректной группе указан неизвестный FileID | Отрицательная фикстура |
| `validate_draft.py` | Демонстрационная проверка JSON Schema, части семантических ссылок, размера и SHA-256 реальных файлов ZIP | **Не production-grade** валидатор |

**Точность фикстуры:** SHA-256 исходного архива записан в манифест и вычислен по реальному `fixture_source_package.zip`; SHA-256 включённых STL/PNG/README также вычислены по фактическим байтам и проверяются скриптом. Сам исходный ZIP-архив внутри ассета **не хранится**. Для демонстрации исключения `__MACOSX/._demo.stl` его запись сохранена в `inputs.entries`, но байты отсутствуют в `fixture_asset.zip`. Условные даты, автор и метки принадлежат только синтетическому примеру.

**Ограничения черновой схемы:** `format.id = asset-catalog/zip` — временное значение; локальные ID (`file_a`, `input_a` и т. д.) пока не окончательно нормированы; `size_bytes` временно задан строкой; `custom_values` — рабочее расположение; доказательства и метаданные конвертации — рабочая структура. Схема требует отдельной фиксации редакции до публикации внешнего SDK или реальных ZIP.

## 5. Валидация и совместимость [СОГЛАСОВАНО]

**Четыре смысловых уровня:** V1 — синтаксис ZIP/JSON; V2 — схема; V3 — семантика отношений/ID; V4 — физическое содержимое. Они сочетаются с быстрым, выборочным и полным режимами проверки целостности.

1. **V1:** валидный ZIP, обязательный `manifest.json`, UTF-8 JSON, отсутствие дублирующихся ключей, безопасный разбор под ограничениями ресурсов.
2. **V2:** проверка обязательных полей, типов и версий по фиксированной схеме. Нормативное ядро строгое; зарегистрированные пространства расширений допускают неизвестные данные без потерь.
3. **V3:** уникальность ID и путей; существование активных FileID/GroupID/PreviewID; ацикличность иерархий; корректность InputID и связей происхождения; хронология и актуальная ревизия; отсутствие двусмысленных путей.
4. **V4:** зарегистрированные файлы действительно существуют; полный режим сверяет **фактические** несжатые размеры, CRC и SHA-256; быстрый режим не выдаётся за полную проверку байтов.
5. **Перед фиксацией нового действующего ZIP:** полная проверка нового контейнера и безопасное commit/recovery. Протокол транзакции проектируется отдельно в P0.4.
6. **Совместимость:** поддерживаемая старая версия читается по её схеме; более новая minor не даёт автоматического разрешения записи; неизвестная major — без изменения, при наличии возможностей ограниченное чтение/экспорт.
7. **Миграция:** изменяющая постоянную схему миграция создаёт новую ревизию, записывает техническое событие в `history` и не удаляет неизвестные расширения. Чистая перепаковка без изменения постоянных данных не увеличивает ревизию.
8. **Машиночитаемая диагностика:** устойчивые коды ошибок и фактический уровень проверки; `unsupported`, `invalid`, `incomplete` различаются. Конкретный API CLI пока рабочий.

### 5.1. Что не проверяет демонстрационный `validate_draft.py`

Это **не** полноценный импортёр и **не** безопасная песочница для недоверенных файлов. Он **не** реализует: защиту от ZIP-bomb, временные/дисковые лимиты, symlink/reparse-point политику, Windows-коллизии имён Unicode/case-folding, сравнение имен на всех целевых ФС, реальные инъекции системных сбоев и commit, внешние плагины, конвертацию, весь граф входных архивов, чтение будущих схем и полную миграцию. Факт его успешного выполнения не означает готовность P0.2 целиком.

## 6. Оставшиеся решения до нормативной схемы

| Код | Открытое решение | Влияние | Предложение к следующему согласованию |
|---|---|---|---|
| MF-01 | **Формат локальных ID**: InputID, FileID, GroupID, PreviewID, SourceID, ObjectID, EntryID | Пути ZIP, ссылки, схему и стабильность | Согласовать единый ID-тип или типы по уровням |
| MF-02 | **Точные 64-битные размеры** в JSON | Точность межъязыкового обмена | Выбрать десятичную строку или числа со строгим ограничением |
| MF-03 | **Значения и определения пользовательских полей** | Редактирование, интерпретация, перенос | Зафиксировать `field_definitions` + расположение значений |
