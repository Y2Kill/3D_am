## O-01 — УТВЕРЖДЕНО (6 принципов)

1. `claims.relation` и `review` описывают **разные** вещи: отношение утверждения к выбранному значению и факт явной пользовательской проверки соответственно.
2. `review` — **необязательный объект**; если есть, содержит обязательное `at` (время проверки), **без** `review.state = confirmed|corrected|rejected`.
3. `relation = supports_selected`: отдельное `value` **запрещено**; должно существовать выбранное значение по адресату или адресуемый объект.
4. `relation = alternative`: собственное типизированное `value` **обязательно**, пользовательская проверка необязательна.
5. `relation = rejected`: собственное отклонённое типизированное `value` и **обязательный `review`**; не смешивать с локальным Dismiss в `userdata.sqlite`.
6. `target.kind = self`: в формате 1.0 допускается **только** `supports_selected`. Для `self + alternative/rejected` нет принятого контракта, поэтому запрещено.

**Что необходимо обновить после передачи:**
- SPEC §9.3: заменить эскиз `review: {state: confirmed|corrected|rejected, at}` на согласованный контракт, добавить матрицу допустимых состояний.
- SCHEMA `$defs.claim`: разрешить `review` с обязательным `at` и без `state`; обеспечить `rejected` => обязательный `review`, `self` => `supports_selected`; сохранить условные требования к `value`.
- Семантический валидатор V3: существование адресата для `supports_selected`, правильность типа и ссылок.
- Пример манифеста и положительные/отрицательные тесты: `supports_selected` без `value`, `alternative` с `value`, `rejected` с `value`+`review`, отбрасывание противоречивых сочетаний, `self` только `supports_selected`.

**Никакие другие O-вопросы не считаются автоматически закрытыми в результате O-01.** В частности, `standard_item` уточняется в O-02.

## O-02 — УТВЕРЖДЕНО (8 принципов, 2026-11-10)

Принято пользователем в диалоге. Все восемь принципов ниже обязательны к передаче и применению. Ранее находившийся в этом файле статус PROPOSED заменён на APPROVED; сам репозиторий на снимке `e2472e9` этим не изменён.

1. **Единый набор необязательных стандартных полей** `title`, `description`, `authors`, `publisher`, `license`, `tags`, `categories`, `links`, `dates` для `asset.metadata`, `groups[].metadata`, `files[].metadata`. Никакого автоматического наследования значений между уровнями; отсутствие лицензии/автора у конкретного файла не превращается в подтверждённые значения из ассета.
2. `claims.target.kind = standard` адресует **стандартное поле целиком**, не вложенный компонент. Адресаты `license.spdx`, `dates.published` и аналогичные пути в формате 1.0 недопустимы.
3. `dates` — объект с необязательными полями `published` и `acquired`, оба строго `YYYY-MM-DD`. `acquired` относится к первоначальному получению описываемого объекта, а не к добавлению ZIP в текущую библиотеку.
4. `standard_item` в 1.0 адресует **только запись `authors[]`**. У индивидуально адресуемого автора есть `authors[].id` UUIDv4, он необязателен для обычного автора и обязателен, когда к нему обращается `claim`.
5. Для `standard_item` разрешён **только `relation = supports_selected`**; `alternative` / `rejected` отдельного автора в 1.0 недопустимы. Альтернативы или отклонения *всего массива авторов* допускаются через `standard.field = authors` с типизированным значением-массивом по O-01.
6. Элементы `links[]`, `categories[]`, `tags[]` и других стандартных массивов **не адресуются индивидуально** через `standard_item` в 1.0; только поле целиком.
7. Для `origin.sources[].claims` действует **отдельный реестр** стандартных полей: `kind`, `name`, `url`, `published_at`, `retrieved_at`. Разрешены `target.kind = standard` и `self`, **запрещены** `custom` и `standard_item`; `source.id` является системным идентификатором, а не таким стандартным полем.
8. Для `alternative` / `rejected` тип `value` совпадает с нормативным типом целевого поля: например, `publisher` — объект, `authors` — массив авторов. V2 проверяет структуру и разрешённые сочетания; V3 — владельца, наличие поля/элемента, UUID-ссылки, типы пользовательских значений и семантическую согласованность.

**Дополнительное подтверждённое уточнение:** утверждение, адресованное массиву `authors`, `tags` или `links` **целиком**, не считается автоматически доказательством происхождения каждого его элемента.

**Обновить после передачи:**
- SPEC §9.1, §9.3: единый словарь и два реестра `standard` (обычные метаданные vs `origin.sources`), ограничение `standard_item`, контракт `dates`, отсутствие наследования.
- SCHEMA `$defs.metadata`, `$defs.claimTarget`, `$defs.source`: допустимые имена и области, `dates`/`standard_item`, запрет недопустимых сочетаний. Взаимные ссылки AuthorID и существование выбранного значения — V3, не исключительно JSON Schema.
- V2/V3: значения `alternative/rejected` типов исходного поля, разрешение `standard_item` только для authors; при удалении адресуемого автора — проверка зависимых claims.
- Тесты: стандартные поля на asset/group/file; `source.url` допустим, `source.title` нет, `metadata.url` нет, вложенные пути `license.spdx` и `dates.published` отклоняются; `standard_item.authors` с существующим/отсутствующим автором, реорганизация авторов без потери ссылок; недопустимость `standard_item.links/categories` и `alternative/rejected` для `standard_item`; отсутствие автоматического наследования.

**Остаются открытыми:** O-10 (индивидуальное происхождение тегов), индивидуальная адресация `links`/`categories`, вложенные поля (`license.spdx`), альтернативы/отклонения отдельного автора. Это **не мешает** применению утверждённого узкого контракта 1.0.

## O-11 — УТВЕРЖДЕНО (9 принципов, 2026-11-10)

**Все девять принципов ниже УТВЕРЖДЕНЫ пользователем в диалоге.** В архиве `e2472e9` содержится лишь исходный неподтверждённый regex; численные ограничения, идентичность PluginID/ExtensionID и семантика TypeID приняты позже. Применить при очередном пакете изменений, не выдавая этот журнал за уже обновлённый репозиторий.

**Утверждённые грамматики для передачи в формальный контракт (ASCII; regex требует эквивалентной машинной реализации):**

```text
LABEL      = [a-z0-9](?:[a-z0-9-]{0,61}[a-z0-9])?
PluginID   = LABEL ("." LABEL)+                   // общая длина 3..96 байт
ExtensionID= PluginID
FieldKey   = [a-z][a-z0-9_]*(?:[.-][a-z0-9_]+)*  // длина 1..64 байта
TypeKey    = FieldKey
TypeID     = "plugin:" PluginID ":" TypeKey
plugin FieldID = "plugin:" PluginID ":" FieldKey
```

1. PluginID/ExtensionID в 1.0 используют один и тот же строковый идентификатор пространства владельца — строчную ASCII reverse-domain запись минимум из двух непустых меток; без Unicode, `_`, `/`, `:`, `@`, пробелов и заглавных букв.
2. Каждая метка имеет длину 1..63, не начинается и не заканчивается дефисом; полный PluginID/ExtensionID 3..96 байт. Лимит пути ZIP (`storage_path` 200 байт) проверяется отдельно.
3. `FieldKey` и `TypeKey` имеют одинаковый синтаксис, длину 1..64 байта, начинают с `a`–`z`, допускают строчные ASCII буквы, цифры и внутренние `_`, `-`, `.` в соответствии с грамматикой.
4. `TypeID = plugin:<PluginID>:<TypeKey>`; `plugin FieldID = plugin:<PluginID>:<FieldKey>`; это **разные роли** идентификаторов, несмотря на общую грамматику. `user:<UUIDv4>` и зарезервированный `core:` не меняются.
5. Версию исполняемого плагина и версию схемы его данных нельзя подменять суффиксом TypeID; в TypeID не включается автоматический `@2`. Представление `extensions.<id>.schema_version` закрывается отдельно в O-14.
6. Стабильный TypeID сохраняет прежнюю семантику при совместимых изменениях; несовместимое значение/смысл требует нового TypeKey и явной миграции. `field_definitions[].schema_revision` не подменяет TypeID.
7. Сравнение идентификаторов точное, побайтовое, без автоматической Unicode/регистровой нормализации. Дополнительные резервные префиксы PluginID в 1.0 не вводятся без конкретного согласования; `core:` остаётся зарезервированным префиксом FieldID.
8. Отсутствие установленного плагина не делает корректно сформированный TypeID ошибкой, не требует обязательной записи `extensions[PluginID]` для одного только поля; строка PluginID не подтверждает подлинность или доверие. Capability ID в SDK — отдельная сущность и не должен смешиваться с PluginID.
9. JSON Schema проверяет грамматику и длину, V3 — разрешимость ID и семантические ограничения. Подготовить positive/negative тесты на длину, дефисы, регистр, Unicode, запрещённые символы, неполные namespace и различие FieldID/TypeID. Не менять полезные байты неизвестных данных.

**Обязательные изменения при применении:** SPEC §8 и §10, SCHEMA `$defs/extensionId`, `$defs/fieldId`, `$defs/typeId`; тесты S-*/negative; согласовать поле `plugin_id` SDK с тем же пространством, не переименовывая автоматически capability IDs. Проверить соответствие общей длины `storage_path` и отсутствие конфликтов регистра/Unicode.

**Связанные открытые вопросы:** O-12 (зависимости), O-14 (точный тип/версия `schema_version`), S7/O-13 (сохранение неизвестного JSON), контракт сторонних владельцев namespace и доверия не решается данным regex.


## O-12 — УТВЕРЖДЕНО (10 принципов, 2026-11-10)

**Все десять принципов ниже УТВЕРЖДЕНЫ пользователем в диалоге 2026-11-10.** Они ожидают применения и проверки на основании снимка e2472e9; это не означает, что исходный репозиторий уже обновлён. База: `e2472e9` уже использует `extensions.<ExtensionID>.dependencies: {state, refs}` с `state = none|declared|unknown`, но `metadata.custom_values[]` не имеет зависимости. Здесь `dependencies` на уровне extension описывает **весь блок** `data` + `attachments[]`, а не конкретное вложение; эта гранулярность сохраняется для формата 1.0.

Утверждённый единый контракт (иллюстративные идентификаторы ниже заменяются на реальные UUIDv4 при реализации):

```json
{
  "dependencies": {
    "state": "declared",
    "refs": [
      {"kind": "file", "file_id": "<UUIDv4>", "sha256": "<64 lowercase hex>"},
      {"kind": "group", "group_id": "<UUIDv4>"},
      {"kind": "field_value", "owner_scope": "file", "owner_id": "<FileID>", "field_id": "user:<UUIDv4>"}
    ]
  }
}
```

1. Использовать **один `$defs.dependencies`** и одинаковую форму `state`/`refs` в `extensions.<ExtensionID>.dependencies` и в конкретной записи `metadata.custom_values[].dependencies` с plugin TypeID. В 1.0 декларация extension относится ко всему блоку (`data` и вложениям); дополнительная per-attachment декларация не обязательна и не вводится попутно.
2. Сохранить существующее имя **`state`**, не создавать альтернативного `mode`. Состояния: `none` = подтверждённое отсутствие нормативных зависимостей; `declared` = полный проверяемый список зависимостей; `unknown` = полнота не установлена. Отсутствующее поле трактовать как `unknown`, не `none`.
3. Связать `state` и `refs`: `none` -> `refs` отсутствует/пуст; `declared` -> непустой полный список; `unknown` -> `refs` может отсутствовать или содержать **неполный** список известных ссылок, который не делает статус declared. Списки без структурных повторов; writer сериализует детерминированно.
4. Каждая ссылка — **один типизированный объект по `kind`**: `file` (`file_id`, необязательный `sha256` для привязки к версии), `group` (`group_id`), `field_value` (`owner_scope` + `owner_id` + `field_id` для одного значения из `custom_values`). `sha256` без `file_id`, смесь нескольких kind и неявные локальные пути не разрешаются; все ссылки внутри одного AssetID. Этот новый kind-формат уточняет, а не механически повторяет нынешние объектные refs схемы.
5. Для известных стандартных типов `custom_values` новые plugin dependencies не являются обязательными; при отсутствии plugin-обработчика для plugin-typed `value` отсутствующий `dependencies` = `unknown`. Наличие `none/declared` представляет декларацию источника, а не независимую проверку ядром содержимого opaque JSON.
6. V2 проверяет форму и комбинации; V3 проверяет разрешимость FileID/GroupID/FieldID/owner ID и хеши; V4 проверяет физические файлы и их хеши. Ссылка на historical FileID, если допустима в существующей модели, не должна превращать историческую версию в текущий файл. Несовпадения версий и отсутствующие источники описывать как `stale/unverifiable/source_missing` там, где возможно, не скрывать.
7. Операции удаления/замены/переназначения зависимого объекта требуют проверки всех деклараций и, при необходимости, безопасного пересоздания/удаления конкретных plugin-данных через обработчик. При `unknown` или непроверенном remap — блокировать потенциально разрушительную операцию; не выбрасывать неизвестные данные молча. Безопасные независимые изменения метаданных разрешены при гарантии сохранности opaque JSON.
8. В независимом копировании применить R-07: все нормативные зависимости переназначаются вместе с объектами только при доказанной безопасности. Само значение `none` или `declared` **не доказывает клонируемость внутреннего формата** расширения; контракт clone/remap остаётся открытым O-07.
9. Декларации описывают только зависимости от объектов **внутри данного ассета**, не внешние файлы/сетевые пути. Полнота зависимостей относится к такой области, а внутренняя семантика/доверие plugin JSON проверяются отдельно; O-13/S7 остаётся блокирующим для безопасной записи.
10. Нужны V2/V3/V4 и транзакционные тесты: состояние none/declared/unknown и отсутствие объекта, пустые/частичные refs, разные kind, UUID и hashes, история, отсутствие обработчика, удаление/замена файла, remap при копировании, byte-preserving roundtrip, запрет потери неизвестных зависимостей.

**Обязательные адресные изменения ПРИ ПРИМЕНЕНИИ:** SPEC §9.2, §10, §11, §12; SCHEMA общий `$defs.dependencies`, `$defs.dependencyRef`, `extension.dependencies`, `metadata.custom_values[].dependencies`; ADR-последовательность после ADR-0036; V2/V3/V4; positive/negative и интеграционные тесты. Проверить отсутствие конфликта с `file.derived_from` и `claims.evidence`: они остаются собственными нормативными механизмами, а не заменяются plugin dependencies.

**Не закрывать этим:** O-07 (контракт безопасного clone/remap), O-13/S7 (точность неизвестного JSON), O-18 (политика хранения historical_files), безопасность/доверие исполняемого кода плагинов.

## O-13 / S7 — ТРЕБОВАНИЯ УТВЕРЖДЕНЫ (9 принципов, 2026-11-10); РЕАЛИЗАЦИЯ ОТКРЫТА

**Пользователь согласовал все девять принципов в диалоге 2026-11-10.** Их предмет — обязательные требования к эксперименту S7 и критерии результата, **не** утверждение конкретного JSON-парсера. Реальный положительный результат S7 ещё отсутствует; поэтому O-13 технически не закрыт. Снимок `e2472e9` и ADR-0036 уже требуют без потерь сохранять числовую лексему в неизвестных JSON-значениях; выбранный `nlohmann/json` (ordered DOM) имеет условный статус до S7. В `roadmap.md` спайк S7 есть, но в снимке **нет подтверждённого результата**.

Пример проверяемого значения (это JSON-число, **не строка**):

```json
{"extensions":{"org.example.geometry":{"schema_version":"2","data":{"coeff":12345678901234567890.000000000000000001}}}}
```

**Девять утверждённых принципов:**

1. **Объект гарантии:** для неизвестных `extensions.<id>.data` и значений `custom_values[].value` с plugin TypeID сохраняется **точная исходная JSON-лексема каждого числа** (включая знак, регистр/знак экспоненты, конечные нули), а также его положение в JSON-структуре. Преобразование JSON-number в JSON-string запрещено. Известные нормативные поля продолжают соблюдать собственные типы (`uint64`-размеры строками, ревизии как safe integers, decimal как точные строки).
2. **Не требуется побайтовая идентичность всего `manifest.json`** после законной правки: форматирование, порядок незначимых пробелов и допустимый порядок ключей могут изменяться. Но лексемы чисел неизвестных значений сохраняются без изменения, а неизвестные ключи/значения не теряются. Для полностью неизменённого ZIP остается обычная возможность raw-копии без перезаписи.
3. **Испытать альтернативы, не выбирать заранее:** `nlohmann/json` DOM как контроль проблемы, SAX/token-preserving путь с нём, RapidJSON с обработкой raw-number, точное непрозрачное поддерево или гибрид. Выбирать по фактическому результату на Windows и Linux; не требовать полной замены JSON-стека, если безопасно работает гибрид.
4. **Полный сценарий приёмки**, а не только parse/serialize: открыть `manifest.json` → проверить нормативную структуру/схему и числовой JSON → изменить постороннее известное поле (`title`) → записать ZIP транзакционно → повторно открыть → сопоставить все неизвестные числовые лексемы и их JSON-пути. Обрабатывать также вложенные объекты/массивы, неизвестные ключи и несколько независимых extension/field entries.
5. **Набор обязательных числовых фикстур:** `12345678901234567890.000000000000000001`, целые за int64/uint64, `1e400`, `-1E-400`, `-0`, `-0.0`, `1.500`, очень длинные дроби и показатели степени. Невалидные JSON-числа (например, `01`, `+1`, `NaN`, `Infinity`) должны отвергаться. Двойные имена свойств, лимиты размера/глубины и аварийные кейсы включаются в результаты тестирования, но их окончательная политика синхронизируется с O-17.
6. **Валидация не должна терять число раньше сериализации.** Проверить, что выбранный путь V1/V2 и JSON Schema не превращает непрозрачные значения в `double` и не отвергает допустимый JSON вроде `1e400` лишь из-за ограничений представления float; решения validator API и opaque storage должны быть совместимы.
7. **Fail-closed при записи:** если для конкретного манифеста безопасность обратной сериализации неизвестных чисел не доказана, не выполнять rewrite/миграцию/независимую копию, при которой данные были бы испорчены; разрешённые операции чтения и экспорт без модификации остаются. Не выдавать ограничение за повреждение ZIP.
8. **Безопасность и ресурсы:** сохраняемая числовая лексема проходит строгий разбор JSON-грамматики и вставляется в выходной JSON только через проверенный механизм; не использовать необработанную текстовую подстановку. Измерить пик памяти и время на больших/адверсариальных токенах; пороги согласовать в O-17.
9. **Артефакты S7:** воспроизводимый тестовый код/фикстуры, результаты Windows/Linux, матрица альтернатив и решение об основном/гибридном JSON-механизме, изменение статуса `libraries.md`, новые интеграционные тесты CI. До **положительного S7** и полного V1–V4 формат 1.0 не публиковать. **Само утверждение этих девяти принципов не закрывает O-13:** только реальное успешное испытание и выбранный контракт исполнения могут его закрыть.

**Обязательно при применении:** SPEC §10, roadmap S7, `libraries.md`, V1/V2/serializer, тесты на пересериализацию и ZIP transaction; результаты эксперимента оформить отдельным техническим решением после ADR-0036. Статус ровно `O-13 requirements APPROVED / technical resolution OPEN`, **не** `O-13 CLOSED`. До положительного S7 fail-closed правило R-09.8 действует без исключений.

**Не решается этим:** O-14 (контракт `schema_version`), O-17 (итоговые численные ресурсные лимиты), O-07 (clone/remap) и неизвестные зависимости O-12 вне их утверждённого уровня гарантии.

## O-14 — УТВЕРЖДЕНО (10 принципов, 2026-11-10)

**Все десять принципов ниже УТВЕРЖДЕНЫ владельцем проекта в диалоге.** Они уточняют действующие правила ADR-0036 (`publisher {name, url?}`, непустой `license`, обязательный `links[].rel`). Передать как обязательные изменения для следующей итерации ADR/SPEC/SCHEMA/тестов; не утверждать, что они уже применены в репозитории `e2472e9`.

**База:** SPEC §4 (`asset.modified_at`), §6 (`files.generation`), §9.1 (`publisher`, `license`, `links`), §10 (`extensions.schema_version`), ADR-0035 п. 12, ADR-0036 п. 7; черновая SCHEMA `$defs.asset`, `$defs.file`, `$defs.extension`, `$defs.metadata`.

1. **`publisher` не менять:** необязательный объект `{name: непустая строка, url?: абсолютный URI}`, как уже принято. Не путать издателя с автором, владельцем URL или источником импорта.
2. **`license` — непустой структурированный объект:** разрешённые ключи `name?`, `spdx?`, `url?`, `notice?`, `file_ref?`; при наличии текстовых значений они не пусты, `url` проходит общую URI-проверку, `file_ref` разрешается в текущий FileID (V3). Отсутствие лицензии не означает разрешение на использование; наличие поля не удостоверяет правовую действительность лицензии.
3. **`license.spdx` — синтаксис SPDX license expression**, включая предусмотренные стандартом пользовательские `LicenseRef`; проверка грамматики отдельным валидатором V3, JSON Schema требует хотя бы непустую строку. Не преобразовывать обычные `name`/`notice` в SPDX автоматически и не требовать `spdx` от каждой лицензии.
4. **`links[]` — структурированные `{url, rel}` с обоими обязательными полями**. `url` проходит существующий контракт абсолютного URI; `rel` — регистрозависимый машиночитаемый идентификатор: простое имя по `^[a-z][a-z0-9_-]{0,63}$` или пространство расширения `plugin:<PluginID>:<RelKey>` по уже принятой грамматике O-11; записывается точно, без молчаливой нормализации. Минимальный утверждённый словарь известных ядру значений: `source`, `homepage`, `documentation`, `download`, `license`, `author`, `publisher`, `mirror`, `related`, `preview`. Неизвестные корректные значения не удалять; не объявлять их семантику известной. Перечень **не является закрытым enum**.
5. **`files[].generation` утвердить как нормативный объект** `{tool, tool_version?, params?}`, где `tool` — непустой стабильный ID обработчика, `tool_version` — строка, `params` — объект JSON, не исполняемый код. Для `origin_kind=generated` запись `generation` обязательна; для `imported` и `user_added` она не применяется. `derived_from` остаётся отдельным механизмом ссылки на исходные версии файлов, пустой `derived_from` допустим для результатов без файловых входов.
6. **`generation.params` — постоянные параметры операции:** нельзя без согласования форматировать или округлять неизвестные/плагинные JSON-числа; требования O-13/S7 применяются к непрозрачным участкам. Наличие `generation` само по себе не доказывает побитовую воспроизводимость алгоритма, а только фиксирует известные параметры.
7. **`extensions.<ExtensionID>.schema_version` — обязательная непустая строка** в присутствующей секции расширения; она обозначает версию контракта его собственных данных, не версию плагина или ZIP. Допустимы простые обозначения `"1"`, `"2"`, `"2.1"`; не преобразовывать в число и не делать предположений о SemVer или возможности миграции только по строке. Правила сравнения/миграции определяет обработчик; неизвестная версия сохраняется по MF-09/MF-11 с запретом небезопасной записи.
8. **`asset.modified_at` обновляется при каждой успешной фиксации новой ревизии постоянных данных** (`metadata`, файлы, `claims`, миграция, разрешённая компактизация) и принимает timestamp этой записи `history.entries`. При создании `created_at = modified_at = timestamp` записи revision 1. При no-op, переиндексации, изменении кэша, чтении, обычном экспорте/перепаковке, backup — без изменения. Ревизия, не время часов, остаётся авторитетным порядком изменений; сбои/откат не меняют `modified_at`.
9. **Хеши и размеры текущих файлов атомарно соответствуют их байтам:** при изменении содержимого заменить `sha256`/`size_bytes` в `files[]` в одной транзакции, при неизменности полезных байтов не пересчитывать хеши в целях изменения логической идентичности. Сохранить старые SHA в `derived_from` для корректного `stale`, не переписывая их под новый файл. Все физические проверки и rollback по V4/ADR-0035. Точная политика истории замены и `historical_files` не подменяется этим решением O-18.
10. **Приёмочные проверки:** schema positive/negative для непустого `license`, `license.file_ref`, URI и `rel`, `generation` по `origin_kind`, `schema_version`; V3/V4 для ссылок, хешей, времени, наглядные тесты транзакций `revision/modified_at/history`, no-op/backup/repack и O-13-safe roundtrip. До итогов S7 не считать тест полной записи неизвестных данных успешным.

**Границы предлагаемого решения:** `license.spdx` не определяет актуальность прав; словарь `rel` здесь открытый; `schema_version` не меняет FormatID; `generation` не заменяет `derived_from` или `claims.evidence`; `modified_at` не является доказательством строгой монотонности системных часов. Нельзя закрывать этим O-17 (ресурсные ограничения), O-18 (полный журнал и compaction), O-13/S7 (реальная точная реализация).

**Адресные изменения при следующей передаче:** SPEC §4/§6/§9.1/§10/§12; SCHEMA `$defs.asset`, `$defs.file.generation`, `$defs.extension`, `$defs.metadata.license/links`; ADR-решение после ADR-0036; тесты схемы и V3/V4; приёмочные матрицы и roadmap. При применении подтвердить обязательность `generation` для generated и `schema_version` для секций расширений в тестах.

## X-01 (§19.5) — УТВЕРЖДЕНО (12 принципов, 2026-11-10): нормативные `origin` / `inputs` и исходные имена

**Проверяемый базовый источник:** SPEC §5, §5.1, SCHEMA `$defs.origin`, `$defs.source`, `$defs.input`, `$defs.inputObject`, `$defs.inputEntry`, `$defs.rawName`; `docs/architecture/import_pipeline.md`; ТЗ v1.8 §19.4.3. В снимке `e2472e9` эти формы ещё были кандидатными. **Пользователь утвердил все двенадцать принципов X-01 после снимка**; они требуют применения к SPEC/SCHEMA/ADR/tests. Это не означает, что репозиторий уже исправлен.

1. `origin` необязателен, `origin.sources[]` хранит независимые SourceID UUIDv4 с обязательным `kind` и необязательными `name`, `url`, `published_at`, `retrieved_at`, `claims`. Источник распространения **не означает автоматически автора**; список `kind` первоначально расширяемый. Claims источника следуют O-01/O-02.
2. `inputs[]` необязателен; каждый элемент означает конкретный акт импорта/добавления (InputID, `imported_at`, `mode: strict|partial`, `objects[]`, `entries[]`, необязательные `source_refs[]`). `strict` — режим по умолчанию, `partial` только с явным разрешением. Отдельно от режима записать фактическую `completeness: complete|incomplete|unknown`; это **новое утверждённое поле X-01**, а не существующий `asset.flags.incomplete`.
3. `objects[]` включает `file`, `directory`, `archive`, `multivolume_archive` с InputObjectID UUIDv4 и исходным именем; `relative_path` только относителен к выбранному корню, абсолютный приватный путь не переносится. Исходная архивная упаковка сама по себе не считается текущим полезным `files[]`.
4. Один многотомный архив — один `multivolume_archive` с `volumes[]`, где `index`, `name` и `missing` описывают каждый известный том. Индексы томов **утверждено** считать уникальными неотрицательными, 0-based; размер/SHA фиксировать только при достоверном знании, не изобретать данные отсутствующего тома.
5. Для вложенного архива сохранять `parent_object_id`, `parent_entry_id`, действие `nested_action: extract|preserve|exclude`; V3 проверяет принадлежность родителя, согласованность пары ссылок и отсутствие циклов. `preserve` сохраняет исходные байты как полезный файл только при явной политике включения; `exclude` не создаёт полезного FileID.
6. `entries[]` документирует все **обнаруженные** записи; SourceEntryID не зависит от строки пути, одинаковые имена у разных записей допустимы. Для явного различения каталоговых записей утверждено новое `entry_kind: file|directory`; для каталога `included` означает логическое сохранение структуры без FileID, для включённого файла FileID обязателен. **Это новое утверждённое изменение контракта, ещё не применённое в схеме.** Ненаблюдавшиеся из-за прерывания записи не должны фиктивно создаваться.
7. Сохраняются шесть результатов: `included`, `included_renamed`, `excluded`, `unavailable`, `failed`, `not_processed`; `rename_reason` обязателен для `included_renamed`, `exclusion` для `excluded`, `problem` для `unavailable/failed`. Историческая связь входной записи с FileID не переписывается при замене/удалении текущего файла, а V3 разрешает его через `files` или `historical_files`.
8. `entries[].path` — **исходный логический путь**, `files[].storage_path` — безопасный путь ZIP, не взаимозаменяемы. Опасные исходные пути могут храниться для аудита, но не используются напрямую для извлечения; переименование не меняет байты полезного файла.
9. `name_raw`/`path_raw` для фактически имеющихся исходных байтов используют строгий RFC 4648 Base64 без переводов строк с необязательным `encoding_guess`; Unicode-строка сохраняется без нормализации, исходные байты — при неоднозначности декодирования. Если исходные байты недоступны, **не синтезировать** их из предположительного текста. Валидация проверяет base64 и ограничивает размер.
10. `modified_at_raw` сохраняет исходное время, в том числе без часового пояса, **без выдуманного UTC**; метаданные вроде `size_bytes`/`crc32` только при фактическом наличии, размеры — `uint64`-строки. Даты `imported_at`/`retrieved_at` — отдельные известные UTC-времена, не замена исходного времени файла.
11. V3 разрешает `source_refs` в `origin.sources`, `entries.object_id` в том же Input, `claims.evidence` к соответствующим SourceID/InputObjectID/SourceEntryID, а также вложенные и исторические FileID; история происхождения переносима и не изменяется задним числом. При независимом копировании переназначать ID по R-07 и проверять V1–V4.
12. Обязательны positive/negative Schema/V3/V4-тесты на разные типы объектов, многотомные и вложенные архивы, переименование/исключение/неполноту, raw names, duplicate paths, unsafe traversal, timestamp без timezone, сохранение исторических ссылок. **Отдельно проверить противоречие `import_pipeline.md: asset.flags.incomplete` с отсутствием такого нормативного поля в корне манифеста; не добавить его молча.**

**Подтверждено X-01:** оба новых поля `inputs[].completeness` и `entries[].entry_kind` утверждены и должны быть реализованы; 0-based индексация томов также утверждена. **Для дальнейшей формализации:** граничные детали каталоговых записей и пропущенных томов, лимиты полноты инвентаризации (O-17), работа с исходными недоступными байтами кодировки. Не считать эти отдельные технические детали автоматически проверенными. Между `origin.sources` и авторством нет неявного вывода; между исходным путём и ZIP storage path нет автоматического тождества. Даже после X-01 открыты O-05/O-07, O-17 и проверка фактической реализации импорта.

## X-02 (§19.5) — APPROVED / УТВЕРЖДЕНО: единицы физических величин и типизированные `constraints` (11 принципов)

**Статус:** все одиннадцать принципов X-02 приняты пользователем 2026-11-10 (сообщение «принято»). В базовом снимке `e2472e9` SPEC §8/§9.2 и ТЗ v1.8 §19.4.9–11 закрепляют разделение dimension/value/unit, точные строковые числовые значения, обязательную единицу для числовой физической величины, необязательную рекомендуемую единицу определения и типизированные ограничения; но UCUM помечен [ПРЕДЛОЖЕНИЕ], а `$defs.fieldDefinition.constraints` пока свободный объект. Ниже утверждённые принципы; они ещё не внесены в репозиторий. Отдельно перечисленные технические поддетали **не считаются закрытыми**.

1. **Три независимых слоя:** `field_definitions[].dimension` — декларация физического смысла, `field_definitions[].unit` — необязательная рекомендуемая единица для UI, `metadata.custom_values[].unit` — единица *конкретного хранимого значения*. Значение и единица не сливаются в одну строку. Настройки единиц UI не переписывают ZIP. Поля без физической размерности (например, количество объектов) не получают выдуманных единиц.
2. **UCUM как словарь кодов хранения, не как повод менять исходные данные:** для известных единиц использовать точный регистрозависимый UCUM-код (`mm`, `cm`, `m`, `g`, `kg`, `Cel` и др.), парсить отдельно от показа локализованного символа/названия. Неизвестная единица — непустая исходная строка: сохраняется, не конвертируется и помечается как семантически непроверенная. Никакого молчаливого исправления написания/домысливания единицы.
3. **Dimension не выводится из имени поля.** Предлагаемый базовый реестр семантических ключей: `dimensionless`, `length`, `area`, `volume`, `mass`, `time`, `temperature`, `temperature_interval`, `speed`, `acceleration`, `force`, `pressure`, `energy`, `power`, `frequency`, `angle`; неизвестный корректный ключ сохраняется без автоматической конвертации. Окончательная грамматика ключа и совместимость разных измерений требуют явной проверки; нельзя считать этот список полным для всей физики.
4. **Обязательность значения unit:** если `type` = `integer`/`decimal` и поле декларирует физическую `dimension` (кроме чистого счёта/безразмерной величины без единицы), `custom_values[].unit` обязателен, даже если единица уже указана в определении. Для неизвестных физических единиц отсутствие парсера не превращает исходный ZIP автоматически в повреждённый, но блокирует недоказанную конвертацию и опасное переписывание.
5. **Только совместимые и точные преобразования:** сравнение/перевод выполнять лишь при известной размерности и проверенной совместимости. Основанием выступает явно поддерживаемое преобразование единиц, использующее точную decimal/rational арифметику там, где это необходимо, без `double`-округления хранимого значения. Температура требует явной поддержки смещения и различения абсолютной температуры от температурной разности. Исходная `unit` не изменяется без явного действия пользователя.
6. **Структура `constraints` зависит от базового `type` и является закрытой (не произвольный JSON):** для `integer`/`decimal` допустимы `minimum?`/`maximum?` как `{value: <typed decimal/int64 string>, unit?: <unit code>}`, включительные границы; для `string`/`text` — `min_length?`/`max_length?` (неотрицательное целое, число Unicode code points без нормализации); для `date`/`datetime` — `minimum?`/`maximum?` в соответствующем формате; для `multi_enum` — `min_items?`/`max_items?` (неотрицательное целое). Не вводить regex, произвольные скрипты и бизнес-правила в ядро формата 1.0.
7. **Границы физических величин имеют собственные единицы:** если constraint описывает числовое поле с физической `dimension`, его числовая граница указывает `unit` явно; рекомендуемая `field_definitions[].unit` не выступает неявной единицей ограничения. При сравнении единицы границы и конкретного значения должны быть совместимы. Для безразмерных чисел единицу границы не требовать.
8. **Перечисления:** для `enum`/`multi_enum` перечень `field_definitions[].options[]` является источником допустимых OptionID; `options[].id` уникален, `label` не участвует в идентичности, `deprecated` не делает старое употреблённое значение невалидным. Сравнение `multi_enum` — как множества; индивидуальные ограничения количества относятся к уникальным ID. Для `boolean`, `url`, `file_ref`, `enum` в 1.0 дополнительный `constraints` либо отсутствует, либо требует отдельного более позднего контракта.
9. **`default` — только рекомендация, не материализованное значение:** когда указан, он должен проходить ту же проверку типа, вариантов и (где применимо) ограничений, что и обычное значение. Отсутствие `custom_values` не равнозначно default. Отдельный вопрос — форма default с единицей для физической величины; предложено использовать тот же `{value,unit}` либо явно не поддерживать default для физических величин в 1.0; **эту поддеталь оставить на отдельное подтверждение до окончательной Schema**.
10. **Сохранность и versioning:** изменение типа, dimension, границ, options или их смысловой интерпретации требует ревизии `field_definitions[].schema_revision` и проверки существующих значений; нельзя молча обесценивать старые данные. Для `plugin:<...>`-типов `constraints` принадлежит контракту плагина: ядро сохраняет непрозрачный JSON по R-09/O-13, не выдаёт его за валидированные стандартные ограничения.
11. **Разделение V2/V3, диагностика и тесты:** V2 проверяет форму типизированного `constraints`, формат чисел/дат/OptionID и допустимость ключей; V3 — совместимость dimension/unit, значение/границы, уникальность options, enum membership, корректность default и scope. Неизвестные единицы явно помечать `unverifiable`, а не молча пересчитывать. Добавить positive/negative тесты mm↔cm, несовместимых единиц, неизвестных кодов, абсолютной температуры/интервала, сохранения decimal `1.500`, диапазонов int64, дата/время, Unicode length, deprecated enum, отсутствующего значения vs default, отсутствующего unit при физической величине и round-trip без переписывания ZIP.

**Открытые поддетали внутри X-02:** точная грамматика/реестр `dimension`, нормативное решение по физическому `default`, используемый парсер UCUM и таблицы конверсии, точные ограничения на длину строк и ключей (O-17), формализованный список разрешённых `constraints` и его расширение для плагинов. Их нельзя считать закрытыми на основании утверждения одиннадцати принципов X-02. Не допускать завершения Schema 1.0 без полной фиксации этих деталей.

**Предлагаемые файлы при последующем применении:** SPEC §8/§9.2; SCHEMA `$defs.fieldDefinition`, `$defs.metadata.custom_values`, новые `$defs.fieldConstraints*`; V2/V3, UI-редактор полей, матрица приёмки, ADR после ADR-0036, дополнительные schema/semantic/roundtrip тесты; правила `O-13/S7` сохраняются.

## O-18 — APPROVED / УТВЕРЖДЕНО: защищённая история и `compacted_ranges` (11 принципов, 2026-11-10)

**Статус:** все **11 принципов утверждены** пользователем («принято», 2026-11-10). Они обязательны к будущему применению в SPEC/SCHEMA/ADR/V2–V4. Документы и исходный репозиторий `e2472e9` ещё не изменены. Отдельные поддетали, перечисленные ниже, остаются открытыми.

**База в `e2472e9`:** SPEC §11 и §11.1, SCHEMA `$defs.history` / `$defs.revisionRecord` (у range есть `{from_revision,to_revision,summary?}`, но `summary` свободный объект), ADR-0035 п. 5, ADR-0036 п. 4 и R-07. Обязателен `asset_created` ревизии 1, при независимой копии там зафиксирована родословная; в P0 компактизация не исполняется. Не заменять старые положения общим разрешением «удалить историю».

**Одиннадцать утверждённых принципов:**

1. **Полное покрытие ревизий.** В `history` все ревизии `1..asset.revision` представлены **ровно один раз**: либо индивидуальной `entries[].revision`, либо одним `compacted_ranges[]`-интервалом. Нет пропусков, пересечений и повторов; оба массива упорядочены по начальной ревизии, V3 проверяет интервалы без разворачивания огромного диапазона в память.
2. **Обязательные крайние записи.** Ревизия `1` всегда отдельная запись `asset_created` (включая `details.creation_kind`, `details.source_asset` при independent_copy). Последняя ревизия всегда отдельная запись с `revision == asset.revision`, её timestamp совпадает с `asset.modified_at` (O-14). Ревизии 1 и текущая не входят в compacted range.
3. **Консервативный защищённый набор событий:** никогда не компактизировать `asset_created`, `format_migrated`, `provenance_changed`, `history_compacted`; также запись любой `operation`, у которой неизвестна семантика, и записи с изменениями `file_remove` / с другими историческими или происхожденческими фактами, для которых не доказано сохранение данных в `historical_files`, `origin`, `inputs` или иных нормативных реестрах. Для `session_committed` проверять каждый вложенный `changes[]`, а не только общий `operation`.
4. **Ограниченная семантика `operation`.** Нормативный базовый словарь из черновика: `asset_created`, `files_changed`, `metadata_changed`, `groups_changed`, `previews_changed`, `provenance_changed`, `field_definitions_changed`, `extension_data_changed`, `format_migrated`, `history_compacted`, `session_committed`. Для иных корректных записей нужен явно именованный контракт или сохранение как непрозрачных; неизвестное имя не делает информацию пригодной для свёртки. Точная закрытость словаря и словарь `changes[].kind` требуют отдельной формальной проверки, не разрешать произвольное выполнение кода.
5. **Нормативная форма сводки:** каждый compacted range имеет `from_revision`, `to_revision`, `summary:{revision_count, operation_counts?}`. `revision_count == to_revision-from_revision+1`, `operation_counts`, если есть, даёт точные неотрицательные счётчики известных операций, сумма которых равна revision_count; никаких выдуманных детальных изменений, operation ID или timestamps удалённых записей. `summary` — **сводка, не замена доказательной первичной истории**.
6. **Только смежные допустимые интервалы.** Компактировать можно лишь последовательность полных, уже существующих и разрешённых к удалению отдельных записей. Между защищёнными событиями диапазон обрывается; ранее свёрнутые диапазоны не объединять с новыми без явно проверенной политики сохранения полной сводки. `operation_id` удалённых записей не переиспользуются, а их повторное выполнение нельзя выводить из отсутствия записи.
7. **Операция компактизации — отдельная ревизия.** Она создаёт запись `operation=history_compacted`, собственный `operation_id`, timestamp, явные диапазоны, повышает `asset.revision` на 1 и обновляет `asset.modified_at`; файловые SHA/байты не меняет. В P0 операция не запускается автоматически и не входит в обязательную реализованную функциональность.
8. **Томбстоуны и происхождение не компактизируются вместе с историей.** `historical_files[]` сохраняет `id`, `removed_at_revision` и доступные `last_known_*` независимо от очистки записей `history`; связи `derived_from`, `inputs.entries`, `claims.evidence` к FileID продолжают разрешаться через `files ∪ historical_files`. Нельзя восстанавливать или придумывать отсутствующие байты исходников.
9. **Неизвестные расширения и идемпотентность — fail-closed.** Не сворачивать историю, если неизвестное расширение может ссылаться на удаляемую запись/OperationID, если есть незавершённая pending-op/активная транзакция, или если механизм восстановления/повтора опирается на individual `operation_id`. Неизвестные JSON-числа и payloads остаются под R-09/O-13/S7.
10. **Верификация и атомарность.** V2 проверяет форму и безопасные числовые границы; V3 — полное покрытие, порядок, защищённые события, непротиворечивую сводку, связи tombstones и `asset.modified_at`. Перед постоянной фиксацией ZIP — V1–V4, atomic write + rollback; повторная запись без логических изменений не должна добавлять ревизию.
11. **Тесты и ограничения выпуска.** Фикстуры: rev1, rev1+last, корректный диапазон, gap/overlap, range включает rev1/last, неверный count, protected event, смешанный `session_committed`, удалённый файл с `historical_files`, исторический `derived_from`, compaction failure/rollback, независимая копия. Пока реальная компактизация не реализована, чтение/валидация корректной структуры разрешены, но публикация версии 1.0 требует закрытия точной схемы и семантики. Сама реализация compaction может оставаться вне P0.

**Открытые уточнения даже после принятия общих принципов:** строгий JSON-словарь `changes[].kind`; допустимость plugin-namespaced `operation`; можно ли сохранять дополнительную диагностику по `timestamp`/`operation_id` в сводке; доказуемый критерий «нет скрытых ссылок на OperationID» в расширениях. Не объявлять их решёнными только из-за общего согласования.

**Файлы для применения:** SPEC §11 / §11.1 и §12 (V3); SCHEMA `$defs.history`/`$defs.revisionRecord` + новая typed `$defs.compactedRangeSummary`; ADR после ADR-0036; `historical_files` и derived_from V3; jobs/recovery contract; schema semantic ZIP tests/acceptance matrix. ТЗ, ADR, Schema, код в исходном `e2472e9` данным журналом не меняются.

## O-15 — APPROVED / УТВЕРЖДЕНО: непрозрачные ZIP-записи, raw-копирование и отчёт V4 (11 принципов)

**Статус:** все **11 принципов O-15 явно утверждены** пользователем («согласовано», 2026-11-10). Это обязательные требования для последующего применения в ADR/SPEC/V1–V4/ZIP-сервисе и тестах; репозиторий `e2472e9` ещё не изменён. Открытые поддетали ниже сохраняют статус OPEN.

**Основание в снимке `e2472e9`:** README, таблица «Хранилище, безопасность, история», O-15; SPEC §1 и §12; ADR-0006 (raw-copy в протоколе commit), ADR-0035 п. 7 (полная проверка зарегистрированных потоков, CRC/размер для opaque без претензии на SHA). Для **вновь создаваемого** 1.0 ZIP незарегистрированные записи в `content/`, `generated/`, `extensions/` недопустимы, произвольные записи в корне также не допускаются. Для старых или будущих контейнеров безопасные неизвестные данные не удаляются молча; при невозможности гарантировать сохранение применяется read-only. Не отменять эти базовые правила.

**Одиннадцать утверждённых принципов:**

1. **Три класса записей.** `registered` — поток описан в `files[]` либо `extensions.*.attachments[]` и проверяется по нормативной модели; `known_structural` — разрешённая системная запись контейнера (`manifest.json`, маркер при его наличии); `opaque` — существующая ZIP-запись, которой текущая версия не может дать нормативную интерпретацию. Классификация применяется к конкретному контейнеру и не даёт права генерировать новые opaque-записи в формате 1.0.
2. **Разделить соответствие формату и возможность чтения.** Новый нормативный ZIP 1.0 обязан удовлетворять строгой структуре. Незарегистрированные пути в `content/`, `generated/`, `extensions/`, произвольные записи корня и неизвестные пространства имён в *новом* 1.0 запрещены. Старые или будущие контейнеры с непрозрачными безопасными записями могут открываться в режиме ограниченной совместимости; это не превращает их в полностью валидный ZIP 1.0.
3. **Сохранение без молчаливой очистки.** Неизвестные байты, записи и метаданные существующего контейнера не удалять и не «нормализовать» при чтении/экспорте. Если безопасная операция записи не доказана, оставить контейнер read-only и предложить неизменённое копирование/экспорт. Изменение версии формата или выкидывание неизвестных данных автоматически запрещено.
4. **Raw-copy — оптимизация, не сертификат целостности.** Сохранять неизменённый сжатый поток при разрешённой операции; при этом проверять согласованность локального заголовка и центрального каталога, путь/флаги/метод, исходный размер и CRC. CRC необходимо вычислять по *распакованному* содержимому поддерживаемым декодером: совпадение записанных CRC в заголовках без проверки потока недостаточно. Unsupported method, encryption, неоднозначный descriptor или небезопасные флаги => нельзя обещать полную проверку или безопасную перезапись.
5. **Раздельные уровни доказательства.** Для зарегистрированных потоков перед фиксацией сохраняется требование полного V4: размер + CRC + SHA-256 несжатого содержимого. Для перенесённых opaque-потоков, если они допустимы режимом совместимости, подтверждается не более размера + CRC; SHA-256 *не объявляется проверенным* без отдельного известного хеша/контракта. CRC32 — контроль случайного повреждения, не криптографическое доказательство подлинности.
6. **Явный отчёт V4 по каждому потоку.** Должны различаться `verified_sha256`, `verified_crc_size_only`, `unverifiable/unsupported`, `failed`; отдельно указывается полнота проверки на уровне контейнера. Нельзя объединять `verified_crc_size_only` и `verified_sha256` в один безусловный `valid`. Ошибка чтения, конфликт каталогов или неверный CRC — отказ, а не успешный частичный результат.
7. **ZIP extra fields и комментарии — не мусор.** Сохранять неизвестные extra fields локальных/центральных заголовков и комментарии, *если* есть доказанный безопасный способ; известные структурные поля (например, ZIP64 со смещениями/размерами) обрабатываются по своему контракту при перепаковке. Неизвестное поле может зависеть от смещений, подписи или формата упаковки; его слепой перенос в изменённые заголовки запрещён. При неразрешимой зависимости — read-only, не silent drop.
8. **Безопасность ZIP без исключений.** Дубликаты/коллизии путей, абсолютные пути, traversal, симлинки/специальные записи с опасной семантикой, конфликт локального/центрального имени, шифрование, zip bomb и ресурсные нарушения не получают исключений из-за `opaque`. Для чтения допускается только безопасный режим анализа; при угрозе извлечения или копирования — fail-closed. Численные пороги остаются O-17.
9. **Совместимость будущих версий — отдельный gate.** Если контейнер объявляет более новую `format.version.minor` или неизвестный major, использовать матрицу `recognize/read/validate/write/migrate` из `versioning.md`. Сам факт способности копировать сжатые байты не разрешает переписывать манифест в неизвестной версии или «понижать» его до 1.0. Перед независимой копией/миграцией применять также R-07/O-07 и O-13/S7.
10. **Транзакционный commit без потери исходника.** Разрешённый rewrite должен сохранять все допустимые непрозрачные данные, пройти структурную и физическую проверку в доступном уровне и только после этого атомарно заменить ZIP по ADR-0006. Нельзя выдавать частичную проверку opaque за полноценный SHA-контроль. Если для операции требуется нормативный 1.0 ZIP, а существующие неизвестные записи делают его невозможным, операция блокируется до явной безопасной миграции.
11. **Тесты и диагностические фикстуры.** Нужны корректные зарегистрированные записи, безопасные legacy opaque в корне/нестандартном префиксе, неизвестная запись в запрещённом пространстве 1.0, future minor, ZIP64 extras, неизвестные extra fields/комментарии, изменённые смещения, CRC mismatch, header divergence, unsupported compression, encrypted entry, traversal/collision, duplicate name, decompression bomb, metadata-only rewrite, raw-copy без потери и инъекция сбоя до атомарной замены. Проверять отчёт V4 и то, что исходник остаётся неизменным после отказа.

**Открытые вопросы внутри O-15:** точный реестр допустимых корневых служебных записей и ZIP extra fields; формальная граница между legacy-совместимостью и нормативной валидацией 1.0; контракты структурных полей и комментариев с внешними смещениями/подписями; варианты `unverifiable` в отчёте V4; численные лимиты O-17. Предложение не переопределяет запрет неизвестных записей в новых 1.0-контейнерах.

**Файлы для последующего применения (O-15 утверждён):** SPEC §1/§12, ADR-0006/ADR-0035 п. 7 и новая ADR, `versioning.md`, ZIP reader/writer + V1/V4, `jobs_and_sessions.md` (commit), тесты совместимости и восстановления, `acceptance_matrix.md`. Проверить отсутствие противоречий с O-13/S7, R-07/O-07 и O-17.

## O-16 — APPROVED / УТВЕРЖДЕНО: точный `uint64` в перестраиваемом SQLite-индексе (11 принципов, 2026-11-10)

**Статус:** пользователь явно утвердил все одиннадцать принципов O-16 сообщением «согласовано» 2026-11-10. **Выбор канонического десятичного TEXT, а не SQLite INTEGER/REAL, принят как целевой контракт.** Реальная SQL-реализация, запросы, C++-конвертеры и тесты ещё не изменены и подлежат независимой проверке. Исходные ТЗ, ADR, SCHEMA и код не изменены.

**Основание в `e2472e9`:** SPEC §2 определяет канонический `uint64` как десятичную JSON-строку диапазона `0…18446744073709551615`. В `schemas/sql/index.sql` размеры `assets.zip_size`, `files.size`, `input_entries.size`, `input_objects.size` имеют SQLite `INTEGER` (диапазон знакового int64); индексные выражения `files_name_size`, `input_entries_name_size`, `input_entries_crc_size`, `input_objects_name_size` предполагают числовую сортировку этого столбца. В `README.md` вопрос O-16 остаётся открытым. Индекс является производным от ZIP, а не источником истины.

**Одиннадцать утверждённых принципов — обязательны для сверки и последующего применения:**

1. **Единый точный контракт размеров во всём диапазоне uint64.** Значения из манифеста — канонические десятичные ASCII-строки `^(0|[1-9][0-9]*)$` со строгим пределом `18446744073709551615`. Нельзя округлять, насыщать (`clamp`) или молча подменять значением `9223372036854775807`; чтение/запись через `double` запрещены.
2. **В SQLite для потенциально полного `uint64` использовать `TEXT` с `COLLATE BINARY`, а не `INTEGER`/`REAL`.** Утверждён тот же канонический десятичный формат без ведущих нулей; допускается сохранение имени столбца `size` при изменении его типа (или `size_dec`, если это потребуется для согласованного API — только с обоснованием совместимости). Требование охватывает `files.size`, `input_entries.size`, `input_objects.size`, `assets.zip_size`.
3. **Сохранить отличие неизвестного размера от нуля.** В допускающих неизвестность таблицах `NULL` остаётся `NULL`, а известный нулевой размер — строкой `'0'`. Не синтезировать значение из CRC, отсутствующего тома или размера файла при отсутствии надёжных данных.
4. **Строгая проверка данных и при индексации, и в SQL.** C++ проверяет канонический формат и переполнение через точный разбор `uint64_t`, передавая значение через `sqlite3_bind_text`; читает через `sqlite3_column_text` с точным разбором, не через `sqlite3_column_int64`. SQLite-схема по возможности содержит `CHECK` на ASCII-цифры, отсутствие ведущих нулей, длину до 20 и граничную максимальную строку. Тип TEXT сам по себе недостаточен для защиты от ошибочного `1e20` или `-1`.
5. **Числовой порядок и сравнения задаются явно.** Для канонических положительных/нулевых десятичных строк порядок `ORDER BY length(size), size COLLATE BINARY` соответствует unsigned numeric order. Фильтр `size >= N` проверяет `(length(size), size)` относительно `(length(N), N)`; лексический `ORDER BY size`, `size > ?`, `CAST(size AS INTEGER)` и SQLite `SUM(size)` не имеют корректной полной `uint64`-семантики.
6. **Сохранить производительность предусмотренных поисков.** Перепроектировать `files_name_size`, `input_entries_name_size`, `input_entries_crc_size`, `input_objects_name_size` с учётом длины десятичной строки и её значения; применять expression indexes `(length(size), size)` либо вычисляемые индексируемые поля, а не обычные числовые индексы старой схемы. Проверить реальные `EXPLAIN QUERY PLAN` для поиска/сортировки по размеру.
7. **Агрегации выполняются в проверяемой точной арифметике.** Сумма размеров нескольких файлов может превысить `uint64` даже при допустимости каждого значения. Не использовать без проверки `SUM()`/`TOTAL()` SQLite для точных общих размеров; вычислять в C++ с контролем переполнения либо с отдельным большим целочисленным представлением; при переполнении показывать явное диагностическое состояние, а не число-заменитель.
8. **Индексатор не должен отклонять валидный ZIP только из-за диапазона SQLite INTEGER.** Перестроение индекса из `manifest.json` сохраняет каждое допустимое uint64 значение точно. Нарушение формата или диапазона исходного значения — ошибка формата/V2, а не основание подгонять его при индексации.
9. **Изменение индексной схемы не изменяет ZIP-ассет.** Поскольку `index.sqlite` полностью производный, совместимую миграцию индекса предпочтительно выполнять перестроением без роста `asset.revision` или `modified_at`; `userdata.sqlite` и `state.sqlite` не переписывать без отдельной причины.
10. **Учитывать потребителей индексных размеров.** UI, поиск, фильтры, отчёты, FTS и API не должны скрыто приводить эти TEXT-значения к double/signed int64. Для вычислений физических файловых размеров нужно различать значение, заявленное манифестом, и фактически подтверждённое V4; наличие очень большого размера в манифесте не доказывает реального существования такого файла.
11. **Тесты точности, порядка и восстановления.** Положительные значения `0`, `9223372036854775807`, `9223372036854775808`, `18446744073709551615`; отрицательные `-1`, `01`, `1.0`, `1e5`, `18446744073709551616`; различение `NULL`/`'0'`; SQLite exact round-trip; фильтры и сортировка, использование индексов, вычисление сумм с overflow, перестроение индекса, Windows/Linux и сохранение ZIP без изменения ревизии.

**Особая оговорка по границе утверждения:** принцип 2 **уже утверждён**: целевой способ хранения — канонический десятичный `TEXT`. Физическая схема `CHECK`, способы индексирования, C++ API и план запросов должны быть испытаны исполнителем. Альтернативный `BLOB` или пара 32-битных чисел не могут молча подменить утверждённый контракт: для такой замены требуется отдельное мотивированное предложение и новое согласование владельца.

**После итоговой проверки и разрешения на применение нужно изменить:** `schemas/sql/index.sql` (столбцы + индексы + CHECK); описание индексатора/SQLite-контракта в SPEC и ADR; библиотечные функции `uint64↔decimal TEXT`; размерные фильтры и агрегаты; проверки D-/M-уровня. В нормативном ZIP 1.0 представление `uint64` **не меняется**. Вопрос O-17 о ресурсных лимитах и S7 о точных неизвестных JSON-числах остаются отдельными.
