# Формат ZIP-ассета — актуальная рабочая консолидация v0.2

**Статус:** рабочая спецификация по всем согласованиям MF-01–MF-12, **НЕ опубликованная нормативная JSON Schema формата 1.0**.  
**Дата:** 2026-11-06.  
**Основа:** раздел §19.4.1–19.4.19 ТЗ v1.8, подготовленный после согласований.  
**Важно:** устаревший bundle v0.1 содержит несовместимые условные значения FormatID, ID и history. Не использовать его schema/ZIP как golden fixtures будущего формата.

**Постоянный FormatID:** `urn:uuid:0d40b3a5-39ae-48e6-a8e8-da18b1b8c128`.

## Структура носителя

```text
<AssetID>.zip
├── manifest.json                      # обязательно, один корневой UTF-8 JSON
├── content/<InputID>/<safe-path>       # оригинальные полезные файлы, байты неизменны
├── generated/...                       # постоянные производные файлы, зарегистрированы в files
└── extensions/<ExtensionID>/...        # регистрируемые бинарные вложения плагинов
```

Внешние исходные упаковочные ZIP/RAR/7z целиком внутрь не вкладываются. Логические данные ассета находятся в ZIP, индекс SQLite перестраиваем; постоянные *библиотечные* пользовательские данные сохраняются/резервируются отдельно.

## Действующий предметный контракт (согласованные принципы)

### 19.4. Нормативные принципы ZIP-манифеста (подразделы согласованы; JSON Schema ещё не опубликована)

#### 19.4.1. Физическая структура ZIP [СОГЛАСОВАНО]

1. В корне ровно один нормативный `manifest.json` (UTF-8 JSON). Содержимое исходных файлов помещается в `content/<InputID>/<safe-relative-path>`, где InputID стабилен и уникален; оригинальные имена/пути остаются в записях входа.
2. Постоянные производные пользовательские файлы могут храниться в `generated/` и регистрируются в `files`. Внешние автоматически перестраиваемые кэши ZIP не изменяют.
3. Физические пути безопасны и однозначны, используют `/`; запрещены traversal/absolute paths/конфликты. Исходная и физическая идентичность файла раздельны.
4. Неизвестные безопасные записи уже существующего ZIP сохраняются, если совместимы с безопасной пересборкой; при невозможности — ограничение записи, а не молчаливая потеря.
5. Исходные **внешние упаковочные** ZIP/RAR/7z не включаются в ZIP-ассет целиком. Вложенный архив как **самостоятельно выбранный полезный файл** допускает отдельное явное решение `preserve`, не являющееся безусловным сохранением внешней упаковки.

#### 19.4.2. `format` и `asset` [СОГЛАСОВАНО]

1. `format.id` — неизменяемый идентификатор семейства; версия — `{major, minor}`. Окончательное значение `format.id` уточнено §19.4.14.
2. `asset.id` — UUIDv4 в стандартном нижнем регистре; не меняется при переносе, переименовании, экспорте, обычном изменении и миграции. **Независимая новая копия** получает новый AssetID.
3. `asset.revision` — положительное JSON-целое с началом 1; одна успешная транзакция постоянного изменения = один инкремент; неуспех/no-op/внешний кэш/переиндексация не изменяют ревизию. Контроль конкурентных правок использует ожидаемую ревизию.
4. Совпадение ID и ревизии не доказывает байтовую или семантическую идентичность независимо изменённых контейнеров; необходимо сравнивать фактическое состояние.
5. Системные моменты времени используют RFC 3339/UTC. Для нового ассета задаются `created_at`, `modified_at`; старые поддерживаемые версии проверяются по их собственным правилам. `LibraryID` не входит в идентичность ZIP.
6. **Уточнённое решение:** миграция постоянной схемы увеличивает ревизию (§19.4.7/§19.4.18); чистая перепаковка ZIP без изменения постоянных данных — нет.

#### 19.4.3. `origin` и `inputs` [СОГЛАСОВАНО]

1. `origin.sources[]` хранит ноль или несколько необязательных источников распространения/происхождения; авторство не выводится из названия сайта или публикации.
2. Входной комплект `inputs[]` отделён от источника; имеет InputID, исходные технические объекты `objects[]` (файл, каталог, архив, один многотомный архив с томами) и записи `entries[]` всех обнаруженных объектов.
3. Для исходных многотомных архивов сохраняются идентичности томов, их имена, размеры и SHA-256; для вложенных архивов — связь с родителем и действие `extract`/`preserve`/`exclude`.
4. Результаты записи: `included`, `included_renamed`, `excluded`, `unavailable`, `failed`, `not_processed`. Причины исключения/проблемы сохраняются; включение переименованного файла не меняет его байты.
5. Стабильные SourceID, InputObjectID, SourceEntryID, InputID; подтверждение/наблюдение/предположение различаются. Условное или частично известное происхождение не мешает созданию ассета.
6. Результат исходного импорта историчен: первоначальная запись остаётся после замены/удаления текущего файла. По умолчанию строгий импорт, частичный — только с явным разрешением.
7. Абсолютные приватные локальные пути по умолчанию не записываются в переносимый манифест; исходные относительные имена и недекодируемые байты имён сохраняются безопасным представлением.

#### 19.4.4. `files` [СОГЛАСОВАНО]

1. `files[]` — **единственный текущий** реестр полезных файлов ZIP; FileID — независимый от хеша и пути стабильный идентификатор, не переиспользуется. Два файла с одинаковыми байтами остаются двумя FileID.
2. При перемещении и **явной замене содержимого** FileID сохраняется, SHA-256 отражает новые несжатые байты; удаление исключает запись из `files`, сохраняя обязательную историю.
3. Каждый текущий файл имеет FileID, уникальный безопасный `storage_path`, `size_bytes` и SHA-256 (64 lowercase hex). Размер обязан описывать несжатый поток точно. Источники/входы связываются по историческим ссылкам.
4. `origin_kind`: `imported`, `user_added`, `generated` — способ появления, не тип/назначение файла. `derived_from` описывает FileID + SHA-256 исходных версий; историческая ссылка допускает удалённый источник.
5. Быстрая/выборочная/полная проверка целостности различаются; полная сверяет байты, размер, CRC и SHA-256.
6. Неизвестные физические записи сохраняются безопасно; текущие группы/предпросмотры/`file_ref` не могут ссылаться на отсутствующий текущий FileID.

#### 19.4.5. `groups` и `previews` [СОГЛАСОВАНО]

1. Группы логические, не совпадают с деревом ZIP или категориями библиотеки; имеют GroupID, в первой схеме **не более одного непосредственного родителя**, произвольную глубину без циклов. Пересечение групп реализуется через общее членство FileID без копирования файлов.
2. `file_refs` — **непосредственное** членство; рекурсивные множества вычисляются. Тип группы расширяемый; отдельная пространственная сцена и трансформации не приравниваются к логической группе.
3. `previews` регистрирует назначения файла по FileID, PreviewID, необязательный `primary_id` и связи с группами; отсутствие предпросмотра допустимо.
4. Оригинальные изображения остаются в `content/`; постоянные сгенерированные превью регистрируются в `files` (обычно `generated/`), миниатюры каталога — вне ZIP.
5. Хеши источников, параметры рендера и источник генерации при наличии позволяют выявить устаревание, но не приводят к удалению результата автоматически.
6. Удаление группы/назначения предпросмотра не удаляет физический файл. Для удаления файла активные ссылки приводятся в корректное состояние в одной транзакции.

#### 19.4.6. `metadata`, `extensions`, `history` [СОГЛАСОВАНО]

1. Нормативные системные поля отделяются от необязательных описательных метаданных и расширений; описательные значения допустимы на уровне `asset`, `group`, `file` без дублирования.
2. Необязательные стандартные поля: title/description/authors/publisher/license/tags/categories/links/даты. Лицензия структурна; отсутствие лицензии не трактуется как свободное использование. Категории содержат переносимые иерархические пути, теги сохраняют исходное написание.
3. Пользовательские определения полей переносятся с ассетом; поддерживаются типы/единицы/перечисления/области применения. Наследование вычисляется, а не размножает значения по объектам.
4. Именованные, версионированные расширения сохраняют неизвестные JSON-значения **без семантических потерь**; пользовательские подтверждения нельзя тихо перезаписывать результатами анализа.
5. `history` — компактные события успешных транзакций, начальная запись содержит реально применимые версии приложения/профиля/обработчиков/правил исключения; не является хранилищем старых байтов или полных снимков.
6. Текущие и исторические ссылки различаются; ошибки/неудачные задания не увеличивают ревизию и находятся вне журнала постоянных ревизий.

#### 19.4.7. Валидация и совместимость [СОГЛАСОВАНО]

1. Четыре смысловых уровня: V1 ZIP/JSON syntax, V2 JSON Schema, V3 семантические связи, V4 физическое содержимое. Быстрый, выборочный и полный режимы проверки целостности независимы от разбиения V1–V4.
2. `manifest.json` ровно один, JSON UTF-8, без дублирующихся ключей, с ограничениями на разбор. Версионированные JSON Schema фиксируются после публикации; строгие системные ключи не смешиваются с namespaces расширений.
3. Семантический валидатор проверяет уникальность ID/путей, наличие активных ссылок, отсутствие циклов групп, связи input/source, историю/компактные диапазоны.
4. Полная проверка фактических байтов, размеров, CRC и SHA-256 обязательна **перед фиксацией созданного/изменённого ZIP**, но не при каждом открытии.
5. Неизвестные безопасные ZIP-записи сохраняются или блокируют небезопасную запись; неподдерживаемая версия допускает лишь подтверждённые операции (`recognize/read` не равно `write`).
6. Изменяющая постоянную схему миграция повышает ревизию; чистая перепаковка — нет. Миграция неизвестных данных не должна терять информацию.
7. Нужны positive/negative golden ZIP, round-trip serialization с сохранением неизвестных чисел/Unicode, перенос в чистую библиотеку, стабильные машинные коды diagnostics и указание фактического уровня проверки.
8. **Открыто для реализации:** численные лимиты, опубликованная JSON Schema, матрица поддерживаемых старых версий.

#### 19.4.8. MF-01: UUID локальных объектов [СОГЛАСОВАНО]

AssetID, InputID, FileID, GroupID, PreviewID, SourceID, InputObjectID, SourceEntryID используют **UUIDv4**, в стандартном lowercase-представлении. Они не зависят от имени, пути, номера позиции или содержимого; при независимом добавлении создаётся новый UUID. **FieldID имеет отдельную namespaced-схему** (§19.4.10). Позднее в этой же ветви согласованы OperationID и AttachmentID (также UUIDv4).

#### 19.4.9. MF-02: точные числовые значения [СОГЛАСОВАНО]

1. Все размеры несжатых файлов, исходных архивов/томов и прочие размеры **в байтах** сериализуются как канонические десятичные строки `uint64`: `^(0|[1-9][0-9]*)$` и диапазон `0..18446744073709551615`. Числа JSON, ведущие нули, знак и экспонента для размера запрещены.
2. Неизвестный размер — отсутствие необязательного поля, не строка `"0"`; текущий файл всегда имеет размер, включая нуль.
3. Версия формата и ревизия — JSON integers с точным диапазоном до `2^53-1`; ревизия от 1, major/minor от 0.
4. Значение пользовательского `integer` — точная десятичная строка `int64`, `decimal` — точная десятичная строка с точкой и без локали/NaN/Infinity. Неизвестные JSON-числа расширений, включая числа за пределами `2^53`, не теряют точность.
5. Значение и единица измерения хранятся отдельно; смена настроек единиц UI ZIP не изменяет. Границы и канонические формы подтверждаются тестами.

#### 19.4.10. MF-03: пользовательские поля [СОГЛАСОВАНО]

1. `field_definitions[]` — переносимые определения; `asset.metadata.custom_values`, `groups[].metadata.custom_values`, `files[].metadata.custom_values` — значения, ссылающиеся на определения по FieldID. Не используемым полям не требуется фиктивное присутствие в каждом ZIP.
2. FieldID: `user:<UUIDv4>` либо `plugin:<plugin-id>:<field-key>`; пространство `core:` зарезервировано. Имя поля не определяет идентичность и может меняться.
3. Определение включает `id`, `schema_revision`, `name`, `type`, `scopes`, опциональные description/dimension/unit/constraints/options/default; область применения ограничивается одним из asset/group/file по определению.
4. Отсутствие значения, пустая строка, нуль, false и пустое множество — **разные состояния**. Default не превращается автоматически в подтверждённое значение.
5. `enum/multi_enum` используют стабильный OptionID, не label; при удалении используемого варианта данные не теряются автоматически.
6. Изменение определения увеличивает его `schema_revision`, конфликт по совпавшему ID и разной схеме не объединяется без проверки; изменение типа может потребовать явной миграции. Переносимое определение не зависит от библиотечного справочника.
7. Плагин может использовать стандартные типизированные поля или специальные `extensions`; данные плагинов не уничтожаются без соответствующего обработчика. SQLite — перестраиваемый производный индекс этих значений.

#### 19.4.11. MF-04: типы полей и единицы [СОГЛАСОВАНО]

| Тип | Нормативное представление значения |
|---|---|
| `string`, `text` | JSON Unicode string |
| `integer` | Каноническая десятичная строка signed int64 `^(0|-?[1-9][0-9]*)$` с проверкой диапазона |
| `decimal` | Точная десятичная строка без экспоненты; сохраняются значащие для записи хвостовые нули; отрицательный нуль не используется канонически |
| `boolean` | JSON boolean |
| `date` | Григорианская календарная дата `YYYY-MM-DD`, без часового пояса |
| `datetime` | RFC 3339 с нормализацией к UTC (`Z`), не приравнивается к `date` |
| `enum` | Строковый стабильный OptionID |
| `multi_enum` | Массив **уникальных** OptionID, семантически множество |
| `url` | Строка URI; при валидации не выполняются сетевые запросы |
| `file_ref` | UUIDv4 **текущего** FileID |

1. Исходные временные метки с неизвестным часовым поясом/точностью не преобразуются в выдуманные UTC-моменты; первоначальные данные сохраняются отдельно.
2. Физическая размерность (`dimension`), значение (`value`) и единица хранения (`unit`) разделены. Для числовой физической величины единица **у значения** обязательна; единица в определении — рекомендуемая. Конвертация только между совместимыми размерностями, с учётом смещений температур; неизвестная единица сохраняется и не конвертируется автоматически.
3. `constraints` типизированы; ограничения обязательного заполнения для бизнес-профилей не являются условием структурной валидности ZIP. Строки Unicode сохраняются без принудительной нормализации и транслитерации.
4. Устаревший, но объявленный вариант `enum` сохраняет корректность; новые OptionID не получают исторически использованную идентичность. Неизвестные специализированные типы плагинов сохраняются без потерь, но не редактируются универсальным редактором.
5. **Открыто:** точный словарь единиц (UCUM — кандидат), контракт расширенных ограничений, механизм безопасного round-trip неизвестных типов.

#### 19.4.12. MF-05: evidence, review и конфликтные метаданные [СОГЛАСОВАНО]

1. Раздельны значение, `method` получения, `evidence` и `review` пользователя. Методы расширяемы: `user_input`, `file_metadata`, `document_extraction`, `filename_inference`, `directory_inference`, `content_analysis`, `geometric_measurement`, `external_metadata`, `ai_inference`, `imported_metadata`, `unknown`.
2. Доказательства ссылаются по FileID/SourceEntryID/InputObjectID/SourceID, когда возможно, не копируя исходные объекты целиком.
3. Для одного поля допускается выбранное значение и альтернативные утверждения. Пользовательское подтверждение/исправление не стирает первоначальный метод получения; подтверждённое значение не перезаписывается автоматически новым анализатором.
4. Необязательная `confidence` — точная decimal-строка в диапазоне `0..1`; не универсальная вероятность между различными обработчиками и не единственный критерий выбора значения.
5. Результат анализатора может содержать ID/версию обработчика, FileID и SHA-256 **конкретной входной версии**. Устаревание вычисляется из зависимостей; старое значение не удаляется автоматически.
6. Анализ в кэше не меняет ревизию; запись результата/доказательства в ZIP меняет. Подтверждение пользователя не требует публикации его имени, ОС/компьютера, email.
7. Конфликт определяется по FieldID/полю, объекту и совместимым единицам, а не просто разнице любых чисел. `history` фиксирует изменения, но не копирует все старые тексты.
8. **Уточнение расположения §19.4.19:** `metadata.claims` — отдельный от текущего значения массив. Открыты точный контракт связи и объём хранения альтернатив.

#### 19.4.13. MF-06: жизненный цикл файлов [СОГЛАСОВАНО]

1. FileID (логическая идентичность), SHA-256 (состояние байтов), SourceEntryID (исторический вход) независимы. `files` содержит только текущие файлы.
2. Добавление: новый FileID и при необходимости новый входной комплект, в том числе позднее после первоначального импорта. Замена/перемещение существующего логического файла сохраняет FileID; замена фиксирует старый/новый SHA-256. Исходный результат SourceEntryID→FileID не переписывается при замене.
3. Удаление удаляет полезные байты и актуальную запись из нового ZIP, но сохраняет исторические данные; действующие file_ref/group/preview связи либо корректно изменяются в той же транзакции, либо операция отменяется.
4. Исторические ссылки на удалённые FileID допустимы для `inputs`, `history`, `derived_from`; активные ссылки — только на `files`. Минимальный tombstone-реестр `historical_files` не хранит старые байты и не смешивается с `files`.
5. Производные файлы хранят FileID+SHA-256 исходного содержимого; удаление источника не удаляет производный файл. Состояние зависимости `current/stale/unverifiable/source_missing` вычисляется, а не становится единственным неизменным флагом.
6. Повторное обычное добавление того же содержимого после удаления создаёт **новый** FileID; удалённые идентификаторы не рециклируются, даже после компактизации.
7. Неизвестные обязательные зависимости могут блокировать разрушительную операцию. Все действия выполняются через единый транзакционный сервис хранения.

#### 19.4.14. MF-07: FormatID, namespace и пути [СОГЛАСОВАНО]

1. Постоянный формат: **`urn:uuid:0d40b3a5-39ae-48e6-a8e8-da18b1b8c128`**. `format.version.major/minor` не зависит от версии приложения, AssetID и revision.
2. Распознавание собственного ZIP: корректный ZIP, один корневой `manifest.json`, совпавший `format.id`, совместимая либо определённо неподдерживаемая версия. Само наличие файла `manifest.json` не гарантирует принадлежности к формату.
3. Нормативные ключи JSON зарезервированы; пользовательские поля используют `field_definitions/custom_values`; плагины — `extensions.<ExtensionID>`.
4. `ExtensionID` — устойчивый безопасный ASCII lowercase идентификатор, предпочтительно в обратной доменной нотации, **не доказательство авторства или доверия**. `plugin:<plugin-id>:<field-key>` отражает идентификатор пространства имён поля.
5. Версии формата контейнера, схемы данных расширения и реализации плагина независимы.
6. Физическое пространство `extensions/<ExtensionID>/` предназначено для внутренних бинарных данных; необязательные данные расширения не становятся автоматически записями `files`.
7. Новые контейнеры не размещают произвольные дополнительные файлы в корне; неизвестные безопасные записи ранее существующих контейнеров не удаляются молча. Пути во всех пространствах (`content/generated/extensions`) проходят общую проверку.
8. **Открыто:** точная regex ExtensionID, кодирование/Unicode/case-коллизии путей и детальная регистрация специальных ZIP-записей.

#### 19.4.15. MF-08: история и компактизация [СОГЛАСОВАНО]

1. История состоит из `RevisionRecord` и вложенных `ChangeRecord`; одна зафиксированная транзакция соответствует ровно одной ревизии; разные изменения одной транзакции не создают дополнительных ревизий.
2. Успешный `OperationID` — UUIDv4, не замена revision. История создания обязательна для новых ассетов, с применимыми версиями приложения, профиля, обработчиков, правил; ложные значения для неприменимых полей не создаются.
3. Классификация событий расширяема: create/file add/remove/replace/move, metadata, group, preview, provenance, field definitions, format migration, history compaction. Прежние полезные файлы и длинные тексты по умолчанию не копируются.
4. Исходное происхождение, исторические идентичности и ключевые события не удаляются обычной компактизацией; P0 **не выполняет автоматическую компактизацию**.
5. Компактизация может заменить подробные события непересекающимися сводными диапазонами без перенумерации исторических ревизий; успешная фиксация компактизации увеличивает `asset.revision` и создаёт техническое событие.
6. `historical_files` — самостоятельный логический реестр, независимый от компактизации событий. Невыполненные задания/восстановление SQLite не создают фиктивной ревизии.
7. Исправление ошибочных метаданных не требует бессрочно хранить прежний текст/персональные данные; строго обязательные сведения об операциях происхождения сохраняются отдельно.
8. **Открыто:** минимальный обязательный набор некомпактируемых событий, численные критерии и точные поля компактных диапазонов.

#### 19.4.16. MF-09: постоянные данные расширений [СОГЛАСОВАНО]

1. `content/` — полезные исходные файлы; `generated/` — постоянные производные полезные файлы; `extensions/<ExtensionID>/` — специализированные служебные бинарные данные.
2. Новые постоянные бинарные вложения регистрируются в `extensions.<ExtensionID>.attachments[]`, с уникальным путём, размером несжатого потока `uint64`-строкой и SHA-256; участвуют в полной проверке целостности.
3. Расширение может объявлять зависимости от FileID+хеша, GroupID и иных нормативных сущностей. Различаются зависимости `none`, `declared`, `unknown`; отсутствие декларации **не доказывает** `none`.
4. Если плагин отсутствует, базовое чтение/экспорт доступны; неизвестные данные сохраняются без потерь. Изменение, способное повредить неизвестные зависимости, запрещается до подтверждения безопасности.
5. Неизвестные физические записи допустимы для ограниченного чтения/диагностики, при записи должны сохраняться несжатые байты и существенные ZIP-атрибуты; если безопасная пересборка невозможна, контейнер read-only.
6. ZIP не выполняет код расширения автоматически. Служебные вложения не являются автоматически `files`; их явное удаление изменяет revision/history, очистка внешнего кэша — нет.
7. **Уточнение §19.4.19:** зарегистрированное постоянное вложение получает **AttachmentID UUIDv4**, имеет одного владельца ExtensionID; совместное физическое владение несколькими расширениями в первой версии не поддерживается.
8. **Открыто:** полный контракт attachments/dependencies, особенности ZIP extra fields и безопасного копирования неизвестных записей.

#### 19.4.17. MF-10: безопасность архивов и ресурсные лимиты [СОГЛАСОВАНО]

1. Недоверенные **входные** ZIP/RAR/7z и **нормативные** ZIP-ассеты используют общую защиту, но разные допустимые профили. Внешние пути не служат путями прямой записи на диск.
2. Исходные имена, включая сырые байты недекодируемого имени, сохраняются как provenance при безопасном переименовании; запрещены traversal, absolute paths, неоднозначные компоненты и перезапись из-за коллизии.
3. Symlink/reparse/special files не разыменовываются и не материализуются автоматически. В нормативных потоках `content/generated` это не обычные полезные файлы.
4. ZIP-bomb защита: независимые лимиты размера записи, суммарного фактического распакованного объёма, числа записей/файлов, глубины вложений, памяти, времени и временного диска; нельзя верить лишь заявленному размеру/коэффициенту сжатия.
5. Лимиты многоуровневые (безусловные + профили + настройки), но их увеличение не снимает проверки путей, структуры и целостности. Вложенные архивы используют **общий** бюджет задания.
6. Потоковые импорт, экспорт, ZIP64 и SHA-256 без загрузки всего файла в RAM; многотомные архивы проверяются как единое целое, отсутствие томов не скрывается.
7. Исходные зашифрованные архивы допускаются при поддержке обработчика; пароли не помещаются в ZIP/логи. Нормативные записи ZIP-ассета 1.0 **не зашифрованы**. Минимальные ZIP-методы — Stored/Deflate и ZIP64.
8. Проверяются ZIP-заголовки, JSON-структура (включая глубину/размеры до чрезмерных аллокаций); `invalid`, `unsupported`, `incomplete` различаются.
9. Превью, анализ и конвертация также работают с недоверенными входными данными под контролем ресурсов; полноценная ОС-песочница **не обещана** в P0.
10. Строгая незавершённая операция не фиксирует усечённый ZIP; частичный импорт возможен только с явным разрешением и полным контролем результата.
11. **Открыто:** конкретные лимиты, алгоритм кросс-ФС коллизий, перечень шифров входных архивов, степень изоляции обработчиков.

#### 19.4.18. MF-11: эволюция и миграции [СОГЛАСОВАНО]

1. Раздельны версии приложения, формата `major.minor`, схем plugin-data. Major — breaking; minor — совместимое изменение структуры, **не гарантирующее старому приложению право записи**.
2. Матрица возможностей `recognize/read/validate/write/migrate` задаётся явно для каждой поддерживаемой версии. Схемы опубликованных версий, их семантика, ZIP-правила и golden fixtures фиксированы; validation полностью офлайн.
3. Миграции — явный граф переходов source→target. Цепочка над временным состоянием атомарно фиксируется **одним** ZIP commit и **одной** новой ревизией; промежуточные шаги не считаются зафиксированными состояниями.
4. История фиксирует source/target, шаги и инструмент. ID и несжатые полезные байты сохраняются; изменение содержания файлов — отдельная явная операция, не скрытая schema migration.
5. Неизвестные расширения не теряются; если зависимости невозможно безопасно сохранить — отказ. Миграция plugin-data отдельно от core-format также повышает revision при фиксации.
6. Обычное чтение/обновление программы не запускает массовую миграцию. Downgrade запрещён автоматически; специальный экспорт в старую версию — отдельная операция с валидацией.
7. Проверка expected revision, прерывание без частичного результата и no-op без инкремента обязательны. Совместимость доказывают неизменяемые эталоны прошлых версий.
8. **Открыто:** глубина поддержки прошлых версий, политика errata схем, прямые миграции в обход промежуточных и формат отчёта сохранности.

#### 19.4.19. MF-12: согласованная топология `manifest.json` [СОГЛАСОВАНО]

**Фиксируем расположение, роли и обязательность разделов.** Пока нет опубликованной нормативной схемы 1.0, ниже — согласованный контракт для подготовки такой схемы, а не утверждение её готовности.

| Корневой ключ | Структура | Обязателен для новых контейнеров |
|---|---|---|
| `format` | object: `id`, `version.major`, `version.minor` | **Да** |
| `asset` | object: `id`, `revision`, `created_at`, `modified_at`, optional `metadata` | **Да** |
| `origin` | object: `sources[]` | Нет |
| `inputs` | array of input sets | Нет |
| `files` | array of **current** file records (может быть `[]`) | **Да** |
| `historical_files` | array of deleted-FileID tombstones | Нет |
| `groups` | array | Нет |
| `previews` | object: optional `primary_id`, `items[]` | Нет |
| `field_definitions` | array | Нет |
| `extensions` | object keyed by ExtensionID | Нет |
| `history` | object: `entries[]`, optional `compacted_ranges[]` | **Да** |

1. Нормативное ядро использует **отсутствие необязательного поля** вместо универсального JSON `null`, если для null не описан особый смысл.
2. Новый `asset` содержит `id`, `revision`, `created_at`, `modified_at`. `created_at` — создание логического ассета, а не текущего ZIP; при чистой перепаковке timestamps не обновляются.
3. `metadata` допускает `title`, `description`, `authors[]` (с ролью), `publisher`, структурную `license` (`name`, необязательное SPDX expression, url, notice, file_ref), `tags[]`, `categories[]` с иерархическим `path`, `links[]` с `rel`, `custom_values[]`, `claims[]`. Автор и источник распространения не отождествляются, неизвестная лицензия не означает свободного использования. Отсутствующие сведения не заполняются фиктивными значениями.
4. `origin.sources` и `inputs` независимы. Каждый InputID и каждый InputObjectID/SourceEntryID/SourceID — UUIDv4. `inputs.entries` описывает историю импорта и статусы всех обнаруженных записей.
5. Запись `files[]`: `id`, `storage_path`, `size_bytes`, `sha256`, `origin_kind` обязательны; optional `metadata`, `derived_from`, роль/тип. Файл не дублируется в логических группах, preview или пользовательских значениях.
6. `historical_files[]` — **отдельный корневой реестр** удалённых файлов; в новой tombstone-записи обязательны `id` и `removed_at_revision`, известные `last_known_sha256/size_bytes/storage_path` сохраняются при штатном удалении. Не может совпадать по ID с текущим `files`.
7. `groups[]`: `id`, `name`, `type`, optional `parent_id`, `file_refs[]`, `metadata`. Отсутствие `parent_id` обозначает корневую группу; прямые file_refs не включают автоматически дочерние. Порядок ссылок не задаёт семантику.
8. `previews`: `items[]` с `id` (PreviewID), `file_id` (текущий FileID), optional `group_refs[]`; optional `primary_id` должен существовать в `items`. Один файл может иметь несколько назначений.
9. `field_definitions` содержит определения, а `metadata.custom_values` — значения; каждый FieldID разрешим. Числа, даты, единицы и перечисления — по §19.4.9–11.
10. **Доказательства физически размещаются в `metadata.claims[]` целевого asset/group/file**, отдельно от текущего стандартного поля или `custom_values`. У `claim` есть собственный UUIDv4, target, relation `supports_selected`/`alternative`/`rejected`, method/review/evidence; при `supports_selected` значение не дублируется как второй нормативный источник истины. Конфликт и актуальность выводятся из утверждений и зависимостей.
11. `extensions.<ExtensionID>.attachments[]`: для каждого зарегистрированного вложения AttachmentID UUIDv4, путь `extensions/<ExtensionID>/...`, `size_bytes`, `sha256`; одна физическая запись принадлежит одному ExtensionID, без совместного владения в первой версии. `dependencies` описывает декларируемые/неизвестные/отсутствующие зависимости.
12. `history` — object с `entries[]` (RevisionRecord + OperationID) и optional `compacted_ranges[]` (непересекающиеся диапазоны). Ревизия 1 хранит событие создания; последняя ревизия — подробную запись; подробные записи и диапазоны не перекрываются; номера не изменяются при компактизации.
13. Порядок ключей JSON несущественен; порядок отдельных массивов определяется их семантикой. Сериализатор не создаёт фиктивные значения и не теряет неизвестные числовые значения/расширения; активные ссылки проверяются до commit.
14. Отсутствие произвольных `origin`, `inputs`, `groups`, `previews`, `field_definitions`, `extensions` допустимо. **`format`, `asset`, `files`, `history` обязательны.**

**Минимальный иллюстративный манифест новой модели (ещё не golden fixture):**

## Граница публикации v1.0

В этом документе описаны **утверждённые принципы и структура**, но ещё нет окончательного валидатора, фиксированной схемы и исчерпывающей таблицы полей. Перед выпуском нормативного v1.0 необходимо: сформализовать `origin/inputs` и raw filenames, `claims`/review, units/constraints и unknown types, extensions dependencies/AttachmentID, историю/компактизацию, UUID/ExtensionID regex, ZIP portability/security, матрицу read/write/migrate; затем создать golden ZIP и negative fixtures и проверить чтение/запись SHA-256.

Список разночтений прежних редакций и проверки приведены в `AUDIT_REPORT.md`.
