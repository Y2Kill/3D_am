2. publisher
Принимаю объект:
{
  "publisher": {
    "name": "Example Publishing",
    "url": "https://example.com"
  }
}

Уточнения к схеме:
- name — обязательная непустая строка.
- url — необязательная строка с проверкой синтаксиса URL.
- Сам объект publisher необязателен.
Здесь признаю замечание проверяющего: в опубликованном тексте ТЗ v1.8 структура publisher действительно не определена однозначно. Я ошибочно представил её как уже закреплённую.

3. groups[].file_refs
Принимаю предложенную модель.

Оба варианта читатель интерпретирует одинаково:
{
  "name": "Components"
}

5. S7 — точное сохранение JSON-чисел
Это наиболее серьёзное замечание отчёта.

Согласованное нами требование сохранения неизвестных данных без потерь не гарантируется обычным использованием DOM nlohmann/json.

Здесь нужна небольшая техническая оговорка: целые числа больше 2^53 не обязательно теряют точность в nlohmann/json, поскольку библиотека поддерживает 64-битные целочисленные типы. Проблема прежде всего касается дробных значений, целых за пределами поддерживаемых диапазонов и сохранения исходной десятичной записи.

Например:
{
  "value": 12345678901234567890.000000000000000001
}

Нельзя допустить, чтобы при изменении названия ассета это значение превратилось в округлённый double.

Для S7 предлагаю более строгий критерий, чем просто успешный разбор JSON:

Неизвестное числовое значение должно сохранять исходную числовую лексему при цикле:

read → modify unrelated field → serialize → read

Проверять следует также большие показатели степени, отрицательный ноль и дробные значения с завершающими нулями.

Сравнить nlohmann/json с собственным механизмом сохранения лексем и RapidJSON. Выбор библиотеки делать по результатам испытаний.

До получения положительного результата S7 запретить запись контейнеров с неизвестными числовыми значениями, точность которых текущий сериализатор не способен гарантировать.

Статус nlohmann/json в libraries.md перевести из окончательно принятого в условно выбранный.

Это не означает обязательной замены всей JSON-библиотеки: возможно, достаточно специализированного механизма для непрозрачных данных расширений.
