# План реализации (вехи и задачи)

**Принципы:**
- Каждая веха заканчивается **работающим вертикальным срезом** с тестами и CLI-командой.
- GUI подключается к уже проверенному ядру (ТЗ 3.1.4–5).
- Номера критериев приёмки (К-n) — из ТЗ §15 (v1.7: 1–136; 112–136 — [ПРЕДЛОЖЕНИЕ]). Нефункциональные требования §14 — ID `NFR-14.x.y`; статусы — в [`acceptance_matrix.md`](acceptance_matrix.md).
- Числовые нормативы не назначаются до измерений (ТЗ §14.9.13); план — [`nfr_measurement_plan.md`](../architecture/nfr_measurement_plan.md).
- Обязательные проверки затронутой функциональности должны пройти до её выпуска (ТЗ §12.9.11). Покрытие сценариев отслеживается в [`coverage_matrix.md`](coverage_matrix.md).

Изменения после ТЗ v1.3–v1.5 (отчёт [03](../reports/03_TZ_v1.3-1.5_vs_prepared.md), Р-4):
- новые спайки S5+ и S6;
- `am analyze` в M3;
- отдельная веха M-S «Сценарии»;
- тестовые плагины — вместе с плагин-хостом;
- LLM — последней.

Изменения после ТЗ v1.7 (отчёт [04](../reports/04_TZ_v1.7_vs_prepared.md), Р-9): резервное копирование (ADR-0030), владелец записи и режим «только чтение» (ADR-0031), модель ошибок (ADR-0032, сделано), ресурсы и свободное место (ADR-0033), английский UI и i18n (ADR-0034); критерии 112–136 распределены по вехам.

## M1 — Предметная модель и контейнер → К-3, 6, 8, 20, 21, 22, 25, 26, 87–89, 107, 113, 116, 117, 122, 128
- `am_domain`: модель ассета, `Manifest` (ordered_json, типизированные аксессоры, сохранение неизвестных полей), статусы значений (ADR-0028), проверка JSON Schema, устойчивые `FileID`/`GroupID`.
- `am_storage`:
  - `ZipWriter`/`ZipReader` (minizip-ng);
  - протокол фиксации (ADR-0006);
  - **`AssetRepository`** — единственный писатель, `ChangeRequest`, блокировки, `AssetSnapshot` (ADR-0025);
  - `Verifier` на 3 уровня;
  - проверка свободного места и `max_file_size` до и во время фиксации (ADR-0033), `LibraryMode`/`StorageCapabilities` (ADR-0031);
  - защита от архивных атак при чтении: пути, лимиты, специальные объекты (К-128).
- CLI: `am asset create <files…> -o x.zip`, `am asset inspect`, `am asset verify --level quick|full`, `am asset extract`.
- Тесты:
  - round-trip, неизвестные поля, повреждённые ZIP;
  - kill-тест фиксации, в том числе **при открытом читателе**;
  - две одновременные записи — сериализация и конфликт ревизий;
  - заполненный том: запись отклоняется, последний ZIP цел (К-117);
  - потоковое хеширование: RAM не растёт с размером файла (К-116).
- Инфраструктура тестов (ADR-0029):
  - генератор `tools/fixtures/` и `tests/fixtures/<case>/expected.json`;
  - схема `schemas/expected.v1.schema.json`;
  - реестр `tests/real/registry.json`;
  - отчёт трассировки `tools/coverage/req_report.py` с тегами `RecordProperty("req", …)` и сверкой с `acceptance_matrix.md`.
- Пользовательский `CHANGELOG.md` (английский) — с первым выпускаемым CLI (ADR-0034).
- Реестр версий [`versioning.md`](../specifications/versioning.md) обновляется вместе с форматами.

## M2 — Библиотека и индекс → К-7, 17, 23, 24, 31, 65, 90, 91, 108, 112, 114, 118–120, 123, 126, 127
- `am_storage/db`: 3 базы (`schemas/sql/*.sql`), миграции, `IJobStore`, библиотечные данные, корзина.
- `am_services/catalog`: `Indexer`, `rebuild`, `sync` (stat-сверка + efsw), шина событий после фиксации, импорт готового ассета, ID-конфликты.
- **Межбиблиотечное перемещение** (ADR-0025 п. 9).
- **Владелец записи библиотеки** `.am/library.lock`, режим «только чтение», статус `unavailable` для отключённого носителя, диагностика `StorageCapabilities` (ADR-0031).
- **Резервное копирование** (ADR-0030): полная копия с манифестом `am-backup` v1, согласованная точка, 4 уровня проверки, восстановление в новую библиотеку, отдельных ассетов и `userdata`.
- Генератор синтетических библиотек 100…250 000 ассетов `tests/performance/gen_library` и первый замер по плану измерений (К-112).
- CLI: `am library init|open|rebuild|sync|verify|trash|restore|purge|move|backup|restore-backup|verify-backup`, `am add-ready <zip>`.
- Тест самодостаточности: ZIP переносится в чистую библиотеку, ID, ревизия, метаданные и история сохраняются.

## M3 — Исследование, импорт и задания → К-1, 2, 4, 5, 11, 32–39, 72, 99–107, 110, 115, 121, 124
- `am_jobs`: персистентная очередь через `IJobStore`, пулы, `needs_decision`, безопасные точки.
- `jobs::ResourceManager` (ADR-0033): лимиты CPU/чтение/запись/внешние процессы, приоритет интерактивных задач, состояния `waiting_resources`/`resource_error`/`cannot_continue_safely`, профили `economy|balanced|performance|custom`, ограничение повторов.
- Журналы (spdlog): структурированные записи с полями `am::Error`, ротация, лимиты объёма, обезличенный экспорт диагностики (ТЗ §14.4.9).
- `am_storage/archive`: бэкенд по итогам S1.
- **`am analyze`** (ADR-0029):
  - уровни `inventory|structure|deep`;
  - `report.md` + `report.json` по схеме `schemas/analysis.v1.schema.json`;
  - статусы полноты, лимиты профиля, `--redact`, кэш и выборочный повторный анализ.
- `am_services/import`: весь конвейер из `import_pipeline.md`, профили (правила источника, `[volumes]`, `[limits]`), профиль `telegram`.
- CLI: `am import scan <dir> --profile telegram --plan out.json`, `am import run --plan out.json`, `am jobs list|pause|resume|cancel|retry`.
- Тестовый корпус:
  - синтетические fixtures по матрице 16 сценариев;
  - реальные примеры через реестр, только чтение, пропуск при отсутствии коллекции.

## M5 — GUI: каталог → К-61–68, 15, 85, 134, 135
- Главное окно с docking.
- `AssetListModel`: ленивая подгрузка из SQLite, карточки и таблица.
- Навигация по библиотекам, категориям, тегам, источникам, коллекциям и сохранённым поискам.
- Быстрый и расширенный поиск.
- Теги: подтверждённые и предложенные (`index.suggestions`).
- Массовые операции через задания, корзина.
- Центр заданий и индикатор «Требуется решение».
- Меню и горячие клавиши строятся из реестра команд; рабочие пространства.
- Английский интерфейс, `tr()`/Qt Linguist, каталог сообщений по `message_id` (ADR-0034); HiDPI 100–200 %, клавиатура, статусы не только цветом, Qt Accessibility (ТЗ §14.8).
- **Безопасный запуск**: без необязательных плагинов и сценариев, без автопродолжения очереди, библиотека открывается только для чтения (ТЗ §14.4.10).

## CI (ТЗ §12.9.10, поэтапно)
- С M1: GitHub Actions или GitLab CI.
  - Матрица: `win-debug-min`, `win-cli`, `linux-min`, далее `linux-cli`.
  - ctest, включая `arch_check`.
  - Артефакты: JUnit XML и отчёт трассировки требований.
- Периодически и перед выпусками: шкала объёмов 100…250 000, импорт больших наборов, миграции, многосуточные тесты утечек RAM/VRAM/дескрипторов (ТЗ §14.4.8), fuzz-тесты парсеров (§14.6.12), матрица ФС (ADR-0031), проверка на реестре реальных данных (на машине с коллекцией).
- Сквозные строгие проверки, обязательные для каждой вехи (К-125, 130, 132, 133, 136): гарантии ФС, отсутствие сетевых запросов, совместимость форматов и миграций, запись в матрице приёмки.

## Порядок работы для каждого модуля (требование ТЗ 3.5.1)
1. Сверить раздел в `docs/research/libraries.md` и при необходимости дополнить: официальный источник, версия, лицензия, ограничения, статус.
2. Короткий спайк, если библиотека новая.
3. Последовательность работ:
   1. интерфейс в `include/am/<level>/…`, контракт — в `contracts/`, если его используют другие уровни;
   2. реализация;
   3. тесты с тегами требований;
   4. CLI-команда;
   5. документация;
   6. строка в `coverage_matrix.md` и/или `acceptance_matrix.md`;
   7. при изменении формата — строка в `versioning.md`.
