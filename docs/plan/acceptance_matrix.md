# Матрица приёмки (ТЗ §14.9.12)

Решение — отчёт 04, Р-8. Матрица связывает требование с проверкой:
- Requirement ID;
- конфигурация;
- набор данных;
- методика;
- метрика или порог;
- результат;
- статус.

Детализация 16 сценариев импорта (§13.2) ведётся отдельно — в [`coverage_matrix.md`](coverage_matrix.md). Здесь на неё даются ссылки по ID `SC-n`.

## Схема идентификаторов требований

| Префикс | Что обозначает | Пример | Источник |
|---|---|---|---|
| `K-<n>` | критерий приёмки §15 (1–136; 112–136 — [ПРЕДЛОЖЕНИЕ] v1.7) | `K-117` | ТЗ §15 |
| `NFR-14.<раздел>.<пункт>` | нефункциональное требование §14 | `NFR-14.4.2` | ТЗ §14.1–14.9 |
| `SC-<n>` | сценарий импорта (1–16) | `SC-6` | ТЗ §13.2, `coverage_matrix.md` |
| `R-<nn>[.m]` | утверждённое уточнение формата 1.0 (44 пункта) | `R-06.2` | [свод R-01…R-09](../tz/R01-R09_approved_handoff.md), ADR-0036 |

- Тесты помечают требования через `::testing::Test::RecordProperty("req", "<ID>")`. Если требований несколько, ID перечисляются через запятую.
- Отчёт трассировки `tools/coverage/req_report.py` (M1) собирает эти метки из JUnit XML ctest и сверяет их с этой матрицей.
- Номера пунктов ТЗ привязаны к версии ТЗ. При перенумерации в новой версии ТЗ ID в тестах обновляются вместе с матрицей.

## Статусы (ровно пять, §14.9.12)

| Статус | Значение |
|---|---|
| **не реализовано** | функциональности нет |
| **реализовано, не проверено** | код есть, проверки по методике нет или она не пройдена полностью |
| **соответствует** | проверка по методике пройдена на указанной конфигурации |
| **не соответствует** | проверка проведена, результат не удовлетворяет требованию |
| **неприменимо к конфигурации** | требование не относится к этой ОС, ФС или сборке |

**Правила заполнения:**
- Измеряемые показатели без согласованного порога записываются как «порог: [ОТКРЫТО]» ([план измерений](../architecture/nfr_measurement_plan.md)).
- Статус «соответствует» для них возможен только после фиксации порога владельцем.
- Неизвестное не записывается как проверенное.

## Промежуточное покрытие импорта: T-028

ImportScan.*, ImportPlan.* и cli_import_scan* проверяют только скан и план для SC-1, 2, 3, 5, 6, 8, 10, 11, 12, 13, 14, 15, 16: чтение источников, предложение границ, исключения, неподтверждённые тома, готовые ассеты и ранние совпадения. Это не завершение сценариев импорта: упаковка и фиксация run остаются следующей задачей. Статусы К-n в таблице по одному скану не повышаются. Фактические итоги — в отчёте T-028; подробности частичного покрытия — в coverage_matrix.md.

## Промежуточное выполнение импорта: T-030

ImportPlanView.*, ImportRun.*, cli_import_run: файловые и каталожные входы SC-1/2, размещение готовых ZIP SC-3, учёт Input/entries и происхождения (K-5), надёжность повторов и отмены (K-121, NFR-14.4.3). JobsExecutor на memory/SQLite проверяет ограниченную выборку K-115 и результаты failed/needs_decision со сбросом при новой попытке. ## ZIP-входы: T-031

ZipInput.*, ImportZipScan.*, ImportZipRun.*, ImportZipRepository.*, ImportZipPlan.* и cli_import_zip покрывают ZIP-подмножество K-5/K-6, SC-1/2/8/13 и NFR-14.4.3: план v2, учёт исходных записей, байты и V1–V4, строгий/частичный режим, свежесть, лимиты и повтор. Тест размера параметров сравнивает 10 и 10 000 записей. SC-7 покрыт только сохранением/исключением вложенного архива; SC-10 — сохранением специализированного ZIP-контейнера как файла. Полные сценарии и K-n по этому подмножеству не повышаются до завершённых. Раскрытие вложенных архивов, тома, RAR/7z и полный корпус остаются вне T-031; итоги прогонов — в отчёте задачи.
