# T-014. Правила V3 по ADR-0039 (кандидат нормативной схемы 1.0)

**Статус:** ready (T-005 принята 2026-11-13; выполняется до T-013) · **Веха:** M1 · **Основание:** ADR-0039 (отчёт 08, решение владельца 2026-11-12), ADR-0035 п. 7, T-011 (каталог правил V3)

## Цель

Владелец закрыл открытые поддетали формата 1.0 (ADR-0039). Управляющий уже применил их к документам и схеме: спецификация, кандидат схемы (`schemas/manifest-1.0.draft.schema.json`; имя файла сменится при публикации), пример, `schema_check` (149 случаев), значения `generation.tool` в тестах переведены на `core:`. Задача — привести **семантическую проверку V3** и связанный код к ADR-0039, чтобы golden ZIP (T-013) строились уже по окончательным правилам.

Порядок: T-005 → **T-014** → T-013. Если T-013 начнётся раньше, корпус придётся перегенерировать.

## Решения управляющего (не пересматривать в задаче)

1. **Физический `default` (ADR-0039 п. 2).** Правило `x02_physical_default_open` (сейчас `unverifiable`) **удаляется** из каталога. Вместо него в существующем правиле `field_default` (или новом `field_default_unit`, если так чище — обосновать в отчёте):
   - у `integer`/`decimal` с физической `dimension` (не `dimensionless`, ключ из базового реестра или неизвестный корректный) `default` обязан быть `{value, unit}` — иначе `error`;
   - у полей без `dimension` и с `dimension = dimensionless` `default` — строка типа; объект `{value, unit}` — `error`;
   - `value` проверяется как значение типа и по `constraints`; если единица `default` отличается от единицы границы — как сейчас для значений: точное совпадение кода проверяется, различие — `unverifiable` (пересчёта нет, ADR-0039 п. 3).
2. **Единица claim (п. 4).** Правило `claim_value_unit_unexpressible` **удаляется**. Новое правило `claim_value_unit`:
   - адресат `{kind: custom}` на поле `integer`/`decimal` с физической `dimension` и в claim есть `value` → `unit` обязателен (`error` при отсутствии);
   - `unit` в любом другом claim (другой адресат, нет `value`, нефизическое поле, `sourceClaim`) → `error`;
   - проверки кода единицы и сравнения с границами — как у `custom_values` (`value_unit_required`, `value_constraints`): тот же код, без копирования.
3. **`changes[].kind` (п. 5).** Новое правило `change_kind_fields`: для базовых видов обязательны поля: `file_replace` — `old_sha256`, `new_sha256` (SHA-256 hex); `file_move` — `old_path`; остальные базовые — только `kind` и `target` (лишние ключи допустимы, они непрозрачны). Неизвестные и плагинные виды не проверяются. `AssetRepository` уже пишет `file_add`, `file_remove`, `file_replace{old_sha256,new_sha256}`, `metadata_set` — сверить, что его вывод проходит правило; менять запись не нужно, если проходит.
4. **Каталоги в описи (п. 9).** Новое правило `input_directory_consistency` в группе правил `inputs`: в одном входе для каждой записи `entry_kind = directory` с `result = excluded` все записи, путь которых лежит внутри каталога (по исходному `path` с разделителем `/`, без нормализации регистра), тоже `excluded` — иначе `error`. Для `included_renamed` каталога: у потомков с `included`/`included_renamed` `storage_path` начинается с переименованного префикса — проверить, если префикс однозначно выводится из данных; если однозначно вывести нельзя — не проверять и указать это в отчёте (не выдумывать эвристику).
5. **Остальные пункты ADR-0039 кода V3 не требуют:**
   - п. 1 (`dimension`), п. 8 (`generation.tool`), п. 10 (`files[].type`) — проверяет схема (V2);
   - п. 3 — поведение уже такое (`x02_unit_conversion_open` остаётся `unverifiable`); сверить текст `detail`, что он не называет движок «открытым вопросом формата» — формулировка: пересчёт не реализован;
   - п. 6 — компактизации в P0 нет; правило для писателя, V3 не меняется;
   - п. 7 — добавить **тест** писателя ZIP: перезапись ассета, у одной записи которого есть чужой extra field (`0x5455`), — неизменённая запись переносится raw-копией с полем как есть, а в заголовки, которые писатель формирует заново, поле не попадает; вновь записанные записи содержат только `0x0001` при необходимости. Если тест показывает расхождение с ADR-0039 п. 7 — остановиться и описать.
6. **Каталог сообщений.** Новые `message_id` (`am.manifest.claim_value_unit`, `am.manifest.change_kind_fields`, `am.manifest.input_directory_consistency`, и для п. 1, если вводится отдельное правило) — в `resources/messages/en.toml` с английским текстом; удалённые правила — убрать из каталога; `message_catalog_check` PASS.
7. **Совместимость с T-011.** Общее число правил в `checked_rules` меняется (−2, +3 или +4) — обновить ожидания тестов, где перечислен состав каталога, и таблицу каталога в комментарии `semantics.cpp`, если она есть. Отложенное `tags_search_key` (O-08) остаётся отложенным.

## Тесты

Для каждого нового или изменённого правила — положительный и отрицательный модульный тест в `test_manifest_semantics.cpp` (`RecordProperty("req", "ADR-0039")`):
1. `default` физического поля: `{value, unit}` — OK; строка — `error`; объект у нефизического поля — `error`; единица отличается от единицы границы — `unverifiable`.
2. Claim: физическое `custom` + `value` + `unit` — OK; без `unit` — `error`; `unit` у `standard`-адресата — `error`; `unit` у `supports_selected` без `value` — `error`.
3. `changes[]`: `file_replace` без `new_sha256` — `error`; `file_move` без `old_path` — `error`; неизвестный `preview_set_primary` и `plugin:…` — без находок; результат `AssetRepository::change` с заменой файла — без находок.
4. Каталог `excluded` с потомком `included` — `error`; с потомками `excluded` — OK.
5. Тест писателя по п. 5 (extra field).
6. `validate_semantics` эталона (`schemas/examples/manifest-1.0.example.json`) — по-прежнему без `error`.

### Вопросы

**В-1. Доступ V3 к `file_replace.old_sha256/new_sha256` и `file_move.old_path`.**

Пункт 3 задачи требует проверять содержимое этих полей и принимать корректную историю, сформированную `AssetRepository::change`. Но `src/domain/manifest/codec.cpp`, `DocumentIndex::identify` (цикл по `history.entries[].changes[]`) считает непрозрачным **каждое** поле, кроме `kind` и `target`. Поэтому после `parse_manifest` строки `old_sha256`, `new_sha256` и `old_path` в `ManifestDocument::known()` заменены binary handles. Проверка через `is_string()`/`str()` в V3 отвергнет и корректную замену/перемещение; проверить только наличие ключа недостаточно для требования SHA-256 hex.

Факт подтверждён минимальной пробой на действующих библиотеках `am_domain`/`am_foundation`: эталонный документ дополнен корректными `file_replace` и `file_move`, затем разобран API кодека. Вывод (exit 0):

```text
old_sha256: binary
new_sha256: binary
old_path: binary
source values preserved: true
```

Контракт `include/am/domain/manifest/semantics.hpp` прямо задаёт V3 над known DOM: «opaque handles are never opened». Это также решение T-011, раздел о непрозрачных значениях: «Значения, скрытые кодеком как непрозрачные, V3 не раскрывает и не разбирает». Публичного read-only доступа к содержимому фрагмента в `ManifestDocument` нет. Сериализация всего документа и повторный разбор фрагментов внутри V3 обошли бы этот контракт, поэтому такой обход не реализован. Сам T-014 явно запрещает менять кодек.

**Требуется решение управляющего о границе известного и непрозрачного JSON для новых нормативных полей.** Предлагаемый вариант для рассмотрения: сделать известными только `old_sha256`/`new_sha256` у базового `file_replace` и `old_path` у базового `file_move`, сохранив остальные дополнительные ключи и неизвестные/плагинные виды непрозрачными. Для такого решения потребуется явно расширить раздел «Файлы» на кодек и его тесты и уточнить действующий контракт сохранности. После решения — продолжить T-014 в этой же ветке и выполнить все оставшиеся проверки; это предложение не применялось.
