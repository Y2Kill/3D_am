# T-004. Спайк S7: точные числа непрозрачного JSON

**Статус:** done (принята 2026-11-11) · **Веха:** M0 (спайк S7, блокирует утверждение формата 1.0) · **Основание:** ADR-0036 п. 6, ADR-0037 п. 4, журнал v0.11 «O-13 / S7» (9 утверждённых принципов: `docs/tz/RC1_decisions_after_e2472e9_v0.11.md`), SPEC §10 «Точность чисел», roadmap M0 «S7»

## Цель

Формат обещает: в непрозрачных участках манифеста (данные плагинов и расширений) каждое JSON-число сохраняется **исходной лексемой** — со знаком, видом экспоненты и завершающими нулями — и на прежнем месте. Пример: `12345678901234567890.000000000000000001`, `1e400`, `-0.0`, `1.500`. DOM `nlohmann/json`, выбранный условно, так не умеет. Спайк должен на фактах показать, какой механизм выполняет обещание в полном цикле «открыть ZIP → проверить → изменить известное поле → транзакционно записать → открыть снова». Отдельно спайк проверяет, совместим ли этот механизм с валидацией V2 по черновой схеме.

**Результат спайка — честная матрица альтернатив, а не «победитель».** Отрицательный итог по кандидату — тоже результат. Решение о механизме принимает управляющий отдельной ADR; исполнитель даёт наблюдения и данные.

## Решения управляющего (не пересматривать в задаче)

- **Спайк изолирован от продукта.** Это отдельный CMake-проект в `spikes/s7/` со своим `vcpkg.json` на **том же** `builtin-baseline` (`9eec002df1cd109f8f104cd966a763daf9751489`). Продуктовые `vcpkg.json`, `CMakeLists.txt`, `CMakePresets.json`, `src/`, `include/` не меняются. Код спайка не обязан следовать уровням ADR-0024 и не подключает `am_*`.
- **Загрузка портов vcpkg для спайка разрешена** (согласие владельца 2026-11-10 на зависимости vcpkg). Кэши — общие, в `.cache/` (как в `tools/build_cli.cmd`); установка — в отдельный `.cache/vcpkg-installed-s7`, сборка — в `build/s7`.
- **Кандидаты (все обязательны):**

  | ID | Механизм | Роль |
  |---|---|---|
  | A | `nlohmann::ordered_json` DOM | контроль: подтвердить проблему |
  | B | nlohmann SAX: лексема из обратного вызова (`number_float(val, s)`), свои узлы с лексемой | путь без смены библиотеки |
  | C | RapidJSON с `kParseNumbersAsStringsFlag`; вывод через `Writer::RawValue` только после строгой проверки лексемы | raw-number |
  | D | Собственный строгий токенизатор (RFC 8259): непрозрачное поддерево хранится как проверенный исходный фрагмент байтов или как дерево токенов с лексемами; известные поля — через nlohmann | точное непрозрачное поддерево / гибрид |
  | E | jsoncons с сохранением чисел без потерь (`lossless_number` / теги `bigint`/`bigdec`) | кандидат, у которого есть валидатор JSON Schema 2020-12 |

  Можно добавить свой вариант гибрида, если данные A–E на него указывают: отдельной строкой матрицы, с обоснованием.
- **Валидация V2 входит в спайк.** Черновая схема `schemas/manifest-1.0.draft.schema.json` написана на draft **2020-12** (`unevaluatedProperties`). Выбранный в `libraries.md` валидатор `json-schema-validator` (pboettch) работает поверх nlohmann. По имеющимся сведениям он поддерживает только draft-07 — **это нужно проверить фактом**. Испытываются:
  1. pboettch на черновой схеме: загрузится ли схема и верен ли результат на примере и фикстурах;
  2. валидатор jsoncons (2020-12) на тех же входах;
  3. для кандидатов без своего валидатора — проверка «теневого» документа: непрозрачные поддеревья заменены заглушками того же JSON-типа. Проверить, ограничивает ли схема значения в непрозрачных местах; если ограничивает, где именно.
- **Linux.** Код спайка переносим: CMake, C++20, без Windows API вне одного файла замера памяти. Прогон на Linux в приёмку T-004 **не входит**: он пойдёт через CI (T-005) или отдельную задачу. Итоговая ADR по S7 без Linux не пишется. Разрешено только **посмотреть**, есть ли уже на машине WSL с компилятором (`wsl --status`, `wsl -l -v`): ничего не устанавливать и не включать.
- **Пороги не назначаются** (ТЗ §14.9.13, O-17). Лимиты размера и глубины в спайке — параметры с пометкой `hypothesis`; в отчёт идут фактические замеры.

### 2. Фикстуры
- Генератор `spikes/s7/tools/gen_fixtures.py` (только стандартная библиотека, запуск `python -I`). Он пишет манифест **как текст**: модуль `json` теряет лексемы, поэтому собирать JSON-текст им нельзя. Основа — `schemas/examples/manifest-1.0.example.json`, только для чтения.
- **Все шесть мест непрозрачного JSON** (ADR-0037 п. 4) заполняются числами из набора:
  - `extensions.<id>.data` — два независимых расширения;
  - `custom_values[].value` с plugin TypeID;
  - `files[].generation.params`;
  - `claims[].value` при адресате с plugin TypeID;
  - `field_definitions[].default` и `constraints` plugin-типа;
  - `history.entries[].details` и дополнительный ключ в `changes[]`.

  В примере нет `custom_values`, `claims` и plugin-типа в `field_definitions`. Добавить их по SPEC так, чтобы документ проходил черновую схему; проверка — Python `jsonschema` из `.cache/pylib`, как в `tests/schema/schema_check.py`. **Если схема не допускает какое-то место — остановиться и описать в отчёте**, схему не менять.
- **Обязательный набор чисел (принцип 5):**
  - `12345678901234567890.000000000000000001`;
  - целые за пределами int64 и uint64, положительные и отрицательные;
  - `1e400`, `-1E-400`, `1E+2`, `-0`, `-0.0`, `0e0`, `1.500`;
  - дробь из 10 000 цифр; показатель степени из 1 000 цифр.

  Числа стоят во вложенных объектах и массивах, рядом с неизвестными ключами.
- **Недопустимые числа**, каждое в отдельном документе: `01`, `-01`, `+1`, `.5`, `1.`, `1e`, `1e+`, `-`, `NaN`, `Infinity`, `-Infinity`, `0x10`.
- **Отдельные документы:** дублирующиеся ключи — в непрозрачном месте и в известном; глубина вложенности 64, 1 000, 100 000; одна лексема 1 МиБ и 16 МиБ; манифест около 64 МиБ.
- Маленькие фикстуры коммитятся в `spikes/s7/fixtures/`. Большие и адверсариальные генерируются при сборке или тесте в `build/s7/` и **не коммитятся**.

### 3. Сценарий полного цикла (одинаковый для каждого кандидата)
Исполняемый файл `s7_run --candidate <A..E> --input <zip|json> [--out <dir>]`; один процесс на один запуск, чтобы мерить пик памяти и переживать падения.
1. Создать тестовый ZIP через minizip-ng: `manifest.json` и один файл содержимого.
2. Открыть ZIP, прочитать `manifest.json`.
3. Проверить V1 (синтаксис JSON) и V2 (схема) — способом, доступным кандидату (см. «Решения»).
4. Изменить `title` в известной части.
5. **Транзакционно** записать новый ZIP: временный файл в той же папке, затем атомарная замена. При ошибке исходный ZIP не меняется.
6. Открыть результат и сверить **все** непрозрачные числа: множество пар «JSON-путь → лексема» до и после совпадает побайтово. Неизвестные ключи не потеряны, новый `title` на месте.

**Fail-closed (принцип 7), общий для всех кандидатов.** Перед заменой файла выходной `manifest.json` разбирается строгим эталонным токенизатором, и множество «путь → лексема» сравнивается с исходным. Если оно не совпадает или кандидат не может разобрать вход, запись не выполняется: код ошибки «запись небезопасна», исходный ZIP остаётся побайтово прежним. Это не считается повреждением ZIP. Эталонный токенизатор — строгий RFC 8259, у кандидата D он может быть тем же кодом.

**Безопасность (принцип 8).** Лексема попадает в вывод только после строгой проверки грамматики числа, без текстовой подстановки. Тест: попытка передать в механизм вставки «лексему» `1,"x":2` или `1}` отвергается.

### 4. Замеры
- Время — медиана из 5 запусков: разбор, проверка V2, сериализация, полный цикл.
- Пик памяти процесса: Windows — `GetProcessMemoryInfo` (`PeakWorkingSetSize`, `PeakPagefileUsage`); Linux — `getrusage(RUSAGE_SELF).ru_maxrss`. Это единственный платформенный файл.
- На всех документах п. 2, включая адверсариальные. Падение или переполнение стека — это **результат**: строка матрицы, а не сбой теста.
- Записать конфигурацию: CPU, ОЗУ, Release или Debug (замеры — **Release**), версии портов.

### 5. Тесты ctest (в проекте спайка)
- `s7_guard`: для каждого кандидата при небезопасной записи исходный ZIP не меняется. A на числе `1e400` или `-0` обязан попасть в этот случай. Проверка: SHA-256 до и после.
- `s7_reject`: каждый кандидат, объявленный в матрице «строгим», отвергает все недопустимые числа п. 2. Если кандидат их принимает, это строка матрицы, а тест проверяет, что матрица говорит правду.
- `s7_matrix`: прогоняет всех кандидатов на всех фикстурах и пишет `build/s7/results.json`. Падает только при ошибке самого стенда, но не при отрицательном результате кандидата.
- `s7_fixtures_schema`: маленькие фикстуры проходят черновую схему (Python `jsonschema`), недопустимые — нет.

### 6. Результаты `spikes/s7/RESULTS.md` (русский)

## Решение управляющего по отчёту от 2026-11-10 (доработка)

**Статус: rework.** Стенд, эталонный токенизатор, защита записи, замеры и результаты по A, B, C, E и по V2 приняты: работа добротная. Что принято без пересмотра:
- pboettch на черновой схеме 2020-12 **ложно принимает** документ с запрещённым `unevaluatedProperties`;
- B теряет знак целого `-0` и отказывает на `1e400` ещё до SAX;
- C отказывает на диапазоне экспоненты;
- E теряет целый `-0`.

**Пробел.** Кандидат D ничего не сериализует. `edit_title` вклеивает новую строку на место токена `title` в исходном тексте, всё остальное остаётся побайтово прежним. Поэтому успех D почти предопределён и показывает механизм «правка исходного текста по месту», а не «известная часть в DOM + вставка непрозрачных фрагментов». B и C тоже меняют `title` этой вклейкой. Продукту нужны структурные правки (добавить запись истории, удалить элемент массива), а они сдвигают индексы. Сравнение по JSON-пути с индексами массивов в этом случае ложно считает данные потерянными.

**Что сделать** (в ветке `codex/T-004`: `git merge main`, без rebase):

1. **Новый кандидат D2 — гибрид:**
   - известная часть — `nlohmann::ordered_json`;
   - каждое непрозрачное поддерево заменено в DOM **заглушкой, которую нельзя подделать содержимым манифеста** и которая переживает сдвиг индексов. Например, значение `binary` nlohmann с номером фрагмента. Выбор и обоснование — в отчёт;
   - правки делаются в DOM;
   - вывод — **собственным писателем** обхода DOM, который на месте заглушки выводит исходный фрагмент. Каждый фрагмент перед выводом заново проверяется эталонным токенизатором как ровно одно полное JSON-значение (принцип 8). Текстовой замены по шаблону нет.
2. **Прежний D переименовать в D1** («правка исходного текста по месту») и оставить в матрице.
3. **Структурная правка в сценарии.** Помимо `title`:
   - добавить одну запись `history.entries[]` (только известные поля);
   - удалить один элемент массива, который стоит **перед** элементом с непрозрачными данными, чтобы индексы сдвинулись. Например, `custom_values[]` обычного поля перед значением plugin-поля, или другой элемент — по SPEC.

   Документ после правки должен проходить черновую схему. Если подходящей правки по SPEC нет — описать и остановиться. Структурная правка обязательна для D1, D2 и E. Для A–C — по возможности, иначе «н/д» с причиной.
4. **Сопоставление в защите записи — по устойчивому ключу владельца, а не по индексу.** Ключи:
   - id расширения;
   - FieldID для `field_definitions` и `custom_values`;
   - `file_id` для `generation.params`;
   - для claims и записей истории — их идентификатор по SPEC, а если его нет — описать в отчёте, какой ключ взят и почему.

   Внутри непрозрачного поддерева путь остаётся JSON-путём. Прежнее сравнение по индексам сохранить как дополнительную колонку для правки только `title`.
5. **Отчёт и `RESULTS.md`:**
   - строки D1 и D2 по всем столбцам матрицы, включая замеры на `lexeme_16m` и `manifest_64m`;
   - для E перечислить, на каких двух фикстурах он не прошёл;
   - отметить, что B и C меняли `title` вклейкой;
   - пик памяти 64 МиБ-манифеста (около 837 МиБ у всех) разложить: какая доля приходится на эталонный токенизатор и карты путей стенда, какая — на кандидата. Хотя бы оценкой.

6. **Linux-прогон в WSL (разрешение владельца 2026-11-10).** Пункт «Linux» из «Решений управляющего» в этой части заменяется следующим.
   - **Разрешено:**
     - запустить уже установленный дистрибутив WSL `Ubuntu`;
     - внутри него поставить через `apt` только недостающие инструменты сборки: `build-essential`, `cmake`, `ninja-build`, `git`, `curl`, `zip`, `unzip`, `tar`, `pkg-config`, `python3`, `python3-jsonschema`. Список фактически поставленных пакетов и их версии — в отчёт.
   - **Запрещено:**
     - менять настройки WSL и Windows (`.wslconfig`, `wsl --set-default`, `--set-version`);
     - ставить другие дистрибутивы;
     - трогать `docker-desktop`;
     - менять что-либо в Ubuntu сверх этих пакетов: профиль, глобальные конфиги git, системные службы.
   - **Всё рабочее — внутри папки проекта** через `/mnt/d/...` (путь с `!!!` — всегда в кавычках):
     - отдельный клон vcpkg на том же теге `2026.10.16` (`9eec002…`) в `.cache/vcpkg-linux`, клонировать из WSL, чтобы скрипты были с LF, и собрать `bootstrap-vcpkg.sh -disableMetrics`;
     - бинарный кэш `.cache/vcpkg-bin-linux`, asset-кэш — общий `.cache/vcpkg-assets`;

     - Windows-клон `.cache/vcpkg` не трогать.
   - **Скрипт `spikes/s7/build_linux.sh`** — аналог `build.cmd`, включая `--offline` с `x-block-origin`. В `.gitattributes` добавить `*.sh text eol=lf`; это разрешённое изменение файла вне `spikes/`.
   - **Прогон:** весь набор ctest спайка и `run_suite` для всех кандидатов, включая D1 и D2. Затем офлайн-повтор после удаления `build/s7-linux` и `.cache/vcpkg-installed-s7-linux`. Компилятор — GCC из Ubuntu, Release.

   - **По окончании** остановить дистрибутив: `wsl --terminate Ubuntu`. До начала он был остановлен.

## Критерии приёмки
