## Цель

ZIP внутри ZIP становится раскрываемым входом. Для каждого вложенного обычного архива доступны три действия по ТЗ §6.4.4: **раскрыть**, **сохранить целиком как файл** или **исключить**.

1. `am import scan` перечисляет записи вложенных ZIP любой глубины в пределах лимитов. К ним применяются правила исключения и решения, как к записям ZIP верхнего уровня.
2. `am import run` раскрывает вложенный ZIP по решению `expand`. Сам вложенный архив в ассет не попадает (ТЗ §6.4.1). Манифест хранит объект архива с родителем, размером, SHA-256 и `nested_action: extract`, а также все его записи.
3. Защита сохраняется на всех уровнях. Действуют лимиты глубины, фактически распакованных байтов и временного места, обнаружение циклов, а без управляемой временной области на диск ничего не извлекается. Достижение лимита фиксируется как неполнота, а не как успех (ТЗ §15.5).
4. Попутно: проверка внутреннего каталога 3MF, отложенная в T-031 (В-7).

RAR/7z внутри ZIP по-прежнему не раскрываются (M3b). Вложенный архив не превращается в отдельного кандидата.

## Решения

### 1. Доступ к байтам вложенного архива

ZIP читается с конца (центральный каталог), поэтому вложенному архиву нужен произвольный доступ.

- **Stored без шифрования** (`method = 0`): источник — поддиапазон байтов родителя, полученный через `raw_range`, без копирования. Перед использованием выполняется один проход, который вычисляет CRC-32 и SHA-256 записи. Несовпадение CRC даёт отказ записи, как в T-031.
- **Сжатая запись**: распаковывается во временный файл управляемой области библиотеки `<library>/.am/.am-tmp/import/<uuid попытки или скана>/`. SHA-256 считается при записи. Объём временных файлов учитывается лимитом `max_temp_bytes` (п. 4).
- **Без библиотеки** (`import scan` без `--library`) сжатый вложенный ZIP не перечисляется. Его запись получает `ask` (сохранить или исключить) с `explanation_id = nested_archive_temp_unavailable`, а скан получает `completeness = incomplete`. Stored-архивы перечисляются и без библиотеки.
- Временные файлы удаляются, когда уровень обработан, а также при завершении или отмене попытки, в том числе с ошибкой. Уборка при открытии библиотеки распространяется на подкаталоги `.am/.am-tmp/import/` старше `orphan_age` по тем же правилам, что и прочие сироты.
- **Граница слоёв.** Цепочка «архив → запись → вложенный архив» описывается в `storage/archive` без зависимости от `services`. Ориентир: у `ZipInputSnapshot` есть необязательный родитель `{snapshot, index}`, а у `ZipInput::open` есть перегрузка от `RandomAccessSource`. Точный API выбирает исполнитель. `asset_zip` по-прежнему не включает `archive/`.

### 2. Глубина и циклы

- Архив файловой системы имеет глубину 1, его вложенный архив — 2, и так далее. Раскрыть можно архив глубины `d`, если `d ≤ max_depth`.
- Действующее значение — минимум из профиля (`[nested] max_depth`) и безусловного потолка 8. Потолок — гипотеза O-17. Источник значения (`plan` или `unconditional`) пишется в `problem`, как в T-031 В-3.
- Архив глубже лимита не перечисляется. Его запись получает `ask` (сохранить или исключить) с `explanation_id = nested_archive_depth_limit`, скан получает `completeness = incomplete`, а `limits_hit` содержит `max_depth`.
- **Цикл.** Если SHA-256 вложенного архива совпадает с SHA-256 одного из его предков, архив не раскрывается. Запись получает `ask` с `explanation_id = nested_archive_cycle`. Решение `expand` для такой записи недопустимо.

### 3. Профиль и решения

- `[nested] action`: `expand` (синоним `extract`), `preserve`, `exclude`. Если действие не указано, ведёт себя как `ask`.
  - При `expand` и `ask` скан перечисляет вложенные ZIP в пределах лимитов. Решение по умолчанию — `expand` для `action = expand`, иначе `ask`.
  - При `preserve` или `exclude` содержимое не читается. Решение — `include` или `exclude`, как в T-031.
- Секция `nested` и `limits.max_temp_bytes` больше не попадают в `profile.not_applied[]`.
- В решениях записей архива появляется значение `expand`. Оно допустимо, только если вложенный архив перечислен в плане (`status = listed`) и это не цикл. Иначе разбор плана возвращает `am.import.plan_invalid` с указателем на решение.
- Правила исключения применяются **до** раскрытия на каждом уровне (ADR-0011). Пример: `__MACOSX/._inner.zip` с сигнатурой AppleDouble исключается и как архив не рассматривается.
- Записи вложенного архива принадлежат кандидату родителя. Новых кандидатов из вложенных архивов скан не предлагает.
- RAR/7z внутри ZIP: `ask` (сохранить или исключить) с `nested_archive_expand_unsupported`, как в T-031.

### 4. Лимиты

- Правила T-031 действуют на каждом уровне без изменений: по фактическим байтам, коэффициент сжатия на запись, время на контейнер.
- `max_unpacked_bytes` суммирует фактически распакованные байты **всех уровней** в одном `ZipInputJob`. Байт, распакованный из внешнего архива во временный файл, и байт, распакованный затем из вложенного, считаются оба. Именно так ограничиваются «бомбы» вида 42.zip.
- `max_temp_bytes` (теперь применяется) ограничивает пиковый суммарный объём временных файлов задания по фактически записанным байтам.
- Превышение любого лимита при run → `Errc::unsupported`, `am.import.archive.limit_exceeded` с указанием лимита, без автоповтора, как в T-031 В-8. При скане архив получает `status = limit_exceeded`, а `completeness = incomplete`.
- Глобальной квоты временного места на все одновременные задания в этой задаче нет (см. п. 10).

### 5. План v3

План v2 опубликован в репозитории и не меняется, его `additionalProperties: false` не допускает новых полей. Поэтому вводится версия 3 (`schemas/import-plan.v3.schema.json`), а строка в `docs/specifications/versioning.md` дополняется.

- `archives[]`:
  - источник — `oneOf`: `{node}` для архива файловой системы или `{entry}` (ID записи `archive_entries[]` родителя) для вложенного. Ключ архива — этот `node` или `entry`, отдельного поля `id` нет (уточнение при реализации 32a: идентификаторы узлов и записей не пересекаются, а T-031 уже ссылался на архив по узлу);
  - `depth` — целое ≥ 1;
  - `sha256` обязателен для перечисленного вложенного архива;
  - `access`: `range` или `temp` — только для вложенного.
- `archive_entries[].archive` ссылается на ключ архива (`node` или `entry`). Родитель стоит в `archives[]` раньше вложенного.
- Перечень решений дополняется значением `expand`, причины — `nested_archive_depth_limit`, `nested_archive_cycle`, `nested_archive_temp_unavailable`, `specialized_container_verified`.
- `profile.limits` содержит `max_depth` в той же форме, что прочие лимиты. `limits_hit` дополняется `max_depth` и `max_temp_bytes`.
- Скан пишет только v3. Run принимает v1, v2 и v3. План v2 выполняется как в T-031 и не раскрывает вложенные архивы. Неизвестная версия → `plan_invalid`.
- `schema_check` проверяет v1, v2 и v3 и печатает число планов по версиям. Статические случаи v1 и v2 сохраняются.
- Кандидат v1 с архивом по-прежнему даёт `archive_plan_rescan_required`.

### 6. Манифест: представление раскрытого архива (решение управляющего 2026-11-25)

Формат 1.0 знает `nested_action: extract`, но не говорит, какой `result` получает **запись родителя**, из которой раскрыт архив. Ни одно значение не подходит буквально:

- `included` по V3 требует `file_id`, а архив по ТЗ §6.4.1 не хранится;
- `not_processed` неверно, потому что запись обработана.

Решение в рамках опубликованной схемы, без её изменения:

- Запись родителя: `entry_kind: file`, `result: excluded`, `exclusion: {rule: "nested_extract", by: profile|user}` по источнику решения (как у прочих решений плана), без `file_id`. Смысл: собственные байты контейнера в ассет не вошли.
- Объект: `kind: archive`, `container: zip`, `name` (последний компонент пути записи), `size_bytes`, `sha256`, `name_encoding`, `parent_object_id`, `parent_entry_id`, `nested_action: extract`. `relative_path` не пишется, как у `preserve` в T-031.
- Записи вложенного архива: `object_id` указывает на этот объект, `path` — путь внутри вложенного архива. Судьба записей — по общим правилам (`included`, `included_renamed`, `excluded`, `unavailable`, `failed`).
- Размещение: `<размещение родителя>/<имя без расширения>/`, например `a/inner.zip` → `a/inner/`. Коллизия с существующим каталогом разрешается переименованием префикса по правилу T-031.
- Внести это уточнение в `container_manifest_v1.md` (рядом с правилом `input_nesting`) со ссылкой на эту задачу.
- Добавить положительный тест V3 «`extract` с родителем `excluded`/`nested_extract`» и отрицательный «`extract` с родителем `excluded`, у которого есть `file_id`». Опубликованные схема и golden-корпус не меняются.
- **Если V3 или схема 1.0 отвергают это представление — остановиться и спросить.** Не менять ни V3, ни схему.

### 7. Выполнение (run)

- Перед попыткой выполняются проверки T-031 для архива верхнего уровня. Затем каждый раскрываемый вложенный архив открывается заново, материализуется при `access = temp`, и сверяются его SHA-256 и перечень записей по `index`, `path_raw`, размерам, CRC и методу. Любое расхождение → `am.import.source_changed` с узлом верхнего уровня, причина в `cause`.
- `AssetRepository` дважды открывает источники (preflight и упаковка). Временный файл живёт всю попытку и удаляется в её конце.
- Механизм заданий T-030 и T-031 не меняется. ID записей и объектов вложенных архивов выдаются при попытке и не хранятся в `params_json`. Тест: размер параметров одинаков для вложенного архива из 10 и из 10 000 записей с точностью до длины путей плана.
- Строгий режим: сбой записи любого уровня → кандидат `failed`, ассета нет. Частичный режим: запись `failed`, `completeness = incomplete`.
- Отмена во время материализации: временный файл удалён, ассета нет.

### 8. Проверка 3MF (отложено из T-031 В-7)

- Запись с ZIP-сигнатурой и расширением `.3mf` открывается как вложенный ZIP тем же механизмом, но только для чтения центрального каталога. Применяются те же лимиты и тот же доступ (`range`/`temp`).
- Есть запись `3D/3dmodel.model` → `include`, `certain`, `specialized_container_verified`.
- Нет такой записи → `ask` с выбором «сохранить файлом» или «раскрыть» и с `specialized_container_unverified`.
- Не удалось прочитать (нет библиотеки, лимит, повреждение) → прежний итог T-031: `include`, `probable`, `specialized_container_unverified`.
- Объект вложенности для сохранённого 3MF не пишется, как в T-031. Прочие специализированные расширения не проверяются, итог прежний.

## Тесты

Синтетические фикстуры генерируются в тестах или в `tests/fixtures/`. Каждый тест помечается `RecordProperty("req", ...)`.

1. **Доступ:** Stored-вложенный открывается поддиапазоном без временного файла. Сжатый — через временный файл в `.am/.am-tmp/import/`. После попытки, после ошибки и после отмены временных файлов нет.
2. **Без библиотеки:** Stored-вложенный перечислен. Сжатый — `ask` с `nested_archive_temp_unavailable`, `completeness = incomplete`.
3. **Глубина:** при `max_depth = 2` раскрыты уровни 1–2. Уровень 3 — `ask` с `nested_archive_depth_limit`, а `limits_hit` содержит `max_depth`. Безусловный потолок 8 побеждает профиль со значением 20, и источник записан как `unconditional`.
4. **Цикл:** архив, содержащий байтовую копию предка, получает `nested_archive_cycle`. `expand` для него → `plan_invalid`.
5. **Бомба:** суммирование по уровням. Архив, у которого каждый уровень в отдельности укладывается в лимит, а сумма нет, при скане получает `limit_exceeded`. При run — `unsupported` / `limit_exceeded` без повторов, ассета и временных файлов нет.
6. **`max_temp_bytes`:** сжатый вложенный больше лимита → `limit_exceeded` с `max_temp_bytes`. Граничные значения: лимит равен размеру и на 1 байт меньше.
7. **Исключения до раскрытия:** `__MACOSX/._inner.zip` с AppleDouble исключён и не перечислен. Правила действуют на записи вложенного уровня.
8. **Профиль:** `expand`, `extract`, `preserve`, `exclude` и отсутствие действия дают ожидаемые решения. `nested` и `max_temp_bytes` отсутствуют в `not_applied`.
9. **План v3:** схема, `schema_check` по трём версиям, ссылки `archives[].id`, `{node}`/`{entry}`. `expand` у неперечисленного архива → `plan_invalid`. План v2 выполняется как в T-031.
10. **Манифест:** родитель `excluded`/`nested_extract` без `file_id`, объект `extract` с SHA-256 и родителем, записи вложенного уровня. V3 и V4 проходят. Тесты V3 из п. 6.
11. **Размещение:** `a/inner.zip` → `a/inner/`. При коллизии с каталогом `a/inner/` префикс переименован. Двойная вложенность `a/inner.zip/deep.zip` → `a/inner/deep/`.
12. **Свежесть:** подмена байтов вложенного архива при неизменном внешнем stat (в том числе подмена центрального каталога вложенного) → `source_changed`.
13. **Строгий и частичный режимы:** битая CRC записи второго уровня. В строгом режиме кандидат `failed`, ассета нет. В частичном запись `failed`, `completeness = incomplete`.
14. **Объём параметров:** 10 и 10 000 записей во вложенном архиве дают одинаковый `params_json`.
15. **3MF:** Stored и Deflate `.3mf` с `3D/3dmodel.model` → `certain`. Без этой записи → `ask`. Нечитаемый → прежний итог T-031.
16. **RAR/7z внутри ZIP:** прежнее `ask` с `nested_archive_expand_unsupported`.
17. **Уборка:** сирота в `.am/.am-tmp/import/<uuid>/` старше `orphan_age` удаляется при открытии библиотеки, более молодая остаётся.
18. **CLI:** `cli_import_zip` (или новый скрипт) — скан со вложенным ZIP, правка решения на `expand`, run, проверка манифеста.

## Критерии приёмки

1. Вложенный ZIP раскрывается по `expand` на любой глубине до лимита. Без управляемой временной области сжатые данные на диск не извлекаются.
2. Лимиты суммируются по уровням, превышение — `unsupported` / `limit_exceeded` без повторов. Глубина и циклы дают `ask`, а скан — `incomplete`.
3. Временные файлы удаляются во всех исходах, сироты убираются при открытии.
4. План v3 со схемой, v1 и v2 по-прежнему исполняются, `schema_check` покрывает три версии.
5. Манифест по п. 6 проходит V3 и V4. Опубликованные схема 1.0 и golden-корпус не изменены.
6. Свежесть вложенных архивов проверяется по SHA-256 и перечню записей.
