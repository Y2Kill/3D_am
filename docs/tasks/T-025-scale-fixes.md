# T-025. Устранение нелинейного масштабирования открытия, `create` и `rebuild` (M2, P0.5 — часть 10)

**Статус:** done (принята 2026-11-22, `3a34f09`) · **Веха:** M2 · **Основание:** первый замер К-112 (T-024, `tests/performance/results/2026-11-18-windows-release-nvme.json`); ТЗ v1.8 §14.1 п. 1, 3, §14.9 п. 3, 11, 13, §4.7, §14.7 п. 11; `docs/specifications/versioning.md` строка 5 (индекс не мигрирует, несовместимый перестраивается); T-016 (решение о проверке баз при открытии — пересматривается здесь), T-017 (`IndexStore`), T-022 (`writer_session`, `verify`)

## Цель

Замер T-024 показал рост хуже линейного (в расчёте на один ассет):

| Ассеты | открытие (`info`), мкс/ассет | `rebuild`, мс/ассет | `create`, мс/ассет |
|---:|---:|---:|---:|
| 1 000 | 114 | 21 | 78 |
| 10 000 | 187 | 33 | 92 |
| 100 000 | 249 | 167 | 212 |

Управляющий нашёл в коде две вероятные причины (их нужно **подтвердить измерением**, а не принять на веру):

- **А. FTS-удаление сканирует таблицу.** `IndexStore::put` перед вставкой вызывает `erase`, а тот выполняет `DELETE FROM fts_assets|fts_names|fts_docs WHERE asset_id=?` (`src/storage/db/index_store.cpp`, `erase`). В FTS5 столбец `asset_id` объявлен `UNINDEXED` (`schemas/sql/index.sql`), поэтому условие по нему — полный проход виртуальной таблицы. Отсюда O(n) на каждый `create`/`change` и O(n²) на `rebuild`.
- **Б. Полная проверка баз при каждом открытии.** `Library::open` выполняет `PRAGMA integrity_check` для всех трёх баз (`src/storage/library/library.cpp`, около строки 299) — это полный проход по каждой базе, включая `index.sqlite` с копиями манифестов. Отсюда открытие, пропорциональное размеру библиотеки, у `info`, `list`, `sync` и любой команды.

Задача: подтвердить, исправить, доказать независимость стоимости от n детерминированными тестами и повторить замер.

## Решения управляющего (не пересматривать в задаче)

1. **Сначала подтверждение.** До изменений исполнитель снимает по библиотеке 10 000 (из T-024 или свежей) разбивку времени открытия по шагам (каждая база: открытие, `integrity_check`, прочее) и стоимость `put` на 1 000 и 10 000 ассетах. Если какая-то гипотеза не подтверждается или найдена третья причина заметного масштаба — описать в отчёте с цифрами; третью причину исправлять, только если она в пределах файлов этой задачи и такого же характера (лишний полный проход); иначе остановиться и спросить.
2. **А — удаление из FTS по ключу, а не сканированием.**
   - Схема `index.sql` меняется, `PRAGMA user_version` индекса: 1 → 2. Старый индекс по существующему правилу (`versioning.md`, строка 5; T-016) считается несовместимым и перестраивается из ZIP; миграций для индекса нет.
   - Способ — на выбор исполнителя, с обоснованием в отчёте. Требование одно: удаление строк FTS одного ассета не зависит от числа ассетов. Допустимые варианты: явная связь `rowid` FTS со строкой ассета (для `fts_assets` — `rowid` = `assets.rowid`), обычная таблица соответствия `(asset_id, fts_rowid)` с индексом по `asset_id` для `fts_names`/`fts_docs`, `contentless_delete` FTS5 (только если версия SQLite из vcpkg это поддерживает — проверить и указать).
   - Поиск по FTS ведёт себя как раньше: существующие тесты индексатора и поиска проходят без изменения ожиданий.
   - Дополнительно разрешено: в `rebuild` по свежей пустой транзакции не вызывать `erase` для каждого ассета — но только как добавка к исправлению А, а не вместо него (`create`/`change` идут через тот же `put`).
3. **Б — открытие без полного прохода по базам.**
   - `Library::open` при обычном открытии выполняет только дешёвые проверки: открытие файла, заголовок SQLite, `user_version`, наличие схемы, `rebuild_required` для индекса. `PRAGMA integrity_check` при обычном открытии **не выполняется**.
   - Полная проверка баз переносится:
     - в `Library` — явный метод проверки базы (`quick_check` или `integrity_check` по уровню);
     - в `am library verify`: быстрый уровень — `PRAGMA quick_check` трёх баз, полный — `PRAGMA integrity_check`; результат по базам — в отчёте `verify` (JSON и текст) и в итоговом коде по правилам T-022 (повреждённая `state`/`userdata` → код 1, повреждённый индекс → отметка `rebuild_required` и предупреждение);
     - в `Catalog::open` (`read_write`) — **при незакрытой предыдущей сессии** (`writer_session` ≠ `closed`, в том числе когда индекс недоступен или отметки нет): `integrity_check` для `state` и `userdata` до восстановления журнала; повреждение → отказ открытия на запись с прежним `message_id` (`am.library.db_error`), как сейчас при открытии. Индекс при этом проверяется тоже; повреждённый индекс → перестроение, как сейчас.
   - Повреждение, обнаруженное SQLite во время обычной работы (`SQLITE_CORRUPT`, `SQLITE_NOTADB`), должно приводить к `Errc::corrupt_data` (для индекса — к отметке `rebuild_required`), а не к `io_error`/`internal`. Если сейчас это не так — исправить в пределах `storage::db`.
   - `read_only` открытие: только дешёвые проверки; при незакрытой сессии — прежнее предупреждение без проверки и без изменений.
   - Это пересмотр решения T-016 п. «index … `integrity_check` ≠ `ok`» и аналогичного для `state`/`userdata`: повреждение по-прежнему обнаруживается, но в `verify`, после аварии и при работе, а не на каждом открытии. ТЗ §4.7 (три уровня проверки) не нарушается.
4. **Доказательство независимости от n — детерминированное, не по времени.**
   - Для `put`/`erase`: число шагов виртуальной машины SQLite (`sqlite3_stmt_status(..., SQLITE_STMTSTATUS_VM_STEP, ...)`) или число прочитанных страниц для удаления одного ассета на индексе из 100 и из 5 000 ассетов отличается не более чем на небольшую константу (указать порог и обоснование в тесте). Можно через тестовый хук или через прямой SQL к базе теста.
   - Для открытия: обычное открытие не выполняет `integrity_check`/`quick_check` — проверка счётчиком (тестовый хук в `Library`, `sqlite3_trace_v2` в тесте или иной детерминированный способ); после незакрытой сессии — выполняет ровно для трёх баз.
   - Тесты со временем как критерием не допускаются (флаки на CI).
5. **Повторный замер** тем же `run_scale.py` (Release, тот же носитель, `--storage nvme-ssd`), новый файл `tests/performance/results/<дата>-windows-release-nvme.json`; файл T-024 не меняется.
   - Объёмы 100 / 1 000 / 10 000 / 50 000 / 100 000 — обязательно. Библиотеки T-024 (`.cache/perf/t024-measurement`) можно использовать повторно: ZIP не меняются, индекс перестроится из-за версии 2 (первое открытие на запись — это и есть `rebuild`, он попадает в замер). Скорость генерации после исправления — свежая генерация 10 000 и 50 000 в отдельный каталог.
   - 250 000 — выполнить, если оценка генерации по свежей скорости на 50 000 не превышает 6 часов; иначе — оценка в отчёте.
   - В отчёте таблица «до/после» по всем операциям и объёмам и пересчёт «в расчёте на ассет». Нормативы не назначаются; наблюдение, что рост остался нелинейным, — описать, не исправлять сверх п. 1.
6. **Совместимость.** Формат ZIP, `state.sql`, `userdata.sql` и их версии не меняются. Протокол фиксации и `AssetRepository` не меняются.

## Тесты

`RecordProperty("req", …)`: масштаб и FTS — `K-112`; проверка баз в `verify` — `K-22`; проверка после незакрытой сессии — `K-24`.

1. **Подтверждение (отчёт, не CTest):** разбивка открытия и стоимость `put` до исправлений — цифры в отчёте.
2. **FTS-удаление не зависит от n** (п. 4): индекс из 100 и 5 000 ассетов, удаление одного ассета — сравнение VM-шагов (или страниц); до исправления этот тест должен падать (проверить и указать в отчёте).
3. **Поиск после изменения схемы:** существующие тесты FTS/поиска/`list` без изменения ожиданий; удаление и повторная вставка ассета не оставляют «осиротевших» строк FTS (подсчёт строк до/после).
4. **Версия индекса:** библиотека с индексом `user_version = 1` (создать в тесте) → открытие на запись перестраивает индекс до версии 2, данные совпадают с ZIP; `read_only` → индекс не меняется, предупреждение `rebuild_required` как сейчас.
5. **Открытие без полной проверки** (п. 4): штатно закрытая библиотека — 0 вызовов проверки; `writer_session = open` — проверка всех трёх баз.
6. **Повреждение:** испорченная страница в `state.sqlite` (или `userdata.sqlite`) — (а) штатное открытие не проверяет, но первая операция, читающая повреждённую область, даёт `Errc::corrupt_data` (если надёжно воспроизвести попадание в повреждённую страницу нельзя — описать и заменить проверкой отображения кода `SQLITE_CORRUPT` → `corrupt_data`); (б) `library verify` → код 1 и база в отчёте; (в) открытие после незакрытой сессии → отказ `am.library.db_error`. Испорченный индекс → `verify` отмечает `rebuild_required`, следующее открытие на запись перестраивает.
7. **CLI:** `am library verify --json` содержит результаты проверки трёх баз; `docs/user/cli.md` обновлён.
8. **Повторный замер** (п. 5): файл результата закоммичен.

### Подтверждение причин до исправления

Измерительный C++-помощник собран MSVC Release `/O2 /MD` с той же SQLite **3.53.4** из vcpkg; исходные библиотеки T-024 не изменялись. `put` — настоящий `IndexStore::replace`, выполняемый в SQLite-копии индекса в памяти; поэтому здесь измеряется SQL-стоимость, без дисковой фиксации. Разбивка открытия — `sqlite3_open_v2`, `integrity_check`, затем `user_version` / чтение схемы / метаданные; конфигурация библиотеки и проверка носителя в эти значения не входят.

Повторный прогретый запуск по 10 000:

| База | open, мс | integrity_check, мс | прочее, мс |
|---|---:|---:|---:|
| userdata | 0,4193 | 10,5151 | 0,0665 |
| state | 0,1375 | 11,2750 | 0,0455 |
| index | 0,2885 | 2622,4700 | 0,1066 |

Первый запуск проверки индекса занимал 6639,9 мс. `put`: 1000 — 3,6735 мс; 10 000 — 27,0540 мс. Обе причины подтверждены; эти времена — наблюдения, не нормативы.

Регрессионный тест запущен с исходными `index_store.cpp`, заголовком и схемой из `815265f` (временные копии в `.cache/t025/`), затем с исправлением. Счётчик сбрасывает накопленные показатели подготовленных FTS-операторов перед замером; `SQLITE_STMTSTATUS_VM_STEP` читается со сбросом при каждом `SQLITE_TRACE_PROFILE`.

```text
До: VM erase 100=2923 5000=120523; put 100=2755 5000=120355
Expected large.erase <= 3051, actual 120523
Expected large.put <= 2883, actual 120355
1 FAILED TEST
После: VM erase 100=613 5000=613; put 100=429 5000=429
```

Допуск теста — 128 VM-шагов для служебной работы разных сборок SQLite, при измеренной разнице 0; старое сканирование добавляло 117600 шагов. Время не участвует в условии PASS. Открытие дополнительно проверено через `sqlite3_trace_v2` на всех создаваемых в тесте соединениях: фактические PRAGMA дают 0 при обычном/RO-открытии и по одной проверке каждой базы при незакрытой сессии.

### Реализация

- Индекс версии 2: `fts_assets.rowid = assets.rowid`; `fts_names_owner` и `fts_docs_owner` дают индексированный поиск rowid по AssetID. Это сохраняет обычные FTS5-таблицы и поиск, включая trigram, и не требует contentless-режима. Для имён запись соответствия создаётся перед FTS-записью; будущий писатель документов обязан использовать такую же связь. Удаление FTS предшествует каскаду обычных дочерних строк. В пустой транзакции rebuild повторное удаление пропущено.
- Обычное открытие читает заголовок, версию, обязательные таблицы схемы и метаданные индекса. Явный `Library::check_database` выполняет quick/full; незакрытая сессия проверяет три базы до восстановления. Повреждённый индекс сохраняется как stale и перестраивается из ZIP; state/userdata не пересоздаются.
- `verify` возвращает три результата баз в JSON и тексте; повреждение state/userdata даёт код 1, включая отказ предварительного открытия. Повреждение индекса предупреждает и устанавливает признаки перестройки. SQLite-обёртка меняет только отображение CORRUPT/NOTADB в `corrupt_data`; запись признаков повреждения выполняется в `IndexStore`. Для повреждённой индексной транзакции отметка сохраняется после отката, чтобы rollback её не отменял.
- Новые тесты: постоянство VM-стоимости, отсутствие сирот и сохранение FTS-поиска; 0/3 проверок открытия; quick/full; повреждённые страницы; runtime-ошибки; старый индекс RO/RW; CLI-отчёт и код 1. Существующие ожидания поиска не изменены; обновлены только значения версии индексной схемы и фикстуры несовместимой версии.
