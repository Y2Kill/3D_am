# T-008. Запись ZIP-контейнера: потоковые записи, raw-копирование с проверкой, ZIP64, проверка записанного

**Статус:** done (принята 2026-11-11) · **Веха:** M1 (`am_storage`, модуль 5 «Контейнер», P0.3) · **Основание:** ТЗ §19.4.1, §19.4.16.5, §19.4.17 (MF-10), ТЗ 4.6, 5.5.1; ADR-0005 (сжатие, ZIP64, бит 11, без шифрования и data descriptor), ADR-0006 пп. 2–4 (raw-копия, сброс на диск, проверка), ADR-0012, ADR-0024, ADR-0031/ADR-0033 (`max_file_size`, нехватка места), ADR-0032, ADR-0035 пп. 2, 7, 8, ADR-0037 п. 9 (opaque-записи, O-15); спецификация §1; T-007 (читатель)

## Цель

Дать программе один способ **создать** ZIP-контейнер, который:
- соответствует правилам спецификации §1 п. 5: Stored/Deflate, ZIP64 только при необходимости, бит 11, без шифрования, без data descriptor;
- целиком читается читателем T-007 без нарушений нормативного профиля, если на вход поданы допустимые имена;
- переносит неизменённые записи старого контейнера **raw-копией**, но проверяет CRC и размер по распакованному потоку **тех же байтов**, которые записывает (спецификация §1 п. 3: raw-copy — оптимизация, а не сертификат);
- не переносит вслепую extra fields и комментарии и не теряет их молча: если перенос не разрешён — ошибка, решение «только для чтения» принимает вызывающий код (§19.4.16.5);
- после записи сбрасывает данные на диск и умеет проверить записанный файл, повторно открыв его читателем T-007.

Это база для протокола фиксации ADR-0006 и `AssetRepository` (следующая задача). Журнала `pending_ops`, временного каталога `.am-tmp`, замены файла (`ReplaceFileW`/`rename`), блокировок, проверки свободного места **до** записи, манифеста и V2–V4 в этой задаче нет.

## Решения управляющего (не пересматривать в задаче)

1. **Собственный писатель, не minizip-ng.** Как и читатель (T-007), писатель сам формирует локальные заголовки, центральный каталог, ZIP64-записи и EOCD; сжатие — потоковый `deflate` zlib (`find_package(ZLIB)`, как в T-007). Причины:
   - raw-копия должна проверяться **одним проходом** по тем же байтам, что пишутся в новый файл, с бюджетом `ReadBudget` T-007; это требует доступа к структурам читателя (`EntryInfo`, `raw_range`);
   - размещение полей ZIP64 должно точно совпадать с тем, что принимает наш читатель (см. п. 4 «Формат записи»), иначе лишняя ZIP64-запись станет `unaccounted_bytes` и нарушением профиля;
   - детерминированный вывод (одинаковый вход → одинаковые байты) нужен для golden ZIP;
   - политика extra fields «не переносить вслепую» и внедрение отказов (заполненный том) через интерфейс приёмника.
   `vcpkg.json` не меняется; судьбу порта minizip-ng (сейчас он лишь тянет `zlib`) решает управляющий при пересмотре зависимостей. `libraries.md` обновляет управляющий.
2. **Размещение (ADR-0024).** `include/am/storage/asset_zip/` и `src/storage/asset_zip/`, только при `AM_WITH_CONTAINER=ON`; zlib и OpenSSL — `PRIVATE`. Общие для читателя и писателя внутренности (чтение/запись little-endian, константы сигнатур, проверка inflate по байтам) — во **внутреннем** заголовке `src/storage/asset_zip/` (не в `include/`). `reader.cpp` разрешено менять только для выноса таких общих частей, **без изменения поведения** читателя (все тесты T-007 проходят без правок их ожиданий).
3. **Размер записи объявляется заранее.** Новая запись открывается с точным `uncompressed_size`. Это делает решение о ZIP64 детерминированным (до записи данных) и ловит изменение исходного файла во время чтения: фактический размер ≠ объявленного → ошибка, запись не завершается.
4. **Имена проверяются строго для всех записей, включая raw-копии.** `am::paths::check_container_path` (T-007) и уникальность `unicode::path_collision_key` в пределах архива. Пространства имён (`manifest.json`, `content/`, `generated/`, `extensions/`) писатель **не** проверяет: при перезаписи старого контейнера в нём могут быть opaque-записи в других местах (спецификация §1 п. 3); их допустимость решает вызывающий код, профиль проверяется `check_normative_profile` после записи. Небезопасное имя (traversal, коллизия, не-NFC и т. д.) не получает исключения из-за `opaque` (§1 п. 3) — такой контейнер перезаписать нельзя, это решение вызывающего кода.
5. **Писатель не создаёт того, что сам не прочтёт:** при создании передаются `ZipLimits` читателя; число записей, длина имени и размер записи сверх них → `am.zip.limit_exceeded` до записи соответствующих байтов.
6. **Ошибки:** отклонённое имя (до записи байтов) оставляет писатель пригодным; любая ошибка данных, ввода-вывода или проверки после начала записи — **окончательная**: последующие вызовы возвращают ту же ошибку, `finish` невозможен. Незавершённый файл удаляется при `abort()` и в деструкторе без `finish`.

## Требования

### 1. Приёмник данных

- `RandomAccessSink`: `write_at(offset, span)` → `Result<void>` (полная запись или ошибка), `flush()` → `Result<void>`, `size()`. Реализации:
  - файл: создаётся **только новым** (`CREATE_NEW`/`O_EXCL`; существующий файл → `conflict`), путь через `am::paths::native()` (Windows — `\\?\`), совместное чтение разрешено (`FILE_SHARE_READ`), `flush` — `FlushFileBuffers`/`fsync`; удаление файла — через отдельный вызов (`discard`), который писатель делает при `abort`;
  - буфер в памяти (для тестов), с возможностью отдать байты после `finish`.
- Ошибка «нет места» ОС (`ERROR_DISK_FULL`, `ERROR_HANDLE_DISK_FULL`, `ENOSPC`) → `insufficient_space`; прочие → `io_error`.
- `WriterLimits::max_file_size` (из `StorageCapabilities` ADR-0031, по умолчанию без ограничения): запись, после которой файл превысил бы предел, отвергается **до** выдачи байтов в приёмник.

### 2. `ZipWriter`

- `ZipWriter::create(sink, WriterOptions)` — `WriterOptions`: `ZipLimits` читателя, `WriterLimits`, уровень Deflate (по умолчанию 6, ADR-0005), время DOS по умолчанию.
- **Новая запись:** `begin_entry(name, EntryOptions{method: stored|deflate, uncompressed_size, dos_time?, sha256 = true})` → `EntryWriter` с `write(span)` и `finish()` → `WrittenEntry` (индекс, имя, метод, CRC-32, сжатый и распакованный размеры, смещение локального заголовка, SHA-256 распакованного потока). Одна открытая запись за раз; `begin_entry`/`copy_raw`/`finish` при открытой записи → `am.zip.write.invalid_state`.
  - Deflate: `deflateInit2(level, Z_DEFLATED, -MAX_WBITS, 8, Z_DEFAULT_STRATEGY)`, потоково, буферы фиксированного размера; память O(1) по размеру записи.
  - CRC-32 и SHA-256 (обёртка T-007) — в том же проходе (ТЗ 5.5.1).
  - После данных писатель возвращается к локальному заголовку и записывает CRC и сжатый размер (бит 3 не используется).
- **Raw-копия:** `copy_raw(const ZipArchive& source, std::size_t index, ReadBudget& budget, RawCopyOptions)` → `WrittenEntry`.
  - Метод не 0/8 или шифрование → `am.zip.unsupported_feature` (CRC проверить нельзя — перенос запрещён).
  - Сжатые байты читаются из `raw_range` порциями; **каждая порция сначала проверяется** (распаковка, CRC, размер, граница Deflate-потока — те же правила, что у потока T-007, бюджет `ReadBudget` списывается), затем пишется. Ошибка проверки — окончательная ошибка писателя (`am.zip.entry_corrupt`), файл подлежит удалению. По окончании CRC/размер совпадают с `EntryInfo`; SHA-256 распакованного потока вычисляется в том же проходе.
  - Имя, метод, CRC, размеры берутся из источника; в новом файле бит 3 сброшен, CRC и размеры — в локальном заголовке, флаги — только бит 11 (если исходное имя — валидный UTF-8, иначе имя не проходит п. 4 «Решений» и копия отвергается); ZIP64 — по правилам этого писателя, не источника.
  - **Extra fields и комментарий записи** (спецификация §1 п. 3, O-15 OPEN): поле 0x0001 (ZIP64) не переносится, а формируется заново. Любое иное extra field источника (локальное или центральное) и непустой комментарий записи переносятся **только** если их id перечислен в `RawCopyOptions::carry_extra_ids` / установлен `carry_comment`; тогда они записываются байт в байт (локальные — в локальный заголовок, центральные — в центральный каталог). Иначе — `am.zip.write.extra_not_preserved` (`unsupported`) **до** записи байтов записи; писатель остаётся пригодным. По умолчанию списки пусты: реестр допустимых полей — O-15, не эта задача.
- **`finish()`** → `WriteSummary` (список `WrittenEntry` в порядке записи, смещение и размер центрального каталога, признак ZIP64, итоговый размер файла): центральный каталог, при необходимости ZIP64 EOCD record + locator, EOCD с пустым комментарием, затем `flush()`. Писатель архивный комментарий не пишет.
- **`abort()`** — прекращает запись и вызывает `discard` приёмника; идемпотентен.

### 3. Политика метода сжатия

`choose_method(std::string_view name, std::span<const std::byte> sample)` → `stored|deflate` (ADR-0005): **Stored** для заведомо сжатых расширений (без учёта регистра: `jpg`, `jpeg`, `png`, `webp`, `gif`, `mp4`, `mkv`, `webm`, `zip`, `7z`, `rar`, `gz`, `bz2`, `xz`, `zst`, `3mf`; список — константа с комментарием «ADR-0005, уточняется измерениями»), иначе — пробное сжатие `sample` (вызывающий передаёт первые ≤ 64 КиБ): коэффициент > 0,95 → Stored, иначе Deflate. Пустой `sample` → Deflate. Функция не читает файлы.

### 4. Формат записи (APPNOTE 6.3.10 §4.3, §4.4, §4.5.3)

Писатель пишет ровно так (детерминированно):
- флаги: только бит 11; метод 0 или 8; время/дата DOS — из `EntryOptions`, по умолчанию 1980-01-01 00:00:00 (`date = 0x0021`, `time = 0`); внутренние и внешние атрибуты 0; `version made by` = 45 (хост 0); `version needed` = 20, для записи с ZIP64 extra — 45; номер диска 0.
- **ZIP64 записи** нужен, если `uncompressed_size ≥ 0xFFFFFFFF` или верхняя оценка сжатого размера (`deflateBound` для Deflate, сам размер для Stored) `≥ 0xFFFFFFFF`. Решение принимается **до** данных.
  - Локальный заголовок такой записи: оба поля размеров = `0xFFFFFFFF`, extra 0x0001 из **обоих** размеров (распакованный, затем сжатый — 16 байт), как требует APPNOTE §4.5.3 для локального заголовка.
  - Центральный каталог: насыщаются (`0xFFFFFFFF`) только поля, значение которых `≥ 0xFFFFFFFF` (распакованный размер, сжатый размер, смещение локального заголовка); extra 0x0001 содержит ровно эти поля в порядке APPNOTE. Поле, не требующее ZIP64, пишется обычным значением.
  - Запись без ZIP64 не получает extra 0x0001 ни в одном заголовке.
- **ZIP64 EOCD record + locator** пишутся **только** если хотя бы одно поле EOCD насыщается: число записей `≥ 0xFFFF`, размер или смещение каталога `≥ 0xFFFFFFFF`. В EOCD насыщаются именно эти поля, остальные пишутся значениями. (Иначе наш читатель не заметит ZIP64-запись, и она станет `unaccounted_bytes`.)
- Промежутков между записями, каталогом и EOCD нет: `unaccounted_bytes = 0`.

### 5. Проверка записанного — `verify_written(source, const WriteSummary&, ReadBudget&)`

Повторно открывает результат читателем T-007 (`ZipArchive::open` с теми же `ZipLimits`) и проверяет:
- список записей совпадает с `WriteSummary` в том же порядке: имя (байты), метод, флаги, CRC, размеры, смещения;
- `unaccounted_bytes == 0`, длина комментария 0;
- CRC и размер **всех** записей — полным потоком (`verify_entry`); SHA-256 — для записей, у которых он есть в `WriteSummary`.
Расхождение → `am.zip.write.verification_failed` (`corrupt_data`) с индексом записи в `ctx.detail`; ошибки читателя передаются в `cause`. Нормативный профиль, манифест и V2–V4 эта функция не проверяет (это протокол фиксации).

### 7. Попутное исправление (замечание 4 приёмки T-007)

## Тесты

Теги `RecordProperty("req", …)`: `K-116` (память), `K-117` (заполненный том — в части писателя), иначе `ADR-0035`/`ADR-0006`.

1. **Круговая проверка:** Stored, Deflate, пустая запись, пустой архив, имена с кириллицей/CJK (NFC), запись 120 000 байт → `verify_written` успешна → `ZipArchive::open` → `check_normative_profile` пуст (для имён в допустимых пространствах) → содержимое и SHA-256 совпадают с исходными данными.
2. **Детерминированность:** два прогона с одинаковым входом и временем дают побайтно одинаковый результат; ожидаемые смещения и значения полей одного маленького архива сверены побайтно с вручную вычисленными (версии, флаги, время 1980-01-01, отсутствие extra 0x0001).
3. **ZIP64 по числу записей:** 70 000 пустых записей → ZIP64 EOCD record + locator, в EOCD насыщено только число записей; читатель открывает, `unaccounted_bytes = 0`. Архив с 65 534 записями — без ZIP64-записей.
4. **ZIP64 по размеру и смещению (К-116):** запись из 4 ГиБ + 1 нулевых байтов (Deflate), за ней маленькая запись (её смещение ≥ 4 ГиБ) → файл в `.cache/zip-tests/`, не в репозитории; `verify_written` с SHA-256; проверены: локальный ZIP64 extra — оба размера, центральный — только насыщенные поля, у второй записи насыщено смещение. Вывести время записи, время проверки и пик памяти процесса (`GetProcessMemoryInfo`), порогов нет.
5. **Размер ≠ объявленному:** меньше и больше на 1 байт (Stored и Deflate) → `size_mismatch`, ошибка окончательная, файл удалён (`discard` вызван).
6. **Raw-копия:** из всех пяти фикстур `tests/fixtures/zip/` (включая data descriptor и `force_zip64`) и из архивов построителя: результат без бита 3 и без лишней ZIP64-разметки, CRC/размер/SHA-256 совпадают, `verify_written` успешна; сжатые байты совпадают с исходными побайтно.
7. **Raw-копия, отказы:** испорченные сжатые данные (CRC, обрыв Deflate, хвост после конца потока) → `entry_corrupt` и удаление файла; метод 12 и шифрование → `unsupported_feature`; источник, возвращающий при чтении диапазона данных **не те** байты, что были при `open` (тестовый `RandomAccessSource`), → ошибка проверки, в выходной файл непроверенные байты не попадают (сверить содержимое приёмника в памяти); исчерпание бюджета → `limit_exceeded`.
8. **Extra fields и комментарии:** источник с extra 0x5455 и 0x7875 и комментарием записи → по умолчанию `extra_not_preserved`, писатель пригоден для следующей записи; с разрешёнными id и `carry_comment` — поля и комментарий перенесены байт в байт в нужные заголовки; поле 0x0001 источника не переносится.
9. **Имена:** все случаи группы 7 T-007 (`../x`, `/x`, `C:x`, `a\b`, `a//b`, …, 201 байт, не-NFC) → `invalid_name`; `A.stl`/`a.stl`, NFC/NFD-пара, точный дубликат → `name_collision`; после отказа писатель пригоден и итоговый архив корректен.
10. **Состояния:** `begin_entry` при открытой записи, `write` после `finish` записи, любой вызов после `finish()` архива → `invalid_state`; после окончательной ошибки — та же ошибка; деструктор без `finish` удаляет файл.
11. **Место и пределы:** приёмник с внедрённым отказом «нет места» на N-м вызове (в данных записи, в центральном каталоге, при `flush`) → `insufficient_space`, файл удалён; `max_file_size` меньше итогового размера → `file_too_large` до превышения (размер приёмника не больше предела); `ZipLimits` (число записей, длина имени, размер записи) → `limit_exceeded`.
12. **Файловый приёмник:** существующий файл → `target_exists` (файл не изменён); путь длиннее MAX_PATH; во время записи файл открывается на чтение другим дескриптором; `flush` вызывается до закрытия (проверка через счётчик в тестовом приёмнике-обёртке).
13. **`verify_written`:** после `finish` в буфере испортить байт данных, CRC в центральном каталоге, имя в локальном заголовке, дописать байт перед EOCD → `verification_failed` (или ошибка читателя в `cause`).
14. **Политика метода:** расширения из списка (в разном регистре) → Stored; 64 КиБ случайных байтов → Stored; текст → Deflate; пустой образец → Deflate.
15. **Интероперабельность (Python):** ctest `zip_writer_interop` (регистрируется при `AM_WITH_CONTAINER` и наличии Python, по правилам `AM_REQUIRE_PYTHON_TESTS`): сначала запускает `$<TARGET_FILE:am_unit_tests> --gtest_filter=ZipWriterInterop.*`, который пишет набор архивов в `.cache/zip-tests/written/` (Stored, Deflate, пустые, Unicode-имена, 70 000 записей, raw-копия из фикстуры с data descriptor) вместе с ожидаемыми SHA-256, затем `python -I tools/fixtures/check_written_zips.py <каталог>` открывает каждый `zipfile`, выполняет `testzip()`, сверяет имена, флаг UTF-8, отсутствие бита 3 и SHA-256 содержимого. Архив 4 ГиБ в эту проверку не входит.

## Решение управляющего по В-1

**2026-11-11.** Вопрос обоснован: это пробел ТЗ. Остановка по п. 3 `AGENTS.md` — правильная. Сигнатура `copy_raw(const ZipArchive&, ...)` сохраняется. API читателя расширяется **аддитивно**: существующие функции, поля и поведение не меняются, ожидания тестов T-007 не правятся.

1. **`EntryInfo::comment`** — `std::vector<std::byte>`, сырые байты комментария записи из центрального каталога. Длина уже ограничена размером каталога (`ZipLimits::max_directory_bytes`), отдельный лимит не нужен. Для записей без комментария — пусто.
2. **`ZipArchive::read_raw(std::size_t index, std::uint64_t offset, std::span<std::byte> output) const`** → `Result<std::size_t>`. Читает **сжатые** байты записи строго внутри `raw_range(index)`, где `offset` отсчитывается от начала сжатых данных. Короткое чтение допустимо, `0` означает конец диапазона. Выход за диапазон невозможен: размер усекается до остатка. Неверный индекс → `am.zip.io_error`, как в `raw_range`. Ошибка источника → его ошибка; неожиданный EOF внутри диапазона → `am.zip.entry_corrupt`. Бюджет `ReadBudget` эта функция **не** списывает: бюджет относится к распакованным байтам, его списывает проверка в `copy_raw`. Сам источник наружу не выдаётся.
3. Тесты читателя на новое (добавить в `tests/unit/test_zip_reader.cpp`, не меняя существующих ожиданий):
   - комментарий записи читается точно, включая пустой и 65 535-байтный в пределах каталога;
   - `read_raw` возвращает ровно байты `raw_range`, включая чтение порциями и с ненулевого смещения;
   - смещение на конце или за концом диапазона → `0`; неверный индекс → ошибка;
   - чтение у записи с data descriptor не захватывает descriptor.
4. Проверка комментария в `copy_raw` — по п. 2 требований («Raw-копия»): непустой `comment` без `carry_comment` → `extra_not_preserved` до записи байтов.
5. **Уровень Deflate 0 в сценарии 4 принят.** С ним физический поток превышает 4 ГиБ, и смещение второй записи гарантированно требует ZIP64. Метод записи остаётся Deflate (8), значение по умолчанию — 6. В отчёте указать использованный уровень.

Остальные требования и критерии приёмки — без изменений. Продолжать в ветке `codex/T-008`. Новый отчёт — разделом «## Отчёт исполнителя (после В-1)» в конце файла, после этого раздела; первый отчёт не удалять.

### Детали реализации, отклонения, вопросы

- В-1 закрыт: `EntryInfo::comment` содержит исходные байты центрального комментария; `read_raw` ограничивает чтение конкретным сжатым диапазоном и не списывает бюджет. Старые ожидания тестов T-007 не изменены. В общую реализацию вынесены LE-примитивы, сигнатуры и потоковая проверка; читатель не использует добавленный callback приёмки raw-порций.
- В raw-копии каждая порция читается один раз в буфер декодера, распаковывается с проверкой границ/размера/бюджета и обновлением CRC/SHA, затем тот же буфер передаётся приёмнику. Последняя сжатая порция удерживается до успешных итоговых CRC/размера/границы потока. При ошибке весь незавершённый результат удаляется; проверочный проход по другому экземпляру источника не используется.
- Для новой Deflate-записи решение о локальном ZIP64 принято до данных по заявленному размеру и `deflateBound_z`: у установленной zlib 1.3.2 это вариант с `z_size_t`, избегающий 32-битного `uLong` на Windows. В raw-копии точный сжатый размер уже известен; исходная ZIP64-разметка не копируется. Центральные и EOCD-поля насыщаются индивидуально.
- В новый интерфейс приёмника включён `close()` с реализацией по умолчанию без действий. `finish` вызывает `flush`, затем `close`: файл можно повторно открыть через T-007, пока объекты писателя/приёмника ещё живы. Файловый `discard` закрывает и удаляет незавершённый файл; обычный close его не удаляет. Порядок проверен счётчиком и реальным чтением файла.
- Ошибки имён и неразрешённых extra/comment до записи не портят писатель. После ошибки данных/приёмника возвращается исходная ошибка, включая последующие операции очистки; `abort` остаётся идемпотентным по действию. Сравнение ключа существующего имени предшествует строгому отказу NFD, чтобы NFC/NFD-пара дала предусмотренный задачей `name_collision`.
- Пустой ZIP проверяется как корректная ZIP-структура. Пустой нормативный профиль проверяется на наборе с корневым `manifest.json`; его отсутствие в пустом архиве остаётся нарушением профиля T-007. Писатель, как предписано, не проверяет манифест или пространства имён.
- Выходов за разрешённый объём нет. Исправление идентификатора OOM в paths выполнено только в указанной ветке обработки; прочее поведение не менялось. Блокирующих вопросов нет. Протокол фиксации, AssetRepository, V2–V4, O-15/O-17 и Linux/CI не реализовывались.

Замечания без доработки — входят в ТЗ следующей задачи (протокол фиксации и `AssetRepository`):
1. **Гранулярность проверки raw-копии.** Порция Deflate выдаётся в приёмник, когда inflate её **поглотил**; часть её распакованного вывода и итоговый CRC проверяются позже. Гарантия «непроверенные данные не попадают в действующий контейнер» держится на том, что файл писателя — временный и используется **только** после успешных `finish()` и `verify_written`. Протокол фиксации обязан это соблюдать: никакого использования временного файла до проверки.
2. **Время DOS при raw-копии** берётся из `WriterOptions`, а не из источника: `EntryInfo` не содержит времени и даты записи. Если вызывающий код задаёт время для `content/`, каждая перезапись сбросит его на значение по умолчанию. Нужно аддитивно добавить время и дату DOS в `EntryInfo` и переносить их при raw-копии.
