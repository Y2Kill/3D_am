# T-033. Экспорт ассета и выборки (M3a)

**Исполнение:** по `AGENTS.md` в ветке `codex/T-033`. Пока у Codex нулевой лимит, задачу выполняет управляющий (Claude Code) по той же процедуре, как T-032: самопроверка по критериям и `/code-review` по diff вместо независимой приёмки.

**Статус:** done (принята 2026-11-26) · **Веха:** M3a (P0.6) · **Основание:** ТЗ v1.8 §1 п. 9, §4.4.3, §10.7 п. 3, §12 (модуль 13), §14.2 п. 3, §14.5 п. 6 и 10, §15 п. 10, 46, 116, 127; ADR-0005 (имя файла при полном экспорте), ADR-0025, ADR-0031, ADR-0036 п. 4; `open_questions_resolution.md` вопрос 4

## Цель

В `am` появляется команда `am export`. Она выдаёт результат за пределы библиотеки, ничего в библиотеке не меняя:

1. **Полный экспорт** (ТЗ §1 п. 9, §15 п. 10) — побайтная копия ZIP-ассета под именем по названию ассета. AssetID внутри не меняется (§4.4.3).
2. **Выборочный экспорт файлами** — обычный ZIP без манифеста с текущими файлами выбранных категорий («3D», «3D и предпросмотр», «для слайсера», явный список FileID). Это пресет «как обычные файлы» из рабочего решения вопроса 4.
3. **Выборка ассетов** — несколько AssetID за одну команду. Каждый ассет экспортируется независимо и даёт свой итог.

Экспорт идёт через общую очередь заданий (§10.7 п. 3), потоково (§14.2 п. 3, K-116) и доступен в режиме только чтения (§14.5 п. 10, K-127). Существующий файл в целевом каталоге никогда не перезаписывается (§14.5 п. 6).

## Решения

### 1. Что не входит и почему: выборочный экспорт в формате ассета

Рабочее решение вопроса 4 описывает выборочный экспорт как ZIP формата 1.0 с новым AssetID. В формате 1.0 он сейчас непредставим без допущений:
- `inputs[].entries[].file_id` неисключённого файла обязан разрешаться через `files ∪ historical_files` (V3 `input_entry_file`);
- в ревизии 1 `historical_files` запрещены (`removed_at_revision ≥ 2`), а перенос истории в независимую копию — открытые O-05/O-06;
- пометить такие записи `excluded` нельзя: по тому же решению исключённые при экспорте записи не помечаются как исключённые при импорте;
- удалить записи нельзя: `entries[]` перечисляет все обнаруженные записи.

Поэтому в T-033 выборочный экспорт выдаёт только обычный ZIP без манифеста. Экспорт в формате ассета ждёт решения владельца по O-05/O-06; он записывается в открытые вопросы, а не закрывается допущением. Если для него понадобится вариант «независимая копия целиком», он уже есть: `am library copy` плюс полный экспорт.

### 2. Команда

```
am export <library> <asset-id>... --to <dir>
          [--files 3d|3d_preview|slicer|all] [--file <file-id>]...
          [--name <name>] [--on-conflict fail|rename]
          [--verify full|quick] [--enqueue-only] [--json] [--verbose]
```

- Без `--files` и `--file` выполняется полный экспорт. С ними — выборочный экспорт файлами. `--files` и `--file` объединяются.
- `--file` допустим только при одном AssetID; неизвестный FileID — ошибка до начала записи (`am.export.file_unknown`).
- `--name` допустим только при одном AssetID (`am.export.name_requires_single_asset`).
- `--to` должен существовать и быть каталогом, без перехода по ссылке в последнем компоненте (`paths::node_info`). Иначе — `am.export.target_unavailable`. Каталог `--to` внутри корня библиотеки запрещён (`am.export.target_inside_library`).
- Повторный AssetID в списке — ошибка использования (код 2).
- Ассеты в корзине не экспортируются (`am.export.asset_in_trash`), как и в `library copy`.

### 3. Имя результата

- Основа имени — `asset.metadata.title`. Если названия нет или после очистки оно пустое, основа — AssetID.
- Полный экспорт: `<основа>.zip`. Выборочный: `<основа> (<пресет>).zip`, где пресет — `3d`, `3d_preview`, `slicer`, `all` или `files` при одном только `--file`; несколько значений `--files` перечисляются через `+` в порядке из п. 5.
- Очистка (одинаковая на всех ОС, чтобы результат переносился):
  - символы `< > : " / \ | ? *` и U+0000–U+001F заменяются на `_`;
  - конечные точки и пробелы основы удаляются;
  - зарезервированные имена Windows (`CON`, `PRN`, `AUX`, `NUL`, `COM1`–`COM9`, `LPT1`–`LPT9`, в том числе с надстрочными цифрами `¹²³`, без учёта регистра, в том числе перед точкой) получают префикс `_`;
  - полное имя вместе с расширением и суффиксом коллизии укладывается в 255 байтов UTF-8 и в 255 единиц UTF-16; основа обрезается по границе кодовой точки;
  - нормализация Unicode не выполняется: байты названия сохраняются.
- Итог сообщает `name_sanitized: true`, если основа изменилась.
- `--name` не очищается: недопустимое имя по тем же правилам — ошибка `am.export.name_invalid`. Расширение `.zip` добавляется, если его нет.
- Коллизия с существующим файлом (в том числе с отличием только в регистре на нечувствительной ФС — её выявляет публикация без замены, п. 7):
  - `fail` (по умолчанию) — `am.export.target_exists`, ничего не записано;
  - `rename` — суффиксы ` (2)` … ` (99)` перед `.zip`; после 99 — `am.export.target_exists`. Предел 99 — гипотеза.

### 4. Полный экспорт

- Источник — один снимок `AssetSnapshot` через `AssetRepository::snapshot`. Байты читаются из открытого им источника, без повторного открытия файла по имени. Параллельная фиксация новой ревизии не смешивает версии: экспортируется ревизия снимка, итог её сообщает.
- Копирование потоковое, блоками; SHA-256 всего файла считается при чтении. Учитывается `ReadBudget`, проверяется `stop_token`.
- После записи временный файл открывается заново и проверяется:
  - размер и SHA-256 всего файла совпадают с прочитанными из источника;
  - `--verify full` (по умолчанию) — V1–V4 через тот же код, что `AssetRepository::verify`, на временном файле;
  - `--verify quick` — V1–V3 без чтения потоков.
- Поврежденный источник (ошибка V1–V4) не экспортируется: `am.export.source_invalid` с причиной. Спасение повреждённого ассета — не T-033.

### 5. Выборочный экспорт файлами

**Категории (таблица `export_categories` v1, рабочая по вопросу 4).** Файл попадает в категорию по `files[].type.id`, если поле есть, иначе по расширению последнего компонента `storage_path` без учёта регистра:

| Категория | `type.id` | Расширения |
|---|---|---|
| `model` | `mesh.*` | `stl`, `obj`, `mtl`, `3mf`, `ply`, `amf`, `fbx`, `gltf`, `glb`, `dae`, `off`, `3ds`, `step`, `stp`, `iges`, `igs`, `blend` |
| `image` | `image.*` | `png`, `jpg`, `jpeg`, `webp`, `gif`, `bmp`, `tif`, `tiff` |
| `slicer` | `mesh.stl.*`, `mesh.obj`, `slice.*`, `gcode` | `stl`, `3mf`, `obj`, `lys`, `chitubox`, `ctb`, `gcode` (дословно по вопросу 4) |

Пресеты:
- `3d` = `model`;
- `3d_preview` = `model` ∪ `image` ∪ файлы из `previews.items[].file_id`;
- `slicer` = `slicer`;
- `all` = все текущие файлы.

Порядок пресетов в имени: `3d`, `3d_preview`, `slicer`, `all`. Таблица — версионированный рабочий список. Изменение — новая версия таблицы в `docs/specifications/export.md`, без изменения кода категорий в других местах. Зависимости (OBJ → MTL → текстуры) автоматически не разрешаются; `mtl` входит в `model` как сопутствующий файл.

**Отбор.** Только текущие `files[]`; `historical_files`, вложения расширений, непрописанные записи ZIP и `manifest.json` не экспортируются. Пустой отбор — `am.export.selection_empty`, файл не создаётся.

**Пути в ZIP.**
- Все записи лежат под корневой папкой с именем результата без `.zip`.
- Из `storage_path` убирается префикс `content/<InputID>/`; `generated/...` сохраняется как есть.
- Коллизии по `unicode::path_collision_key` в порядке `files[]`: второй и следующие файлы получают ` (2)`, ` (3)`… перед расширением последнего компонента. Каждое переименование попадает в итог (`renamed[]: {file_id, path}`).
- Путь проверяется `paths::check_container_path`; предел 200 байтов формата к обычному ZIP не применяется.

**Запись.** Сжатые потоки копируются raw (`ZipWriter::copy_raw` с `target_name`), без перекомпрессии; CRC сохраняется. Имена — UTF-8 с битом 11. Маркера `am-asset` и манифеста нет, поэтому результат не распознаётся как ассет.

**Проверка.** Временный файл открывается заново, все записи проверяются по CRC, их размер и SHA-256 — по `files[]` источника. `--verify quick` здесь не отличается от `full`: прочитать выбранные потоки нужно в любом случае.

### 6. Задания

- Запись в библиотеку возможна → родитель `export.run` и по дочернему `export.asset` на ассет. Это та же схема, что у `import.run`/`import.asset`. `am export` ставит задания и выполняет их до простоя; `--enqueue-only` только ставит.
- Параметры дочернего задания: `asset_id`, `mode` (`full`|`files`), `presets[]`, `file_ids[]`, `target_dir`, `name?`, `on_conflict`, `verify`.
- Библиотека открыта только на чтение → задания не сохраняются, экспорт выполняется тем же кодом напрямую, в итоге `queued: false`. `--enqueue-only` для такой библиотеки — `am.export.queue_unavailable`.
- Ресурсы: чтение — устройство библиотеки, запись — устройство цели (`detect_media`), через `ResourceManager`.
- **Повтор после сбоя.** Перед публикацией дочернее задание сохраняет через `report` `{target_name, sha256, size}`. Если при повторе файл с этим именем уже существует и его размер и SHA-256 совпадают с сохранёнными, задание завершается успехом без новой записи. Иначе действует правило коллизий п. 3.
- Частичный итог выборки: ошибка одного ассета не прерывает остальные. Код выхода 0 — все успешны, 4 — хотя бы один не экспортирован, 2 — ошибка аргументов.

### 7. Временный файл и публикация

- Временный файл — в целевом каталоге: `.am-export-<op_id>.tmp`. Так публикация остаётся переименованием на одном томе.
- Перед записью:
  - проверка свободного места (`space().available` меньше оценки → `am.export.insufficient_space`, `Errc::insufficient_space`);
  - проверка `max_file_size` по типу ФС из `fs_support.md`, если тип определён (FAT32 — 4 ГиБ − 1). Неизвестный тип — без предварительной проверки, ошибка записи отображается в ту же `insufficient_space` или `io_error`.
- Запись → `FlushFileBuffers`/`fsync` → проверка (п. 4, 5) → публикация без замены → на POSIX `fsync` каталога.
- **Публикация без замены — один общий помощник** в `storage`, например `storage::fs::publish_no_replace(temp, target)`:
  - Windows: `MoveFileExW(MOVEFILE_WRITE_THROUGH)` без `REPLACE_EXISTING`;
  - Linux: `renameat2(RENAME_NOREPLACE)`, при `ENOSYS`/`EINVAL`/`EOPNOTSUPP` — `link` + `unlink`;
  - существующая цель → `Errc::conflict` (п. 3).
  Можно вынести существующий `move_no_replace` из `protocol.cpp`. Три копии в `application` переводить на помощника не обязательно: это кандидат на отдельное укрепление (записать в отчёт).
- Любой исход, кроме успеха (ошибка, проверка, отмена), удаляет временный файл.
- **Остатки после аварии.** Перед записью в каталог `--to` удаляются только обычные файлы (не ссылки) с именем строго `.am-export-<UUID>.tmp`, если самый свежий `mtime` старше `orphan_age` (24 ч, гипотеза, как в `commit::recover`). Занятый файл пропускается. Другие файлы каталога не трогаются.

### 8. Журнал и данные пользователя

- Библиотека доступна на запись → запись `export` в `op_log`: `asset_id`, `revision`, `mode`, `presets`, число файлов, итог. Путь цели — только в `detail` (обезличенный экспорт диагностики его убирает).
- Только чтение → без записи в журнал; это не ошибка.
- Данные `userdata.sqlite` (аннотации, коллекции, решения Dismiss) в результат не попадают (K-46): полный экспорт копирует только ZIP, выборочный — только файлы.

### 9. Размещение кода

- `include/am/services/export/`, `src/services/export/` — новый модуль уровня `services` (модуль 13 §12): отбор категорий, имена, задания `export.run`/`export.asset`, `register_export_jobs`.
- Чтение источника, запись ZIP, проверка и публикация — `storage` (repository/asset_zip и помощник п. 7). Действующие ZIP библиотеки экспорт не меняет (ADR-0025).
- `application`: `export_assets(...)` для CLI; `am export` в `main.cpp`.
- `arch_check` проходит по матрице ADR-0024 без новых исключений.
- `docs/research/libraries.md`: дописать, что экспорт использует собственный `asset_zip` и новых зависимостей нет.

### 10. Чего в T-033 нет

- Выборочного экспорта в формате ассета (п. 1; O-05/O-06).
- Экспорта в каталог как отдельных файлов: `am asset extract` уже даёт извлечение одного ZIP.
- Конвертации с экспортом (§9), экспорта реестра связей и коллекций (ADR-0007, JSONL), резервного копирования.
- Спасения повреждённого ассета.
- GUI.

## Тесты

Синтетика — в `tests/fixtures/` или генерацией в тестах. В каждом тесте `RecordProperty("req", ...)`.

1. Полный экспорт: байты результата равны байтам ZIP в библиотеке; имя — по названию; AssetID и ревизия в итоге (K-10).
2. Полный экспорт при параллельной фиксации новой ревизии: результат побайтно равен одной из ревизий и сообщает её (тестовый крючок между снимком и копированием).
3. Санитизация: запрещённые символы, конечные точки и пробелы, `CON`, `com¹.zip`, длинное название из многобайтных символов (обрезка по кодовой точке, 255 байтов и 255 единиц UTF-16), пустое название → AssetID.
4. `--name` с недопустимым именем → `am.export.name_invalid`, файла нет.
5. Коллизия: `fail` → `target_exists`, существующий файл не изменён; `rename` → ` (2)`; на Windows — коллизия, отличающаяся только регистром.
6. Повреждённый источник (CRC) → `source_invalid`, временного файла нет.
7. Выборочный экспорт: `3d`, `3d_preview` (вместе с файлом из `previews`, у которого расширение не из таблицы), `slicer`, `all`, `--file`; категории по `type.id` и по расширению; результат без `manifest.json` и без маркера; пути без `content/<InputID>/`, под корневой папкой; потоки raw (CRC и метод сжатия совпадают с источником).
8. Коллизия путей двух входных комплектов → ` (2)` и запись в `renamed[]`.
9. Пустой отбор → `selection_empty`, файла нет. Неизвестный FileID → `file_unknown` до записи.
10. Отмена во время копирования и ошибка проверки (крючок портит байт временного файла) → временный файл удалён, цели нет.
11. Нехватка места (крючок оценки) → `insufficient_space` до записи.
12. Публикация без замены: цель появилась между проверкой и публикацией → `target_exists`, временный файл удалён, чужой файл цел.
13. Повтор задания после публикации до записи итога → успех без второй записи (совпадение SHA-256); при несовпадении — правило коллизий.
14. Выборка из трёх ассетов, один в корзине → два файла, один отказ `asset_in_trash`, код выхода 4.
15. Библиотека только для чтения: полный и выборочный экспорт выполняются напрямую, `queued: false`, файлы библиотеки и `state.sqlite` не изменены (K-127); `--enqueue-only` → `queue_unavailable`.
16. Остатки `.am-export-<uuid>.tmp`: старый удаляется, молодой и занятый остаются, похожее имя и ссылка не трогаются.
17. Потоковость (K-116): экспорт ассета с файлом больше выбранного порога не требует памяти порядка размера файла. Методика — по `nfr_measurement_plan.md` (метка `periodic`, если тест долгий); порог не назначается до измерения.
18. `--to` внутри библиотеки, `--to` — ссылка или файл → ошибки п. 2 до записи.
19. CLI: JSON и текст `am export`, коды выхода, `--enqueue-only` с последующим `am jobs run`.

## Критерии приёмки

1. Полный экспорт выдаёт побайтную копию ревизии снимка под очищенным именем; AssetID не меняется; результат проходит V1–V4.

5. Повтор задания после сбоя не создаёт второго файла.
6. Выборочный экспорт в формате ассета не реализован и записан как зависящий от O-05/O-06; открытые вопросы не закрыты допущениями.

## Отчёт исполнителя

### Выполнение критериев приёмки

1. Полный экспорт читает удерживаемый источник `AssetSnapshot`, сохраняет AssetID/ревизию и копирует ZIP побайтно. Источник проходит V1–V4; временный файл — повторный SHA/размер и V1–V3, при `full` также V4. Тест конкурентной фиксации подтверждает старую ревизию целиком; отдельный тест наблюдает реальные отчёты верификатора: V4 источника при обоих режимах, ноль проверенных потоков временного файла при quick и один при full.
2. Выборка использует ровно таблицу категорий v1, приоритет TypeID над расширением, объединение пресетов/FileID и текущие файлы. Создаётся обычный ZIP с корневой папкой, без корневого манифеста/маркера; raw-потоки, CRC, методы, размеры и SHA проверяются. Проверены NFD, пути длиннее 200 байтов, коллизии разных входных комплектов, preview вне списка расширений, пустой отбор и неизвестный FileID.
3. `storage::fs::publish_no_replace` не заменяет цель, в том числе при гонке. Проверены fail/rename и регистровая коллизия Windows. Временный файл очищается при отмене/ошибке; уборщик различает возраст, строгий UUID, ссылки и занятые файлы. Живая аренда временного файла сохраняется после закрытия writer до конца публикации, поэтому длительный сон не превращает активный файл в сироту.
4. `export.run`/`export.asset` зарегистрированы в общем JobService, поддержан enqueue-only с последующим `am jobs run`. Режим только чтения использует тот же код напрямую, `queued:false`; очередь отклоняется. Ошибка одного ассета не останавливает остальные; batch с ассетом в корзине даёт два успешных результата и один отказ. Изменения библиотеки проверяются по точному правилу В-6. В writable-журнал добавляется `export`, путь находится только в detail; userdata не читается для отбора и не переносится.
5. Строгий checkpoint синхронно записывается до публикации и переживает восстановление/release/retry в memory, SQLite и делегирующих хранилищах. Обычные результаты сбрасываются как в T-030. Проверены отказ записи checkpoint, независимость от отложенного прогресса, сбой после публикации, успех без повторной записи по SHA и обе политики при несовпадении. Успешный итог заменяет checkpoint.
6. Выборочного ZIP в формате ассета нет. В вопросе 4 добавлена отдельная пометка об обычном ZIP и зависимости формата ассета от O-05/O-06; исходное решение не переписано.
7. Команды, фактические итоги и логи приведены в разделе проверок ниже; периодическое измерение памяти отделено от обязательных прогонов `-LE periodic`.
8. Добавлена спецификация экспорта; обновлены английская CLI-документация, обзор архитектуры, исследование библиотек, jobs_and_sessions, CHANGELOG и строки матрицы приёмки.
