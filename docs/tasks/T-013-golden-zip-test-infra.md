# T-013. Golden ZIP формата 1.0 и инфраструктура тестов M1

**Статус:** in_progress · **Веха:** M1 · **Основание:** ADR-0035 п. 1 (формат публикуется при схеме, валидаторе V1–V4 и golden ZIP; ТЗ §19.6.4), ADR-0029 пп. 4–5 (`expected.json`, генератор, трассировка), `docs/plan/roadmap.md` M1 «Golden ZIP» и «Инфраструктура тестов», замечание 1 приёмки T-012

## Цель

1. **Корпус golden ZIP** — положительные и отрицательные ассеты формата 1.0, сгенерированные **независимо от нашего писателя** (Python, стандартная библиотека), с машинно-читаемыми ожиданиями. Корпус проверяется в каждом прогоне ctest и CI через собранный `am`.
2. **Схема эталона** `schemas/expected.v1.schema.json` (ADR-0029 п. 4) — для golden ZIP сейчас, расширяемая для случаев импорта (M3a).
3. **Отчёт трассировки** `tools/coverage/req_report.py` (ADR-0029 п. 5): требования из `RecordProperty("req", …)` и меток ctest `req:*` → тесты → результат, со сверкой с `acceptance_matrix.md`.
4. **Закрыть замечание 1 приёмки T-012:** файл, который не разбирается как ZIP, — это провал проверки V1 (код 1), а не ошибка операции (код 4).

Публикация формата 1.0 в задачу **не входит** (она следует за этой задачей). Владелец закрыл открытые пункты (ADR-0039, отчёт 08): корпус строится по **кандидату нормативной схемы** и правилам V3 после T-014; случаи для новых правил ADR-0039 (физический `default`, `claims[].unit`, `change_kind_fields`, каталоги в описи, `generation.tool`, `dimension`) входят в обязательный состав.

## Решения управляющего (не пересматривать в задаче)

1. **Размещение.**
   - Исходники случаев: `tools/fixtures/golden/<case>/` — `manifest.json` (**текст как есть**, без пересериализации: важны точные числа, порядок ключей, дубли и неверный UTF-8 в отрицательных случаях), полезные данные или их описание, параметры упаковки.
   - Генератор: `tools/fixtures/make_golden_zips.py` — только стандартная библиотека Python, без нашего C++-кода.
   - Результат: `tests/fixtures/golden/<case>/asset.zip` + `expected.json` — **в репозитории** (малые файлы, ADR-0029 п. 4); общий `tests/fixtures/golden/README.md` с таблицей случаев.
   - Имя случая: `pos-<что>` / `neg-v1-<что>`, `neg-v2-…`, `neg-v3-<rule>`, `neg-v4-…`, `neg-zip-…`.
2. **Генератор.**
   - Детерминирован: фиксированные UUID (константы в исходниках случаев), время записей ZIP `2020-01-01 00:00:00`, порядок записей задан явно. Повторный запуск даёт побайтно те же ZIP.
   - Подстановки в тексте манифеста только через явные метки, которые генератор заменяет вычисленными значениями: SHA-256 и размер полезного файла (`"@sha256:<путь>"`, `"@size:<путь>"` или аналогичный однозначный синтаксис — выбрать и описать в README). Всё остальное в манифесте — байты исходника.
   - Отрицательные случаи с повреждённой структурой ZIP (неверный CRC, неподдерживаемый метод, флаг шифрования, `../` в имени, дубли имён) генератор строит правкой байтов готового архива по описанию случая — описание в исходнике случая, не ручная правка `asset.zip`.
   - Ограничение размера: каждый `asset.zip` ≤ 64 КиБ (гипотеза, чтобы репозиторий не рос); ZIP64 — принудительными полями, не объёмом.
   - ctest `golden_regen_check` (Python, `-I`): генерирует корпус во временный каталог в `.cache/` и побайтно сравнивает с `tests/fixtures/golden/`. Расхождение — провал с перечнем случаев.
3. **Обязательный состав корпуса** (минимум; больше — можно):
   - **Положительные (код 0):** минимальный ассет (один файл); ассет со всеми необязательными разделами схемы (`claims` с разными адресатами, `field_definitions`/`custom_values`, `historical_files`, `generated`-файлы с `generation`, превью, лицензии, зависимости, группы, `extensions` с непрозрачными данными); непрозрачные точные числа S7 во всех шести местах (`12345678901234567890.000000000000000001`, `1e400`, `-1E-400`, `-0`, `-0.0`, `1.500`) — проверка, что V1–V4 их принимают; Unicode и пробелы в путях; смесь Stored/Deflate; data descriptor; принудительный ZIP64; ассет, созданный нашим `am asset create` **не** используется (корпус независим от писателя).
   - **Положительные с кодом 3:** манифест минорной версии 1.1 с неизвестными ключами (`newer_minor`); находки `unverifiable` (открытые X-02: разные единицы, физическое значение по умолчанию). Незарегистрированный безопасный поток в существующем ZIP (`pos-opaque-stream`, решение В-2): `verify --level full` — код 3, поток `verified_crc_size_only`, свод `partial`; `validate` — код 0.
   - **V1 (код 1):** нет `manifest.json`; два `manifest.json`; манифест не UTF-8; дубли ключей (известных и непрозрачных); недопустимые числа (`01`, `+1`, `NaN`); манифест сверх лимита кодека — если лимит достижим в ≤ 64 КиБ ZIP, иначе исключить с причиной.
   - **V2 (код 1):** отсутствует обязательное поле; неверный тип; лишнее поле под `unevaluatedProperties`; неверная версия формата 1.0 по схеме.
   - **V3 (код 1):** по одному случаю **на каждое правило каталога V3, способное дать `error`** при документе, проходящем V2. Список правил — из `checked_rules` прогона; правило, которое невозможно нарушить документом, проходящим V2, — в таблицу отчёта с объяснением. `tags_search_key` (отложено, O-08) — не проверяется.
   - **V4 (код 1):** SHA-256 не совпадает; размер не совпадает; поток отсутствует; неверный CRC; неподдерживаемый метод сжатия; флаг шифрования.
   - **Структура и безопасность (код 1):** не ZIP вообще (нет EOCD); `../` и абсолютный путь в имени; обратный слэш; дубли имён записей; коллизия регистра; запись с атрибутами символьной ссылки — каждый с ожидаемым `message_id`.
4. **`expected.json` и схема `schemas/expected.v1.schema.json`.** Схему по этой структуре пишет исполнитель (разрешено в этой задаче):
   ```json
   {
     "format": "am-expected", "version": 1, "kind": "golden_zip",
     "case": "neg-v4-sha-mismatch", "description": "…", "req": ["K-3", "K-6"],
     "input": { "zip": "asset.zip" },
     "checks": [
       { "command": "verify", "args": ["--level", "full"], "exit_code": 1,
         "json": { "v1": "passed", "v2": "passed", "v3": "passed", "container_verification": "partial",
                   "v4": [ { "status": "failed" } ] } }
     ]
   }
   ```
   - `kind` — перечисление; сейчас только `golden_zip`. Новые виды (импорт, M3a) добавятся новыми значениями `kind` без смены `version`.
   - `json` — **шаблон-подмножество** вывода `am asset … --json`: объекты сравниваются по ключам шаблона рекурсивно; массивы — той же длины, элементы сопоставляются без учёта порядка по подмножеству. ID и время в шаблон не пишутся (сравнение по свойствам, ADR-0029 п. 4).
   - Каждый случай содержит минимум проверки `validate` и `verify --level full`; для положительных — также `inspect`.
   - Все `expected.json` проверяются по схеме в ctest (расширить `schema_check` или новый `expected_schema_check` — на выбор исполнителя; `jsonschema` из `.cache/pylib`).
5. **Прогон корпуса.** ctest `golden_zip` (Python, `-I`, только при `TARGET am_cli`): для каждого случая выполняет команды из `checks` через собранный `am`, сверяет код выхода и шаблон. Метки ctest — `req:K-3;req:K-6;req:ADR-0035`. Вывод при провале — случай, команда, расхождение по пути JSON.
6. **Не-ZIP как провал V1** (замечание 1 приёмки T-012). В `storage::repository::verify_container`: ошибка `ZipArchive::open` с `Errc::corrupt_data` или `Errc::unsupported` даёт отчёт `v1 = failed` с этой ошибкой в `error` (как сейчас при ошибке чтения манифеста), а не ошибку `Result`. Ошибки ввода-вывода (`not_found`, `io_error`, `permission_denied`, `resource_exhausted`) остаются ошибкой операции (код 4). Путь `AssetRepository` (load/check/commit) не меняется. Обновить `docs/user/cli.md` (коды выхода) и `CHANGELOG.md`. Тест T-012, ожидающий 4 для не-ZIP, если такой есть, меняет ожидание на 1 — это единственное разрешённое изменение ожиданий существующих тестов.
7. **Отчёт трассировки `tools/coverage/req_report.py`.**
   - Источники: XML GoogleTest для каждого теста (`gtest_discover_tests(... XML_OUTPUT_DIR <build>/gtest-xml)` — свойства `req` из `RecordProperty`); метки ctest `req:*` из `ctest --show-only=json-v1`; результаты PASS/FAIL/SKIP из JUnit XML ctest (`--output-junit`, T-005).
   - Грамматика ID (уточнена решением В-1): требования и решения — `K-<n>`, `NFR-14.<x>.<y>`, `SC-<n>`, `ADR-<nnnn>`, `O-<nn>`, `R-<nn>[.<n>]`, `X-<nn>`, `MF-<nn>`; случаи приёмки из `docs/tz/R01-R09_approved_handoff.md` — `S-<nn>`, `M-<nn>`, `N-<nn>`, `D-<nn>`, `U-<nn>`; несколько — через `|` в `RecordProperty`, отдельными метками в ctest. Неверно оформленный ID — **ошибка** отчёта (код 1) с перечнем мест.
   - Результат: `req_report.md` и `req_report.json` в каталоге сборки: требование → тесты → итог; тесты без `req` — отдельный список; ID из тестов, которых нет в `acceptance_matrix.md`, и строки матрицы без тестов — **информационные** списки (не ошибка).
   - Подключение: ключ `--ci` скриптов сборки (T-005) после ctest запускает отчёт; workflow `ci.yml` загружает `req_report.*` артефактом. ctest `req_report_selftest` — модульная проверка разбора на малых синтетических XML/JSON в `tests/tools/fixtures/`.
   - Проставить `req` тестам, у которых его нет, задача **не требует** — только перечислить их в отчёте исполнителя (число и примеры).

### Отклонения и вопросы

**В-2. Какое ожидание требуется для безопасного незарегистрированного потока при отдельной CLI-проверке ZIP?**

Пункт 3 требует случай «V4 (код 1): … незарегистрированный поток», а п. 5 запускает его именно через собранный `am`. Фактически `am asset verify <zip> --level full --json` возвращает 3 и `verified_crc_size_only`. Это соответствует `docs/specifications/container_manifest_v1.md` §1 (строки 42–50: безопасные неизвестные записи существующего контейнера относятся к opaque и сохраняются) и §12 (строки 435–444: запрет opaque относится к новым контейнерам; `verified_crc_size_only` — не ошибка, свод `partial`).

Причина в коде: `src/storage/repository/repository.cpp:259` отклоняет незарегистрированный поток только при переданном `allowed_opaque`, если пути нет в разрешённом наборе. Самостоятельный `verify_container` вызывает `check_container` без этого набора (строка 284), поэтому для безопасного потока с верным CRC используется ветвь `verified_crc_size_only` (строка 263). Контекст создания/изменения репозитория отличается от отдельного чтения ZIP.

Самостоятельно заменить требуемый код 1 на 3 нельзя: раздел «Файлы» прямо запрещает подгонять ожидание при расхождении корпуса со спецификацией/валидатором и предписывает остановку. Менять семантику самостоятельного чтения также не разрешено: единственное заданное изменение `verify_container` — классификация ошибки открытия не-ZIP по п. 6; поведение `AssetRepository` должно сохраниться.

Предлагается уточнить состав корпуса: безопасный opaque-поток существующего ZIP проверять как частичный результат `verify = 3`, а запрет создания нового контейнера с незарегистрированным потоком проверять в контексте создания/фиксации, где передаётся `allowed_opaque`. Если для standalone `verify` требуется именно код 1, нужно согласовать соответствующее изменение требований/спецификации и разрешённого объёма кода. До решения управляющего выполнение остановлено; продолжать следует в той же ветке `codex/T-013`.

**В-3. Разрешить исправление проверки типа ZIP-записи при standalone validate/verify и определить уровень/`message_id` для отказа?**

Пункт 3 задачи требует код 1 для symlink; решение В-2 п. 2 повторяет это требование, включая незарегистрированные записи. Воспроизведение теперь закоммичено в корпусе: `neg-zip-symlink` и `neg-zip-opaque-symlink`. В обоих `case.json` меняется только `external_attr` нужной записи на `0o120777 << 16`; central `create_system = 3` (Unix), поток/CRC/размер/манифест остаются корректными. Это атрибут записи внутри ZIP; ссылок на файловой системе тест не создаёт и ничего не извлекает.

```text
python -I tests/golden/run_golden.py --am build/win-cli/bin/am.exe --corpus tests/fixtures/golden --case neg-zip-symlink
  validate: expected exit 1, actual 0; expected V3 failed, actual passed
  verify full: expected exit 1, actual 0; expected V3 failed, actual passed

python -I tests/golden/run_golden.py --am build/win-cli/bin/am.exe --corpus tests/fixtures/golden --case neg-zip-opaque-symlink
  validate: expected exit 1, actual 0; expected V3 failed, actual passed
  verify full: expected exit 1, actual 3; expected V3 failed, actual passed
```

Причина: ZIP-механизм распознаёт `EntryKind::symlink` (`src/storage/asset_zip/reader.cpp`, разбор Unix mode), но сам допускает чтение такого потока. `check_normative_profile` выдаёт `am.zip.profile.entry_kind` для любого не-regular типа (`src/storage/asset_zip/profile.cpp:24`); в standalone-пути этот профиль не вызывается. Репозиторный `Invariants::validate` добавляет `zip_paths`, но проверяет только длину/безопасность имени и коллизии, без `EntryInfo::kind`. Поэтому все V1–V3 проходят и V4 считает зарегистрированный symlink проверенным по SHA.

Ожидания не изменены на фактические 0/3; исправление проверки безопасности не включено в единственное разрешённое изменение `repository.cpp` по п. 6 (классификация ошибки открытия ZIP). Нужно решение управляющего о месте и объёме исправления, уровне и стабильном ID находки. Нельзя без отдельного решения просто подключить весь `check_normative_profile`: он также выдаёт нарушение для data descriptor, тогда как положительный descriptor обязателен в этом корпусе. После решения продолжать в той же ветке `codex/T-013` с сохранённой частичной реализацией.

### Решение управляющего по В-3 (2026-11-13)

**Дефект подтверждён; исправление входит в задачу.** Ожидания `neg-zip-symlink` и `neg-zip-opaque-symlink` верны (SPEC §1 п. 3: нарушения безопасности не получают исключений из-за `opaque`); принимать запись-ссылку как проверенный поток нельзя — при извлечении это путь к записи за пределы целевого каталога. SPEC §1 п. 3 дополнен явной фразой (коммит управляющего в этой ветке).

1. **Место.** Новое правило репозитория `zip_entry_kind` в `Invariants::validate` (`src/storage/repository/repository.cpp`), рядом с `zip_paths` и тем же способом: `checked_rules` получает `zip_entry_kind`; для каждой записи ZIP с `EntryInfo::kind` ≠ `EntryKind::regular` — находка уровня `error`, `rule = zip_entry_kind`, `message_id = am.manifest.zip_entry_kind`, `pointer` пуст, `detail` — диагностическое имя записи (как у `zip_paths`) и тип (`symlink`/`special`/`directory`). Проверка применяется ко всем записям — зарегистрированным, opaque и `manifest.json`.
2. **Почему не `check_normative_profile`.** Профиль — правила **писателя** (запрещает data descriptor, требует UTF-8-флаг), а читатель обязан принимать descriptor (положительный корпус). Из профиля берётся только смысл одной проверки, сам профиль в standalone-путь не подключается.
3. **Каталожные записи** (`kind = directory`, имя с `/` на конце) уже дают `zip_paths` (пустой компонент пути); вторая находка `zip_entry_kind` для них допустима и не считается дублем. Отдельный случай корпуса не требуется.
4. **Уровень и код.** Находка V3 `error` → `v3 = failed`, `validate`/`verify` — код 1. Для зарегистрированного symlink V4 по-прежнему может дать `verified_sha256` — шаблоны `expected.json` проверяют V3 и код выхода, состояние V4 у этих случаев не фиксировать.
5. **Каталог сообщений.** `resources/messages/en.toml`: `"am.manifest.zip_entry_kind" = "A ZIP entry is not a regular file (for example, a symbolic link)."`
6. **Тест.** Новый тест в `tests/unit/test_asset_repository.cpp`: ZIP через `zip_test::build` с записью Unix symlink — зарегистрированной и незарегистрированной; `verify_container` → `v3 = failed`, находка `zip_entry_kind` с именем записи в `detail`. `RecordProperty("req", "K-6|ADR-0037")`.
7. **Влияние на `AssetRepository`.** `Invariants` общий: ассет с такой записью перестанет открываться на изменение — это намеренно (контейнер с нарушением безопасности не изменяется). Прочие ожидания существующих тестов не меняются; если какой-то упадёт — остановиться и сообщить.

**Расширение раздела «Файлы» для В-3:** `src/storage/repository/repository.cpp` — только `Invariants::validate` (правило `zip_entry_kind`) сверх п. 6; `resources/messages/en.toml` — одна строка; `tests/unit/test_asset_repository.cpp` — один новый тест; `CHANGELOG.md` — строка про отказ для записей-ссылок. Продолжать в той же ветке `codex/T-013`, статус — `in_progress`.
