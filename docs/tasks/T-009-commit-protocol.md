# T-009. Протокол фиксации ZIP: журнал, проверка до замены, атомарная замена, восстановление (NTFS; спайки S5/S5+ в части NTFS)

**Статус:** done (принята 2026-11-12) · **Веха:** M1 (`am_storage`, P0.4) + M0 (S5, S5+ — только NTFS) · **Основание:** ТЗ 4.6, 4.8.2, §14.2.7–8, §14.5.2–3, §19.4.7.4; ADR-0006, ADR-0025 пп. 1, 3, 4, 6, ADR-0031 пп. 3–4, ADR-0033 п. 1, ADR-0035 п. 7, ADR-0024, ADR-0032; критерии 116, 117; T-007 (читатель), T-008 (писатель, раздел «Приёмка»)

## Цель

Дать хранилищу один способ **заменить действующий ZIP новым так, чтобы в любой момент на диске был хотя бы один корректный ZIP** (ADR-0006, ТЗ 4.6.2):
1. до начала — запись в журнале `pending_ops` и проверка свободного места;
2. новый ZIP пишется писателем T-008 во временный файл на том же томе;
3. перед заменой — полная проверка нового файла;
4. атомарная замена, при которой уже открытый читатель продолжает видеть старое содержимое (S5+);
5. восстановление после сбоя на любом шаге — при следующем запуске.

Одновременно задача отвечает на вопросы спайков **S5** и **S5+ для NTFS**: работает ли переименование с POSIX-семантикой при открытом читателе, атомарна ли видимость, восстанавливается ли состояние после `kill` на каждом шаге. Остальные ФС (ext4, exFAT, FAT32, SMB) и отключение питания — не здесь.

`AssetRepository` (`ChangeRequest`, `expected_rev`, ревизии и `history`, мьютекс в процессе, `AssetSnapshot`, события), индекс, манифестная проверка V2–V4 и режим поколений в задачу **не входят**. Они строятся поверх этого слоя в следующей задаче.

## Решения управляющего (не пересматривать в задаче)

1. **Размещение (ADR-0024).**
   - Протокол — `am_storage`, каталог `commit/`: `include/am/storage/commit/`, `src/storage/commit/`.
   - Журнал на SQLite — `am_storage`, каталог `db/`: `include/am/storage/db/`, `src/storage/db/`. Это первая часть слоя `db` из M2, ограниченная таблицей `pending_ops`.
   - Всё собирается только при `AM_WITH_CONTAINER=ON`. sqlite3 — `PRIVATE` (порт уже в `vcpkg.json`, `libraries.md`: ✅, собственная тонкая RAII-обёртка).
2. **Журнал — `state.sqlite` по `schemas/sql/state.sql` без изменений.** Если базы нет, она создаётся выполнением `state.sql` целиком: схема утверждена, `user_version = 1`. Текст схемы встраивается в сборку на этапе конфигурации из файла `schemas/sql/state.sql` (не копией в коде). Если база есть, но `user_version` ≠ 1, — `unsupported` (миграции — M2). Протокол работает с журналом через интерфейс `CommitJournal`. В тестах допускается реализация в памяти, но kill-тесты используют **настоящую** SQLite-реализацию.
   - Каждый переход состояния **долговечен до возврата** (`synchronous = FULL` из схемы, отдельная транзакция на переход).
3. **Способ замены на Windows — переименование с POSIX-семантикой** (ADR-0025 п. 3, основной режим):
   - `SetFileInformationByHandle(FileRenameInfoEx, FILE_RENAME_FLAG_POSIX_SEMANTICS | FILE_RENAME_FLAG_REPLACE_IF_EXISTS)` на дескрипторе временного файла, открытом с правом `DELETE`;
   - при отказе ОС **именно** из-за неподдерживаемой функции (`ERROR_INVALID_PARAMETER`, `ERROR_NOT_SUPPORTED`, `ERROR_INVALID_FUNCTION`) — запасной путь `MoveFileExW(MOVEFILE_REPLACE_EXISTING | MOVEFILE_WRITE_THROUGH)`; в результате фиксации указывается, каким путём сделана замена;
   - `ReplaceFileW` с резервной копией `.am-bak` **не используется**: замена переименованием атомарна, а резервная копия создаёт третье состояние без пользы для восстановления. Колонка `backup_path` журнала остаётся `NULL`.
   - POSIX-ветка (`rename` + `fsync` каталога) пишется, но только компилируется условно: проверить её здесь нечем (Linux — T-005). В отчёте она помечается как непроверенная.
   - Режим поколений (exFAT, SMB) — не здесь. Если на томе нет ни POSIX-переименования, ни `MoveFileExW`, это ошибка `unsupported`; молчаливой деградации нет.
4. **Читатели действующего ZIP открывают его с `FILE_SHARE_READ | FILE_SHARE_DELETE`.** Это необходимое условие замены при открытом читателе. `file_source` из T-007 сейчас открывает файл только с `FILE_SHARE_READ`; разрешение `FILE_SHARE_DELETE` добавляется **аддитивно** — параметром или отдельной функцией, поведение по умолчанию не меняется.
5. **Проверка перед заменой — обязательная и расширяемая** (ADR-0006 шаг 4, ADR-0035 п. 7). Протокол всегда выполняет:
   - `verify_written` (T-008): структура, CRC всех записей, SHA-256 новых;
   - `probe_container` → `own` (свой контейнер поддерживаемой версии).
   После этого вызывается проверка вызывающего кода (callback). В `AssetRepository` это будут V1–V4 и сверка манифеста; здесь — точка расширения с тестами. Любой отказ — до замены.
   - Временный файл используется **только** после успешных `ZipWriter::finish()` и полной проверки (замечание 1 приёмки T-008). Никакой код не читает и не переименовывает временный файл до состояния `verified`.
6. **Межпроцессная блокировка ассета** (ADR-0025 п. 4): `.am/locks/<asset_id>.lock`, `LockFileEx` (эксклюзивная, без ожидания либо с таймаутом из параметров). Она держится всю фиксацию и всё восстановление этого ассета. Занята — `Errc::locked`. Блокировка — ОС-объект; содержимое файла (PID, время) — только диагностика. Мьютекс внутри процесса и `library.lock` — не здесь (`AssetRepository`, M2).
7. **Свободное место** (ADR-0033 п. 1): до записи `prepared` вычисляется `need = estimated_size + max(5 %, 256 МиБ)`. Запас — гипотеза с комментарием `hypothesis, O-17`; `estimated_size` передаёт вызывающий код. Если `GetDiskFreeSpaceExW` для тома временного каталога показывает меньше `need` — `insufficient_space` **до** создания временного файла и до записи в журнал. Нехватку во время записи ловит писатель (T-008); она завершает операцию до замены. `StorageCapabilities::max_file_size` передаётся в `WriterLimits`.
8. **Пути библиотеки:** `<library>/.am/state.sqlite`, `<library>/.am/.am-tmp/<asset_id>.<op_id>.zip` (`docs/architecture/jobs_and_sessions.md`), `<library>/.am/locks/<asset_id>.lock`. Целевой путь ZIP передаёт вызывающий код. Он должен лежать в `<library>` и на том же томе, что `.am-tmp`; иначе — `invalid_argument` до записи в журнал.
9. **Ошибки** — новые `message_id` `am.commit.*` (п. 7 «Требований»), новые `Errc` не добавлять.

## Требования

### 1. `CommitJournal` и `StateJournal` (SQLite)

- Запись журнала — поля `pending_ops` из `state.sql`: `op_id` (UUIDv4), `asset_id`, `kind` (`create`/`update`/…, строки из схемы), `target_path`, `temp_path`, `backup_path` (всегда `NULL`), `base_rev`, `base_size`, `base_mtime_ns`, `base_manifest_sha256`, `state`, `expected_rev`, `started_at`, `updated_at` (RFC 3339 UTC), `job_id`.
- Операции: `insert(prepared)`, `advance(op_id, from, to)` (только допустимые переходы `prepared → verified → committed → indexed`, и сравнение с ожидаемым текущим состоянием: иначе `conflict`), `remove(op_id)`, `list()`, `find(op_id)`. Ошибка SQLite → `io_error` `am.commit.journal_error`, причина SQLite — в `ctx.detail`.
- `StateJournal::open(library_root)` создаёт `.am/` и базу при отсутствии (п. 2 «Решений»), проверяет `user_version`, включает `foreign_keys`; WAL и `synchronous = FULL` — из схемы.

### 2. Фиксация — `commit_zip(CommitRequest)` → `CommitResult`

`CommitRequest`: `library_root`, `asset_id`, `kind`, `target_path`, `op_id` (если не задан — новый UUIDv4), `base` (ожидаемое состояние целевого файла: отсутствует — для `create`, либо `size`, `mtime_ns`, `manifest_sha256` и `base_rev`), `estimated_size`, `StorageCapabilities` (минимум `max_file_size`), `ZipLimits`, `producer` (callback, получает `ZipWriter&` и возвращает `Result<void>`), `verifier` (callback, получает открытый `ZipArchive` нового файла, может быть пустым), `ReadBudget&` проверки, хуки внедрения отказов (только для тестов, п. 6).

Шаги (номера = ADR-0006):
1. Блокировка ассета. Проверка путей (п. 8 «Решений»). Сверка `base` с фактическим целевым файлом: размер, `mtime`, SHA-256 записи `manifest.json` (читатель T-007, поток с SHA-256). Расхождение → `conflict` `am.commit.base_changed`. Проверка места. Запись `prepared` в журнал.
2. Создание временного файла (`FileSink`, `CREATE_NEW`), вызов `producer`, `ZipWriter::finish()` (он же делает `flush`). Ошибка `producer` или писателя → удаление временного файла, удаление записи журнала, ошибка наружу.
3. Повторное открытие временного файла **только на чтение**, проверка по п. 5 «Решений». Отказ → удаление временного файла и записи журнала, `corrupt_data` `am.commit.verification_failed` (причина — в `cause`).
4. `advance(prepared → verified)`.
5. Повторная сверка `base` (между шагами 1 и 5 файл мог измениться вне протокола, несмотря на блокировку, — например, другой программой). Расхождение → откат (как в шаге 3), `am.commit.base_changed`.
6. Замена (п. 3 «Решений»). `advance(verified → committed)`.
7. Вызов необязательного `on_committed` (в будущем — переиндексация; здесь — точка расширения), `advance(committed → indexed)`, `remove(op_id)`, снятие блокировки.

`CommitResult`: `op_id`, итоговый размер, SHA-256 `manifest.json` нового файла, `mtime_ns`, способ замены (`posix_rename`/`move_file_ex`/`rename`), `WriteSummary`.

### 3. Восстановление — `recover(library_root, ...)` → отчёт по операциям

Вызывается при открытии библиотеки на запись (в будущем) и в тестах явно. Для каждой записи журнала — под блокировкой ассета:
- `prepared` → удалить временный файл (если есть), удалить запись. Цель не трогается.
- `verified` — три случая, проверяются в этом порядке:
  1. временный файл есть, цель совпадает с `base` (размер, `mtime`, SHA-256 манифеста), временный файл заново проходит встроенную проверку п. 5 «Решений» → завершить замену и шаги 6–7, исход `completed`. Callback вызывающего кода при восстановлении недоступен; в отчёте восстановления это помечается (`verifier_skipped = true`), а `AssetRepository` решит, достаточно ли этого;
  2. временного файла нет, а размер и SHA-256 манифеста цели равны **ожидаемым для нового файла** → замена уже произошла (переименование атомарно: имя временного файла исчезает ровно в момент замены), исход `already_committed`, далее шаги 6–7;
  3. иначе — откат: удалить временный файл, если есть, удалить запись, исход `rolled_back`. Цель не трогается.

  Для случая 2 при переходе в `verified` в журнал записываются ожидаемые размер и SHA-256 манифеста нового файла. В `pending_ops` для этого нет колонок, поэтому `StateJournal` создаёт **дополнительную** таблицу `pending_ops_new(op_id TEXT PRIMARY KEY REFERENCES pending_ops(op_id) ON DELETE CASCADE, new_size INTEGER NOT NULL, new_manifest_sha256 TEXT NOT NULL)` через `CREATE TABLE IF NOT EXISTS`, в той же транзакции, что и переход. `state.sql` и `user_version` не меняются; включение таблицы в схему v2 — решение управляющего в M2 (миграции).
- `committed` → `on_committed`, `indexed`, удалить запись.
- `indexed` → удалить запись.
- Временные файлы `.am/.am-tmp/*.zip`, не упомянутые в журнале, удаляются только если старше 24 ч (время — параметр, для тестов подставляемое) **и** не открыты другим процессом (проверка открытием с запретом совместного доступа; занятый файл не удаляется) — ТЗ 4.6.5, ADR-0006.

Отчёт восстановления: по каждой операции — исход (`rolled_back`, `completed`, `already_committed`, `cleaned`, `skipped_locked`, `failed` с ошибкой) и признак `verifier_skipped`. Ошибка одной операции не мешает остальным.

### 4. Чтение действующего ZIP при замене (S5+)

- Аддитивно к T-007: способ открыть `file_source` с `FILE_SHARE_READ | FILE_SHARE_DELETE` (п. 4 «Решений»).
- Читатель, открытый до замены, после замены продолжает читать **старое** содержимое целиком и без ошибок CRC; новый `file_source`, открытый после замены, видит новое содержимое.

### 5. Попутное изменение (замечание 2 приёмки T-008)

- Аддитивно: `EntryInfo::dos_time`, `EntryInfo::dos_date` — значения из центрального каталога.
- `copy_raw` переносит время и дату записи источника; время из `WriterOptions` для raw-копии больше не используется. Тесты T-008, проверяющие байты raw-копии, остаются в силе. Если какой-то тест закреплял время по умолчанию у raw-копии, ожидание меняется **только** в этой части, с пояснением в отчёте.

### 6. Внедрение отказов и kill-тесты

- Точки отказа (перечисление, только для тестов): `after_lock`, `after_prepared`, `mid_write` (после половины данных `producer`), `after_finish`, `after_verify`, `after_verified_journal`, `before_replace`, `after_replace`, `after_committed_journal`, `after_indexed_journal`.
- Режим «исключение/ошибка» — для unit-тестов в процессе.
- Режим «kill» — вспомогательный исполняемый файл `am_commit_crash_helper` (только в тестах, `tests/integration/` или `tests/unit/`): выполняет фиксацию и в заданной точке завершает **свой процесс** немедленно (`TerminateProcess(GetCurrentProcess(), …)`), без деструкторов и сброса буферов. Родительский тест запускает его, дожидается завершения, затем проверяет инварианты и вызывает `recover`.

### 7. Коды ошибок

| Ситуация | `Errc` | `message_id` |
|---|---|---|
| цель или временный каталог вне библиотеки / на другом томе | `invalid_argument` | `am.commit.invalid_path` |
| блокировка ассета занята | `locked` | `am.commit.locked` |
| цель не совпала с `base` | `conflict` | `am.commit.base_changed` |
| мало места до начала | `insufficient_space` | `am.commit.insufficient_space` |
| проверка нового файла не прошла | `corrupt_data` | `am.commit.verification_failed` |
| ошибка замены ОС | `io_error` | `am.commit.replace_failed` |
| нет способа атомарной замены на томе | `unsupported` | `am.commit.replace_unsupported` |
| ошибка журнала / недопустимый переход | `io_error` / `conflict` | `am.commit.journal_error` |
| `user_version` базы ≠ 1 | `unsupported` | `am.commit.journal_version` |

Ошибки писателя и читателя передаются как есть (их `message_id`) или в `cause`. Подробности — в `ctx.detail` на английском; исключения через границу модуля не проходят.

## Тесты

Теги `RecordProperty("req", …)`: `K-117` (заполненный том), `K-116` (память при проверке), иначе `ADR-0006`/`ADR-0025`/`ADR-0033`.

1. **Успешная фиксация:** `create` (цели нет) и `update` (цель есть) — новый файл на месте, журнал пуст, временный каталог пуст, `CommitResult` совпадает с фактом (размер, SHA-256 манифеста), способ замены — `posix_rename` на NTFS.
2. **Журнал:** создание базы из `state.sql` (сверка `user_version = 1` и наличия таблиц схемы), допустимые и недопустимые переходы, долговечность — запись видна новым соединением сразу после возврата, `user_version` = 2 → `journal_version`.
3. **Отказы до замены (в процессе)**, для каждой точки до `before_replace`: ошибка `producer`, ошибка писателя, отказ `verifier`, отказ встроенной проверки (испорченный CRC через тестовый `producer`, `probe` ≠ `own`) — цель не изменена побайтно, временный файл удалён, записи журнала нет.
4. **`base_changed`:** цель изменена до шага 1 и между шагами 1 и 5 (через хук) → откат, цель — изменённая чужая версия, не перезаписана.
5. **Блокировка:** второй процесс (`am_commit_crash_helper` в режиме «держать блокировку») держит `.lock` → фиксация `locked`, ничего не создано; после его завершения — успех. Блокировка снимается ОС при `kill` держателя.
6. **Место:** `estimated_size` больше свободного места (через подставляемую функцию запроса места) → `insufficient_space`, нет временного файла и записи журнала; нехватка во время записи (приёмник с внедрённым отказом через тестовый хук создания приёмника) → цель цела (К-117).
7. **Kill-тесты (S5, NTFS):** для **каждой** точки отказа п. 6 — `kill` вспомогательного процесса, затем проверка:
   - цель — либо старый, либо новый корректный ZIP (`ZipArchive::open` + `verify_entry` всех записей), никогда не промежуточный;
   - `recover` приводит к ожидаемому исходу: до `after_verified_journal` — откат (старый ZIP), `after_verified_journal`/`before_replace` — завершение (новый ZIP), `after_replace` и позже — `already_committed`/`completed` (новый ZIP);
   - после `recover` журнал пуст, `.am-tmp` пуст, блокировка свободна.
   Каждую точку прогнать не менее 3 раз; итоговая таблица «точка → исход × число прогонов» — в отчёте.
8. **Открытый читатель (S5+, NTFS):** читатель открыт с `FILE_SHARE_DELETE` до фиксации → замена успешна, старый читатель дочитывает **все** записи старой версии с верным CRC, новый — новую; то же при `kill` после замены. Читатель **без** `FILE_SHARE_DELETE` → замена получает `replace_failed`, цель цела, временный файл удалён откатом (фиксирует, почему п. 4 «Решений» обязателен).
9. **Запасной путь замены:** через тестовый хук заставить POSIX-переименование вернуть `ERROR_NOT_SUPPORTED` → замена `MoveFileExW`, результат `move_file_ex`; иная ошибка ОС (например, `ERROR_ACCESS_DENIED`) → запасной путь **не** используется, `replace_failed`.
10. **Очистка `.am-tmp`:** файлы без записи журнала — моложе 24 ч не удаляются; старше — удаляются; старше, но открытые другим дескриптором — не удаляются (`skipped`).
11. **`recover` при нескольких операциях:** три записи в разных состояниях и одна с занятой блокировкой → независимые исходы, занятая — `skipped_locked`, запись остаётся.
12. **Время DOS при raw-копии:** источник с ненулевыми временем и датой → в копии те же значения; новая запись по-прежнему использует `EntryOptions`/`WriterOptions`.
13. **Память проверки (К-116):** фиксация нового ZIP с записью 1 ГиБ нулей (Deflate) — пик процесса выводится в отчёт, порога нет.

## Решение управляющего по В-1

**2026-11-11.** Вопрос обоснован, остановка по п. 3 `AGENTS.md` правильная. Воспроизведение показало и второй дефект ТЗ: в случае 2 (`already_committed`) совпадение размера и SHA-256 манифеста тоже не доказывает, что на месте цели лежит **наш** новый файл, а не посторонний с тем же манифестом. Оба случая решаются одним механизмом — **тождеством файла по SHA-256 всех его байтов**, а не повторной сверкой с утраченным `WriteSummary`.

1. **Что хранится.** Дополнительная таблица — с такими колонками (заменяет прежний состав):
   `pending_ops_new(op_id TEXT PRIMARY KEY REFERENCES pending_ops(op_id) ON DELETE CASCADE, new_size INTEGER NOT NULL, new_file_sha256 TEXT NOT NULL, new_manifest_sha256 TEXT NOT NULL)`.
   Строка пишется **в той же транзакции**, что и переход `prepared → verified`. `new_manifest_sha256` нужен для `CommitResult` и как `base` следующей операции; для восстановления решает `new_file_sha256`. `WriteSummary` не сериализуется.
2. **Защита временного файла от изменения между проверкой и заменой (шаги 3–6).** После `ZipWriter::finish()` временный файл открывается **один раз** дескриптором с доступом `GENERIC_READ | DELETE` и совместным доступом **только** `FILE_SHARE_READ | FILE_SHARE_DELETE` (без `FILE_SHARE_WRITE`). Пока он открыт, никто не может писать в файл. Через этот дескриптор:
   - вычисляется SHA-256 всех байтов файла (последовательное чтение буфером фиксированного размера);
   - выполняется встроенная проверка п. 5 «Решений» (`verify_written`, `probe_container`) и `verifier` вызывающего кода — источник T-007 над этим дескриптором;
   - выполняется переименование (`SetFileInformationByHandle` требует права `DELETE` на этом же дескрипторе; запасной `MoveFileExW` — после закрытия дескриптора, по имени: в этот промежуток писатель ещё может вмешаться, поэтому после `MoveFileExW` протокол сверяет размер и SHA-256 цели с `new_size`/`new_file_sha256`, а при расхождении возвращает `am.commit.replace_failed`, и восстановление обрабатывает такой исход по п. 4).
   Источник над существующим дескриптором — внутренняя часть `am_storage` либо аддитивная функция рядом с `file_source`, на выбор исполнителя; поведение `file_source` по умолчанию не меняется.
3. **Восстановление `verified` — новые правила** (заменяют случаи 1–3 п. 3 «Требований»):
   1. временный файл есть, его размер и SHA-256 всех байтов равны `new_size`/`new_file_sha256`, цель совпадает с `base` → файл **тождествен** тому, что прошёл полную проверку до сбоя; повторная поэлементная проверка не нужна. Выполнить замену (через защищённый дескриптор по п. 2) и шаги 6–7, исход `completed`. `verifier_skipped = false`: проверка вызывающего кода уже прошла до записи `verified`, а тождество файла это доказывает;
   2. временного файла нет, размер и SHA-256 всех байтов цели равны `new_size`/`new_file_sha256` → замена уже произошла, исход `already_committed`, далее шаги 6–7;
   3. иначе — откат: удалить временный файл, если он есть, удалить запись, исход `rolled_back`; цель не трогается. Сюда же попадает временный файл, изменённый после сбоя: SHA-256 не совпал.
4. **`committed`** — перед шагами 6–7 размер и SHA-256 цели сверяются с `new_size`/`new_file_sha256`. Если цель уже другая, кто-то изменил её после фиксации: запись удаляется, исход `failed` с `am.commit.base_changed` в отчёте; цель не трогается.
5. **Признак `verifier_skipped` остаётся в отчёте** на будущее. В T-009 он всегда `false`: состояние `verified` пишется только после успешного `verifier`.
6. **Стоимость:** один дополнительный последовательный проход по временному файлу при фиксации и по цели или временному файлу при восстановлении. В отчёте указать время этого прохода в сценарии 13 (1 ГиБ); нормативов нет (O-17).
7. **Тесты — дополнения к разделу «Тесты»:**
   - kill после `after_verified_journal` с **подменой** байтов временного файла до `recover` (испортить один байт данных или подложить другой корректный ZIP с тем же `manifest.json`) → `rolled_back`, цель — старая;
   - kill после `after_replace`, затем замена цели посторонним корректным ZIP с тем же `manifest.json` до `recover` → не `already_committed`, а `rolled_back` (запись удалена, цель не трогается), с пояснением в отчёте восстановления;
   - попытка открыть временный файл на запись другим дескриптором между шагами 3 и 6 (через хук) → отказ ОС `ERROR_SHARING_VIOLATION`, фиксация продолжается успешно;
   - запасной путь `MoveFileExW`: подмена цели между закрытием дескриптора и переименованием невозможна в тесте напрямую; достаточно теста, что расхождение SHA-256 после `MoveFileExW` (через хук, подменяющий файл перед переименованием) даёт `replace_failed`.

### Kill-тесты: NTFS

`am_commit_crash_helper` использует настоящий StateJournal и завершает свой процесс через TerminateProcess(GetCurrentProcess(), 91), без деструкторов. Родитель проверяет код 91, валидность ZIP до/после recover (все записи с CRC/SHA), освобождение блокировки, пустые journal и .am-tmp. В каждом из двух полных прогонов:

| Точка | Исход recover | Прогонов | Цель после recover |
|---|---|---|---|
| `after_lock` | `no_pending_operation` | 3 | старый |
| `after_prepared` | `rolled_back` | 3 | старый |
| `mid_write` | `rolled_back` | 3 | старый |
| `after_finish` | `rolled_back` | 3 | старый |
| `after_verify` | `rolled_back` | 3 | старый |
| `after_verified_journal` | `completed` | 3 | новый |
| `before_replace` | `completed` | 3 | новый |
| `after_replace` | `already_committed` | 3 | новый |
| `after_committed_journal` | `completed` | 3 | новый |
| `after_indexed_journal` | `cleaned` | 3 | новый |

Для after_lock запись ещё не создана, поэтому отчёт пуст. Для after_indexed_journal возвращается cleaned согласно прямому правилу раздела «Восстановление» для indexed; новая цель сохраняется. Это уточняет обобщённую формулировку сценария 7 «after_replace и позже — already_committed/completed».

Подмена temp на другой валидный ZIP с тем же manifest и порча одного байта после verified дают rolled_back, исходная цель сохранена. Подмена target после after_replace даёт rolled_back с пояснением о несовпадении проверенного файла; чужая цель не меняется. Подмена после committed даёт failed / am.commit.base_changed; запись удалена, чужая цель сохранена. Попытки открытия temp на запись после проверки, после verified и непосредственно перед заменой получают ERROR_SHARING_VIOLATION. Подмена перед MoveFileExW обнаруживается после переноса как am.commit.replace_failed; verified остаётся для recover.

### S5/S5+: наблюдения и пределы подтверждения

Фактическая среда: `ENV Windows=10.0 build=19045 filesystem=NTFS volume=D:\` (версия ядра Windows; MSVC 14.44, SDK 10.0.26100.0). Все временные библиотеки — в `.cache/commit-tests/` на этом томе.

POSIX-переименование FileRenameInfoEx успешно при открытом читателе с FILE_SHARE_DELETE: старый дескриптор дочитывает все старые записи с корректными CRC/SHA, новые открытия видят новую версию. Это же подтверждено после kill в after_replace. Читатель с прежним share READ запрещает замену: replace_failed, старые байты сохранены, temp и journal удалены откатом.

Параллельный наблюдатель открывал файл во время трёх замен на разные версии; каждое чтение проверяло все CRC/SHA и полное побайтное совпадение с одной из четырёх ожидаемых версий:

Промежуточного, отсутствующего или повреждённого ZIP в этих наблюдениях не было. Это экспериментальное подтверждение атомарной видимости на данном NTFS и восстановимости после завершения процесса, не испытание отключением питания. **Durability NTFS — assumed, не verified**: FULL/flush и journal-переходы задействованы, но сбои питания/контроллера/кэша не проверялись. Для ext4 остаются rename/fsync и crash/power-loss проверки; для exFAT/FAT32/SMB — поддержка замены, совместный доступ, семантика сети/сбоев и необходимость режима поколений. Эти ФС здесь не тестировались; POSIX-ветка написана условно и на Linux не собиралась/не запускалась.

- Решение В-1 выполнено точно: доказательство (размер, SHA-256 файла и манифеста) пишется в `pending_ops_new` в той же транзакции, что и `prepared → verified` (сравнение с ожидаемым состоянием через `UPDATE … WHERE state=?` и `sqlite3_changes`). Временный файл после `finish()` открывается одним дескриптором `GENERIC_READ | DELETE` с совместным доступом только на чтение и удаление; через него идут хеш, `verify_written`, probe, `verifier` вызывающего кода, SHA-256 манифеста и POSIX-переименование.
- Восстановление опирается на тождество файла: `verified` с временным файлом — замена только если файл тождествен и цель равна `base`; без временного файла — `already_committed` только если цель тождественна новому файлу; `committed` — сверка цели, иначе `failed`/`base_changed` без изменения цели. `indexed` — `cleaned`.
- Блокировка ассета держится до конца операции, включая очистку при ошибке. После замены ошибки журнала и `on_committed` не откатывают файл, а оставляют запись для `recover()`.
- Очистка сирот: файлы `.am-tmp` вне журнала, старше 24 ч, открываются эксклюзивно и удаляются через тот же дескриптор, поэтому занятый файл не удаляется.
- SQLite подключена PRIVATE; схема `state.sql` встраивается при конфигурации без копии в исходниках; минимальная сборка не тянет sqlite/zlib/OpenSSL.
- Попутные изменения аддитивны: `file_source(path, share_delete)` с прежним поведением по умолчанию; время и дата DOS в `EntryInfo` и их перенос при raw-копии (замечание 2 приёмки T-008 закрыто).

Замечания без доработки — входят в ТЗ задачи `AssetRepository` или в план:
1. **Запасной путь `MoveFileExW`.** Если между закрытием дескриптора и переносом временный файл подменили, расхождение обнаруживается, но цель уже перезаписана посторонними байтами, а `recover()` откатывает запись — старая версия утрачена. На NTFS этот путь не используется (POSIX-переименование поддерживается). Для ФС, где нужен запасной путь, это ограничение режима — оно учитывается в `fs_support.md` при испытании такой ФС.
2. **Все читатели действующих ZIP обязаны открывать файл с `FILE_SHARE_DELETE`**, иначе фиксация получает `replace_failed`. Это входит в контракт `AssetSnapshot` и любого кода чтения библиотеки.
3. **Ошибка проверки** оборачивается в `am.commit.verification_failed` (`Errc::corrupt_data`), исходный код `verifier` — в `cause`. `AssetRepository` должен брать коды V1–V4 из `cause`, а не из верхней ошибки.
4. **Замер дополнительного прохода SHA-256** (около 3 мс) сделан на сжатом ZIP около 1 МБ из 1 ГиБ нулей и для несжимаемых данных не показателен. Замер на несжимаемых 1 ГиБ добавить в план NFR.
5. `StateJournal::open` для существующего, но пустого `state.sqlite` (сбой при создании) возвращает `am.commit.journal_version`, а не создаёт схему. Допустимо до миграций схемы в M2; там же `pending_ops_new` войдёт в схему v2.
