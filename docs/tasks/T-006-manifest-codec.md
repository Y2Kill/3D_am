# T-006. Кодек `manifest.json` по ADR-0038: строгий токенизатор, гибрид D2, проверка V2, защита записи

**Статус:** rework · **Веха:** M1 (`am_domain`, модуль 4 «Манифест») · **Основание:** ADR-0038 (итог S7), ADR-0037 п. 4, ADR-0036 п. 6, ADR-0024, ADR-0032; спецификация §1, §2, §8, §9, §10, §11; стенд `spikes/s7/` (T-004)

## Цель

Перенести механизм, доказанный спайком S7, в продукт: прочитать `manifest.json` строго, сохранить каждое непрозрачное значение исходным текстом, дать доменному коду править известную часть в DOM, записать результат собственным писателем и **до записи** доказать, что ни одно непрозрачное значение и ни одна числовая лексема не изменились. Это байтовый слой модуля «Манифест». Предметной модели (типизированных аксессоров), V3/V4 и ZIP в этой задаче нет.

Код стенда — образец поведения, а не код для копирования: в продукте нужны `am::Result`, линейная сложность, документированный API и тесты.

## Решения управляющего (не пересматривать в задаче)

1. **Размещение по уровням (ADR-0024).**
   - Строгий токенизатор JSON не зависит от сторонних библиотек → `am_foundation` (`include/am/foundation/json_text.hpp`, `src/foundation/json_text.cpp`). Он собирается и тестируется в минимальной сборке.
   - Кодек — модуль 4 «Манифест» → `am_domain` (`include/am/domain/manifest/`, `src/domain/manifest/`). Он зависит от nlohmann/json и jsoncons и собирается **только при `AM_WITH_CONTAINER=ON`** (пресет `win-cli`). В минимальной сборке `am_domain` остаётся INTERFACE-целью, как сейчас.
   - nlohmann/json — публичная зависимость `am_domain` (DOM известной части виден в API); jsoncons — **приватная** (V2 скрыта за pimpl). Заголовки jsoncons не попадают в публичные заголовки.
2. **Зависимости (`vcpkg.json`):** добавить `jsoncons`, удалить `json-schema-validator` (ADR-0038 пп. 4–5). Версия берётся из baseline `2026.10.16` (jsoncons 1.9.0). Загрузка порта разрешена; он уже лежит в `.cache/vcpkg-assets` и бинарном кэше после T-004, поэтому офлайн-повтор должен пройти.
3. **Шесть непрозрачных мест** (ADR-0037 п. 4, SPEC §10) определяются так, как в стенде (`spikes/s7/src/reference.cpp`, `opaque_groups`), с одним усилением:
   - `extensions.<ExtensionID>.data`;
   - `custom_values[].value` в `metadata` ассета, каждой группы и каждого файла, если `field_id` определён в `field_definitions[]` с `type` вида `plugin:…`;
   - `files[].generation.params`;
   - `claims[].value` в тех же `metadata`, если `target.kind = custom` и `target.field_id` — поле plugin-типа;
   - `field_definitions[].default` и `field_definitions[].constraints` для plugin-типов;
   - `history.entries[].details` и все ключи элемента `changes[]`, кроме `kind` и `target`.
   - **Усиление (fail-closed):** если `field_id` у `custom_values[]` или у claim с `target.kind = custom` **не разрешается** в `field_definitions[]`, значение тоже хранится как непрозрачный фрагмент. Тип такого значения неизвестен, поэтому через DOM оно не проходит. Ошибку разрешимости сообщит V3 (вне задачи).
4. **Числа известной части** (ADR-0038 п. 3). Перед передачей в nlohmann каждая числовая лексема известной части переводится **собственным кодом без `double`**:
   - если значение — целое в пределах int64 или uint64 (допустимы `1.0`, `1e2`, `-0` — их значения целые), в DOM попадает каноническая запись целого (`1`, `100`, `0`);
   - иначе (`1.5`, `1e400`, целое вне диапазона) — ошибка V1 `am.manifest.known_number_out_of_range` (`Errc::corrupt_data`).

   Сохранять лексему известного поля не требуется: известные поля подчиняются своим типам (принцип 1 O-13).
5. **Заглушки и фрагменты** — как D2: на месте корня непрозрачного поддерева в DOM стоит `binary` из 8 байт (номер фрагмента, little-endian). Писатель выводит каждый фрагмент **не более одного раза**, только после повторного строгого разбора фрагмента как ровно одного полного JSON-значения без дублей ключей. Любой другой `binary` в DOM (чужой размер, номер вне таблицы, повтор) — ошибка записи.
6. **Защита записи** сверяет непрозрачные значения по **ключам владельцев** (ADR-0038 п. 6): ExtensionID; область (`asset`, FileID, GroupID) + FieldID; FieldID определения; ClaimID (`id`); OperationID (`operation_id`) + ключ внутри записи истории; для `changes[]` — OperationID + индекс изменения + ключ. Внутри фрагмента — типизированный JSON-путь (`o:`/`a:`). Индексы массивов `files`, `groups`, `custom_values`, `claims`, `field_definitions`, `entries` в ключ **не входят**. Одинаковые ID у двух владельцев одного вида — запись запрещена.
7. **Намеренные изменения непрозрачных данных** объявляются явно. Удалить расширение, значение plugin-поля или claim — законные правки, но защита должна знать о них заранее. Вызывающий передаёт набор ключей владельцев, которые удалены, добавлены или заменены; всё остальное обязано совпасть точно.
8. **Пределы — гипотезы** (ТЗ §14.9.13, O-17 открыт): глубина 1024, размер 128 МиБ, глубина известной части 64. Это параметры структуры `CodecLimits` со значениями по умолчанию и комментарием `hypothesis, O-17`. Тесты не закрепляют их как норму.
9. **Коды ошибок** (ADR-0032; ядро не формирует текст для пользователя):

   | Ситуация | `Errc` | `message_id` |
   |---|---|---|
   | синтаксис JSON, недопустимый UTF-8, BOM, лишние данные после значения | `corrupt_data` | `am.manifest.invalid_json` |
   | дубли ключей | `corrupt_data` | `am.manifest.duplicate_key` |
   | превышены глубина или размер | `resource_exhausted` | `am.manifest.limit_exceeded` |
   | число известного поля вне типа | `corrupt_data` | `am.manifest.known_number_out_of_range` |
   | нарушение схемы (V2) | `corrupt_data` | `am.manifest.schema_violation` |
   | неоднозначный владелец, неизвестный или повторный `binary` | `unsupported` | `am.manifest.write_blocked` |
   | защита записи нашла расхождение | `internal` | `am.manifest.preservation_failed` |
   | нехватка памяти | `resource_exhausted` | `am.manifest.out_of_memory` |

   Токенизатор foundation не знает о манифесте и использует общие `am.json.invalid_json`, `am.json.duplicate_key`, `am.json.limit_exceeded` с теми же `Errc`. Кодек переводит их в `am.manifest.*`, а исходную ошибку кладёт в `cause`.

   Исключения nlohmann, jsoncons и `std::bad_alloc` перехватываются внутри модуля и через его границу не проходят. Технические подробности (байтовая позиция, ключ владельца, JSON-путь) — в `Error::message` и `ctx.detail` на английском, не в `message_id`.

## Требования

### 1. Токенизатор `am::json` (foundation)

- `Result<Tree> parse_strict(std::string_view text, const ParseLimits&)`. Дерево — плоский вектор узлов: вид (`object`, `array`, `string`, `number`, `literal`), байтовые границы `[begin, end)` в исходном тексте, родитель, дети, ключ ребра (декодированный) или индекс в массиве, декодированное значение строки.
- Грамматика RFC 8259 без расширений: недопустимы `01`, `+1`, `.5`, `1.`, `NaN`, `Infinity`, висячая запятая, комментарии, одинарные кавычки, управляющие символы U+0000…U+001F внутри строки, неизвестные escape-последовательности, лишние данные после значения.
- Вход — UTF-8 без BOM; недопустимый UTF-8 — ошибка. Escape `\uXXXX` с непарным суррогатом — ошибка (манифест — корректный Unicode).
- Дубли ключей сравниваются по **декодированным** ключам (`"a"` и `"a"` — дубль) и дают ошибку.
- **Без рекурсии по глубине входа**: явный стек. Предел глубины проверяется при входе в контейнер. Вход в 100 000 уровней при пределе 200 000 разбирается без переполнения стека.
- Сложность — линейная от размера входа (без повторного сканирования детей ради каждого ключа сверх проверки дублей хеш-таблицей).
- Функция `bool is_json_number(std::string_view)` для проверки отдельной лексемы.
- Без сторонних библиотек: только стандартная библиотека и `am_foundation`.

### 2. Документ манифеста (domain)

Публичный API в `include/am/domain/manifest/` (точные имена — на усмотрение исполнителя, смысл — обязателен):

- `struct CodecLimits` — `max_depth`, `max_bytes`, `max_known_depth`; значения по умолчанию — гипотезы из «Решений», п. 8.
- `Result<ManifestDocument> parse_manifest(std::string_view text, const CodecLimits& = {})` — V1:
  1. строгий разбор `am::json`;
  2. поиск корней шести непрозрачных мест (п. 3 «Решений»);
  3. перевод чисел известной части (п. 4);
  4. проверка глубины известной части до передачи в nlohmann;
  5. построение `nlohmann::ordered_json` известной части с заглушками `binary`.

  Документ хранит исходный текст и таблицу фрагментов.
- Доступ на чтение и запись к DOM известной части (`ordered_json&`). Правки делает вызывающий; кодек не знает доменных операций.
- `Result<nlohmann::ordered_json> ManifestDocument::make_opaque(std::string_view json_text)` — добавить новое непрозрачное значение (например, plugin-значение с большим числом). Текст проверяется строгим токенизатором как одно полное значение без дублей; возвращается новая заглушка.
- `std::vector<OpaqueKey> opaque_keys() const` — ключи владельцев всех непрозрачных корней текущего DOM, чтобы вызывающий мог сформировать набор намеренных изменений.
- `Result<std::string> write_manifest(const ManifestDocument&)` — собственный писатель обхода DOM (п. 5 «Решений»). Ключи и известные значения экранирует nlohmann; вывод компактный, порядок ключей — как в `ordered_json`.
- `Result<void> verify_preserved(std::string_view before, std::string_view after, const IntendedChanges&, const CodecLimits& = {})` — защита записи (пп. 6–7 «Решений»). Оба текста разбираются заново тем же кодом; сравниваются вид, декодированные строки, литералы и **точные лексемы** чисел каждого листа каждого непрозрачного значения по ключу владельца и типизированному пути. Ключ из `IntendedChanges` может отсутствовать до или после либо отличаться; любой другой ключ обязан совпасть. Сложность — O(n log n) или лучше: группы и индекс владельцев строятся **один раз** на документ.
- `class SchemaValidator` (pimpl, внутри jsoncons): `static Result<SchemaValidator> create(std::string_view schema_json)`; `Result<void> validate(const ManifestDocument&) const` — V2 по draft 2020-12 на теневом документе. В нём известная часть как в DOM (с каноническими числами), а каждое непрозрачное значение заменено пустым значением того же JSON-типа: `{}`, `[]`, `0`, `""` или исходный литерал. Схему кодек получает текстом и не читает файлы сам.

### 5. Тесты (`RecordProperty("req", "ADR-0038")`, для точных чисел также `R-09.8`)

Токенизатор (минимальная сборка):
1. Все недопустимые формы из п. 1, недопустимый UTF-8, BOM, непарный суррогат, лишние данные — ошибка с правильным `message_id`.
2. Дубли ключей, в том числе через escape.
3. Глубина: 100 000 уровней при пределе 1024 → `limit_exceeded`; при пределе 200 000 → успешный разбор, процесс не падает.
4. Допустимые числа (`-0`, `-0.0`, `1E+2`, `1e400`, `-1E-400`, `1.500`, длинные дроби) → `is_json_number` и разбор принимают их, границы лексемы точные.

Кодек (сборка `win-cli`):
5. **Без правок:** все допустимые фикстуры `tests/fixtures/manifest/s7/valid_*.json` → `parse_manifest` → `write_manifest` → `verify_preserved` с пустыми намеренными изменениями проходит; известная часть до и после совпадает.
6. **Структурная правка** на `valid_all.json` (сценарий T-004): изменить `title`; удалить первый `user:`-элемент `custom_values` перед plugin-значением; добавить запись `history.entries` только с известными полями; увеличить `asset.revision`; `modified_at` = timestamp новой записи. Защита проходит, выход проходит V2.
7. **Защита, отрицательные случаи:** изменённая лексема (`1.500` → `1.5`), сменённый владелец, удалённое и не объявленное непрозрачное значение, неоднозначный владелец (два расширения или две записи истории с одним ID) → ошибка. То же удаление, объявленное в `IntendedChanges`, проходит.
8. **Заглушки:** объект `{"bytes":[0,…],"subtype":null}` и строка-маркер во входе остаются обычными данными; `binary` чужого размера, с номером вне таблицы или повторный → ошибка записи.
9. **`make_opaque`:** `1,"x":2`, `1}`, `{} []`, `{"x":1,"x":2}` отвергаются; `[1e400,-0,1.500]` принимается и выводится байт в байт.
10. **Неразрешимый `field_id`** с `1e400` в значении сохраняет лексему.
11. **Числа известной части:** `"revision": 1.0` → в DOM `1`; `1.5`, `1e400`, `18446744073709551616` в известном целом поле → `known_number_out_of_range`.
12. **V2:** `schema_invalid_claim_extra.json` отвергается (`unevaluatedProperties`); все допустимые фикстуры принимаются; `1e400` в непрозрачном месте не мешает проверке.
13. **Глубина в непрозрачном месте:** 100 000 уровней внутри `extensions.*.data` при `max_depth` = 200 000 → чтение, запись и защита проходят без падения. Те же 100 000 уровней в известной части → `limit_exceeded` до nlohmann.
14. **Объём:** сгенерированный манифест не меньше 16 МиБ с не менее чем 100 000 непрозрачных листов → полный цикл (чтение, V2, правка `title`, запись, защита) проходит. Время и пик памяти — в отчёт, без порога в тесте.

### Сложность и замер сценария 14

- Токенизатор: один проход байтов и явный стек контейнеров; дубли проверяются хеш-таблицей объекта. Ожидаемая сложность O(n), память O(n), где n — объём входа/число узлов. Строки и escape декодируются собственным кодом, числа остаются с исходными границами. Дерево плоское, его разрушение тоже не рекурсивно по входу.
- Непрозрачные корни: индекс членов каждого объекта строится один раз (сортировка), поиск члена — бинарный. FieldID → plugin/core/неизвестен строится один раз. Владельцы представлены короткими векторами интернированных компонентов; длинный FileID/GroupID не копируется в каждый дочерний ключ. Общий пул до/после даёт точное равенство компонентов без хеш-коллизий. Регрессия проверяет V1 с FileID длиной 128 КиБ и 10000 владельцев до любой проверки UUID в V2.
- Защита: O(n log n) или лучше на сортировках/деревьях индексов; одинаковые owners сравниваются прямым итеративным обходом их деревьев. Для объекта сравниваются отсортированные декодированные ключи, для массива — индексы, для листьев — вид и декодированная строка/литерал/исходная числовая лексема. Это эквивалентно сравнению типизированных путей, но не материализует длинный путь каждого листа. Путь собирается только один раз при ошибке. Явный вывод строковых ключей методом opaque_keys дополнительно требует памяти/времени пропорционально размеру выдачи.
- Известные числа: грамматика проверяется отдельно, мантисса/масштаб обрабатываются десятичными цифрами. Экспонента насыщается на границе, выведенной из длины входа; огромная нулевая экспонента не требует разворачивания. Сравнение с пределами int64/uint64 — по длине и цифрам. Через double исходные известные числа не проходят.

### Отклонения и уточнения реализации

- API расположен в am::json и am::manifest; публичные имена и форма OpaqueKey/IntendedChanges выбраны в рамках задачи. OpaqueKey — экранированное scope-qualified имя корня, IntendedChanges содержит точный набор таких ключей. При непригодном DOM opaque_keys возвращает пустой список; подробная ошибка доступна через write_manifest, пустой список ничего не разрешает защите. Это документировано в заголовке.
- Дополнительно проверяется взаимно-однозначное соответствие binary и текущих непрозрачных корней. Правильный по размеру/номеру handle, перенесённый в известное поле, блокируется, чтобы V2 не заменяла известное значение заглушкой. Новый/заменяемый непрозрачный корень создаётся make_opaque; обычный DOM-объект вместо raw handle блокируется. Удалённые фрагменты могут оставаться в таблице и не выводятся; использованный handle выводится максимум один раз.
- Перед разбором переданной схемы также проверяются UTF-8/дубли и глубина её DOM: применяется существующая гипотеза max_known_depth из CodecLimits по умолчанию, поскольку create не принимает отдельного параметра лимитов. V2 получает текст и использует встроенный meta-resolver jsoncons; файлового/сетевого загрузчика кодек не подключает.
- Дополнительные регрессии выше усиливают обязательные сценарии; новых продуктовых нормативов не вводилось. Значения CodecLimits остаются hypothesis, O-17. OOM-ветви перехвачены, принудительная инъекция нехватки памяти не выполнялась.
- Стенд, схемы, ADR, спецификация, libraries.md, матрицы, roadmap, CLI и другие уровни не менялись. Linux/CI, V3/V4, ZIP и AssetRepository не выполнялись согласно границам T-006.

### Д-1 (блокирует). Построение DOM известной части квадратично по числу ключей объекта

`nlohmann::ordered_json` хранит объект в `ordered_map` — векторе пар; `emplace`, `operator[]` и `find` ищут ключ линейно. Квадратичны два места в `parse_manifest`:
1. `Json::parse(known)` — при разборе каждый член объекта вставляется через поиск среди уже вставленных;
2. цикл `pending`: `(*dom)[edge]` для каждого дочернего узла объекта.

Замер управляющего (MSVC 19.44, `/O2`, отдельная программа, объект `extensions` с N членами вида `"org.example.eI":{"data":null}`):

| N | Байт | `ordered_json::parse`, мс | `jsoncons::json::parse`, мс |
|---:|---:|---:|---:|
| 10 000 | 338 906 | 235 | 9 |
| 20 000 | 688 906 | 628 | — |
| 40 000 | 1 388 906 | 3 043 | 38 |
| 80 000 | 2 788 906 | 16 127 | — |
| 160 000 | ~5,6 МБ | не запускался | 190 |

При пределе 128 МиБ недоверенный манифест с одним большим объектом в известной части (`extensions`, где каждое `data` непрозрачно, либо любой иной объект) занимает разбор на часы. V2 (jsoncons) линейна, проблема только в построении DOM nlohmann. Критерий 5 формально касался токенизатора, поиска мест и защиты, но цель ADR-0038 — чтение недоверенного входа без неограниченных затрат, а не только без переполнения стека.

**Требуется:**
- Строить DOM известной части **прямо из дерева токенизатора**, одним итеративным обходом (явный стек), без `Json::parse` текста известной части и без поиска по ключу при построении: члены объекта добавлять в конец базового вектора `ordered_map` (`object_t` наследует `std::vector<std::pair<const Key, T>>`; дубли уже отвергнуты токенизатором). Числа — через `integer()` в `number_integer`/`number_unsigned`, строки — декодированные строки токенизатора, литералы — `true`/`false`/`null`, корни непрозрачных поддеревьев — сразу заглушки `binary`. Предел `max_known_depth` проверяется как сейчас, до построения.
- Проверить, что в остальных путях кодека (`emit`, `render`, `opaque_keys`, `verify_preserved`, `shadow`) нет поиска по ключу в DOM внутри цикла по членам. Поиск по ключу вызывающим кодом (`dom["asset"]`) допустим: это O(k) на один вызов.
- Регрессионный тест: объект `extensions` с 200 000 членов (каждое `data` непрозрачно) проходит `parse_manifest` → `write_manifest` → `verify_preserved` → повторный `parse_manifest` с равенством `known()`; отдельно — V1 для документа, где объект с 200 000 членов целиком в известной части (без V2). Время и пик памяти — в выводе теста, без порога (как тест 14).
- В отчёте: время этого теста на исправленной реализации и, для сравнения, на `39b3cb5` (или экстраполяция по замеру выше, если прогон старой версии занимает больше 10 минут).

### Исправление Д-1

Замечание подтверждено: первоначальная оценка сложности не учитывала линейный поиск внутри ordered_map как при Json::parse(known), так и при заполнении заглушек через (*dom)[edge]. Оба квадратичных места удалены.

- Глубина всей известной части проверяется отдельным проходом до создания контейнеров DOM, как и раньше. Непрозрачные поддеревья пропускаются по диапазонам токенов.
- DOM строится прямо из плоского дерева токенизатора одним итеративным обходом. Объекты/массивы создаются пустыми, их хранилища однократно reserve на число дочерних узлов. Члены объекта добавляются emplace_back в публичный базовый вектор Json::object_t::Container; уникальность декодированных ключей уже доказана токенизатором. Массивы заполняются append в array_t. Поиск по ключу при построении отсутствует.
- Строки и ключи берутся декодированными из токенов; true/false/null создаются типизированными конструкторами. Числа канонизируются неизменённым integer(), затем std::from_chars переводит их в number_integer_t/number_unsigned_t до вызова конструктора JSON. Ни текстовый JSON-парсер известной части, ни double не используются. Непрозрачные корни сразу становятся binary с новым индексом фрагмента.
- Явный стек хранит текущий контейнер и следующий токен ребёнка. Благодаря полному reserve адреса Json внутри векторов не инвалидируются при добавлении следующих соседей. Порядок членов/элементов соответствует порядку токенов. Само построение DOM линейно по узлам и копируемым строкам; предшествующий Analysis по-прежнему O(n log n) или лучше.
