# T-031. ZIP как вход: раскрытие обычных ZIP при скане и импорте (M3a)

**Статус:** in_progress · **Веха:** M3a · **Основание:** ТЗ v1.8 §6.4.1, §6.4.3–6.4.5, §6.5.2, §6.5.6, §6.6, §6.8.6, §6.9, §19.4.3, §19.4.17; ADR-0011, ADR-0012, ADR-0025, ADR-0035, ADR-0037 (X-01); приёмки T-028 (уточнения реализации), T-030 (замечание 1)

## Цель

Обычный ZIP (тип по сигнатуре, не ассет собственного формата) становится полноценным входом импорта:

1. `am import scan` перечисляет записи ZIP: имена с исходными байтами и способом декодирования, размеры, CRC, вид записи, тип по сигнатуре. К записям применяются правила исключения, решения видны и редактируются в плане так же, как для файлов.
2. `am import run` создаёт ассет из включённых записей. Байты переносятся без изменений, а в манифесте учитываются объект архива с SHA-256 и все записи, включая исключённые и недоступные.
3. Защита недоверенного входа по §19.4.17: безопасные пути, отказ от материализации ссылок и специальных объектов, лимиты по фактически распакованным байтам, различение `invalid` / `unsupported` / `incomplete`.
4. Ни одна запись не теряется молча: строгий режим не создаёт неполный ассет, частичный — только по выбору пользователя, с признаком неполноты.

Попутно исправить нестабильный тест скана T-028 (см. п. 9).

Многотомные наборы, RAR и 7z остаются отложенными (M3b). Вложенные архивы в этой задаче не раскрываются: для них в плане есть выбор «сохранить файлом» или «исключить» (п. 6).

## Решения управляющего (не пересматривать в задаче)

### 1. Бэкенд чтения входных ZIP

- Входные ZIP читаются **собственным читателем `asset_zip::ZipArchive`** (T-007), а не libarchive. Он уже проверяет перекрытия, расхождения заголовков и границы потоков, считает фактические байты через `ReadBudget` и работает со ZIP64. Новая зависимость для P0 не нужна. Выбор libarchive или 7z.dll для RAR/7z остаётся за спайком S1 (M3b).
- Проверки **профиля собственного формата** (`asset_zip/profile`, требования ADR-0035 к ассету) к входным архивам **не применяются**. Применяется только структурная защита читателя.
- Новый модуль уровня `storage`: `include/am/storage/archive/zip_input.hpp`, `src/storage/archive/zip_input.cpp`. Он открывает входной ZIP, выдаёт перечень записей с декодированными именами (п. 3) и открывает поток записи с лимитами (п. 4). Сервисы импорта работают только через него. Читатель `asset_zip` можно расширять небольшими дополнениями (например, сведения для лимита времени), каждое — в отчёт с причиной. Существующее поведение для ассетов не меняется, проверки читателя не ослабляются.
- Некоторые архивы из реальной жизни строгий читатель отклонит (мусор перед архивом, SFX, расхождения заголовков). Для P0 это допустимо: такой архив получает `archive_unreadable` (п. 5). В отчёте перечислить, какие проверки читателя дают отказ на входных архивах и как каждый отказ классифицируется: `invalid`, `unsupported` или `incomplete` (§19.4.17.8). Восстановление повреждённых ZIP по локальным заголовкам в задачу не входит.
- В `docs/research/libraries.md` записать решение: «входной ZIP — собственный читатель (решение управляющего 2026-11-25); libarchive — кандидат для RAR/7z, спайк S1».

### 2. План импорта v2

- Скан пишет план `am-import-plan` **версии 2**: новая схема `schemas/import-plan.v2.schema.json`. Файл схемы v1 не меняется. Строку 12 в `docs/specifications/versioning.md` обновить: текущая версия 2, v1 читается.
- Добавления v2 к v1:
  - `archives[]` — по элементу на каждый обычный ZIP-узел: `node`, `container: "zip"`, `status` (`listed` / `unreadable` / `limit_exceeded`), `problem?`, `entry_count`, `name_encodings[]` (какие способы декодирования встретились), сводка (`zip64`, `comment_length`, `encrypted_entries`, `unsupported_entries`).
  - `archive_entries[]` — по элементу на запись центрального каталога:
    - `id`, `archive` (id узла), `index` (порядок в центральном каталоге);
    - `path` (декодированное), `path_raw` (hex исходных байт), `name_encoding` (п. 3), `encoding_exact`, `encoding_confidence?`;
    - `kind` (`file` / `directory` / `symlink` / `other`);
    - `size` и `compressed_size` (заявленные), `crc32` (8 hex), `method`, `encrypted`, `modified_at_raw?`;
    - `detected` (тип по сигнатуре из образца начала записи);
    - `status` (`available` / `unavailable`), `problem?`.
  - Элемент `entries[]` кандидата ссылается либо на `node` (как в v1), либо на `archive_entry`. Это `oneOf`, решения те же: `include` / `exclude` / `ask` / `skip`.
- `parse_plan` / `PlanView` читают v1 и v2. Кандидат v1 с архивным входом run откладывает с причиной `archive_plan_rescan_required`, без дочернего задания. Прочие кандидаты v1 выполняются как в T-030.
- Семантическая проверка v2 расширяет проверку v1: ссылки `archive` и `archive_entry` существуют, запись принадлежит архиву из входов того же кандидата, у каждой записи ровно одно решение, пары `index` уникальны в архиве. Как и для v1, raw-hex проверяется линейно (В-6 T-030).

### 3. Имена записей

- Порядок декодирования — ADR-0012 и `text_encoding.hpp`:
  1. бит 11 → UTF-8 (`utf-8(bit11)`); если байты при этом не являются строгим UTF-8 — запись получает `problem{code: name_invalid_utf8}`, имя декодируется заменой, а исходные байты сохраняются;
  2. поле Info-ZIP Unicode Path `0x7075` → UTF-8, только если CRC32 из поля совпадает с CRC исходного имени (`utf-8(0x7075)`); иначе поле игнорируется, и это отмечается в `problem` записи;
  3. строгий UTF-8 без флага → `utf-8(valid)`;
  4. `guess_name_encoding` → `cp866(heuristic)` / `cp1251(heuristic)` / `cp437(heuristic)` с `encoding_confidence`.
- Ручное переопределение кодировки (шаг 5 ADR-0012) в задачу не входит. Порогов уверенности не назначать: спайк S3 не выполнен, догадка только записывается. Пока имена не исправлены, кандидат с догадкой не блокируется. Добавляется причина кандидата `name_encoding_guessed`, чтобы пользователь видел её в плане.
- В манифест: `inputObject.name_encoding` — способ для архива. Если способов несколько, через запятую в порядке первого появления, например `utf-8(bit11),cp866(heuristic)`. `path_raw` пишется Base64 с `encoding_guess`, если исходные байты отличаются от UTF-8 отображаемого пути. Для догадки так бывает всегда.

### 4. Безопасность и лимиты (§19.4.17)

- **Пути.** Имя записи никогда не используется как путь записи на диск: распаковки на диск нет вовсе (п. 5). Опасными считаются:
  - абсолютный путь, буква диска, UNC;
  - компоненты `.` / `..`, пустые компоненты;
  - `\` как разделитель;
  - NUL и управляющие символы;
  - точные дубликаты имени;
  - коллизии после нормализации NFC и без учёта регистра.

  Такие записи получают в плане `ask` с `explanation_id` (`unsafe_entry_path`, `duplicate_entry_name`, `case_collision`). При `include` запись проходит `ZipPathMapper` и становится `included_renamed` с `rename_reason`: `invalid_chars` для небезопасного пути, `collision` для дубликата или коллизии. Исходные байты сохраняются в `path_raw`.
- **Ссылки и специальные объекты.** Если по внешним атрибутам запись — symlink или специальный объект, она не материализуется и не разыменовывается (§19.4.17.3). Она учитывается так же, как ссылка файловой системы в T-030: решение `skip` → `not_processed` с `problem{code: link_not_followed}`. Для специальных объектов код — `special_not_materialized`.
- **Шифрование и методы.** Зашифрованная запись или метод, отличный от Stored/Deflate, — `problem{code: encrypted_unsupported | method_unsupported}`:
  - `include` в строгом режиме — ошибка кандидата до записи;
  - в частичном режиме — `unavailable` с этим `problem` и `completeness = incomplete`;
  - `exclude` — учёт без чтения данных.

  Пароли не запрашиваются и нигде не хранятся. Процедура работы с паролями (ТЗ 6.4.6, 6.6.4) остаётся открытой, в задаче её не закрывать.
- **Лимиты.** Действующий лимит — минимум из безусловного `ZipLimits` и `[limits]` профиля:
  - `max_entries`;
  - `max_unpacked_bytes` — **фактически** распакованные байты всего задания, через общий `ReadBudget`; заявленным размерам не доверять;
  - `max_ratio` — по фактическому выходу записи относительно `compressed_size`. Проверка включается, когда выход записи превысил 1 МиБ; этот порог — гипотеза O-17, константа с комментарием;
  - `max_seconds_per_container` — с внедряемыми часами для тестов.

  `max_temp_bytes` не применяется: временных файлов нет. Он перечисляется в `profile.not_applied[]`. Числа лимитов остаются гипотезами O-17, нормативами не объявляются.
- Превышение лимита **в любом режиме** делает кандидата ошибкой `am.import.archive.limit_exceeded` с именем лимита в `problem`, без создания ассета. Частичный режим лимиты не обходит (§19.4.17.5). В скане архив получает `status = limit_exceeded`, а кандидат — `ask` с `archive_limit_exceeded`.
- **Скан** читает центральный каталог и образец начала каждой файловой записи: столько же байт, сколько скан читает у файла для сигнатуры. Образец нужен для `detected` и правил исключения (AppleDouble `00 05 16 07`). Чтение образцов идёт в общем бюджете. Полностью записи в скане не распаковываются.

### 5. Создание ассета из записей ZIP

- **Без распаковки на диск.** Источник содержимого — запись входного ZIP. `FileInput` расширяется необязательным источником-записью архива, например `archive_entry{archive_path, index, raw_name, crc32, size}`. Ровно один из `source` и `archive_entry` задан. `AssetRepository` сам открывает входной ZIP через модуль п. 1, читает запись в обоих проходах (preflight-хеш и запись) с проверкой CRC и размера и сверяет с `expected_sha256`, если он задан.
  - Повреждение записи (CRC, обрыв потока) — `SourceFailure{read_failure = true}`.
  - Подмена архива между проходами — `source_changed`.
  - Ошибки назначения `SourceFailure` не задают (как в T-030).

  Сжатие в ассете выбирается прежней политикой `compression_policy`. Raw-копирование Deflate-потока без перекомпрессии — не в этой задаче.
- **Свежесть.**
  - Перед записью: размер и `mtime_ns` ZIP-файла совпадают с планом; перечень записей при повторном открытии совпадает с планом по `index`, `path_raw`, размерам, CRC и методу. Если в плане есть `sha256` архива, он сверяется. Любое расхождение — `am.import.source_changed` с узлом архива.
  - После фиксации повторно проверяется `stat` архива. При изменении ассет переносится в корзину, как в T-030.
- **SHA-256 архива обязателен** (ТЗ 6.8.6): run вычисляет его потоково и пишет в `inputObject.sha256`. Если SHA в плане есть, он сверяется.
- **Состав манифеста.** Input на кандидата — как в T-030.
  - Объект архива: `kind: archive`, `container: zip`, `name`, `name_raw?`, `relative_path`, `size_bytes`, `sha256`, `name_encoding`.
  - `entries[]` — по записи на каждую запись центрального каталога, с `object_id` архива:
    - каталоги — `entry_kind: directory`, без `file_id`;
    - `crc32`;
    - `size_bytes`: фактический для включённых, заявленный для остальных;
    - `modified_at_raw` — только если представление определено в `container_manifest_v1.md`; если нет, поле не заполнять и записать это в отчёт, формат не придумывать.

  Итоги записей и `exclusion.by` — по правилам T-030.
- **Повреждённый архив.** Если центральный каталог не читается, в скане архив получает `status = unreadable` с `problem`, а кандидат — `ask` с `archive_unreadable`. В run такой кандидат с явным `include` — ошибка кандидата в любом режиме: перечня записей нет, частичный импорт невозможен. Отдельная запись с ошибкой CRC в частичном режиме — `failed` с `problem`, в строгом — ошибка кандидата.
- **Размещение в ZIP ассета.** Через `ZipPathMapper` с префиксом `content/<InputID>/`:
  - кандидат из одного архива — пути записей от корня;
  - архив внутри кандидата с несколькими объектами — каталог на месте архива в исходной иерархии кандидата: путь архива относительно `base_path`, где имя файла заменено именем без расширения. Например, `sub/model.zip` → `sub/model/<записи>`.

  Коллизии с соседними каталогами и файлами разрешаются переименованием (`included_renamed`, `collision`), а не отбрасыванием.
- **Заголовок.** `title` кандидата из одного архива — имя архива без расширения.

### 6. Вложенные архивы

- Запись, которая по сигнатуре сама является архивом (ZIP, RAR, 7z), в плане получает `ask` с `explanation_id = nested_archive_expand_unsupported`. Значение `[nested] action = "expand"` профиля в этой задаче не исполнимо и остаётся в `profile.not_applied[]`. Правила исключения применяются раньше (ADR-0011): `._model.zip` с сигнатурой AppleDouble исключается правилом и как архив не рассматривается.
- Выбор пользователя:
  - `include` = «сохранить целиком как файл содержимого» (ТЗ 6.4.4). Запись включается как обычный файл, плюс `inputObject{kind: archive, container, parent_object_id, parent_entry_id, nested_action: preserve}`;
  - `exclude` → запись `excluded` и такой же объект с `nested_action: exclude`.
- Специализированные форматы с ZIP-упаковкой (3MF и подобные) архивами не считаются и включаются как файлы (SC-10, ТЗ 6.4.5). Использовать тот же признак, что и скан T-028.

### 7. Задания, идемпотентность, объём параметров

- Механизм T-030 не меняется: `import.run` родитель, `import.asset` дочерние, ключ `(plan_sha256, candidate_id)`, заранее выданные `asset_id` и `InputID`, повтор после фиксации распознаётся по `InputID`, корзина требует решения (В-10).
- **Объём параметров.** В архиве могут быть десятки тысяч записей. Параметры дочернего задания **не** хранят ID на каждую запись архива: `FileID` и `SourceEntryID` записей архива выдаются при попытке. Это безопасно, потому что повтор после фиксации распознаётся по `InputID`, а несостоявшаяся попытка ничего не сохраняет. Тест: размер `params_json` дочернего задания одинаков для архива из 10 и из 10 000 записей с точностью до длины пути плана.
- Если в T-030 ID узлов файловой системы хранятся в параметрах, это не меняется.

### 8. Что остаётся отложенным (итоги кандидатов)

| Вход | Итог run | Причина |
|---|---|---|
| RAR, 7z (по сигнатуре) | deferred | `archive_input_unsupported` (как в T-030) |
| набор томов любого вида, включая zip split `.z01…` | deferred | `volume_set_unsupported` |
| кандидат v1 с архивом | deferred | `archive_plan_rescan_required` |
| ZIP-ассет собственного формата | как в T-030 (`ready_asset`) | — |

Перевод номеров томов с 1 на 0 (`missing_indices` → `volumes[].index`) понадобится, когда наборы станут выполняться, т. е. в M3b. В этой задаче он не нужен.

### 9. Нестабильный тест скана (замечание 1 приёмки T-030)

`ImportScan.StableByteOrderAndDeterministicSerialization` падает примерно в 5–7 % запусков на NTFS. `mtime_ns` каталога `a`, только что изменённого записью `a/z`, обновляется между двумя сканами. Исправить тест, не ослабляя проверку детерминизма. Варианты на выбор исполнителя, с обоснованием в отчёте:
- после записи фикстуры явно установить время каталогов и файлов и только затем сканировать;
- сравнивать планы, нормализовав только `mtime_ns` каталогов, и отдельно проверять, что все прочие поля и порядок совпадают побайтно.

Код скана ради теста не менять. Если выяснится, что нестабилен сам скан (например, `mtime` каталога читается из разных источников), — остановиться и задать вопрос. Проверка: 300 повторов без провалов на Windows и в WSL.

### 10. Чего в T-031 нет

- Раскрытие вложенных архивов, RAR/7z, наборы томов, подтверждение томов по заголовкам (M3b и следующая задача M3a по вложенным архивам — по итогам этой).
- Пароли, ручное переопределение кодировки имён, восстановление повреждённых ZIP.
- Raw-копирование сжатых записей без перекомпрессии.
- `export`, корпус 16 сценариев (следующие задачи M3a).
- Реальная коллекция: только синтетические фикстуры. Бинарные фикстуры в репозиторий не добавляются, ZIP строятся в тестах.

## Тесты

Фикстуры строит тестовый помощник, собирающий байты ZIP вручную (Stored и Deflate через zlib). Он должен управлять флагами, именами (сырые байты), extra-полями (`0x7075`, ZIP64), внешними атрибутами, CRC и заявленными размерами, включая ложные. Требования из `RecordProperty("req", …)` — по матрицам.

1. **Базовый ZIP.** Скан → план v2 с `archives[]` и `archive_entries[]` → run. Проверяется:
   - байты файлов равны исходным записям;
   - V1–V4 и `verify --full` проходят;
   - объект `archive` с `container`, `sha256` (равен SHA файла), `size_bytes`, `name_encoding`;
   - каталоги — `entry_kind: directory`;
   - `crc32` записей.
2. **Кодировки имён.** Бит 11; UTF-8 без флага; `0x7075` с верным и неверным CRC; CP866-байты (догадка, `path_raw` + `encoding_guess`, причина кандидата `name_encoding_guessed`); бит 11 с невалидным UTF-8. Несколько способов в одном архиве дают `name_encoding` через запятую.
3. **Опасные пути.** `../x`, `/abs`, `C:\x`, `\\srv\x`, `a\b`, `a//b`, NUL, точный дубликат, `A.txt` + `a.txt`, NFC/NFD. В плане — `ask` с нужным `explanation_id`. После `include` — `included_renamed` с верным `rename_reason`, исходные байты сохранены, ничего не записано вне ZIP ассета.
4. **Ссылки и специальные записи** (внешние атрибуты Unix): не материализуются, итог `not_processed`.
5. **Шифрование и методы** (флаг шифрования, метод 99, методы 12/14/93): строгий режим — ошибка до записи; частичный — `unavailable` и `incomplete`; `exclude` — данные не читаются (hook чтения).
6. **Повреждения:** нет EOCD, повреждён центральный каталог, расхождение локального и центрального заголовков → `unreadable` в скане, ошибка в run. Ошибка CRC одной записи: строгий режим — ошибка кандидата; частичный — `failed`, остальное включено, `incomplete`.
7. **Лимиты:** число записей; фактический объём при заниженных заявленных размерах; коэффициент сжатия; время (внедрённые часы). Ассет не создаётся ни в строгом, ни в частичном режиме, `problem` называет лимит, временных файлов и строк журнала фиксации не остаётся.
8. **Вложенный архив:** ZIP в ZIP и RAR-сигнатура в ZIP → `ask`; `include` → файл и объект с `nested_action: preserve`; `exclude` → `excluded` и `nested_action: exclude`. `._x.zip` с AppleDouble исключается правилом. 3MF включается файлом.
9. **Исключения внутри архива:** `__MACOSX/`, `.DS_Store`, AppleDouble по сигнатуре образца; `exclusion.by` по правилам T-030.
10. **Смешанный кандидат:** каталог с `sub/model.zip` и соседним каталогом `sub/model/` → размещение и переименование при коллизии; несколько архивов в одном кандидате.
11. **Свежесть:** архив изменён после скана (размер/`mtime`; тот же размер и `mtime` с другим содержимым при `sha256` в плане; другой перечень записей) → `source_changed`. Изменён во время упаковки (hook между проходами) → ошибка без ассета. Изменён после фиксации → корзина, `asset_id` в результате.
12. **Повтор и объём:** повтор после фиксации распознаётся по `InputID`, второго ассета нет. Размер `params_json` не зависит от числа записей (10 и 10 000).
13. **План:** v2 проходит схему и семантику; ошибки ссылок `archive` и `archive_entry` дают прежний класс ошибки с JSON Pointer; v1 читается; кандидат v1 с архивом → deferred `archive_plan_rescan_required`.
14. **Неизменность источника:** снимок дерева до и после скана и run совпадает, все открытия только на чтение.
15. **Отложенные входы:** RAR/7z → `archive_input_unsupported`; zip split `.z01` + `.zip` → `volume_set_unsupported`.
16. **CLI:** `am import scan` → `am import run` на каталоге с ZIP: коды возврата, сводка (`--json`) с числом записей архива и отложенных кандидатов.
17. **Тест п. 9:** исправленный тест; 300 повторов в отчёте.

## Критерии приёмки

1. Четыре прогона зелёные: `build_min --ci`, `build_cli --ci -LE periodic`, `build_cli --offline --ci -LE periodic`, Linux CLI `--offline --ci -LE periodic` (SKIP — с причинами).
2. Каждая запись центрального каталога учтена в манифесте ровно одной записью `inputs[].entries` с верным итогом. Ни одна запись не включена без решения, ни одно `ask` не исполнено без пользователя.
3. Созданные ассеты проходят V1–V4 и `verify --full`. Байты включённых файлов равны распакованным записям. SHA-256 архива записан и верен.
4. Опасные имена, ссылки, шифрование, неподдерживаемые методы, повреждения и превышение лимитов не приводят ни к записи вне ZIP ассета, ни к молча созданному неполному ассету (тесты 3–7).
5. Лимиты считаются по фактическим байтам и не обходятся частичным режимом. Числа лимитов остаются гипотезами O-17.
6. Изменение архива после скана, во время упаковки и после фиксации обнаруживается (тест 11). Повтор не создаёт второго ассета, объём параметров не растёт с числом записей (тест 12).
7. План v2 описан схемой, v1 читается, версия отражена в `versioning.md`.
8. Тест п. 9 стабилен: 300 повторов без провалов на Windows и в WSL.
9. `arch_check` проходит. ZIP ассета пишет только `AssetRepository`, входной ZIP читается только через модуль п. 1.
10. Матрицы покрытия и приёмки обновлены по фактическому статусу. Вложенные архивы, тома, RAR/7z и полный корпус завершёнными не объявляются.

### Вопросы

- В-1: п. 4 и тест 3 требуют перечислять точные дубликаты и после include импортировать их с переименованием. Сейчас `ZipArchive::open` отклоняет их как `am.zip.duplicate_name` до выдачи перечня (`reader.cpp`, проверка множества raw_name; прежний тест ZipReader выше). При этом п. 1 запрещает ослаблять проверки читателя. Предложение: отдельный явно выбираемый режим входного ZIP, разрешающий только повтор raw_name; индекс записи остаётся идентификатором, проверки перекрытий/границ/локальных заголовков/CRC и прочие лимиты не меняются. Режим по умолчанию и прежние тесты ассетов остаются строгими. Требуется решение по этому исключению.
- В-2: `tests/schema/schema_check.py` проверяет все `.cache/import-plan-cases/*.json` только схемой v1. После перехода scan на v2 обязательный schema_check начнёт отвергать реальные планы. Файл отсутствует в разрешённом списке. Предложение: точечно добавить проверку схемы v2, отдельные положительные/отрицательные случаи, а реальные планы направлять к валидатору по версии (неизвестную версию отклонять). Схема v1 и её прежние контрактные случаи не меняются.
- В-3: scan получает полные настройки профиля, но план содержит только profile.id/version/sha256/not_applied. Run и восстановленные задания не имеют исходных settings; пользовательский профиль мог быть загружен из произвольного файла. Для воспроизводимого применения лимитов предлагается обязательный снимок profile.limits в v2 (max_entries, max_unpacked_bytes, max_ratio, max_seconds_per_container, max_temp_bytes); PlanView читает его, run использует его минимум с безусловными лимитами. Settings заново по ID не подбираются, SHA профиля сохраняется. Это дополнение списка полей v2 в п. 2 требует решения управляющего.
- В-4: для ZIP внутри каталога T-030 сохраняет файловый узел ZIP как запись корневого объекта. После раскрытия ZIP исходные ZIP-байты не хранятся в content, поэтому included у этой файловой записи невозможен без FileID (V3). Предлагается оставить решение node как внешнее условие: include применяет решения archive_entry, exclude исключает все записи этого ZIP, ask откладывает кандидат. В манифесте expanded ZIP представлен дополнительным объектом archive с parent_object_id/parent_entry_id и nested_action=extract; родительская файловая запись — not_processed с problem.code=archive_expanded (сам ZIP не упакован файлом). При exclude — родитель excluded, nested_action=exclude и все известные внутренние записи excluded. Для одиночного ZIP родительская запись не нужна: он сам исходный объект. Требуется решение по этой неописанной в п. 5 судьбе файлового узла контейнера.
- В-5: дополнительное условие 6 В-1 требует ready_asset_invalid для собственного манифеста с дубликатом. Сейчас probe_container после структурного отказа немедленно возвращает invalid_zip, не проверяя признак собственного формата; scan создаёт new_asset/import. Воспроизведено на синтетическом ZIP с manifest.json первым и двумя same.bin (`.cache/t031/probe_duplicate.py`). Предлагается при am.zip.duplicate_name дополнительно выполнить ограниченную пробу первого manifest.json и вернуть own_corrupt только при доказанном идентификаторе собственного формата; сам ZIP остаётся отклонён строгим читателем, исходная ошибка сохраняется причиной. Нужен явный приоритет условия 6 над требованием побайтно прежней пробы из условия 1 В-1. Иные ошибки и обычные ZIP не переклассифицируются.
- В-6: для общего бюджета дополнительной пробы В-5 нужен необязательный контекст probe_container (shared ZipInputJob и путь контейнера для его часов). Декларация находится в include/am/storage/asset_zip/probe.hpp, которого нет в разделе «Файлы». Предлагается добавить перегрузку с контекстом; прежняя трёхаргументная перегрузка и поведение без контекста сохраняются, кроме уже согласованной классификации В-5. Input открывается только через модуль zip_input. Запрошено точечное разрешение заголовка.
- В-7: п. 4 ограничивает пробу записи 96 байтами и запрещает полную распаковку в scan; п. 6 требует распознавать вложенный 3MF тем же признаком T-028 (`3D/3dmodel.model` среди записей внутреннего ZIP). У Deflate-записи центральный каталог внутреннего ZIP находится у конца распакованного потока и может не попадать в образец. Имя .3mf само по себе — лишь подсказка, не прежний признак. Нужен приоритет: разрешить для обнаруженных ZIP-записей расширенную ограниченную бюджетом пробу внутреннего каталога (вплоть до конца записи, без извлечения её файлов на диск), либо оставить неопределённую ZIP-запись ask с явным сохранением файлом/исключением до следующей задачи. По одному расширению объявлять project.3mf без решения не предлагается.

### Продолжение реализации после В-7

- План v2 и типизированный PlanView реализованы; v1 и её схема сохранены. Есть архивные индексы, исходные hex-имена, метаданные, обязательный снимок пяти лимитов, взаимоисключающие ссылки node/archive_entry и семантическая проверка принадлежности/полноты/индексов. Raw-поля проверяются линейно. MSVC-ограничение длины одного raw literal обходится разбиением встраиваемой v2-схемы по строкам при генерации в каталоге сборки; исходная схема остаётся единственным источником.
- Scan перечисляет записи с образцами до 96 байт, правилами и решениями; сохраняет все дубликаты. Распознавание собственного повреждённого ZIP при дубликате использует контекстную пробу В-5/В-6 и тот же общий бюджет.

- Run использует существующий durable-механизм T-030: отдельные верхнеуровневые объекты ZIP, исходные записи и CRC, частичные повторы с failed, вложенные preserve/exclude, политику В-7, проверку stat до и после фиксации. ### Классификация отказов читателя входного ZIP

| Проверка / причина | Категория | Поведение |
|---|---|---|
| EOCD отсутствует или неверна граница комментария; неполные/противоречивые EOCD/ZIP64/extra/descriptor | invalid | Читатель возвращает corrupt_data / am.zip.invalid_structure; скан сохраняет archive_invalid, unreadable, ask. Восстановления по локальным заголовкам нет |
| Несогласованность размеров/границ центрального каталога, сигнатур, локальных и центральных имён/методов/флагов/CRC/размеров | invalid | Тот же структурный отказ; run с include не создаёт ассет |
| Пересечения областей, общий локальный заголовок у двух центральных записей, переполнение диапазона | invalid | Отказ в обоих профилях; точные дубликаты разных записей допускаются только входным профилем |
| Неучтённые начальные данные, SFX и мусор перед структурами, если нарушают структурные проверки читателя | invalid | Не исправляются автоматически; отдельной терпимой ветви нет. Само наличие gaps не является отказом структурного читателя: оно отражено в unaccounted_bytes; профиль ассета проверяется отдельно |
| Многодисковые поля и признаки томов | unsupported | Читатель не пытается собрать тома; подтверждение и выполнение наборов остаются M3b |
| Шифрование, методы кроме Stored/Deflate | unsupported | Запись видна; include strict — ошибка, partial — unavailable, exclude — без чтения |
| Превышение лимита входа | unsupported **по текущим лимитам**, не incomplete (В-8) | Окончательный failed / am.import.archive.limit_exceeded, cause сохранён, problem содержит имя, значение и источник; автоматического повтора нет |
| Ошибка чтения ОС, недоступный источник, остановка, настоящая нехватка памяти/ресурсов | incomplete как результат обследования | Причина сохраняется; нехватка ресурсов машины не переводится в unsupported и у задания остаётся resource_error; отмена — прежний interrupted |
| CRC/некорректный Deflate/несовпадение фактического размера отдельной записи | invalid для записи | Строгий импорт прекращается; явно частичный учитывает failed и incomplete, без утраты записи |
| Перечень/SHA или stat источника изменились | conflict, не вердикт формата | source_changed до фиксации; после неё — source_changed_during_import и корзина |

Новый адаптер не анализирует текст detail для выбора сорвавшегося файла. SourceFailure содержит FileID; целый контейнер, назначение и лимиты не становятся повтором отдельной записи.

Направление зависимости проверено: `rg -n '#include.*storage/archive' include/am/storage/asset_zip src/storage/asset_zip` — совпадений нет. `rg -n 'ZipReadProfile::input' include src` — выбор профиля только в двух местах zip_input.cpp (открытие и callback пробы); reader.cpp лишь сравнивает профиль. В ProbeContext дополнительно передаётся нейтральный callback фактического выхода манифеста, чтобы коэффициент проверяла та же функция zip_input, что и у обычных потоков.
