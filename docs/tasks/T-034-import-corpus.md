# T-034. Корпус сценариев импорта SC-1…SC-16 (M3a)

**Исполнение:** по `AGENTS.md` в ветке `codex/T-034`. Если у Codex нулевой лимит, задачу выполняет управляющий (Claude Code) по той же процедуре, как T-032/T-033: самопроверка по критериям и `/code-review` по diff вместо независимой приёмки.

**Статус:** in_progress · **Веха:** M3a (P0.6, последний пункт вехи) · **Основание:** ТЗ v1.8 §13.2 (16 сценариев, п. 1–4), §13.3 п. 4–5, §13.4 п. 1–3, 6, 7, 10, 11, §12.9.8; ADR-0029 (синтетические данные и реестр), ADR-0035 (`content/<InputID>/`, внешняя упаковка не вкладывается), ADR-0037; `coverage_matrix.md`

## Цель

M3a почти закрыта: скан и импорт файлов, папок, ZIP и вложенных ZIP (T-028…T-032), экспорт (T-033). Но каждая задача проверяла свой срез своими тестами, а матрица `coverage_matrix.md` в колонке (б) почти везде говорит «нет». ТЗ §13.4.7 требует, чтобы каждый тестовый набор имел машинно-читаемые ожидания, а §13.2.3 — честно различать «предусмотрено», «реализовано» и «проверено».

T-034 создаёт **единый декларативный корпус** синтетических случаев импорта:

1. Случай описан текстом (`case.json`): какие файлы, каталоги и ZIP создать, какие правки плана сделать, какие команды выполнить.
2. Ожидания (`expected.json`) записаны **по ТЗ и спецификациям**, а не сняты с вывода программы.
3. Единый прогонщик выполняет настоящий CLI: `import scan` → правки плана → `import run` → `library verify --full` → разбор манифестов — и сверяет результат с ожиданиями.
4. Каждый сценарий SC-1…SC-16 получает хотя бы один случай. Если сценарий реализован не полностью, случай фиксирует **фактическое и допустимое по ТЗ** поведение текущей сборки (например, «RAR сохранён непрозрачным архивом, не раскрыт») и отмечает разрыв в матрице. Сценарий при этом не объявляется реализованным.
5. `coverage_matrix.md` обновляется по фактам: колонки (б) и (д) — с именами случаев и результатами.

Новой функциональности импорта T-034 не добавляет. Если случай обнаруживает дефект, это **находка**, а не повод подогнать ожидание (см. п. 7 решений).

## Решения

### 1. Входные данные генерируются, а не хранятся

- В репозитории — только `tests/fixtures/import/<case>/case.json` и `expected.json`. Двоичных входов в git нет.
- Генератор `tools/fixtures/make_import_cases.py` создаёт входы в каталоге сборки (`<build>/import_corpus/<case>/source/`) при каждом прогоне.
- Зачем так:
  - длинные пути (> 260 символов), NFD-имена, имена с регистровыми коллизиями и ссылки нельзя надёжно хранить в git на Windows;
  - ZIP с повреждениями и без флага UTF-8 проще описать байтами в JSON, чем держать как двоичный файл;
  - репозиторий не растёт.
- Детерминизм:
  - содержимое файлов задаётся явно (текст, hex или «N байтов по шаблону»);
  - время изменения фиксировано;
  - ZIP собираются тем же способом, что golden: фиксированное время, явный порядок записей, Deflate уровня 0. Общий код упаковки вынести в модуль, импортируемый обоими генераторами; поведение `make_golden_zips.py` и опубликованный golden-корпус не меняются (`golden_regen_check` остаётся зелёным).
- Генератор запускается как `python -I`. Он не читает коллекцию владельца и ничего не пишет вне `<build>` и `.cache/`.
- Случаи, которые нельзя создать на данной ОС или без прав (символическая ссылка на Windows без привилегии, имена с `:` на Windows и т. п.), помечаются в `case.json` условием `requires` и пропускаются с явной причиной. Молча такие случаи не пропадают.

### 2. Формат случая

`case.json` (схема `schemas/import-case.v1.schema.json`, новая, проверяется `schema_check`):

- `case` — имя, совпадает с каталогом; `scenarios` — `["SC-n", …]`; `req` — ID требований (`K-n`, `NFR-…`, `SC-n`); `description`.
- `source` — дерево: каталоги, файлы (`content` / `hex` / `pattern`+`size`), ZIP (записи с методом, флагами, исходными байтами имени, вложенными ZIP, патчами заголовков как в golden), ссылки.
- `scan` — аргументы `am import scan` (профиль, `--single`, `--hash`, `--library`).
- `plan_edits` — правки плана **по селекторам**, а не по индексам и не по случайным ID: например, «кандидат, содержащий объект с относительным путём X → action=ask», «перенести объект Y в кандидат с объектом Z», «вложенный архив с путём P → preserve». Набор операций — минимально нужный корпусу. Каждая операция сводится к правке JSON плана v3 по его схеме.
- `steps` — последовательность команд: `scan`, `run`, `verify`, `rescan` (для SC-15), `add-ready` (для SC-14) — с ожидаемым кодом выхода.
- `requires` — условия ОС/прав (п. 1).

`expected.json` (схема `schemas/expected-import.v1.schema.json`, новая; `expected.v1` для golden не трогается):

- для `scan`: число кандидатов и их состав (относительные пути объектов), действия, исключения с правилом, вопросы, полнота (`complete`/`incomplete` с причиной), объекты томов и вложенных архивов;
- для `run`: итог каждого кандидата (`created`/`deferred`/`failed`/`skipped` + `message_id`), для созданных ассетов — состав `files[]` (исходные пути, SHA-256, размер), `inputs[]` (объекты, записи, `result`, `exclusion.rule`, `rawName`, `nested_action`), отсутствие непрошенной конвертации (байты = байты источника), отсутствие обязательного предпросмотра и источников, где это проверяет сценарий;
- для `verify`: `library verify --full` без `corrupt`;
- инварианты на все случаи (их проверяет прогонщик всегда, в `expected.json` не повторяются): источник неизменен (путь, размер, mtime, SHA-256 каждого файла до и после), во временной области импорта не осталось файлов, никакой ZIP-ассет не содержит исходный внешний архив целиком (ADR-0035, §19.4.1.5), если случай не требует обратного (3MF, SC-10).

Сравнение — рекурсивное подмножество, массивы без порядка с взаимно однозначным сопоставлением, как в `run_golden.py`. ID и время проверяются по свойствам (формат UUID, уникальность, ревизия 1), не по значению. Общий сравниватель вынести из `run_golden.py` в модуль `tests/tools/expect_match.py`; поведение `golden_zip` не меняется.

### 3. Прогонщик и ctest

- `tests/import_corpus/run_import_corpus.py --am <exe> --cases <dir> --work <dir> --case <name>`: генерирует вход, выполняет шаги, сверяет, печатает расхождения в виде «JSON-указатель: ожидалось / получено».
- **Один ctest на случай** (`import_corpus.<case>`), список собирает CMake по каталогам `tests/fixtures/import/*`. Метки: `import_corpus`, `req:SC-n` и прочие `req:` из `case.json`, чтобы `req_report` учитывал сценарии.
- Отдельный ctest `import_corpus_regen_check`: генератор дважды создаёт входы всех случаев, деревья совпадают побайтно (пути, байты, mtime); заодно проверяется, что `make_import_cases.py` не создаёт файлов вне указанного каталога.
- Тесты входят в пресет `cli` (как `golden_zip`), проходят под `-LE periodic`; ни один случай не дольше 30 с на машине разработчика (гипотеза, не норматив).
- Окружение изолируется, как в `test_import_zip_cli.py` (HOME/USERPROFILE/LOCALAPPDATA/XDG_STATE_HOME/TMP → каталог случая, без `AM_LOG_*`).

### 4. Поведение на Linux и в режиме только чтения

На Linux запись в библиотеку по `fs_support.md` отклоняется. Прогонщик там:

- выполняет все шаги `scan` и сверяет ожидания скана полностью;
- для `run` ожидает отказ `am.library.storage_read_only` (код 4) и источник без изменений;
- остальные проверки `run`/`verify` помечает в выводе как «не применимо на этой ФС», без провала.

Это те же правила, что в существующих CLI-тестах. Когда ext4 получит запись (S5+), ожидания `run` начнут проверяться и на Linux без изменения случаев.

### 6. Ожидания — по ТЗ, не по программе

- Сначала по ТЗ, спецификации и задачам T-028…T-033 пишется `expected.json`, затем выполняется прогон.
- При расхождении выясняется, что неверно:
  - **ожидание противоречит спецификации** → исправить ожидание и записать, какое место спецификации было прочитано неверно;
  - **программа противоречит ТЗ или спецификации** → это дефект. Случай остаётся с правильным ожиданием. Если исправление мелкое и локальное (несколько строк в одном модуле, без изменения формата и плана), его можно внести с регрессионным юнит-тестом (§13.4.10) и описать в отчёте. Иначе — вопрос управляющему и метка `known_defect` в `case.json` со ссылкой на вопрос; такой ctest помечается `WILL_FAIL` **только** по решению управляющего;
  - **ТЗ допускает оба варианта** → ожидание проверяет только свойство, требуемое ТЗ.
- Копировать вывод программы в `expected.json` целиком запрещено.

### 7. Матрица покрытия и документы

- `coverage_matrix.md`: для каждого SC обновить (б) — список случаев, (д) — ctest-имена и итог на Windows и Linux. Колонки (в)/(г) менять только по фактам; «реализовано» не ставится, пока сценарий проходит только частично. Добавить раздел «Дополнение T-034» с перечнем разрывов (например, SC-6 и SC-7 без RAR/7z, SC-9 без предложения разделения, SC-15 без поиска по содержимому — M4).
- Таблица характеристик §13.4.2 в той же матрице — строки для `ch-*`.
- `tests/fixtures/README.md` — раздел о корпусе импорта (генерация вместо хранения, схемы, как добавить случай).
- `tests/regression/README.md` — отметить, какие обязательные случаи §12.9.8 закрыты корпусом, какие остаются (многотомные RAR, проверка без импорта, поиск по SHA-256 в каталоге).

- `docs/research/libraries.md`: новых библиотек нет; если для генерации понадобится что-то сверх стандартной библиотеки Python — сначала вопрос.

### 8. Чего в T-034 нет

- Реальные образцы коллекции (`tests/real/registry.json`). Это отдельная задача после корпуса: нужен сеанс с владельцем по составу коллекции на момент замера.
- Сквозная цепочка «импорт → экспорт → перенос в чистую библиотеку» и проверка самодостаточности §13.4.4 — это P0.8.
- RAR/7z, настоящие многотомные архивы, предложение разделения (SC-9), поиск совпадений по содержимому (SC-15, M4).
- Обнаружение без импорта §13.4.5 и `am analyze` — M3b.
- Изменение опубликованных схемы 1.0, golden-корпуса и `expected.v1`.

## Тесты

1. Все случаи из таблицы п. 5 (или с записанной причиной отсутствия) проходят на Windows под `build_cli --ci -LE periodic` и `--offline`.
2. Те же случаи проходят на WSL/CI Linux: скан полностью, `run` — ожидаемый отказ.

### Уточнения и вопросы

- **В-1, решён владельцем.** SC-5: один ассет, один Input на акт импорта,
  два InputObject archive с раздельными подкаталогами; байты не смешиваются.
  Требование двух InputID в таблице задачи — неточность. В колонке (в)
  строки SC-5 coverage_matrix.md исправляется такое же неточное описание.

  без review допустим как неподтверждённое происхождение (принятое правило

  отсутствие origin.sources вообще. Первоначальное ожидание has_sources=false

  matches=[], action=import, в том числе с --skip-identical. Основные ожидания
  после успешного импорта сохраняются; совпадение/пропуск на read-only ФС
  неприменимы. Альтернатива — признать оба rescan целиком неприменимыми.
