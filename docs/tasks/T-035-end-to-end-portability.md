## Место в P0.8

P0.8 разбит на три задачи. Каждая проверяет уже реализованное ядро, новой функциональности не добавляет:

1. **T-035 (эта)** — сквозная цепочка «импорт → ZIP → индекс → экспорт → перенос в чистую библиотеку», восстановление индекса из ZIP, переносимость Windows → Linux.
2. **T-036** — отказы на каждом шаге цепочки: принудительное завершение процесса в точках фиксации всех пишущих команд, нехватка места (подставленная и, по решению владельца, на настоящем малом томе), восстановление после сбоя `state.sqlite`. Закрывает K-117 и остаток K-122.
3. **T-037** — один владелец записи между процессами (K-123), восстановление очереди после прерывания, итоговая сводка матрицы приёмки P0 и состав обязательных регрессий CI.

## Цель

Каждая команда ядра уже проверена по отдельности. ТЗ §13.4.4 требует большего: ZIP-ассет, созданный в одной библиотеке, перенесён в **чистую** библиотеку без исходников и без прежних баз — и там видно то же содержимое, метаданные, группы, классификация, происхождение, ID, ревизия и история.

T-035 проверяет это сквозными сценариями на настоящем CLI и отвечает на три вопроса:

1. **Самодостаточность.** Индекс второй библиотеки, построенный только из перенесённого ZIP, совпадает с индексом первой по всем полям, которые берутся из ZIP.
2. **Индекс — производные данные.** Пересборка индекса из ZIP (`rebuild`, удаление `index.sqlite` с последующим открытием) даёт тот же результат, что инкрементальная запись при импорте.
3. **Переносимость.** ZIP и экспорт, созданные на Windows, на Linux проходят V1–V4 и читаются с тем же результатом. Направление только Windows → Linux: на Linux запись библиотеки пока запрещена политикой ФС (`fs_support.md`).

## Решения

### 1. Сценарии

Прогонщик `tests/e2e/run_e2e.py` (одна ctest-проверка на сценарий, метка `e2e`), устроенный как корпус T-034: декларативное описание, ожидания по ТЗ, инварианты после каждого шага. Минимальный набор сценариев:

| Сценарий | Шаги | Что доказывает |
|---|---|---|
| `e2e-import-transfer` | Генерированный источник (папка + ZIP + вложенный ZIP, без внешнего золотого файла) → `import scan/run` в библиотеку A → `export` полный → `library init` B → `add-ready` B → сравнение A и B | Импортированный ассет самодостаточен (§13.4.4) |
| `e2e-ready-transfer` | Каждый `pos-*` golden-ассет → `add-ready` A → `export` → `add-ready` B → сравнение | Перенос сохраняет группы, claims, происхождение, историю нескольких ревизий, новую minor, нечитаемые чужие поля |
| `e2e-copy-transfer` | Ассет в A → `library copy` (независимая копия) → экспорт обоих → B | Независимая копия переносится с `derived_from`, новым ID и ревизией 1 по ADR-0036 п. 4 |
| `e2e-index-rebuild` | Библиотека A после сценариев выше: снимок индекса → `rebuild` → снимок; затем удалить `index.sqlite` → открытие на запись → снимок; затем `sync --full` → снимок | Индекс полностью выводится из ZIP; все четыре снимка равны |
| `e2e-trash-roundtrip` | `trash` → экспорт из корзины недоступен или доступен по спецификации → `restore` → экспорт → B | Корзина не меняет байтов ZIP и не ломает перенос |
| `e2e-selective-export` | Ассет из `e2e-import-transfer` → выборочный экспорт каждого пресета | Содержимое обычного ZIP побайтно равно выбранным файлам ассета; манифеста нет |

Если шаг сценария требует поведения, которого в ядре нет (например, экспорт из корзины), ожидание пишется по спецификации. Если спецификация молчит — вопрос В-n, а не допущение.

### 2. Сравнение двух библиотек

- **Снимок индекса** — функция прогонщика: нормализованный JSON из `library list --json` и `asset inspect --json` по каждому AssetID, плюс выборка из `index.sqlite` только для чтения (SQLite из стандартной библиотеки Python, режим `mode=ro`) по таблицам, производным от ZIP.
- Из сравнения исключаются **только** поля, локальные для библиотеки: путь ZIP относительно корня, время индексации, `in_trash`, идентификатор сессии записи, rowid. Список исключений — явный, в одном месте прогонщика, с обоснованием по схеме индекса. Исключать таблицу целиком нельзя.
- `userdata.sqlite` не переносится по спецификации §11: прогонщик проверяет, что в B она пуста, а не сравнивает её.
- Байты ZIP в A и B равны (полный экспорт и `add-ready` — побайтные). Это проверяется, но **не заменяет** сравнения индексов: смысл теста — в том, что индекс B выведен из ZIP без участия A.
- Сравнение — `expect_match` в режиме полного равенства (не подмножества) после нормализации.

### 3. Изоляция «чистой библиотеки»

Библиотека B создаётся в отдельном каталоге после того, как:

- сгенерированный источник переименован, так что исходные пути недоступны;
- библиотека A закрыта, её каталог переименован;
- окружение (HOME/USERPROFILE/LOCALAPPDATA/XDG_STATE_HOME/TMP) для команд B — отдельное.

Так проверка не может пройти за счёт обращения к исходникам или к A. Неизменность источника до переименования проверяется как в T-034.

### 4. Переносимость Windows → Linux

- Шаг **сборки пакета** (на Windows, ctest `e2e_portability_bundle`, метка `e2e`): после сценариев создаётся каталог `build/e2e/portability/` — экспортированные ZIP, результаты выборочного экспорта, снимки индекса и `asset inspect --json` с Windows, файл `bundle.json` со списком и SHA-256. Размер пакета — не более 2 МиБ (гипотеза для артефакта CI).
- В пакет входит и маленькая библиотека, созданная на Windows (2–3 ассета, один в корзине), упакованная обычным ZIP-архивом каталога с сохранением путей.
- Шаг **проверки пакета** (на Linux, `tests/e2e/check_portability.py`):
  - SHA-256 файлов пакета сверяются с `bundle.json` до любой проверки;
  - для каждого ZIP-ассета: `asset validate`, `asset verify --level full`, а `asset inspect --json` сравнивается со снимком Windows;
  - библиотека распаковывается во временный каталог сборки и открывается на Linux: `library info` сообщает режим только чтения, `library list --json --trash` и снимок индекса равны снимку Windows (по правилам п. 2), `library verify --full` без `corrupt`, полный экспорт в режиме только чтения (`queued:false`) даёт файл, побайтно равный экспорту с Windows;
  - `add-ready` в эту библиотеку получает ожидаемый отказ записи.
- **Локально:** управляющий запускает проверку пакета в WSL по готовому каталогу сборки Windows (команда в `docs/plan/` или `tests/e2e/README.md`).
- **CI:** задание `win-cli` выгружает пакет артефактом; новое задание `portability-linux` (`needs: win-cli`) скачивает его и запускает проверку. Действия CI — с теми же закреплёнными SHA, что уже используются в `ci.yml`. Четыре существующих задания не меняют своего поведения. После приёмки число обязательных зелёных заданий — пять.
- Обратное направление (Linux → Windows) и различия файловых систем при записи — после разрешения записи на ext4 (S5+), в T-035 не входят.

### 5. Требования и матрицы

- Каждый ctest e2e получает метки `req:` (K-10, K-22, K-31, K-122 в части индекса и т. д. по `case`-описанию).
- `acceptance_matrix.md`: строка для §13.4.4 (самодостаточность) и уточнения K-22/K-31 — только по фактам прогона. Статус «соответствует» не ставится там, где проверена лишь часть (например, переносимость в одну сторону).
- `coverage_matrix.md` не меняется: это сценарии импорта, а не цепочки.
- `tests/e2e/README.md` — что проверяется, как добавить сценарий, как запустить проверку пакета в WSL.

### 6. Ожидания — по ТЗ, не по программе

Как в T-034 п. 6: сначала ожидание по спецификации, потом прогон. Расхождение разбирается: ошибка ожидания → исправить с указанием места спецификации; дефект программы → мелкое локальное исправление с регрессионным тестом или вопрос управляющему и метка `known_defect`; `WILL_FAIL` — только по решению управляющего. Копировать вывод программы в ожидания запрещено.

### 7. Чего в T-035 нет

- Принудительное завершение, нехватка места, сбой `state.sqlite` — T-036.
- Владелец записи между процессами и очередь после прерывания — T-037.
- Запись на Linux, обратная переносимость, реальные образцы коллекции.
- Изменения формата 1.0, golden-корпуса, `expected.v1`, схем корпуса T-034.
