# T-028. `am import scan`: обход источников, предложение границ и план импорта (M3a, P0.6 — часть 3)

**Статус:** done (принята 2026-11-24, `7c100c3`) · **Веха:** M3a · **Основание:** ТЗ v1.8 §6.1–6.3, §6.5, §6.8 п. 1–5, §6.9, §13.2 (SC-1…SC-16), §13.4; ADR-0011 (тип по сигнатуре), ADR-0012 (исходные имена и raw-байты), ADR-0024 (уровни), ADR-0029 (общие обработчики импорта и исследования), ADR-0035 (`content/<InputID>/`), ADR-0037 п. 6 (полнота акта, X-01); `docs/architecture/import_pipeline.md` (этапы 1–5, 7); T-020 (`add-ready`, проба собственного формата), T-026 (отмена, прогресс), T-027 (журнал)

## Цель

Первая часть конвейера импорта: из файлов и папок, выбранных пользователем, получить **план импорта** — проверяемый и редактируемый JSON. План описывает:

- что найдено: каждый узел файловой системы, его тип по сигнатуре и размер;
- какие ассеты предлагается создать (кандидаты) и почему;
- что исключается и с какой уверенностью, что нужно решить пользователю;
- какие входы уже знакомы библиотеке.

Источники при этом **не изменяются и не копируются**, ассеты не создаются. Упаковка и фиксация по плану — следующая задача (`import run`), которая будет читать этот план, поэтому разбор и семантическая проверка плана входят сюда.

Содержимое архивов в этой задаче **не раскрывается**: архив — непрозрачный входной объект с типом по сигнатуре. Перечисление записей ZIP — задача «ZIP как вход», RAR/7z — M3b.

## Решения управляющего (не пересматривать в задаче)

### 1. Размещение и интерфейс

- Код — `src/services/import/`, заголовки — `include/am/services/import/` (уровень `services`). CLI и фасад — `application`.
- Внешние библиотеки — только уже имеющиеся в `vcpkg.json`. TOML профиля разбирается toml++ на том уровне, где ADR-0024 и `arch_check` это допускают; если `services` не может зависеть от toml++, разбор — в `application`, а `services` получает готовую структуру `ImportProfile`.
- Набросок API (имена можно уточнить, состав — нет):

```cpp
namespace am::import {
struct ScanRequest {
  std::vector<std::filesystem::path> roots;   // files and/or directories, mixed
  ImportProfile profile;
  bool single_candidate = false;              // --single: all roots -> one candidate
  std::optional<std::filesystem::path> library; // read-only matching
  bool hash_inputs = false;                   // --hash
  bool skip_identical = false;                // --skip-identical (requires hash_inputs)
  std::function<bool()> cancelled;            // polled between nodes
  std::function<void(const ScanProgress&)> on_progress;
  ScanHooks hooks;                            // test injection: stat/open/read failures, clock
};
Result<ImportPlan> scan(const ScanRequest&);
std::string serialize_plan(const ImportPlan&);          // deterministic, UTF-8
Result<ImportPlan> parse_plan(std::string_view json);   // schema + semantic checks (п. 7)
}
```

### 2. Обход (этап 1) — только чтение

- Рекурсивный обход корней. Для каждого узла: путь относительно корня (`/`), исходное имя, вид (`file`, `directory`, `symlink`, `other`), размер, `mtime` (целые наносекунды, строкой), тип по сигнатуре: `detect_kind` по первым `kSignatureProbeBytes` байтам и размеру.
- Файлы открываются **только на чтение** и только для чтения заголовка (и для SHA-256 при `--hash`). Никаких записей, переименований, смены атрибутов, временных файлов рядом с источником.
- **Ссылки не разыменовываются.** Символьные ссылки, junction и прочие reparse points внутри обхода записываются узлом `symlink` с решением `skip` (`am.import.link_not_followed`) и не обходятся. Корень, явно указанный пользователем, разрешается один раз (это его выбор), вложенные ссылки — нет.
- **Имена.** Windows: UTF-16 → UTF-8; непарные суррогаты — U+FFFD в отображаемом имени и исходные байты UTF-16LE в `name_raw` (hex). POSIX: байты имени; невалидный UTF-8 — U+FFFD в отображаемом имени и исходные байты в `name_raw`. Длинные пути — через `paths::native`. Нормализация Unicode не выполняется.
- **Ошибки отдельных узлов** (нет доступа, файл исчез во время обхода, ошибка чтения заголовка) не прерывают скан: узел получает `status = unavailable` и `problem{code, message_id}`, кандидат — причину `has_unavailable`. Отказ доступа к самому корню — ошибка операции.
- **Лимиты** — из `[limits]` профиля; в скане действует `max_entries`. Его достижение останавливает обход, `scan.completeness = incomplete`, в `scan.limits_hit[]` пишется лимит. Остальные лимиты `[limits]` относятся к раскрытию архивов и в скане не применяются, но разбираются и проверяются.
- Сетевые пути (UNC, сетевые диски) **допустимы** как источник: импорт с NAS — штатный сценарий. Отклонять их, как в `diag export`, не нужно.
- Порядок узлов в плане детерминирован: по байтам UTF-8 пути внутри корня; корни — в порядке аргументов.

### 3. Классификация записей (этап 7, без вложенных архивов)

- Для каждого файла вызывается `ExclusionEngine::evaluate`, но учитываются только правила, перечисленные в `[exclusions].rules` профиля. Если в профиле указан неизвестный движку ID правила, профиль недопустим (`am.import.profile_invalid`).
- Решения: `certain` → `exclude` (по умолчанию, пользователь может изменить); `probable` → `ask`; иначе → `include`. В записи — `rule_id`, `confidence` и `explanation_id`.
- Неизвестные типы, файлы без расширения, файлы нулевого размера и потенциальные дубликаты включаются (ТЗ 6.5.3–6.5.4).
- Каталоги в решения не попадают, но остаются узлами плана. Пустой каталог отмечается `empty: true`.
- Конфликт имён без учёта регистра внутри одного кандидата (`A.stl` и `a.stl` из POSIX-источника) — предупреждение `case_collision` у кандидата. Само переименование делает `import run` (ADR-0012), не скан.

### 4. Тома и собственный формат

- Файлы-архивы каждого каталога проходят `group_volumes` с правилами из `[volumes]` профиля.
- Набор томов — один входной объект `multivolume_archive` со всеми известными томами и `missing_indices`. Отсутствующие тома не скрываются (§19.4.17.6).
- Если набор требует подтверждения по заголовкам (`needs_header_confirmation`) или является RAR/7z без бэкенда, у него стоит `confirmed: false` и причина `volume_set_unconfirmed`.
- Набор томов **никогда не делится** между кандидатами. Если границы кандидатов разрезали бы набор, весь набор уходит к одному кандидату и добавляется причина `volume_set_kept_together`.
- ZIP по сигнатуре проходит пробу собственного формата, той же логикой, что `add-ready` (T-020):
  - валидный ассет → кандидат вида `ready_asset` (SC-14) с `asset_id` и ревизией из манифеста;
  - манифест есть, но проверка не пройдена → кандидат `ready_asset` с действием `ask` и причиной `ready_asset_invalid`;
  - манифеста нет → обычный архив.
  - Для этой пробы ZIP читается: это не раскрытие содержимого. Признаки распознавания берутся только из реализованных ADR-0035/0039. Открытый вопрос ТЗ 6.1.4 не закрывается.
- Специализированные контейнеры (3MF и подобные) — обычные включаемые файлы (SC-10), архивами не считаются.

### 5. Границы кандидатов (этап 3) и профили

ТЗ 6.2.7 (эвристики) открыт. Ниже — стратегии **версии 1**, оформленные как правила профиля, а не как закрытие вопроса. Результат — всегда **предложение**: план редактируется пользователем.

- **Профиль `default`** (встроенный, применяется без `--profile`), стратегия `root`:
  - каждый корень-каталог — один кандидат целиком, со всеми подкаталогами (ТЗ 6.2.2: «папка изделия — один ресурс»), причина `root_directory`;
  - каждый корень-файл — отдельный кандидат, причина `root_file`;
  - с `--single` все корни дают одного кандидата (SC-2, SC-8), причина `user_single`.
- **Стратегия `leaf_dir_with_payload`** (профиль `telegram`) с `context_levels = N`:
  - каталоги на глубине 1…N под корнем — контекст. Их имена — предположения по `[provenance].parent_as` (например `telegram_channel`) с `confirmed: false`;
  - каталог на глубине N+1, в поддереве которого есть хотя бы один включаемый файл, — один кандидат целиком со всеми подкаталогами, причина `depth_rule`;
  - каталог без включаемых файлов кандидатом не становится (узел `empty` или `excluded_only`);
  - свободные файлы на глубине ≤ N — каждый отдельным кандидатом с уверенностью `low` и причиной `loose_file_in_context`. Архив или набор томов на этой глубине — тоже отдельный кандидат.
- **Уверенность** `high | medium | low` и **причины** — машинные коды из закрытого перечня в схеме. Человекочитаемые тексты — в каталоге сообщений (`am.import.reason.*`).
- **Входы кандидата.** Кандидат содержит `inputs[]` — будущие входные комплекты (`inputs[]` манифеста, ADR-0035, строка SC-5 `coverage_matrix.md`):
  - каждый архив или набор томов — отдельный комплект;
  - свободные файлы и каталоги кандидата — один комплект вида `directory` (или `file` для одиночного файла).
  - Если чтение ADR-0035 и `container_manifest_v1.md` §5 даёт иное правило, следовать документам и описать расхождение в отчёте.
- **Ссылки `.url`** (`[provenance].url_files = "suggest"`): в INI-файле `[InternetShortcut]` читается `URL=`. Ссылки, совпавшие с `url_ad_patterns`, помечаются `ad: true` и не предлагаются. Остальные — `suggested_links[]` кандидата с `confirmed: false`. Сам `.url` остаётся включаемым файлом. Префикс `(?i)` в шаблоне — флаг нечувствительности к регистру: `std::regex` его не понимает, его нужно снять и передать как флаг.
- **Формат профиля v1.** Ключи `id`, `version`, `[boundaries]`, `[provenance]`, `[nested]`, `[exclusions]`, `[previews]`, `[groups]`, `[mode]`, `[volumes]`, `[limits]`. Неизвестный ключ или неверный тип → `am.import.profile_invalid` с путём к ключу.
  - Секции, которые скан не применяет (`[nested]`, `[previews]`, `[groups]`), разбираются и проверяются, а в плане перечисляются в `profile.not_applied[]`.
  - `--profile` принимает ID встроенного профиля (`default`, `telegram`) или путь к `.toml`.
  - Встроенные профили встраиваются в исполняемый файл при сборке (как каталог сообщений) и не ищутся на диске.
  - В плане фиксируются `id`, `version` и SHA-256 байтов профиля.
  - `profiles/telegram.toml` можно дополнить ключами, нужными стратегии, без изменения смысла существующих.

### 6. Ранние совпадения (этап 5) — только с `--library`

- Библиотека открывается **только на чтение**, тем же способом, что в `diag export` (T-027): без восстановления, без записи в базы, без открытия ZIP ассетов.
- Для каждого входного объекта (файл, архив, том):
  - **`name_size`** (слабое): `(имя без учёта регистра, размер)` по `input_objects` и `files`;
  - **`sha256_input`** (точное, только с `--hash`): SHA-256 объекта совпал с `input_objects.sha256` (повторное предъявление того же архива, SC-15);
  - **`sha256_file`** (точное, только с `--hash`): совпал с `files.sha256` (тот же файл в другой упаковке).
- Для `ready_asset` — `same_asset_id` с сравнением ревизии: `same_revision | newer | older`. Различие содержимого при той же ревизии выясняет `import run` (ТЗ 6.3.4).
- **Действие кандидата** `import | skip | ask`:
  - без совпадений → `import`;
  - любое совпадение → `ask`;
  - `skip` — только при `--skip-identical` и только если каждый входной объект кандидата имеет `sha256_input`. Слабое совпадение никогда не даёт `skip`.
  - Объединение, замена и перезапись в плане не выражаются вовсе (ТЗ 6.3.3).
- `--hash` без `--library` допустим: SHA-256 просто записываются в план. `--skip-identical` без `--hash` — ошибка использования.

### 7. План импорта: формат, разбор и проверка

- JSON `format = "am-import-plan"`, `version = 1`, схема `schemas/import-plan.v1.schema.json`. Строка в `versioning.md` — только для этого формата.
- Размеры и `mtime` — десятичные строки, как в манифесте (ADR-0038), чтобы `uint64` не терялись в JSON-инструментах.
- Состав (уточнения в отчёт):
  - `created_at`;
  - `generator{name, version}`;
  - `profile{id, version, sha256, not_applied[]}`;
  - `mode` — из `[mode]` профиля; разрешение частичного импорта — забота `run`;
  - `roots[]{path, path_raw?}`;
  - `scan{completeness, limits_hit[], counts{…}}`;
  - `nodes[]{id, root, path, name_raw?, kind, size?, mtime_ns?, detected?, status, problem?, empty?}`;
  - `candidates[]{id, kind: new_asset|ready_asset, root, base_path, title_hint, context{…}, confidence, reasons[], inputs[]{id, kind, objects[]{node | volume_set}}, entries[]{node, decision: include|exclude|ask|skip, rule_id?, confidence?, explanation_id?}, volume_sets[], suggested_links[], matches[], warnings[], action}`.
- **Абсолютные пути в плане допустимы**: план — локальный рабочий файл, по нему `run` будет читать источники. В манифест абсолютные пути не попадут, это уже обязанность `run` (§19.4.3.7). В отчёте и логах путь — поле `FieldKind::path`.
- **Детерминизм.** ID узлов и кандидатов — последовательные (`n000001`, `c0001`). При одинаковом дереве и параметрах `serialize_plan` даёт одинаковые байты, кроме `created_at`.
- **`parse_plan`** — схема и семантика:
  - все ссылки `node` и `volume_set` существуют;
  - узел-файл принадлежит не более чем одному кандидату;
  - набор томов не разделён;
  - у `ready_asset` ровно один вход из одного ZIP;
  - `skip` только при `sha256_input` у всех объектов;
  - версия формата известна;
  - пользовательские правки (перенос узлов между кандидатами, смена решений, удаление кандидата, объединение) допустимы, если инварианты выполняются.
  - Ошибка — `am.import.plan_invalid` с JSON-указателем на место.
- **Проверка устаревания** (сама проверка — в `run`): у каждого входного узла есть `size` и `mtime_ns`, у объектов при `--hash` — SHA-256. Этого достаточно, чтобы `run` отказал, если источник изменился после скана.

### 8. CLI и выход

- `am import scan <path>... [--profile <id|file.toml>] [--library <dir>] [--hash] [--skip-identical] [--single] --plan <out.json> [--json]`.
- Вывод — сводка: число узлов, кандидатов по видам и действиям, исключений, `ask`, совпадений, полнота. С `--json` — один объект.
- **План пишется атомарно**, как выход `diag export`: временный файл в каталоге назначения и публикация без замены. Существующий выход — код 4, файл не тронут.
- **Выход внутри любого из сканируемых корней запрещён** (`am.import.output_inside_source`, код 2): запись плана в источник нарушила бы неизменность источника.
- Коды выхода — по принятой таблице CLI (T-012, T-026, T-027): 0 — успех (в том числе при `completeness = incomplete`, это видно в сводке); 2 — ошибки использования и профиля; 4 — выход существует или недоступен. Отмена по Ctrl+C (обработчики из T-026) — код отмены `jobs run`; план не пишется, временный файл удаляется.
- **Журнал:** `import.scan.started` / `import.scan.finished` (info: счётчики, профиль, полнота, длительность); `import.scan.node_unavailable` (warning, путь как `FieldKind::path`); достижение лимита — warning.
- Задание (`import.scan` в исполнителе T-026) в этой задаче **не создаётся**: отмена и прогресс в API уже есть, обёртка заданием появится вместе с `import run`.

## Тесты

Синтетические деревья строятся тестами во время выполнения во временном каталоге сборки (`.cache/` / `build/`). Готовые ассеты копируются из `tests/fixtures/golden/` (копия, исходник не меняется). Бинарные фикстуры в репозиторий не добавлять. Реальная коллекция не используется (см. уточнение о её переносе в `CLAUDE.md`).

1. **`ImportScan.*` (обход):**
   - одиночный файл;
   - несколько файлов-корней (без `--single` — по кандидату, с ним — один);
   - каталог с подкаталогами — один кандидат;
   - смешанный набор корней;
   - пустой каталог;
   - файл нулевого размера;
   - неизвестный тип;
   - тип по сигнатуре при ложном расширении (RAR под именем `.zip`);
   - детерминизм двух сканов (байты плана без `created_at`);
   - порядок узлов.
2. **Неизменность источника:** снимок дерева (пути, размеры, `mtime`, SHA-256 байтов) до и после скана с `--hash` и `--library` совпадает. Наблюдатель в `ScanHooks` подтверждает, что ни один файл источника не открывался на запись.
3. **Ссылки:** символьная ссылка на каталог вне корня и цикл ссылок не обходятся и записываются узлом `symlink` с `skip`. На Windows — junction, если создаётся без прав администратора; иначе `GTEST_SKIP` с причиной.
4. **Имена:** POSIX — имя с байтом `0xFF` (raw сохранён, отображаемое с U+FFFD); Windows — непарный суррогат; длинный путь > 260 символов; `case_collision`.
5. **Отказы:** внедрённые через `ScanHooks` отказы `stat`, открытия и чтения заголовка → `unavailable` с `problem`, скан продолжается. Исчезновение файла между перечислением и `stat`. Недоступный корень — ошибка операции. Отмена посреди обхода → ошибка отмены, выход не создан.
6. **Лимит:** `max_entries` → `incomplete`, `limits_hit`, обход остановлен.
7. **Исключения:**
   - AppleDouble с сигнатурой под `__MACOSX/` → `exclude certain`;
   - `._x.3mf` без сигнатуры → `ask` (или по фактической логике движка, с объяснением в отчёте);
   - `.DS_Store`, `Thumbs.db` с сигнатурами;
   - правило, не перечисленное в профиле, не применяется;
   - неизвестный ID правила в профиле → `profile_invalid`;
   - дубликаты одинаковых файлов в разных подпапках включаются.
8. **Тома:**
   - `X.part1.rar`, `X.part2.rar` без `part3` при наличии номера дальше → `missing`;
   - `X.7z.001`/`.002`;
   - `copy_suffix` → `confirmed: false`;
   - набор на границе стратегии `leaf_dir_with_payload` не делится.
9. **Готовый ассет:** валидный ZIP из golden → `ready_asset` с `asset_id` и ревизией; ZIP с повреждённым манифестом → `ask` с `ready_asset_invalid`; обычный ZIP → архив `new_asset`.
10. **Профили:**
    - `default` и `telegram` (контекст канала с `confirmed: false`, кандидаты на глубине 2, свободный файл на уровне канала → `low`);
    - профиль из файла;
    - неизвестный ключ, неверный тип → ошибка с путём ключа;
    - `not_applied`;
    - SHA-256 профиля в плане;
    - `.url`: ссылка предложена, рекламная (`(?i)free ?download`) отфильтрована.
11. **Совпадения:** библиотека создаётся существующими средствами тестов (`add-ready` или генератор T-024 в малом масштабе), затем:
    - `name_size`;
    - `sha256_input` и `sha256_file` с `--hash`;
    - `same_asset_id` с `same_revision` и `newer`;
    - `--skip-identical`: `skip` только при точном совпадении всех объектов;
    - `--skip-identical` без `--hash` → код 2;
    - байты баз и ZIP библиотеки до и после скана совпадают.
12. **`ImportPlan.*` (`parse_plan`):**
    - круговой проход `serialize → parse → serialize` (байты равны);
    - каждая семантическая ошибка из п. 7 отдельным случаем с проверкой JSON-указателя;
    - допустимые правки (перенос узла, смена решения, удаление кандидата) проходят.
13. **`schema_check`:** новая схема, положительные и отрицательные примеры, реальные планы из тестов проходят схему.
14. **`cli_import_scan` (Python):**
    - коды 0, 2, 4;
    - `--json`;
    - выход существует → 4, файл не тронут;
    - выход внутри корня → 2;
    - Ctrl+C (где тестовая среда позволяет, как в T-026) → план не создан и нет временных файлов;

15. **Измерение без порога:** скан сгенерированного дерева ~10 000 файлов в 1 000 каталогах — время на узел, с `--hash` и без. Результат — в отчёт как порядок величины, без имени компьютера, пользователя и путей. Норматив не назначается (ТЗ §14.9.13).

### Вопросы

В-1, В-2 и В-3 решены управляющим в чате и отражены в import_pipeline.md.

**Для отдельного решения управляющего по ТЗ 6.5.2 (не блокирует согласованный В-3):** windows.desktop_ini даёт certain по имени desktop.ini и размеру <4096 без проверки сигнатуры; os.icon_r — по одному имени Icon с завершающим CR, без проверки размера или сигнатуры. macos.ds_store, windows.thumbs_db и macos.appledouble требуют соответствующую сигнатуру для certain. Понижать confidence при противоречащей известной сигнатуре в T-028 не стали. Регрессия В-3 покрывает валидный/невалидный ZIP, certain (desktop.ini)/probable (.DS_Store), обычную стратегию/--single и приоритет ask перед автоматическим skip при точном совпадении.

В WSL/DrvFS имя с байтом FF изменяется самой файловой системой при создании: перечисление возвращает UTF-8 U+FFFD вместо исходного FF. Тест сырых имён выделен отдельно и пропускается только при таком изменении имени; длинные пути проверяются самостоятельным тестом. Сырые UTF-16LE-имена Windows проверяются фактическими байтами.

Предсуществующий архив владельца не изменён и не включён в коммиты. Реальная коллекция не используется; бинарные фикстуры в репозиторий не добавляются.

### Замечания

1. **Нестабильный тест T-026** (см. выше) — исправить тест в T-029. Продукт не меняется.
2. **Reparse points на Windows.** Скан считает ссылкой любой узел с `FILE_ATTRIBUTE_REPARSE_POINT`. Под это попадают и файлы OneDrive «по запросу» (`IO_REPARSE_TAG_CLOUD_*`), и дедупликация (`IO_REPARSE_TAG_DEDUP`), и другие обычные файлы с тегами. Коллекция в OneDrive или на дедуплицированном томе целиком окажется `skip`: видимо в плане, но неверно. Ссылками считать только `IO_REPARSE_TAG_SYMLINK`, `IO_REPARSE_TAG_MOUNT_POINT` и `IO_REPARSE_TAG_LX_SYMLINK`. Файлы с `FILE_ATTRIBUTE_RECALL_ON_DATA_ACCESS` / `RECALL_ON_OPEN` не открывать ради заголовка: открытие запускает скачивание. Такой узел помечается `status = unavailable` с отдельной причиной `am.import.cloud_placeholder` и решением `ask`. То же правило — в проверке источников `diag export` (T-027). Исправление — T-029.
3. **Имена только по имени файла в `ExclusionEngine`** (вопрос исполнителя по ТЗ 6.5.2). Решение: если `detect_kind` установил известный нетекстовый тип (контейнер, изображение, 3D, PDF), противоречащий правилу, то `certain` по одному имени понижается до `probable` (`ask`), объяснение `am.import.exclusion.signature_conflict`. `windows.desktop_ini` и `os.icon_r` остаются `certain`, если содержимое не опознано или текстовое. Исправление — T-029. Правило В-3 для готовых ассетов остаётся.
4. **Модель плана — JSON без типизированного представления.** `ImportPlan` и `ImportProfile` — обёртки над `nlohmann::json`. Это допустимо, пока план только пишется и проверяется. `import run` будет читать план, поэтому в нём нужен типизированный вид поверх проверенного `parse_plan` JSON, чтобы обращения к полям не были рассыпаны строковыми ключами по коду.
