# T-007. Безопасное чтение ZIP-контейнера: структура, потоки записей, распознавание «своего» ZIP

**Статус:** ready · **Веха:** M1 (`am_storage`, модуль 5 «Контейнер», P0.3) · **Основание:** ТЗ §19.4.1, §19.4.14.2, §19.4.17 (MF-10); ADR-0005 (сжатие, ZIP64, без шифрования и data descriptor), ADR-0006 п. 2 (raw-копия), ADR-0012, ADR-0024, ADR-0032, ADR-0035 пп. 2, 7, 8, ADR-0037 п. 9 (классы записей, V4); спецификация §1, §12

## Цель

Дать программе один безопасный способ читать ZIP-ассет: разобрать структуру архива, не доверяя заявленным значениям, найти нарушения безопасности **до** распаковки, читать записи потоком с проверкой CRC, размера и общего бюджета распаковки, и определить, «свой» ли это контейнер (спецификация §1 п. 2). Это база для V1/V4, `Verifier`, raw-копирования в писателе (T-008) и `AssetRepository`.

Записи ZIP, классификации `registered`/`opaque` по манифесту, V3/V4 и CLI в этой задаче нет.

## Решения управляющего (не пересматривать в задаче)

1. **Собственный разбор структуры, не minizip-ng.** Читатель сам разбирает EOCD, ZIP64 EOCD locator/record, центральный каталог и локальные заголовки; распаковка Deflate — потоковый `inflate` из **zlib** (`find_package(ZLIB)`, порт `zlib` уже установлен как зависимость minizip-ng). Причина: защита по ТЗ §19.4.17 и спецификации §1 требует видеть то, что API minizip-ng скрывает, — перекрытие диапазонов данных (zip bomb через общий локальный заголовок), расхождение локального заголовка и центрального каталога, дубликаты имён, точные границы Deflate-потока. Выбор библиотеки для **записи** решается в T-008. `libraries.md` обновляет управляющий.
2. **Размещение (ADR-0024).**
   - Читатель — `am_storage`, каталог `asset_zip/`: `include/am/storage/asset_zip/`, `src/storage/asset_zip/`. Собирается **только при `AM_WITH_CONTAINER=ON`**; в минимальной сборке `am_storage` не меняется.
   - SHA-256 — тонкая обёртка над OpenSSL EVP (`libraries.md`: ✅) в том же модуле (`include/am/storage/asset_zip/sha256.hpp`); `am_foundation` остаётся без внешних зависимостей. zlib и OpenSSL — **приватные** зависимости `am_storage`; их заголовки не попадают в публичные.
   - Проверка путей нормативного профиля — функция в `am_foundation` (`am::paths`), без сторонних библиотек: правила ADR-0012 и спецификации §1 п. 6, ключ коллизии — существующий `unicode::path_collision_key`. Она собирается и тестируется в минимальной сборке.
3. **Два уровня проверки.**
   - **Механизм** (`ZipArchive::open`) отвергает то, что опасно или неразбираемо для любого ZIP: нарушения структуры, перекрытие, выход за файл, несогласованность заголовков, превышение лимитов. Чужие ZIP с допустимыми, но не нормативными свойствами (data descriptor, имена не в UTF-8, каталоги, метод 12) открываются: эти свойства видны в `EntryInfo`.
   - **Нормативный профиль 1.0** (`check_normative_profile`) — отдельная функция над открытым архивом: перечисляет все нарушения правил спецификации §1 пп. 1, 3, 5, 6 для **нового** контейнера. Её результат — вход V1/V4 и проверки перед фиксацией (ADR-0035 п. 7).
4. **Потоковое чтение записи** (ТЗ §19.4.17.4, §19.4.17.6). Никогда не верить заявленным размерам:
   - распакованных байтов не больше заявленного `uncompressed_size`: первый лишний байт → ошибка, чтение прекращается;
   - Deflate-поток должен закончиться **ровно** на `compressed_size`: ранний конец, хвостовые байты, обрыв — ошибка;
   - по окончании CRC-32 и размер совпадают с центральным каталогом;
   - каждый распакованный байт списывается с **общего бюджета** (`ReadBudget`), разделяемого всеми потоками одного задания (§19.4.17.5); исчерпание → `resource_exhausted` до выделения памяти под данные;
   - память читателя не зависит от размера записи (буферы фиксированного размера).
5. **Лимиты — гипотезы** (ТЗ §14.9.13, O-17 открыт): структура `ZipLimits` со значениями по умолчанию и комментарием `hypothesis, O-17`: число записей 100 000; размер центрального каталога 64 МиБ; длина имени 4 096 байт; заявленный и фактический распакованный размер одной записи 64 ГиБ; суммарный бюджет задания — параметр `ReadBudget`. Тесты не закрепляют их как норму; для проверки срабатывания тесты передают малые значения.
6. **Распознавание «своего» ZIP** (спецификация §1 п. 2): `probe_container` читает корневой `manifest.json` через `am::manifest::parse_manifest` (T-006) и возвращает один из исходов:

   | Исход | Условие |
   |---|---|
   | `not_zip` | структура ZIP не найдена (нет EOCD) |
   | `invalid_zip` | EOCD найден, но механизм отверг архив (ошибка — в результате) |
   | `foreign_zip` | корректный ZIP без корневого `manifest.json`, либо `manifest.json` разобран, но `format.id` не совпадает |
   | `own` | `format.id` = `urn:uuid:0d40b3a5-39ae-48e6-a8e8-da18b1b8c128`, `major` = 1 |
   | `own_unsupported_version` | `format.id` совпадает, `major` ≠ 1 |
   | `own_corrupt` | `manifest.json` не разобран (V1 кодека) или `format` не читается, но в байтах **первой записи архива** найдена строка FormatID |

   Если корневых записей `manifest.json` несколько (точное совпадение имени) — `invalid_zip` (дубликаты отвергает механизм). Чтение манифеста ограничено `CodecLimits::max_bytes`. V2 и V3 `probe_container` не выполняет.
7. **Коды ошибок** (ADR-0032; ядро не формирует текст для пользователя):

   | Ситуация | `Errc` | `message_id` |
   |---|---|---|
   | нет EOCD, обрыв, неверная сигнатура, значения вне файла, несогласованность EOCD/ZIP64/каталога, локальный заголовок ≠ центральный | `corrupt_data` | `am.zip.invalid_structure` |
   | перекрытие диапазонов данных или каталога | `corrupt_data` | `am.zip.overlapping_entries` |
   | дубликат имени (точное совпадение байтов) | `corrupt_data` | `am.zip.duplicate_name` |
   | CRC, размер или граница Deflate-потока не совпали; ошибка inflate | `corrupt_data` | `am.zip.entry_corrupt` |
   | многотомный архив, шифрование, метод не 0/8 при чтении потока | `unsupported` | `am.zip.unsupported_feature` |
   | превышен лимит или бюджет | `resource_exhausted` | `am.zip.limit_exceeded` |
   | файл не найден, ошибка чтения ОС | `io_error` | `am.zip.io_error` |
   | нехватка памяти | `resource_exhausted` | `am.zip.out_of_memory` |

   Подробности (смещение, индекс записи, имя в hex для недекодируемых) — в `ctx.detail` на английском. Исключения zlib/OpenSSL/`std::bad_alloc` через границу модуля не проходят. Новые `Errc` не добавлять.

## Требования

### 1. Источник данных

- `RandomAccessSource` — интерфейс чтения по смещению (`size()`, `read_at(offset, span)` → `Result<std::size_t>`), реализации: файл (`am::paths::native()`, Windows — `\\?\`-пути) и буфер в памяти (для тестов).
- Файл открывается только на чтение, с разрешением совместного чтения другими процессами. Изменение файла во время чтения не обязано обнаруживаться, но не должно приводить к UB: любые прочитанные байты проходят те же проверки.

### 2. `ZipArchive::open(source, limits)` — механизм

Разбор (без рекурсии, без чтения данных записей):
- **EOCD:** поиск сигнатуры с конца в окне 22 + 65 535 байт; комментарий EOCD должен точно доходить до конца файла; несколько кандидатов — выбирается последний, удовлетворяющий этому условию, иначе `invalid_structure`.
- **ZIP64:** если поля EOCD насыщены (`0xFFFF`/`0xFFFFFFFF`) — ZIP64 EOCD locator обязателен и указывает на корректную ZIP64 EOCD record; значения берутся из неё. ZIP64 extra field (0x0001) у записи читается строго по порядку полей APPNOTE: присутствуют только поля, насыщенные в основной записи.
- **Многотомность** (номера дисков ≠ 0, число дисков ≠ 1) → `unsupported_feature`.
- **Центральный каталог:** смещение + размер в пределах файла и до EOCD (с учётом ZIP64-записей); число записей из EOCD = фактическому; каждая запись с корректной сигнатурой; extra fields разбираются как последовательность (id, size) точно до своей длины.
- **Локальный заголовок** каждой записи читается и сверяется с центральным: сигнатура; имя (байты) идентично; метод; флаги шифрования; если бит 3 не установлен — CRC и размеры (с учётом ZIP64 extra в локальном заголовке) совпадают. Если бит 3 установлен — размеры и CRC берутся из центрального каталога; data descriptor после данных, если он умещается до следующего диапазона, читается и сверяется (с сигнатурой и без).
- **Диапазоны:** у каждой записи диапазон `[смещение локального заголовка, конец данных (+ data descriptor))`. Диапазоны записей не пересекаются друг с другом и с центральным каталогом / ZIP64-записями / EOCD; конец данных ≤ начала центрального каталога. Пересечение → `overlapping_entries`. Промежутки допускаются механизмом, но учитываются (`unaccounted_bytes` в сводке).
- **Дубликаты имён** (точное совпадение байтов) → `duplicate_name`. Проверка за O(n log n).
- Лимиты `ZipLimits` проверяются **до** выделения памяти под соответствующие структуры (число записей и размер каталога — по значениям из EOCD).

`EntryInfo` (только чтение) — минимум: индекс; сырые байты имени; имя как UTF-8, если установлен бит 11 **и** байты — валидный UTF-8 (иначе пусто); метод; общий флаг; признаки `encrypted`, `data_descriptor`, `utf8_flag`; CRC-32; сжатый и распакованный размер (64-бит); смещение локального заголовка и начала данных; `version_made_by`, внешние атрибуты; **вид**: `regular`, `directory` (имя оканчивается на `/`), `symlink` (Unix: `version_made_by` host 3 и `S_IFLNK` в старших 16 битах внешних атрибутов), `special` (иные не-регулярные Unix-типы); признак наличия ZIP64-полей; сырые extra fields (для T-008: решение «можно ли их переносить» принимается там).

Сводка архива: число записей, смещение и размер центрального каталога, признак ZIP64, длина комментария EOCD, `unaccounted_bytes` (сумма промежутков, включая данные перед первой записью).

### 3. Чтение записи

- `ZipArchive::open_entry(index, ReadBudget&)` → поток с `read(std::span<std::byte>)` → `Result<std::size_t>` (0 — конец, после успешной финальной проверки CRC/размера). Метод 0 и 8; иные методы, шифрование → `unsupported_feature` при открытии потока. Каталоги, symlink и special как потоки открываются (их байты — данные), решение о материализации — не дело читателя.
- Требования п. 4 «Решений». Ошибка — окончательная: последующие `read` возвращают ту же ошибку.
- Необязательный SHA-256 распакованного потока (флаг при открытии); итоговый хеш доступен после конца потока.
- `raw_range(index)` → смещение и длина сжатых данных (для raw-копирования в T-008; проверка CRC по распакованному потоку остаётся обязательной, спецификация §1 п. 3).
- `verify_entry(index, ReadBudget&, bool sha256)` — удобная функция: читает поток до конца, возвращает CRC/размер/SHA-256 или ошибку.

### 4. Нормативный профиль 1.0 — `check_normative_profile(const ZipArchive&)`

Возвращает список нарушений (код + индекс записи + деталь), пустой — профиль соблюдён. Нарушения (коды — стабильные строки `am.zip.profile.*`, фиксируются в заголовке):
- запись зашифрована; метод не 0/8; установлен бит 3 (data descriptor); не установлен бит 11; имя не валидный UTF-8;
- вид записи не `regular` (каталоги, symlink, special);
- путь нарушает правила спецификации §1 п. 6 / ADR-0012 (функция foundation, п. 5 ниже): пустой компонент, `.`/`..`, абсолютный путь, `\`, буква диска, запрещённые символы, управляющие символы, хвостовые точка/пробел, зарезервированные имена Windows, > 200 байт UTF-8, не NFC;
- две записи с одинаковым ключом коллизии (`unicode::path_collision_key`);
- нет корневой записи `manifest.json`; запись вне пространств `manifest.json`, `content/`, `generated/`, `extensions/` (спецификация §1 п. 3: произвольных файлов в корне нет);
- `unaccounted_bytes` > 0;
- комментарий EOCD не пуст — **[ПРЕДЛОЖЕНИЕ управляющего]**, помечается в коде как предложение, отдельным кодом `am.zip.profile.archive_comment`.

`manifest.json` — первая запись — правило **писателя** (ADR-0035 п. 2) и в профиль читателя **не входит**. Проверка регистрации записей в `files[]`/`attachments[]` (`registered`/`opaque`) — V4, не эта задача.

### 5. Проверка пути в foundation

`am::paths::check_container_path(std::string_view utf8_path)` → `Result<void>` (или список причин — на выбор исполнителя, с документированием), правила п. 4. Не меняет существующее поведение `ZipPathMapper`. Если правила `ZipPathMapper` и новой функции расходятся (например, по набору запрещённых символов), — общая реализация правил одна, расхождение описать в отчёте; поведение маппера не менять без согласования.

### 6. `probe_container(source, limits, codec_limits)`

По п. 6 «Решений». Возвращает исход и, где применимо, `Error` механизма или кодека (в `cause`), версию формата для `own`/`own_unsupported_version`.

## Тесты

Синтетические архивы строятся **в коде тестов** тестовым построителем ZIP, который пишет заголовки побайтово и позволяет испортить любое поле (`tests/unit/zip_builder.hpp/.cpp` или аналог). Плюс небольшой набор интероперабельности: ZIP, созданные Python `zipfile` (Stored, Deflate, data descriptor при записи в поток, ZIP64 принудительно `force_zip64=True`), генератор `tools/fixtures/make_zip_fixtures.py`, результаты — `tests/fixtures/zip/` с `README.md` (как получены, SHA-256). Генератор запускается вручную; тесты читают закоммиченные файлы и Python не требуют.

Обязательные сценарии (теги `RecordProperty("req", …)`: `NFR-14.x.y`/`K-n` по `acceptance_matrix.md`, при отсутствии подходящего — `ADR-0035`):
1. Корректные архивы: Stored, Deflate, пустая запись, пустой архив, комментарий EOCD, ZIP64 (по EOCD и по extra полям записи с малыми фактическими размерами); имена и данные читаются точно, CRC/размер/SHA-256 совпадают с ожидаемыми.
2. EOCD: отсутствует; обрезан; комментарий не доходит до конца файла; ложная сигнатура внутри комментария; ZIP64 locator указывает вне файла / не на запись.
3. Каталог: число записей ≠ EOCD; смещение/размер вне файла; неверная сигнатура записи; extra field выходит за свою длину; ZIP64 extra с отсутствующим обязательным полем.
4. Локальный заголовок ≠ центральный: имя, метод, размер, CRC, флаг шифрования; смещение вне файла.
5. **Перекрытие:** две записи центрального каталога на один локальный заголовок (классическая bomb с перекрытием); данные записи заходят на соседнюю; данные заходят на центральный каталог.
6. Дубликаты имён; коллизия по `path_collision_key` (`A.stl`/`a.stl`, NFC/NFD) — механизм открывает, профиль сообщает.
7. Пути профиля: `../x`, `/x`, `C:x`, `a\b`, `a//b`, `./a`, `a/.`, хвостовая точка и пробел, `CON.stl`, управляющий символ, 201 байт, не-NFC, запись в корне кроме `manifest.json`.
8. Многотомный архив, шифрование (бит 0, метод 99), метод 12 — механизм / поток / профиль ведут себя по пп. 2–4.
9. **Поток:** Deflate распаковывается больше заявленного (останов на первом лишнем байте); меньше заявленного; хвостовые байты после конца Deflate-потока; обрыв; неверный CRC; заявленный размер больше лимита записи — отказ до чтения; общий бюджет исчерпан на второй записи.
10. Data descriptor: с сигнатурой и без, совпадает / не совпадает с центральным каталогом.
11. Вид записи: каталог, symlink (Unix-атрибуты), special.
12. Лимиты: число записей и размер каталога сверх малых лимитов — отказ до выделения (проверяется тем, что архив с заявленными 2^32−1 записями и крошечным файлом отвергается быстро и без большой аллокации).
13. **Память не растёт с размером записи (К-116):** запись из 4 ГиБ нулей (Deflate, ZIP64; построитель сжимает потоком, файл во временном каталоге `.cache/` или в памяти — на выбор, но не в репозитории) читается целиком с SHA-256; вывести время и пик памяти процесса, порога нет.
14. `probe_container`: все шесть исходов, включая `own_corrupt` (повреждённый JSON с FormatID в первой записи) и `foreign_zip` для чужого `format.id`.
15. Интероперабельность: все архивы `tests/fixtures/zip/` открываются; содержимое совпадает с ожидаемым из `README.md`/`expected.json`.

## Критерии приёмки

1. `tools\build_min.cmd` — PASS без предупреждений; минимальная сборка не тянет zlib/OpenSSL; новые тесты путей foundation в ней выполняются.
2. `tools\build_cli.cmd` и `tools\build_cli.cmd --offline` — PASS без предупреждений; офлайн-повтор без сетевых загрузок.
3. Все сценарии раздела «Тесты» реализованы и фактически выполнены; в отчёте — таблица «сценарий → тесты».
4. Публичные заголовки не содержат заголовков zlib и OpenSSL; исключения не выходят за границы модуля; `arch_check` проходит.
5. Разбор структуры — без рекурсии, O(n log n) по числу записей; поток — память O(1) по размеру записи. В отчёте — обоснование и замер теста 13.
6. Отчёт по `AGENTS.md`: ветка, коммиты, выполнение каждого критерия, вывод тестов, отклонения, вопросы.
