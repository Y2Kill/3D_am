## Решения управляющего (не пересматривать в задаче)

### 1. Гонка в тесте `PauseCancelAndShutdown…` — исправляется тест, не продукт

- Причина установлена при приёмке T-028. Тест отпускает обработчик сразу после `stop.request_stop()`, а остановка доходит до `context.stop()` асинхронно, через цикл исполнителя. Если обработчик успевает завершиться раньше, исход `succeeded` корректен по контракту «завершённая работа побеждает позднюю остановку».
- Исправление: после `release` обработчик ждёт, пока `context.stop().stop_requested()` станет истинным, с ограничением по времени (как у остальных `Gate` теста). Только после этого он возвращает `interrupted()`. Если за отведённое время остановка не пришла — явный провал теста с сообщением, а не `success()`.
- Проверить остальные тесты `test_jobs.cpp` и `test_jobs_services.cpp` на ту же схему «запросить остановку → сразу отпустить → ожидать прерывание». Найденные исправить так же. `CompletedWorkWinsOverLateShutdown` намеренно проверяет обратный исход и не меняется.
- Поведение `Executor` не меняется. Если при разборе выяснится, что гонка есть и в продукте (остановка теряется, а не запаздывает), — остановиться и задать вопрос.
- Доказательство: исправленные тесты запускаются с `--gtest_repeat=300` на Windows и Linux без единого провала. Также приводится, сколько провалов было на исходной версии теста при тех же условиях.

### 2. Журнал (замечания 1–3 T-027)

- **Стоимость выключенного журнала.** Рядом с атомарным указателем на приёмник хранить `std::atomic<int>` с минимальным уровнем. Приёмника нет — значение «выше `critical`». `set_sink` обновляет оба значения, `enabled(level)` читает только уровень (`memory_order_relaxed` достаточно). `write` по-прежнему загружает приёмник и проверяет его на `nullptr`. Короткое расхождение уровня и приёмника во время замены допустимо, но не должно приводить к падению. Гарантию «после возврата `set_sink(nullptr)` старый приёмник больше не получает записей» дать без блокировки нельзя (поток мог уже загрузить указатель), поэтому фактическую гарантию описать в `logging.md` и отчёте. Время жизни приёмника обеспечивает `shared_ptr`, как сейчас.
- В `ExecutorState::emit` не создавать `log::Scope` и строки полей, если ни один из нужных уровней не включён.
- Повторить измерение T-027 (тот же тест) и привести «до/после» без нормативов.
- **Квота.** В `quota()` использовать варианты `std::filesystem` с `std::error_code`. Файл, который не удалось удалить (держит другой процесс, нет прав), пропускается: квота переходит к следующему, а `open_file_log` не завершается ошибкой из-за квоты. Обход каталога — через `paths::native`. Для теста добавить внедрение отказа удаления в `LoggingOptions` (по образцу `before_write`).
- **Форматирование.** Вставки журналирования T-027 в `src/jobs/executor.cpp` и `src/storage/commit/protocol.cpp` отформатировать по `.clang-format` проекта. Только эти места, без переформатирования остального файла.

### 3. Reparse points и облачные заглушки (замечание 2 T-028)

- Общая функция классификации узла — в `foundation` (только API ОС, без внешних зависимостей). Имя и место уточнить; например, `paths::node_info(path)` → `{kind: file|directory|link|other, reparse_tag?, cloud_placeholder: bool, ...}`.
- **Ссылкой считается** только узел с тегом `IO_REPARSE_TAG_SYMLINK`, `IO_REPARSE_TAG_MOUNT_POINT` (junction и точки монтирования) или `IO_REPARSE_TAG_LX_SYMLINK`. Остальные теги (`IO_REPARSE_TAG_CLOUD*`, `IO_REPARSE_TAG_DEDUP`, `IO_REPARSE_TAG_WCI*`, неизвестные) — обычные файлы или каталоги по атрибутам. Тег читается через `FindFirstFileW` (`dwReserved0`) или `GetFileInformationByHandleEx(FileAttributeTagInfo)` с открытием без доступа к данным (`FILE_FLAG_OPEN_REPARSE_POINT`, без чтения содержимого).
- **Облачная заглушка** — файл с `FILE_ATTRIBUTE_RECALL_ON_DATA_ACCESS`, `FILE_ATTRIBUTE_RECALL_ON_OPEN` или `FILE_ATTRIBUTE_OFFLINE`. Скан **не открывает** такой файл ради заголовка и хеша: открытие запускает скачивание (ТЗ §14.6). Размер и `mtime` берутся из метаданных каталога. В плане у узла:
  - `status = unavailable`;
  - `problem.code = cloud_placeholder` и `message_id = am.import.cloud_placeholder`;
  - решение `ask`;
  - кандидат получает причину `has_unavailable`.
  Каталоги с облачными атрибутами обходятся (перечисление не читает содержимое файлов).
- Схема плана v1: если `cloud_placeholder` не помещается в существующие перечни `problem.code` / причины, добавить значение в перечень. Это расширение перечня, а не новая версия формата: план — локальный рабочий файл, совместимость строк плана с прошлых версий не требуется. Строку `versioning.md` уточнить, если там сказано иное.
- **`diag export`** (T-027) использует ту же функцию: отвергаются ссылки, а облачные заглушки журналов и баз не читаются и считаются недоступными с причиной в отчёте экспорта. Прочие reparse-теги больше не отвергаются.
- POSIX: поведение не меняется (`symlink_status`).
- **Тесты:**
  - классификация на таблице `(атрибуты, тег) → результат` через внедрение, потому что облачные заглушки и дедупликацию в тестовой среде создать нельзя;
  - скан с внедрённой классификацией: заглушка не открывается (наблюдатель `on_open` не вызывается), попадает в план как `unavailable`/`ask`;
  - реальный junction и символьная ссылка, как в T-028, по-прежнему `symlink`/`skip`.

### 4. Конфликт имени и сигнатуры в `ExclusionEngine` (замечание 3 T-028, ТЗ 6.5.2)

- У каждого правила — допустимые типы содержимого (`expected_kinds`). Если `detect_kind` вернул **известный** тип (не `unknown`), не входящий в `expected_kinds` правила, совпадение по имени не может дать `certain`: оно понижается до `probable` с объяснением `am.import.exclusion.signature_conflict`.
- Для `windows.desktop_ini` и `os.icon_r` допустимы `unknown` и текстовые типы, которые `detect_kind` может ошибочно присвоить тексту. Правила с обязательной сигнатурой (`macos.appledouble`, `macos.ds_store`, `windows.thumbs_db`) не меняются.
- `kExclusionRulesVersion` → 2, изменение описать в `import_pipeline.md`.
- Решение В-3 (готовый ассет против исключения → `ask`) остаётся и проверяется прежними тестами.
- **Тесты:** `desktop.ini` с содержимым PNG и с ZIP → `probable`/`ask`; `desktop.ini` с текстом INI → `certain`; `Icon\r` с содержимым ZIP → `probable`; прежние тесты `test_exclusion.cpp` и группа 7 T-028 проходят без ослабления.

### Отклонения, границы и вопросы

Значения metadata.unavailable.name ограничены служебными именами журналов/баз/конфигурации/блокировки; абсолютные пути отвергает схема. Пустое поле не пишется. JSON и текст без пропусков проверены побайтно с прежним порядком полей; старые CLI-тесты T-027 не менялись. skip не меняет успешный код возврата; текст строится в application из am.diag.skipped и DiagnosticReport.

В LogContext тестовая настройка debug теперь повторно устанавливает приёмник после смены minimum, как требует кэш уровней; проверки фаз и контекста не менялись. В ходе подготовки один вспомогательный запуск arch_check был ошибочно выполнен вне окружения MSVC и нарушил CMake-кэш; кэш восстановлен через --fresh из локальных установленных пакетов, проверки CMake перенесены обратно под build_cli.cmd. Скрипты сборки и пресеты проекта не менялись; сетевых загрузок не было. Предварительные неуспешные прогоны не использованы как доказательство финального PASS.

Облачный провайдер и реальная дедупликация в среде не создавались: проверены все заданные теги/атрибуты, реальные OFFLINE-флаги и отсутствие чтения через наблюдателей/содержимое ZIP. import run, типизированная модель плана и изменение семантики остановки не входят в эту задачу. **Замечания (не блокируют):**
1. Облачная заглушка в скане даёт `unavailable` и, как любой недоступный узел T-028, помечает скан неполным. В `import run` решить, блокирует ли такой узел выполнение плана или исполняются остальные кандидаты с отчётом о пропуске.
2. `diag export`: ошибка чтения метаданных файла журнала (`take(source_info)`) прерывает весь экспорт, хотя раньше отсутствующий файл просто пропускался. Гонка с ротацией/квотой между перечислением и проверкой даст отказ. Исправить попутно при следующей правке диагностики: исчезнувший файл — пропуск.
3. `within()`/`normalized()` в скане используют реальный `node_info`, а не hook запроса. Для текущих тестов безразлично; при расширении тестов на корни-заглушки учесть.
4. `skipped_summary` показывает причину первого элемента; при появлении второй причины перечислять все.
