# T-027. Структурированные журналы и обезличенный экспорт диагностики (M3a, P0.6 — часть 2)

**Статус:** done (принята 2026-11-23, `3704e98`) · **Веха:** M3a · **Основание:** ТЗ v1.8 §14.4 п. 2, 9 [СОГЛАСОВАНО], §14.6 (нет скрытой передачи данных), критерий К-130; ADR-0024 (уровни: `foundation` без внешних зависимостей), ADR-0032 п. 4 (журналы с полями `am::Error`, обезличенный экспорт без `detail` с абсолютными путями), ADR-0034 (технические тексты — английские); `docs/research/libraries.md` §17 (spdlog); T-026 (исполнитель заданий, контекст `job_id`)

## Цель

1. Единый для всех уровней фасад журнала в `foundation`. У него нет внешних зависимостей; по умолчанию он ничего не пишет и почти ничего не стоит.
2. Файловый приёмник на spdlog в `application`:
   - записи в формате JSON Lines;
   - уровни Trace…Critical;
   - ротация и лимит общего объёма;
   - отдельный файл на процесс;
   - сброс на диск при Warning и выше.
3. Контекст записей: компонент, `job_id`, `asset_id`, `library_id`, `operation`. Внутри заданий T-026 он проставляется автоматически.
4. Первичная разметка ключевых точек: запуск и выход CLI, открытие и восстановление библиотеки, протокол фиксации, задания, ошибки верхнего уровня.
5. `am diag export` — обезличенный экспорт диагностики в ZIP: журналы, сведения о системе и (по желанию) сводка библиотеки. Без путей, имени пользователя и имени компьютера.
6. Схема записи журнала `schemas/log-record.v1.schema.json` и схема описания экспорта `schemas/diagnostics.v1.schema.json`.

Журнал программы (этот документ) и журнал операций библиотеки `op_log` (T-023, §6.7 п. 5) — **разные** вещи:
- `op_log` — пользовательская история операций внутри `state.sqlite`;
- файловый журнал — техническая диагностика программы, не привязанная к библиотеке.

Задача не заменяет и не дублирует `op_log`.

## Решения управляющего (не пересматривать в задаче)

1. **Фасад — `include/am/foundation/log.hpp`, `src/foundation/log.cpp`**, только стандартная библиотека. Набросок (имена можно уточнить, отклонения — в отчёте):

   ```cpp
   namespace am::log {
   enum class Level { trace, debug, info, warning, error, critical };
   enum class FieldKind { plain, path, name };          // для обезличивания, п. 7
   struct Field { std::string key; std::variant<std::string, std::int64_t, std::uint64_t, bool, double> value;
                  FieldKind kind = FieldKind::plain; };
   struct Context { std::optional<std::string> job_id, asset_id, library_id, operation; };
   struct Record {
     Level level; std::string_view component, event;     // event — стабильный код "job.started"
     std::string_view message;                           // технический текст на английском, без путей
     std::span<const Field> fields; const Error* error = nullptr;
     Context context;                                    // итог: стек областей + явные значения записи
   };
   class Sink { public: virtual ~Sink() = default;
     virtual Level min_level() const noexcept = 0;
     virtual void write(const Record&) noexcept = 0; };  // никогда не бросает и не блокирует навсегда
   void set_sink(std::shared_ptr<Sink>) noexcept;        // nullptr — журнал выключен (по умолчанию)
   bool enabled(Level) noexcept;                         // одна атомарная загрузка, без блокировок
   void write(Level, std::string_view component, std::string_view event, std::string_view message,
              std::initializer_list<Field> = {}, const Error* = nullptr) noexcept;
   class Scope {                                         // thread_local стек контекста, RAII, вложенный
    public: explicit Scope(Context); ~Scope(); Scope(const Scope&) = delete; };
   Context current_context();                            // для передачи контекста в другой поток
   }
   ```

   - Это **единственное** глобальное состояние журнала в процессе. Приёмник хранится как атомарный `shared_ptr`: замена приёмника во время записи из других потоков безопасна. Тест выполняет это под TSan/ASan, где доступно.
   - Если `enabled(level)` ложно, поля не формируются. Вызывающий код проверяет `enabled` до построения дорогих полей; для этого допустим макрос `AM_LOG(level, …)`.
   - Фасад доступен всем уровням ADR-0024. `foundation` по-прежнему не имеет внешних зависимостей (`arch_check`).
   - В минимальной сборке без vcpkg работает фасад и тестовый приёмник в памяти; spdlog-приёмник собирается только при `AM_WITH_CONTAINER`.

2. **Формат записи — JSON Lines**, одна запись — одна строка UTF-8, `\n` в конце. Схема — `schemas/log-record.v1.schema.json` (Draft 2020-12, как остальные схемы).

   ```json
   {"v":1,"ts":"2026-11-23T10:15:30.123Z","level":"info","component":"jobs","event":"job.started",
    "msg":"job started","pid":1234,"tid":5678,
    "ctx":{"job_id":"…","asset_id":null,"library_id":"…","operation":null},
    "fields":{"type":"library.verify","attempt":1},
    "kinds":{"root":"path"},
    "error":{"code":"am.insufficient_space","errc":12,"severity":"error","component":"storage",
             "operation":"commit","message_id":"…","message":"…","detail":"…","actions":["free_space"],
             "cause":[{…}]}}
   ```

   - `ts` — RFC 3339 UTC с миллисекундами.
   - `ctx` — всегда все четыре ключа (`null`, если нет значения).
   - `fields` — плоский объект; ключ поля — `^[a-z][a-z0-9_]*$`; повтор ключа → побеждает последний, в отчёт тестов.
   - `kinds` — только для полей не `plain`.
   - `error` — только при наличии. Цепочка `cause` разворачивается в массив, глубина не больше 16; превышение отмечается `"cause_truncated":true`.
   - Числа `uint64` пишутся точно. Нечисловые `double` (NaN, ∞) пишутся строкой.
   - Некорректный UTF-8 в любом тексте заменяется на U+FFFD; в записи добавляется `"utf8_repaired":true`. Строка журнала всегда остаётся корректным JSON.
   - Длина одного текстового значения ограничена: гипотеза — 4 КиБ, хвост заменяется на `…`, с флагом `"truncated":true`. Длина записи — не больше 64 КиБ.
   - Пишется собственным сериализатором `foundation` (точные числа и экранирование уже решены в кодеке). spdlog используется только как приёмник: файл, ротация, многопоточность, шаблон `%v`. Форматирование JSON средствами fmt не допускается.

3. **Файловый приёмник — `application`** (`include/am/application/logging.hpp`, `src/application/common/logging.cpp`):

   ```cpp
   struct LoggingOptions { std::filesystem::path directory; log::Level level = log::Level::info;
                           std::uint64_t max_file_bytes = 10ull << 20; unsigned max_files_per_process = 3;
                           std::uint64_t max_total_bytes = 100ull << 20; };
   Result<std::shared_ptr<log::Sink>> open_file_log(const LoggingOptions&);   // и set_sink
   ```

   - Числа по умолчанию — **гипотезы**. В `nfr_measurement_plan.md` они не вносятся как норматив.
   - **Файл на процесс:** `am-<UTC yyyymmddThhmmssZ>-<pid>.jsonl` с ротацией spdlog `rotating_file_sink_mt` (`.1.jsonl`, `.2.jsonl`). Несколько процессов (GUI и CLI) никогда не пишут в один файл и не ротируют чужие файлы.
   - **Лимит общего объёма:** при открытии приёмника удаляются самые старые файлы **только по шаблону имени п. 3**, пока сумма не станет ≤ `max_total_bytes`. Файлы текущего процесса не удаляются. Чужие файлы в каталоге не трогаются: ни удаление, ни перемещение.
   - **Сброс:** `flush_on(warning)` и периодический сброс не реже раза в 2 с (гипотеза). Запись уровня Error и выше оказывается на диске до возврата из `write`.
   - **Отказы:** ошибка записи (диск полон, нет прав) не прерывает операцию и не бросает исключение. Отброшенные записи считаются. При следующей успешной записи, а также при закрытии добавляется `log.dropped {count}`. Если каталог не открывается, `open_file_log` возвращает ошибку `am.log.open_failed`, а CLI продолжает работу без файла журнала, выдав предупреждение в stderr.
   - Приёмник не пишет в stdout/stderr: вывод CLI определяется командами, как раньше.

4. **Где и когда пишется журнал.** По умолчанию CLI **не создаёт** файлов журнала. Включение — в порядке приоритета:
   1. `--log-dir <dir>`;
   2. переменная окружения `AM_LOG_DIR`.

   - Уровень: `--log-level trace|debug|info|warning|error|critical` или `AM_LOG_LEVEL`, по умолчанию `info`.
   - Каталог создаётся при необходимости.
   - Каталог журнала по умолчанию для GUI (`%LOCALAPPDATA%`, `$XDG_STATE_HOME`) выбирается в M5 вместе с настройками приложения, не здесь.
   - Причина: CLI работает в скриптах и тестах, а неявная запись в профиль пользователя — побочный эффект. Кроме того, разработка и тесты не должны писать за пределы каталога проекта (`CLAUDE.md`).
   - Тест проверяет, что без этих настроек файлов нет: в тесте `HOME`, `LOCALAPPDATA`, `XDG_STATE_HOME` и `TMP` указывают на временный каталог в дереве сборки, который после запуска пуст.

5. **Контекст.**
   - `log::Scope` — `thread_local` стек; вложенная область дополняет внешнюю, явные значения записи имеют приоритет.
   - Исполнитель T-026 открывает `Scope{job_id}` в рабочем потоке на время `run`.
   - `Catalog` открывает `Scope{library_id}` на время своих публичных операций.
   - Для переноса контекста в другой поток — `current_context()` + новый `Scope` в нём. Пример — фоновые потоки исполнителя.

6. **Первичная разметка** (стабильные `event`; полный перечень с уровнем и полями — в `docs/architecture/logging.md`, раздел создаётся задачей):

   | `event` | Уровень | Где | Поля |
   |---|---|---|---|
   | `app.start` | info | CLI | `version`, `command` (имя подкоманды, **без аргументов**), `os`, `arch` |
   | `app.exit` | info | CLI | `exit_code`, `duration_ms` |
   | `cli.error` | error | CLI, ошибка верхнего уровня | `error` с цепочкой |
   | `library.open` | info | `Catalog::open` | `mode`, `recovered`, `jobs_requeued`, `jobs_failed`, `unclosed_session` |
   | `library.open_failed` | error | `Catalog::open` | `error` |
   | `library.warning` | warning | предупреждения `OpenReport`/операций | `error` |
   | `commit.phase` | debug | протокол фиксации | `op_id`, `phase` (`prepared`/`verified`/`committed`/`indexed`) |
   | `commit.aborted` | warning | отказ до замены | `op_id`, `error` |
   | `commit.recovered` | info | восстановление `pending_ops` | `op_id`, `outcome` |
   | `job.started` / `job.finished` | info / по итогу как в T-026 п. 11 | исполнитель | `type`, `attempt`, `state` |
   | `job.progress` | trace | исполнитель | `done`, `total`, `unit`, `stage` |
   | `db.corrupt` | error | отображение `SQLITE_CORRUPT`/`NOTADB` | `database` (`state`/`userdata`/`index`), `error` |
   | `log.dropped` | warning | приёмник | `count` |

   - Пути — только полями `FieldKind::path`, имена файлов и ассетов — `FieldKind::name`. Пути не попадают в `msg` и `event`.
   - Параметры заданий (`params_json`) целиком не пишутся.
   - Секретов в проекте нет, но правило фиксируется в `logging.md`: никаких паролей, токенов и содержимого файлов.

7. **Обезличенный экспорт — `am diag export <out.zip> [--log-dir <dir>] [--library <dir>] [--since <RFC3339>] [--dry-run]`.**
   - Источник журналов — `--log-dir`, затем `AM_LOG_DIR`. Если источника нет, экспорт содержит только сведения о системе: это не ошибка, отмечается в выводе.
   - **Состав ZIP:**
     - `diagnostics.json` по схеме `diagnostics.v1.schema.json`: `{"format":"am-diagnostics","version":1,"created_at","app":{version,build},"system":{os,os_version,arch,cpu_count,memory_bytes?},"logs":[{name,records,dropped_lines}],"library":…?,"redaction":{salted:true,rules:[…]}}`;
     - `logs/<исходное имя>.jsonl` — обезличенные копии;
     - при `--library` — `library.json`: версии баз, число ассетов по состоянию, `StorageCapabilities`, тип носителя T-026, последние 1000 записей `op_log` (обезличенные). Библиотека открывается `read_only`.
   - **Обезличивание:**
     - поля `path` и `name`, `error.detail`, а также любые строки, похожие на абсолютный путь (`X:\…`, `\\server\…`, `/home/…`, `/Users/…`, `/mnt/…`, `/media/…`, а также любой путь, начинающийся с каталога пользователя, временного каталога или корня библиотеки), заменяются токеном `<path:xxxxxxxx>` / `<name:xxxxxxxx>`. Токен — первые 8 hex HMAC-SHA-256 со **случайной солью этого экспорта** (соль в экспорт не попадает). Одинаковые значения в пределах одного экспорта дают одинаковый токен, поэтому корреляция сохраняется, но между экспортами токены разные и подбор по словарю бесполезен. Расширение файла сохраняется (`<name:1a2b3c4d>.stl`);
     - имя пользователя и имя компьютера (из ОС, а также `USERNAME`/`USER`/`COMPUTERNAME`/`HOSTNAME`) заменяются на `<user>`/`<host>` в **любых** строках, регистронезависимо, только как целые слова;
     - `asset_id`, `job_id`, `library_id`, `op_id` — случайные UUID без личных данных, сохраняются;
     - строка журнала, которую не удалось разобрать как JSON, не копируется, а считается в `dropped_lines`.
   - Кроме журналов, экспорт ничего не читает: ни ZIP ассетов, ни содержимое файлов, ни сетевые ресурсы. Сети нет вовсе (К-130).
   - Выходной файл не перезаписывается: существует → код 4. Запись — во временный файл рядом, затем переименование без замены. ZIP пишется существующим писателем `storage` или эквивалентным минимальным писателем без новых зависимостей.
   - `--dry-run` выводит состав и число замен по правилам, ничего не пишет.
   - Коды выхода:
     - 0 — успех;
     - 2 — аргументы;
     - 4 — выход существует, каталог журналов недоступен при явном `--log-dir` или библиотека не открывается.
   - Дампы памяти не создаются и в экспорт не входят (§14.4.9: потенциально чувствительные данные).

8. **Версии:** в `docs/specifications/versioning.md` добавляются строки:
   - «Запись журнала» — `v` в записи, схема `log-record.v1.schema.json`, версия 1; новые необязательные поля не меняют версию, изменение смысла поля → +1;
   - «Экспорт диагностики» — `format = "am-diagnostics"`, `version`, схема `diagnostics.v1.schema.json`, версия 1.

   Опубликованная схема манифеста 1.0 не затрагивается.

9. **Библиотеки.** Перед реализацией дополнить `docs/research/libraries.md`, строка spdlog:
   - фактическая версия 1.17.0;
   - используемые части (`rotating_file_sink_mt`, `flush_on`, шаблон `%v`);
   - отказ от форматирования JSON через fmt и причина;
   - HMAC-SHA-256 через уже используемый OpenSSL EVP.

   Новых портов vcpkg нет.

## Тесты

GoogleTest с `RecordProperty("req", …)`:
- `NFR-14.4.9` — журналы и экспорт;
- `K-130` — экспорт без сети и без чтения ассетов.

В `acceptance_matrix.md` — новая строка NFR-14.4.9.

- **`Log.*`** (фасад, работает и в минимальной сборке):
  - выключенный журнал не вызывает приёмник и не строит поля (счётчик вызовов построителя через `AM_LOG`);
  - `enabled` по уровням;
  - вложенные `Scope` и приоритет явных значений;
  - перенос контекста в другой поток;
  - замена приёмника во время записи из 8 потоков (нет гонок под санитайзером, где доступно).
- **`LogRecord.*`:**
  - каждая строка проходит `json::parse_strict` и схему `log-record.v1`;
  - точные `uint64` (2^64−1);
  - NaN/∞;
  - некорректный UTF-8 → U+FFFD и `utf8_repaired`;
  - усечение длинных значений;
  - цепочка `cause` глубже 16;
  - `kinds` только для не-`plain`.
- **`FileLog.*`:**
  - имя файла по шаблону;
  - ротация при малом `max_file_bytes`;
  - лимит общего объёма удаляет самые старые **свои** файлы и не трогает посторонние (`notes.txt`, `am-foo.jsonl` не по шаблону) и файлы текущего процесса;
  - диск недоступен / каталог только для чтения → счётчик `log.dropped`, операция не падает;
  - запись уровня Error видна на диске сразу после `write` (чтение файла другим дескриптором);
  - аварийное завершение процесса сразу после записи Error (механизм kill-тестов T-009) — запись присутствует.
- **`LogContext.*`:**
  - задание T-026 даёт записи `job.started`/`job.finished` с `ctx.job_id`, в том числе из рабочего потока;
  - операция `Catalog` даёт `ctx.library_id`;
  - фаза `commit.phase` при уровне `debug` присутствует, при `info` — нет.
- **`DiagExport.*`:**
  - синтетические журналы с абсолютными путями Windows и POSIX, UNC, путём в `error.detail`, полями `path`/`name`, именем пользователя и компьютера (подставляемые значения теста) → в ZIP нет ни одного исходного значения (поиск по всем байтам распакованных записей);
  - одинаковые пути дают одинаковый токен, два экспорта — разные токены;
  - расширение сохраняется;
  - UUID сохраняются;
  - битая строка → `dropped_lines`;
  - `--since`;
  - `--library` — `library.json` по описанию, библиотека не изменена (байты баз и ZIP не меняются, режим `read_only`);
  - выход существует → 4;
  - `--dry-run` ничего не пишет;
  - `diagnostics.json` проходит схему;
  - экспорт не открывает ZIP ассетов (проверка через подставляемый наблюдатель чтения или отсутствие обращений к `assets/` — способ описать в отчёте).
- **CLI (Python, `cli_logging`):**
  - без `--log-dir`/`AM_LOG_DIR` файлов нет нигде (п. 4);
  - `--log-dir` и `AM_LOG_DIR` дают файл с `app.start`/`app.exit`, `command` без аргументов (путь библиотеки в аргументах не попадает в журнал);
  - `--log-level debug` добавляет `commit.phase`;

### Уточнения наброска и ограничения

- Фасад дополнен write(Record), level_name, serialize и RecordLimits: тестовый и файловый приёмники используют один сериализатор; явный контекст записи имеет приоритет. Макрос также поглощает исключение построителя включённого поля, чтобы отказ журналирования не прерывал команду.
- В LoggingOptions добавлены flush_interval (гипотеза) и before_write (внедрение отказа конкретного экземпляра). Периодический сброс выполняется собственным потоком без глобального реестра spdlog. При повторном открытии в ту же секунду выбирается свободное имя со следующим UTC-временем; чужой файл не перезаписывается. Квота не удаляет текущий PID и ссылки: если защищённые файлы сами превышают лимит, приоритет имеет их сохранность.
- DiagnosticOptions/DiagnosticReport выделяют экспорт из CLI для проверки без запуска подпроцесса. users/hosts/roots и on_read служат внедрению синтетических значений/наблюдателя. Для целых слов используется отдельная таблица категорий Unicode L/M/N/Pc, генерируемая из уже закреплённых данных; зависимость foundation не менялась.
- Сетевые пути и пути с reparse points/символьными ссылками отвергаются консервативно. На POSIX публикация без замены реализована link+unlink в одном каталоге, на Windows — MoveFileW. Экспорт собирает обезличенные записи в памяти перед записью ZIP; потоковый экспорт больших журналов остаётся возможным последующим улучшением, норматив объёма не вводился.
- При систематическом разборе сбоя экспорта (навык investigate) подтверждено: std::filesystem для расширенного Windows-пути возвращал корень префикса устройства, и GetDriveTypeW ошибочно отклонял локальный источник. Исправлено вычисление корня по нормализованному пути; добавлен регрессионный тест native-пути, затем DiagExport выполнен успешно. Поведение протокола commit и содержимое op_log не изменялись.

### Замечания (не блокируют; исправить в следующей задаче, затрагивающей журнал, не позднее выбора каталога журнала GUI в M5)

1. **Стоимость выключенного журнала.** `enabled()` каждый раз загружает `std::atomic<std::shared_ptr<Sink>>`; в MSVC эта операция идёт под внутренней блокировкой с изменением счётчика ссылок — отсюда ~108 нс/проверку в Debug и возможная конкуренция потоков. Кэшировать минимальный уровень в отдельном `std::atomic<int>` (обновляется в `set_sink`), а приёмник загружать только при включённом уровне. В `ExecutorState::emit` не создавать `log::Scope`, если ни один уровень не включён.
2. **Квота и чужие открытые файлы.** `quota()` вызывает `fs::remove` в варианте с исключением. На Windows файл другого работающего процесса (например, GUI) открыт без `FILE_SHARE_DELETE`, удаление бросает исключение, и `open_file_log` целиком завершается ошибкой — CLI работает без журнала. Нужно: вариант с `std::error_code`, неудачные удаления пропускать; обход каталога — через `paths::native`. На POSIX удаление живого файла другого процесса проходит молча — учесть при проектировании журнала GUI (например, не удалять файлы младше срока или с живым PID).
3. **Форматирование.** Вставки разметки в `executor.cpp` и `protocol.cpp` записаны плотными строками без пробелов, в отличие от окружающего кода. Привести к стилю файла при следующей правке этих мест.
